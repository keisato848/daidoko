# 設計書と実装の乖離を探す

`CLAUDE.md` §2 の設計書は「実装前に必ず参照」する前提で書かれている。
**その前提は、設計書が実態を映しているときだけ成り立つ。**

## 実例（このリポジトリで実際に起きた）

- **設計にあるのに未実装**: `docs/画面設計.md` S06 の「画面ロック中も続きから再開できる
  （ステップ番号を保存）」は長らく未実装で、`useState` だけだった。「スワイプ or ボタンで
  ステップ移動」もボタンのみだった
- **実装が設計と違うのに設計書が未更新**: ボトムタブが 5 本になり設定がホームの歯車へ
  移ったのに、`docs/画面設計.md` のナビ表と TabBar 行は 4 タブのままだった
- **設計書どうしの食い違い**: 献立 M1 の設計は「日カードに写真」と書いているのに、
  実装は写真を落とし、サービス層は `heroPhotoUri: null` を返して
  「画面側で引く」とコメントしたまま誰も引いていなかった
- **節番号のずれ**: ホームは S03 なのに、別の節が「S01 ヘッダ先頭」と書いていた

## 探し方

1. **画面の実体を数える**
   - `app/(tabs)/_layout.tsx` の `Tabs.Screen` のうち `href: null` でないものを数える
     → **実際のタブ本数**
   - `docs/画面設計.md` のナビ構成・TabBar の記述と突き合わせる
   - `app/` 配下のルートファイルを列挙し、設計書の S 番号一覧に**無い画面**、
     設計書にあって**実在しない画面**を出す

2. **設定画面のような「項目が増える場所」**
   - `settings.tsx` のセクションと行を数え、設計書 S15 の項目一覧と突き合わせる

3. **設計書が明示的に決めたことが守られているか**
   - 「**残す**」「**しない**」「**〜にする**」と書かれた決定を `Grep` で拾う
     （`決定` / `方針` / `〜は残す` / `〜しない` / `決定変更`）
   - それぞれについて実装がその決定に沿っているかを確かめる
   - **沿っていない場合、どちらが正か判断しない。** 「設計書が古い」のか
     「実装が設計に反した」のかは人が決めることなので、両方の事実を並べて報告する

4. **コメントが残した「未実装」の痕跡**
   - `Grep` で `TODO` / `未実装` / `将来` / `後で` / `画面側で` / `いまは`
   - とくに「**〜は画面側で引く**」のような**責任の受け渡しがコメントだけ**の箇所は、
     受け取る側が実装されているかを必ず確かめる（実例あり）

5. **設計書に書かれた数値・閾値**
   - `docs/品質基準.md` のカバレッジ閾値、`docs/フリーミアム設計.md` の無料枠、
     `CLAUDE.md` §9 の性能目標
   - **CI やコードで実際に強制されているか**を確かめる。強制されていないなら
     「文書と実態の乖離」として報告する（例: mobile のカバレッジ閾値は未強制）

## 規律

- **どちらが正かを決めない。** 設計書と実装の両方を引用し、判断材料だけを揃える
- 古い記述を機械的に「間違い」と呼ばない。**いつの決定か**（日付・Issue 番号）を
  読み取り、後の決定で覆されていないか確かめる
- 「決定変更」と書かれた節は、**そう決め直した理由**が書いてある。
  同じ論点を蒸し返す提案をしていないか自分で点検する
- 網羅より確度を優先する。**曖昧なものは info** に落とす
- 見つからなければ「見つからなかった」と書く
