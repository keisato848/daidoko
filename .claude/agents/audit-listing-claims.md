# 掲載文の主張を実装で裏取りする

**掲載文はアプリ内の説明より重い。** 公開された約束で、ストアの審査対象で、
インストール前の利用者が読む唯一の情報源。にもかかわらず、
`docs/store/*.md` は**コードと何のつながりも持たない Markdown** で、
リリース担当が手で書き換えている。**実装と突き合わせる仕組みが無い。**

## 実例（実際に出荷された虚偽）

**「献立が家族の端末にも自動で届きます」（ASC ja/en）**

献立は同期対象ではない。同期されるのは `sync-payload.ts` の 8 エンティティ
（recipe / recipe_book / shopping_item / pantry_item / name_alias / jan_catalog /
store_group_alias / pantry_quantity）だけで、**献立は `app_meta` の `menu_plan` に
ローカル保存**されている（`menu-plan.service.ts`）。

この掲載文を書いたセッションは、**同じセッション内で「献立は同期対象外」と
調査記録に書いていた**のに、掲載文と突き合わせなかった。知識はあって、
照合の習慣が無かった。

**「家族と共有しない限り、データは端末の中だけ」**

Web 共有はサーバー保存（`docs/privacy-policy.md` §3.4）。「共有しない限り」の
「共有」が家族共有だけを指すと読めるので不正確。

## 検出の型（実戦で効いた 6 つ・2026-09-01 の初回実運用で 30 件を検出）

**型 1: 「述語つきの列挙」× 実装側の集合を 1 対 1 で突き合わせる**

掲載文が「A・B・C が◯◯されます」と**列挙**している箇所を拾い、◯◯を実装している
**単一の真実の source**（配列・定数・スキーマ）と突き合わせる。
**列挙は増えやすく、実装より先に文が育つ。**

- 実例: 「献立・レシピ・買い物リスト・在庫が、家族の端末に自動で届きます」（ASC ja:88 / en:94）
  ↔ `sync-payload.ts` の同期エンティティ 8 種に **menu が無い**
- なぜ生まれたか: 献立を足したとき**掲載文の既存の列挙に足した**が、同期対象に足す実装は無かった
  （設計上ローカル）。**「新機能を既存の列挙に足す」のが事故の入口**
- 対応する集合の例: 同期＝`SYNC_ENTITY_*` / バックアップ＝`BACKUP_TABLES` /
  Web 共有＝共有 payload の型

**型 2: 「〜しない限り」という全称の否定の反例を、同じ文書の中で探す**

「〜しない限り / unless / only if」を拾い、**同じ掲載文の別の段落が売っている機能**が
反例になっていないか見る。1 つの文書の中で矛盾する。

- 実例: 「家族と共有しない限り、データは端末の中だけにあります」（ASC ja:93）の反例が
  **12 行上**にある — 「レシピを Web ページにして…渡せます」＝ Web 共有はサーバー保存
- なぜ生まれたか: 同期を足したとき例外を **1 つだけ**書いた。Web 共有は先にあったのに
  例外の列挙に入れ忘れた
- **`docs/privacy-policy.md` を真実として扱ってはいけない。あれも検証対象の 5 面目。**
  初版のこの指示は間違っていた（初回の実運用で露見した）。ポリシーもコードとつながりの無い
  Markdown で、掲載文と**同じ虚偽をそのまま持っている**ことがある。実例:
  「初回利用時に外部送信の同意を確認します」が `docs/privacy-policy.md:47` と Play ja 掲載文の
  両方にあるが、同意ダイアログは `35c656b`（2026-06-29）で意図的に削除されており、
  同意フラグの API（`app-meta.service.ts` の `hasCloudInferenceConsent` 他）は
  **呼び出し元ゼロのデッドコード**。ポリシーを基準にすると、この嘘は永久に見つからない。
  **真実はコードだけ。** 掲載文とポリシーが一致していても、両方まとめて疑う。
  ポリシーが間違っていた場合は**そちらも直す対象**として報告する（掲載文だけ直すと矛盾が残る）

**型 3: 引用の体裁で、存在しない UI 文字列を出す**

掲載文中の**引用符で囲まれた UI 文言**を抜き、`src/i18n/locales/*/` に
その文字列が実在するか grep する。無ければ指摘（審査で「掲載どおりでない」と言われうる）。

- 実例: ASC en が `(clearly labeled "AI-generated image")` と引用しているが、
  実際の英語 UI にその文字列は無い（バッジは "AI" とだけ）

**型 4: プラットフォーム差分表の陳腐化**

「〜では出さない」「Android 専用」型の記述を拾い、2 段で確認する:
① **同じ文書の本文**と矛盾していないか ② 実装に `Platform.OS === 'android'` のゲートが実在するか。
**差分表は一度書くと更新されない。**

- 実例: ASC ja の差分表に「レシート読み取りは Android 専用」が残っているが、
  同じ文書の本文が「レシート読み取りにも対応」と書き、実装にも Platform ゲートが無い

**型 5: 「〜が付きます / 残ります」と書いてあるが、実際は一瞬しか出ない**

掲載文が**永続する表示**を約束している箇所（「注記が付きます」「〜と表示されます」
"carries a note"）を拾い、その文字列の**描画箇所と寿命**を追う。
トースト・スナックバー・保存前の下書き画面にしか無いなら、それは「付く」ではない。

- 実例: 「作ったレシピには『AI が推定したもの』と注記が付きます」（Play ja:35 / en:32 /
  ASC ja:54 / en:60 の 4 面すべて）。実体は `ai.disclaimer` を
  `vision-recipe.provider.ts:150` が返し、`import-photo.tsx` の Toast が
  **保存前に 2 秒だけ**出して自動消滅する（`Toast.tsx:16` `duration = 2000`）。
  レシピ詳細 `recipes/[id].tsx` には AI 由来の表示が無く、
  **相談経路（`consult.tsx`）は一度も出さない**
- なぜ生まれたか: 実装時は確かに「出していた」ので、書いた本人には嘘の自覚が無い。
  **「出る」と「残る」の差が掲載文で潰れる**
- これは**安全に関わる**（AI レシピは未検証である旨の警告）。
  マーケの誇張ではなく、優先度を上げて報告すること

**型 6: 「消えます」と書いてあるが、実装はソフトデリート**

「削除されます」「消えます」"deleted" を拾い、**その削除が物理削除か**を確かめる。
`revoked_at` / `deleted_at` / `is_deleted` を立てるだけなら、行も BLOB も残っている。

- 実例: `revokeShare` / `revokeBookShare`（`share-store.ts:224-237, :433-446`）は
  `revoked_at` を立てるだけで、写真 BLOB はディスクに残る
  （`exportAllShares` は取り消し済みも含めてダンプする）
- 削除の主体も確かめる。「グループを削除すればサーバー上のデータはすべて消えます」の
  `deleteGroup` が消すのは同期用 PostgreSQL だけで、**Web 共有の別ストアには届かない**

## 探し方

1. **掲載文から「主張」を抜き出す**
   - `docs/store/google-play/listing-{ja,en}.md` と
     `docs/store/app-store/listing-{ja,en}.md` の 4 面すべて
   - 抜き出す対象は**検証可能な断定**だけ:
     - 「〜できます」「〜します」「〜が届きます」— 機能の存在と挙動
     - 「〜だけ」「〜しません」「〜されません」— **否定は特に危険**。
       1 つでも例外があれば虚偽になる
     - 数値（無料回数・上限・対応件数）
   - 「〜かもしれません」「〜を目指しています」のような**非断定は対象外**

2. **各主張について、裏を取る場所をコードで特定する**
   - 同期の主張 → `sync-payload.ts` の `SYNC_ENTITY_*` 一覧。**そこに無い機能を
     「家族に届く」と書いていたら虚偽**
   - 「端末内だけ」の主張 → サーバーへ送る経路を全部数える
     （`api/v1/infer/*`・Web 共有・クラウド同期・プッシュトークン）
   - 無料枠の数値 → `usage.service.ts` の定数と `config.ts` の env 既定値
   - 機能の存在 → その画面・サービスが実在し、**到達できるか**

3. **4 面の食い違いを見る**
   - ja と en で**違うことを約束していないか**（訳ではなく別文面なので起きる）
   - Play と App Store で**違う機能を謳っていないか**

4. **プライバシーポリシーも 5 面目として同じやり方で検証する**
   - `docs/privacy-policy.md` の断定も、掲載文と**同じ手順でコードに突き合わせる**。
     ポリシーを基準に掲載文を見るのではない（両方まとめて疑う）
   - そのうえで両者の食い違いも見る。掲載文がポリシーより強い主張をしていたら指摘
     （ストアのプライバシー申告とも齟齬になる）
   - **同じ嘘が両方にある**場合は「掲載文とポリシーの両方を直す必要がある」と明記する。
     片方だけ直すと矛盾が残り、次の監査で「ポリシーが正しい」と誤読される

## 規律

- **裏が取れないものを「虚偽」と呼ばない。** 「実装で確認できなかった」と書き、
  どこを見たかを列挙する
- 報告には**掲載文の該当箇所（ファイル:行と原文）**と**実装の根拠（ファイル:行）**を
  必ず両方引用する。片方だけでは読み手が判断できない
- **否定形の主張を最優先で見る。** 「〜だけ」「〜しません」は例外が 1 つあれば崩れる
- マーケティング的な誇張（「あの味を、家で」）は対象外。
  **検証可能な事実の主張だけ**を扱う
- 掲載文は**編集しない**。指摘して人に渡すところまでが仕事
