# 歯の無いテストを探す

**このリポジトリには前例がある。** `jest.mock('../../db/client', () => ({ isNativePlatform: false }))`
のせいで native 経路が一度も実行されず、**修正を丸ごと revert しても 916 件が緑のまま**
だったことがある（`docs/品質基準.md` §2.3）。緑は「守っている」の証拠にならない。

## 探す型

**① 差し替えた mock を一度も assert しない**

```
jest.mock('../../services/notification.service', () => ({
  presentCookingNotification: jest.fn(),   // ← 差し替えたが expect が 1 つも無い
  dismissCookingNotification: jest.fn(),
}));
```

→ 通知のライフサイクルを丸ごと消しても緑。実例あり。

**② 実装をコピーしただけの assertion**

期待値が実装の値をそのまま書き写しているだけで、**実装を変えたらテストも変える**運用に
なっているもの。とくに「変更と同時に期待値だけ書き換えた」履歴があるものは疑う。
例: 絵文字の対応表を変えたとき、`'miso soup'` と `'soup'` が同値になり、
その行を消しても緑になった。

**③ 出荷経路が一度も実行されない**

`isNativePlatform: false` や `Platform.OS` の既定値によって、テストが常に早期 return の
枝しか通らないもの。**カバレッジを見れば分かるが、このリポジトリの mobile は
カバレッジ閾値を強制していない**ので、人が見るしかない。

**④ 手動モックが実物とずれている**

`apps/mobile/__mocks__/` の各ファイルを、対応する `node_modules/<pkg>` の型定義と
突き合わせる。**ずれていると、テストは「間違った振る舞い」を正解として固定する。**
実例: `__mocks__/expo-notifications.js` の `AndroidImportance` が実物と別の値で、
実装が使う `LOW` が存在せず `undefined` のまま通っていた。権限の戻りに `granted` が
無く、`getPermissionsAsync().granted` を見る実装がテストでは常に false だった。

**⑤ モックを広げて通しただけ**

新しい依存が増えたときに `jest.mock` の返り値へプロパティを足して「落ちないようにした」
だけで、**新しい依存の振る舞いは何も検証していない**もの。

## 探し方

1. 直近で変更された実装ファイルに対応するテストを引く（`git log` は使えないので、
   `Grep` で機能名から当たる）
2. 各テストで `jest.mock(...)` を列挙し、**差し替えた各シンボルに対応する `expect` が
   あるか**を数える。0 件なら報告
3. `__mocks__/` の各ファイルについて、実物の型定義（`node_modules/<pkg>/build/*.d.ts`）と
   キー・値を突き合わせる
4. **「この行を消したらテストは赤くなるか」を各 assertion について自問する。**
   赤くならないなら歯が無い

## 規律

- **推測で「歯が無い」と言わない。** 報告には「実装のどこをどう変えると緑のままか」を
  具体的に書く（例: 「`identifier` を外しても通る」）
- 変異検証を提案する。書き直しの提案には「この変異で赤くなること」を受け入れ条件として添える
- 意図的に薄いテストは責めない。UI の見た目など、テストより実機検証が適切な領域はある。
  その場合は「実機検証の項目に入っているか」を確かめて報告する
- `docs/品質基準.md` §2.2 の閾値（サービス層 ≥80% / ユーティリティ ≥90% / UI ≥60%）を
  引くときは、**mobile では CI で強制されていない**ことも併記する（文書と実態の乖離）
