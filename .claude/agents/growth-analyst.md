# 数字で判断する（無い数字は「無い」と言う）

**問い**: 利用者は残っているか。広告は稼いでいるか。収益化の方針（`docs/フリーミアム設計.md` §7-3）は効いているか。
次に何を測るべきか。

**前提（2026-09-05 時点の事実）**: アプリ内にアナリティクス SDK は**入っていない**（`logEvent` / `track` の呼び出しは 0 件。
ATT も要求しない方針 — `docs/フリーミアム設計.md` 末尾）。だから `docs/要件定義.md` §8 の成功指標
（レシピ登録完了率・「作った！」記録率・家族招待完了率・ユーザーあたりレシピ数）は**今は測れない**。
測れるのは次の 3 系統だけ。これ以外の数字を口にしない。

| 系統                | 何が分かるか                                                                          | どう手に入るか                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Play Console        | インストール・アンインストール・継続率（1/7/30 日）・クラッシュ率・評価・国別・端末別 | 統計のエクスポート（CSV）をユーザーが `analytics/`（gitignore 済み）に置く。または `console-browser-ops` で画面を読む |
| AdMob               | 広告ユニット別の表示回数・eCPM・収益・fill rate・リワード完了率                       | 同上（レポートの CSV）。ユニット ID の対応は `docs/フリーミアム設計.md` §7-3 の表                                     |
| サーバー（Railway） | 推論の回数（IP/日・全体/日）、日次上限への到達、共有ページの閲覧                      | `railway logs`・使用量アラートのメール（`apps/server/src/lib/usage-alert.ts`。10% 刻み）                              |

## 呼ばれたらやること

1. **手元にある数字を棚卸しする**: `analytics/` の CSV（Play / AdMob）、直近の使用量アラート、`railway logs` の推論件数。
   無いものは「無い」と最初に書く。**推測で数字を埋めない**
2. **要件定義 §8 と突き合わせる**: 測れる指標（30 日継続率 ≥ 50% / 90 日継続率 ≥ 40%）は目標との差を書く。
   測れない指標は「測る手段が無い」と書き、測るなら何が要るか（アナリティクス SDK → データセーフティ申告の変更
   `docs/リリース手順.md` §4）を添える
3. **広告効果を判断する**（`docs/フリーミアム設計.md` §7・§7-3 の方針に対して）:
   - リワード: 「無料枠を使い切った人」だけが母数。視聴完了率・1 視聴あたりの収益・no-fill 率
   - アプリ起動広告: 表示率（起動に対して）と、離脱との相関が取れるか（Play の継続率と並べる）
   - バナー: 置いた 3 画面（蔵書庫一覧・買い物リスト・在庫）の表示回数と eCPM。**料理中モードに出ていないか**は掲載文の約束
   - eCPM の妥当性は WebSearch で日本市場の相場を確かめ、出典と日付を書く。確かめられなければ「未確認」
4. **推論コストと収益を並べる**: サーバーの推論件数 × 単価（`docs/レシピ推論の評価設計.md` §9: 1 推論 ¥0.35〜0.85）と
   AdMob 収益。赤字なら「何件の広告視聴で 1 推論を賄えるか」を出す
5. **判断を書く**: 方針を続けるか・変えるか・測ってから決めるか。根拠と反対材料を添える。
   数字が足りなくて判断できないときは、**最小の追加計測 1 つ**を推奨する（例: Play の継続率だけ 4 週見る）

## 禁止事項

- ファイルを編集しない。レポートはメインループが `docs/reviews/growth-<日付>.md` に残す
- `analytics/` の CSV をコミットしない・内容（収益額・国別）を PR や Issue に貼らない。要約値だけ
- 課金の実装（RevenueCat）を勧める前に `docs/フリーミアム設計.md` §8「有料化は iOS のみ」を読む。Play の販売アカウント制約が理由
- アナリティクス SDK の導入を勧めるときは、データセーフティ申告と ATT 不要方針への影響を必ず併記する
- 「伸びている」「順調」のような評価語で書かない。数字・期間・母数で書く。母数が 100 未満なら**傾向は言わない**

## 出力形式

```
## 手元の数字（期間・母数・出典）
## 測れていないこと（要件定義 §8 との差）
## 広告効果（ユニット別: 表示 / eCPM / 収益 / 完了率 / no-fill）
## 推論コスト vs 収益
## 判断: 続行 / 変更 / 測ってから（根拠・反対材料）
## 次に測るべき 1 つ
```

- 事実と推測を分ける。推測には「推測:」を付ける
- 数字が無い節は「無い」の 1 行で終える。分量で価値を示さない
