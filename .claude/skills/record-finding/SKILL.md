# 分かったことをリポジトリに残す

**目的**: 次に触る人（＝次のセッション）が同じ穴を掘り直さないこと。
会話の中やセッションのメモに書いても、次の作業者からは見えない。**リポジトリが唯一の正**。

根拠: `CLAUDE.md` §5「分かったことは必ずリポジトリに残す」。
索引の実体は `scripts/agent/lib/knowledge-map.mjs`（SessionStart の表示と Stop の督促が共有）。

## 1. どこへ書くか

| 分かったこと                                | 置き場所                                                       |
| ------------------------------------------- | -------------------------------------------------------------- |
| テストの書き方の罠（緑のまま本番が死ぬ類）  | `docs/品質基準.md` §2.3                                        |
| 実機・エミュレーター操作の罠                | `docs/開発ハーネス.md` §4 ＋ `.claude/skills/emulator-verify`  |
| 仕様・設計の判断と、その理由                | 該当する `docs/*設計.md`（`CLAUDE.md` §2 の索引）              |
| 「設計書どおりに書いたら壊れた」            | **同じ設計書に、なぜ変えたか込みで**（例: クラウド同期 §5-1b） |
| リリース・ストア運用でハマったこと          | `docs/リリース手順.md` / 該当 Skill                            |
| ハーネス（フック・Skill・スクリプト）の挙動 | `docs/開発ハーネス.md` §1〜§3                                  |
| 未着手だが忘れてはいけないこと              | GitHub Issues（`docs/開発ハーネス.md` §7-2 が正）              |
| **コードを読めば分かること**                | **書かない**（重複は必ず腐る）                                 |

判断に迷ったら「次に同じ作業をする人が、**着手前に**読む場所はどこか」で決める。

## 2. どう書くか

**症状 → 原因 → 対処**の順。読む人が最初に出会うのは症状なので、症状から引けるようにする。

```md
| 落とし穴                                      | 症状                                             | 対処                                 |
| --------------------------------------------- | ------------------------------------------------ | ------------------------------------ |
| jest.mock のファクトリから外側の class を参照 | エラーにならず `instanceof` の分岐だけ黙って死ぬ | class はファクトリの中で定義して返す |
```

散文で書くときも同じ順序:

```md
- **キーボードに隠れた入力欄を叩くと、キーボードのキーが押される**（2026-08-22 Pixel 9a）。
  `uiautomator dump` の bounds は裏の欄も返すので、座標だけ見て叩くと打鍵が別の欄に入る。
  叩く前に `dumpsys input_method` で閉じているか確かめる。
```

添えると価値が上がるもの:

- **いつ・どの版で踏んだか**（日付・端末名・SDK 版）— 次の人が「まだ有効か」を判断できる
- **何を溶かしたか**（「20 分溶かした」）— 対処を読む動機になる
- **なぜそうなるか**の 1 行 — 応用が効く。原因不明なら「未確認:」と明示する

## 3. 書かない・薄くするもの

- コードを読めば分かる構造（関数名・引数・ファイル構成）
- そのセッション限りの事情（「今日は 5433 で立てた」— 手順として残すなら別）
- 憶測。確かめていないことは「未確認:」を付けるか、書かない

## 4. 手順

1. 索引（上の表）で置き場所を決める。既存の節があればそこへ**足す**（新しい文書を増やさない）
2. 症状 → 原因 → 対処の順で書く
3. 未着手の作業が残るなら GitHub Issue を立て、文書から番号でリンクする
4. `npx prettier --write <書いた文書>`（pre-commit でも整形されるが、差分を小さく保つ）
5. コミットは `docs:` で、**何を分かったか**が件名で分かるように

## 5. Stop フックに督促されたとき

「調査コマンドを実行したのに記録が増えていない」と止められた場合:

- 記録すべきことがあれば、上の手順で書いてから終える
- **本当に無ければ**、「記録すべき発見は無かった」とユーザーへの報告に明記して終える
  （既存の挙動を確認しただけ・既知の手順をなぞっただけ、など）

督促は 1 回きり（`stop_hook_active` でループしない）。黙って無視しないこと。
