# 要望を設計できる要求まで掘る

**目的**: 「こう言われたから、こういうことだろう」で設計を始めない。
司令塔が推測した指標で 3 往復ぶんの設計を無駄にした実例がある（`docs/AIに聞く設計.md` §19）。

**成果物**: `docs/reviews/hearing-<YYYY-MM-DD>.md`。
発見を `F1, F2…`、設計に渡せる要求を `R1, R2…` で番号を振り、優先順位まで付けて終わる。

---

## 1. 進め方

### 1-1. 理想ではなく、実際にあったことを聞く

「こういう機能があったら便利ですか」は当たらない。ほぼ全員が「便利そう」と答える。

| 悪い問い                       | 良い問い                                         |
| ------------------------------ | ------------------------------------------------ |
| 声で操作できたら便利ですか     | 直近で、声で頼みたいと思った場面はありましたか   |
| 献立機能は使いやすいですか     | 直近で献立を決めたとき、実際に何をしましたか     |
| この機能は続けて使えそうですか | 入れた最初の週に何回使うと思いますか。1 か月後は |

### 1-2. 1 回 3〜4 問で区切る

まとめて 15 問出さない。**答えが次の問いを決める**。
1 回目は「いまの暮らしの中でこのアプリがどこにいるか」から入り、詰まりが見えたらそこだけ掘る。

### 1-3. 選択肢は答えやすさのために付ける。自由記述を歓迎する

選択肢に無い答えほど価値が高い。実例:

- 「検索できないのが痛い」→ アプリ内の検索機能のことではなく「アプリの中から Web のレシピを探したい」だった
- 「追いつかなくていい」→ 直すべき欠陥だと思っていたものが、**直さなくてよいという許可**だった

### 1-4. 答えが途中で切れていたら必ず追う

「使っているが」で止まった答えを追ったら「**レシピがない状態から使いづらい**」が出て、それが全体の詰まりの特定につながった。
**「が」「ただ」「ちょっと」の後ろに本音がある。**

### 1-5. 言葉が曖昧なら、そのままにしない

「最高管理」（音声入力の変換ミス）を「在庫管理」と読んだうえで、**読み替えたことを明示して確認する**。
本人が「ちょっと曖昧」と言った項目は、**曖昧のまま記録して未解決に置く**。埋めたことにしない。

## 2. やってはいけないこと

### 2-1. 推測した指標で判断を進める

**今日いちばんの失敗がこれ。**「台所で手がふさがっている」という発言から
「効率＝タッチ数の問題だ」と推測し、その指標で「アプリ内の入口は無意味」という結論まで出した。
利用者は一度もタッチ数の話をしておらず、目的は「言ったことが実行される」という**性質**だった。

指標を置いたら、**その指標が本人の目的と一致しているかを先に確かめる**。
「速さの問題ですか、できること自体の問題ですか」と聞けば 1 往復で済む。

### 2-2. 復唱せずに設計へ進む

理解が固まったと思った時点で、**箇条書きで復唱して確認を取る**。
本人の言葉をそのまま引用する。要約すると、要約した側の解釈が混ざる。

### 2-3. 使われていない機能を「知らないのだろう」と決めつける

実装を読んでから聞く。実例:

- レシピ検索は実装済みだった → だから「検索できない」は別の意味だった
- 本番はレシピ 0 件から始まる（`db/sampleData.ts`）→ 「最初は空」は感想ではなく仕様だった

**聞く前にコードで裏を取ると、質問が具体的になる。**

## 3. 記録の形

`docs/reviews/hearing-<日付>.md` に、次の順で書く。

| 節                      | 中身                                                            |
| ----------------------- | --------------------------------------------------------------- |
| きっかけ・方法・回答者  | 何往復したか。1 人の証言なら**一般化に注意**と明記              |
| 分かったこと `F1..`     | **本人の言葉を引用**。実装で裏が取れたものは file:line を添える |
| 詰まりの構造            | F をつないで、どこで輪が切れているかを図か箇条書きで            |
| 設計に渡せる要求 `R1..` | **ヒアリングから直接出たものだけ**。推測を混ぜない              |
| 要求されなかったこと    | **これが重要**。作らない理由になる                              |
| 優先順位                | R に順番を付ける。依存があれば明記                              |
| まだ聞けていないこと    | 未解決を隠さない                                                |

### 「要求されなかったこと」を必ず書く

実例（2026-09-14）:

- 記録・在庫を正確に追いつかせること → 「追いつかなくていい」
- 誰が変えたか分かること → 選択肢にあったが選ばれなかった
- 一括でレシピを流し込むこと → 選ばれなかった
- タッチ数を減らすこと → **明示的に否定された**

書いておかないと、次のセッションが同じものを設計し直す。

## 4. 終わり方

次が揃ったら終わってよい。

- [ ] 要求に番号が振られ、それぞれ**本人の言葉**が根拠として添えてある
- [ ] 優先順位が付き、依存関係（これが直らないとあれが成立しない）が書いてある
- [ ] 要求されなかったことが列挙してある
- [ ] 未解決が「未解決」と書いてある（埋めたことにしていない）
- [ ] 規模が違う案（別機能・別 Epic 相当）は**保留**として切り分けてある

揃ったら `app-leader` へ実装計画と見積を、`product-manager` へ価値と名前を渡す。
受入基準・スコープ外・Phase 計画まで票にするなら `harness:intake` の形式が近い（daidoko には未配布）。
