## 0. 一言で

**どの画面からも 1 タップで「このアプリの使い方」を聞けて、答えの中から当の機能をその場で開ける**入口を足す。
Android の Gemini アプリが「設定を変えて」でその画面を開く・切り替えるのと同じ型を、
だいどこの中に閉じて作る（**アプリの中の機能を、アプリの中の AI が呼ぶ**）。

守る一線は既存の設計と同じ — **決めるのは常に利用者**（`docs/相談してレシピを作る設計.md` §2）。
AI は「どこにあるか」「何ができるか」を答え、画面を開くところまでは自動、
**データを変える操作は利用者のタップを 1 回挟む**（Phase 2 は 2026-09-13 に解凍し Phase 1 と同梱 — §10 問 3・§12）。

位置づけ（PM 判断）: これは**初週の保険**であって、継続利用の道具ではない。
「見れば分かる」導線の改善を止める言い訳にしない（§14 反対材料 5）。

## 1. なぜやるか（調査で分かったこと）

### 1-1. 機能が増え、案内が追いついていない

| ホームのコーチマーク 2 枚目が存在しないカートを指していた（案内の陳腐化が実際に起きた）                    | `docs/reviews/ux-help-currency-2026-08-31.md`  |
| ペルソナ検証: スマホ不慣れ層「毎回迷う」、几帳面層「どちらか確信できない」、「タップできるのか分からない」 | `docs/reviews/persona-help-home-2026-09-03.md` |
| 在庫は「2 段奥にあって使われなかった」→ タブへ昇格（**導線の発見性が使用率を決めた実例**）                 | Issue #182、`(tabs)/_layout.tsx` のコメント    |
| ホームの導線は増殖しやすく、監査役（`audit-nav-duplication`）を置くほど                                    | `docs/開発ハーネス.md` §7                      |

つまり **「どこにあるか分からない」を、導線を増やして解くのは限界**にある。
導線を足すほどホームが太り、案内文は腐る。
「聞けば分かる・聞けば開く」という**1 本の横断導線**で、個別導線の増殖を止めたい。

ただし並行して進めるものがある: **既にある重複導線 5 組（`ux-help-currency-2026-08-31.md` §1 B1）を削る。** ピルはルート `_layout` の常駐要素でホームに積まれないので B1 は技術的な前提ではない（2026-09-13 app-leader）。ただし暦／写真の畳み込みは HelpButton 統合と同じハンクなので、順序は §12 の前提行に従う。
削らずに横断導線を足すのは「前の対処を置き換えずに上へ積む」型そのもの（§10 判断 7）。

### 1-3. 「Gemini から OS 設定」の型を分解する

Android の Gemini（および iOS の Siri / App Intents）がやっていることは 3 層に分かれる。

| 層                    | Gemini/OS                          | だいどこでの対応                                                     |
| --------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| ① 呼べる操作の一覧    | AppFunctions / App Intents の宣言  | **機能カタログ**（§4）— 画面・設定・操作を 1 か所に宣言する          |
| ② 自然文 → 操作の解決 | LLM が一覧から選ぶ                 | Gemini に**カタログを渡して**候補を JSON で返させる（§6）            |
| ③ 実行と安全          | 「設定を開く」は即・「消す」は確認 | **navigate は即、mutate は確認カード、destructive は載せない**（§5） |

OS 側からアプリを呼ぶ方向（Android 16 の AppFunctions・iOS App Intents）は**別物**で、
本設計の後段（§12 Phase 3）に置く。理由: ①のカタログを先に持てば、両方向に同じ宣言を使える。

## 2. 名前と文言（レビューで差し替え）

| ところ                 | ja                           | en                     | 理由                                                                                                            |
| ---------------------- | ---------------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| 常駐ボタン（ラベル）   | **使い方**                   | How to                 | 「聞く」は「相談」と区別がつかず、「?」は既存の HelpButton と混同された（ペルソナ 4/4）。**物の名前**を先に置く |
| ボタンのアイコン       | `MessageCircleQuestion`      | 同                     | 「?」単体（`CircleHelp`）は使わない — 既存 HelpButton と同じ記号を並べない                                      |
| シートのヘッダー       | **このアプリの使い方を聞く** | Ask how to use the app | ペルソナ 3/4「使い方の相談か料理の相談か迷う」→ 「アプリ」と「ごはん」という物の名前を頭に置くのが最小の直し    |
| 設計書・コード上の呼称 | AIに聞く / `assistant`       | —                      | マスコット名は付けない（相談設計 §3-2 の判断を引き継ぐ）                                                        |

「相談しながらつくる」（食べ物の話）は既存文言なので変えない。
「使い方を聞く」で食べ物の話を振られたら、AI は答えずに
「それは『相談しながらつくる』でできます → [開く]」と**送り出す**（§5 の navigate アクション）。
**送り出すときは質問文をそのまま `seed` で渡す**（`consult.tsx` は既に `seed` パラメータを受けて入力欄に入れる）。
「サイゼリヤのドリアを作りたい」と聞いた人が、相談画面でもう一度打ち直さずに済む。
入口は 1 つ（使い方ボタン）で、**料理の質問も再現の相談もそこから始められる** — 「AI に聞けば料理も再現できる」は、
この受け渡しで成立させる（2 つのチャットを 1 つに統合はしない。プロンプトの責務を混ぜない）。

**既存の HelpButton（?）は統合する**（当初案「残す」はペルソナ 4/4 が「同じものが二つある」と踏んだので撤回）。
シートの中に「この画面の案内をもう一度見る」（＝ `coach.show`）を置き、ヘッダの「?」は外す。
影響: `HelpButton` を使う 7 画面と `CoachMarkOverlay` の最終ステップ。

## 3. UX 設計

### 3-1. 常駐ボタン（1 アクション目）

```
┌───────────────────────────┐
│ ヘッダ（各画面の既存）      │
│                           │
│   画面の中身               │
│                           │
│                 ┌─────┐   │
│                 │💬使い方│   │ ← ピル。**右下**（2026-09-13 決定）。高さ 44、金の輪郭、半透明の背景。ラベル付き
│                 └─────┘   │
│ ┌─ Now Cooking バー ─────┐ │ ← 調理中はこの上に積む
│ └───────────────────────┘ │
│ ┌─ 広告バナー（3 画面）──┐ │ ← バナーのある画面ではさらにその上に積む（§8）
│ ホーム レシピ ＋ 在庫 買物 │
└───────────────────────────┘
```

| 決めたこと                                                                     | なぜ                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ルート `_layout` に 1 つだけ**マウント                                       | `CookingResumeBar` と同じ。43 画面に個別に置くと必ず抜ける。**全画面ラッパーで包まない**（包むなら `pointerEvents="box-none"`）                                                                                                                                                                                                           |
| 位置は**右下・タブバーの直上**（2026-09-13 決定。9/10 の下端中央案から戻した） | 右下なら買い物・在庫の最下行の**文字**には被らず、「＋」タブと視覚的に分離できる（PM 当初案）。代償: 左手持ちで遠い（9/10 のユーザー指摘）。右端の戻るジェスチャ域（約 20dp）から `right: 20` 以上で逃がし、ピル上で始まる横スワイプは実機で確認する。**右端のチェック列に被る**ので買い物・在庫の `paddingBottom` を 84 に（app-leader） |
| 「＋」タブと混同させない                                                       | ラベル「使い方」を必ず付ける（アイコンだけにしない）。「＋」はタブバーの中、ピルはその上で浮いている。色も金の輪郭で、「＋」の塗り円と分ける                                                                                                                                                                                              |
| 利き手設定は**作らない**                                                       | 設定が増えるほど「どこだっけ」が起きる。左手持ちの到達性はシート側の候補チップ（大きい）で補う                                                                                                                                                                                                                                            |
| タブ外（ルート Stack）の画面でも**同じ位置**                                   | 「常に同じ場所」が「常にワンアクション」の本体                                                                                                                                                                                                                                                                                            |
| **出さない画面**は共通フックで判定                                             | `FULLSCREEN_CHILD_ROUTES` と `HIDDEN_ROUTE_SEGMENTS` は既に 2 写し。**3 写し目を作らず** `useOverlayVisibility()` に寄せてから乗る（§8）                                                                                                                                                                                                  |
| `presentation:'modal'` の画面では出さない                                      | iOS は UIKit モーダルが RN ルートの上に乗るので、兄弟の absolute View は下に沈む（Android は出る）。OS 差を作らない                                                                                                                                                                                                                       |
| ドラッグ移動はしない                                                           | 位置が動くと「いつもの場所」が壊れる。被って困る画面は表で逃がす                                                                                                                                                                                                                                                                          |
| ストア用スクショでは消す                                                       | `EXPO_PUBLIC_DISABLE_COACH_MARKS` と同じ流儀で `EXPO_PUBLIC_DISABLE_ASSISTANT`。無いと全スクショにピルが写る                                                                                                                                                                                                                              |
| **リスト最下行との干渉は実機で確認**                                           | たけし「カゴ持ちながら親指でチェック中に最下行でかすりそう」。右下配置は右端のチェック列に被る。買い物・在庫のリストは `contentContainerStyle` の下余白（24 → 84）でピルぶん逃がす。選択モードの下端アクションバーとも被るので実機で確認                                                                                                  |

**代案（PM から）**: 常駐ピルではなく「設定・ホーム・追加タブの 3 か所に入口を置く」だけでも Phase 0 の価値の大半は出る。
発見率を先に見たいならこちら。本書は依頼どおり「常にワンアクション」を主案にするが、判断は §10-6。

### 3-2. シート（2 アクション目で答え・3 アクション目で機能に着く）

**RN `Modal` ベースの `BottomSheet` は使わない。** ルート `_layout` に in-tree（Reanimated の absolute View）で置く。
理由: Modal だと (a)「答えを見ながら下の画面を操作」が原理的に不可能、(b) `router.push` を開いたまま呼ぶと iOS で Modal が上に残る、
(c) 画面ツリーに描かれる `Toast` がシートの裏に隠れる（`DialogHost` が Modal の裏に隠れた実績: クラウド同期設計 §5-1b 付近）、
(d) Android edge-to-edge ＋ RN Modal ＋ keyboard-controller は 3 回壊れた前例（ウィジェット設計）。
in-tree ならキーボードはルートの `KeyboardProvider` 直下で扱え、Modal の罠を全部避けられる。

```
┌───────────────────────────┐
│ ── このアプリの使い方を聞く ──  いま: 在庫 │ ← 現在画面のチップ
│                           │
│ [在庫に何ができる？]        │ ← 画面ごとの候補 3 つ（カタログの suggestedQuestions）
│ [レシートから登録するには]   │    **打たずに済む道**が最初にある（ペルソナ 4/4「まずチップを押す」）
│ [家族と在庫を分けたい]      │
│ [このアプリでできること]     │ ← 全画面共通の 1 つ
│ [この画面の案内をもう一度見る] │ ← 旧 HelpButton の統合先（コーチマークのある 7 画面だけ）
│                           │
│ 🧑 レシートで登録できる？    │
│ 🤖 できます。在庫の右上の    │ ← 3 文以内（相談と同じ規約）
│    「レシート」から撮影します │
│    ┌────────────────────┐ │
│    │ 📷 レシート読み取りを開く → │ │ ← navigate。シートを閉じてから push
│    └────────────────────┘ │
│                           │
│ ┌───────────────┐ [送信] │
│ │ 質問を入力…      │       │
│ └───────────────┘       │
│ 答えは AI が作ります。間違うことがあります。無料枠は減りません │ ← 14px 以上・薄色にしない
└───────────────────────────┘
```

| 決めたこと                                         | なぜ                                                                                                                                                                                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全画面ではなく**シート**（in-tree）                | いま見ている画面の上に重ねる。「戻ったらどこだっけ」を起こさない                                                                                                                                                                                                                  |
| **入力中は端末内の候補**（カタログ検索）を即時表示 | 通信なし・0 円・0 秒。サーバーが落ちていても「機能を探す」はできる（§7）                                                                                                                                                                                                          |
| 送信したときだけ AI                                | 「何を送ったか見えている」（相談設計 §4 と同じ思想）                                                                                                                                                                                                                              |
| 答えは 3 文以内、質問は 1 つまで                   | 相談と同じ規約                                                                                                                                                                                                                                                                    |
| アクションは**答えの下のカード**として出す         | 文中リンクは老眼・不慣れ層に見つけられない（13px 薄色が読めなかった実績）。カードは 44px 以上                                                                                                                                                                                     |
| navigate は**シートを閉じてから** `router.push`    | 開いたままだと iOS で上に残る。戻るで元の画面に帰れる                                                                                                                                                                                                                             |
| mutate は**確認カード**（Phase 2・Phase 1 と同梱） | ペルソナ 3/3「安心・面倒ではない」。使う場面はユーザーが挙げた: **OS キーボードの音声入力で「砂糖を買い物に追加」→ 確認カード → リストに入る**（2026-09-13）。実行後の「入りました」Toast は必須（3/3）。グローバル Toast は現状無いのでルート Toast ホストを新設する（§12 PR-7） |
| 会話はシートを閉じると消える                       | 相談と同じ（設計 §6）                                                                                                                                                                                                                                                             |
| 免責＋「無料枠は減りません」を**常時 1 行**        | 「AI が作った」を隠さない（Issue #266 と同じ流儀）。みさ「無料枠が減らないと一言あれば押せる」                                                                                                                                                                                    |

### 3-3. 初回体験への組み込み

- ホームのコーチマーク**1 枚目**を「困ったらここ」（使い方ボタン）に**差し替える**（枚数は増やさない。既存 2 枚のうち 1 枚を落とす）。
  理由: 案内の陳腐化（#264・2026-08-31）で一番腐りにくいのは「ここで聞ける」で、**他のすべての案内の保険**になる。
  **#264（コーチマークの版）はリリースの条件**（2026-09-13 決定: 同梱必須・別 PR）。版が無いと既存ユーザーにこの 1 枚が出ない。1 枚目をピルに差し替えると `assistantRef` で枠が出せるので、9/11 P5（枠が無い）も同時に解ける。
- `CoachMarkOverlay` の最終ステップに「もっと聞く」を置く。overlay は Modal なので**閉じてから**シートを開く。
- 空状態（`EmptyState`）へのリンクは **Phase 0 では足さない**。「空状態のときピルを隠す」に必要な信号（画面→ルートのストア）が無く、43 画面に配線が生えるため。

### 3-4. 出さない・やらない

| やらない                           | なぜ                                                                                                                                                           |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マスコット・人格                   | 相談設計 §3-2 の判断。「深夜の私設蔵書庫」の世界観と噛み合わない                                                                                               |
| 音声入力（アプリ機能として）       | 台所での価値は高いが、権限・誤認識・i18n が乗る。Phase 3。**OS キーボードのマイクで入力する**のはこの限りでなく、mutate の主な使い方として想定する（§10 問 3） |
| 料理・レシピの内容の質問への回答   | それは「相談しながらつくる」の領域。**答えずに送り出す**                                                                                                       |
| 削除・共有公開・家族脱退・課金・鍵 | AI から呼べる操作に**載せない**（§5 の denylist）。誤爆したとき戻せない                                                                                        |
| 質問文のサーバー保存               | プライバシー。改善のために集めるなら**オプトイン**で別途判断（§10）                                                                                            |
| 同意ダイアログの新設               | 質問文しか送らない機能に**写真系より先に**同意を出すのは順序の逆転。#265 に戻す（§6-5）                                                                        |

## 4. 機能カタログ（設計の中心）

**AI が知っていること・呼べること・テストが検証すること、を 1 つの宣言に集める。**
これが無いと「AI が存在しない機能を答える」「案内が腐る」「テストが守らない」の 3 つが同時に起きる。

```ts
// apps/mobile/src/assistant/catalog.ts（案）
export interface CatalogEntry {
  id: string; // 'pantry.receipt'
  kind: 'screen' | 'setting' | 'action';
  route?: string; // '/receipt'。動的は '/recipes/[id]' のようにパターン文字列のまま
  title: () => string; // t('assistant.catalog.pantry.receipt.title')
  summary: () => string; // AI へ渡す 1 文（≤90 字）。**利用者に見せる文言と同じ辞書**から引く
  suggestedQuestions?: () => string[]; // シートに出す候補。**AI には送らない**
  requires?: ('family' | 'byok' | 'premium' | 'android' | 'ios')[]; // 出す条件
  /** action のときだけ */
  tier?: 'navigate' | 'mutate'; // destructive は**書けない**（型で塞ぐ）
  args?: z.ZodTypeAny; // mutate の引数スキーマ
  run?: (args: unknown) => Promise<void>; // 既存 service を呼ぶだけ。ここに業務ロジックを書かない
}
```

| 決めたこと                                                   | なぜ                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文言は **i18n 辞書から引く**（カタログに生文字列を書かない） | 画面と同じ言葉で答える。辞書を直せば答えも変わる（二重管理を作らない）                                                                                                                                                                                                              |

| `run` は既存 service の 1 呼び出しに限定                     | アシスタント経由と画面経由で挙動が分かれない                                                                                                                                                                                                                                        |

## 5. アクションの 3 段階（安全設計）

| 段階            | 例                                     | 実行                                          | 取り消し        | Gemini/OS の対応        |
| --------------- | -------------------------------------- | --------------------------------------------- | --------------- | ----------------------- |
| **navigate**    | 「レシート読み取りを開く」             | カードをタップ → シートを閉じて `router.push` | 戻るで元の画面  | 「設定画面を開く」      |
| **mutate**      | 「牛乳を買い物に追加」「単位を lb に」 | 確認カードの中のボタン 1 回 → Toast で結果    | 各画面の既存 UI | 「Wi-Fi をオンにして」  |
| **destructive** | 削除・公開・脱退・課金                 | **カタログに書けない**（型で塞ぐ）            | —               | Gemini も確認を挟む領域 |

- AI が返す `actions[]` は**カタログの id で参照**する。id がカタログに無ければ**黙って落とす**
  （モデルが幻覚した操作を実行しない）。`args` は各エントリの Zod で検証し、通らなければカードを出さない。
- 1 回の返答に載せるアクションは**最大 2 つ**。並べるほど「どれ」が起きる。
- 「作れるレシピ」「写真からレシピ」など**AI 機能へ送り出した先**では、その機能の既存ゲート
  （`ensureInferenceCredit()`）がそのまま働く。アシスタントは枠を代理消費しない。
- mutate は 2026-09-13 に**解凍**し Phase 1 と同梱する（§10 問 3）。`catalog.ts` の `run` は export せず `actionRunner.confirmMutate(id, args)` だけを公開し、それが確認カードの `onConfirm` からしか呼ばれないことをテストで守る。AI 経由の書き込みは家族同期に流れるので、`source` の印を付けるかは実装時に決める（M3-6 と同じ論点）。

## 6. アーキテクチャ

### 6-1. 構成

```
[使い方ボタン] ── ルート _layout（CookingResumeBar と同列・useOverlayVisibility で出し分け）
      │ open
[AssistantSheet]（in-tree・Reanimated）
      ├─ 入力中: catalogSearch(query, currentScreenId)  … 端末内・同期
      ├─ 送信:   assistant.provider.ask({ messages, context, catalogText })
      │           └─ POST /api/v1/infer/assist（Phase 1 は**サーバー経由のみ**。BYOK 直は後述）
      └─ 返答:   { reply, actions[], suggestions[], offTopic }
                  └─ actionRunner.run(action) → close sheet → router.push / catalog[id].run
```

**BYOK 直経路は Phase 1 に入れない。** 相談 provider は BYOK 用にシステムプロンプトの写しを端末に持ち
「片方だけ直さないこと」で運用しているが、本機能で同じ二重管理を再演しない。
BYOK 利用者もサーバー経由で構わない理由: 本機能は**無料枠を消費しない**ので、BYOK の動機（上限解除）が効かない。
将来入れるなら、プロンプト骨子を `packages/shared` に置いて両側から import する。

### 6-2. リクエスト（端末 → サーバー）

```jsonc
{
  "messages": [{ "role": "user", "text": "レシートで登録できる？" }], // 直近 12 発言まで（相談は 24。用途が短いので半分）
  "context": {
    "route": "/pantry", // 現在画面（グループ名を除いたパス）
    "screenId": "pantry", // カタログの id
    "locale": "ja",
    "unitSystem": "metric",
    "state": {
      // **数と有無だけ**。中身は送らない
      "recipeCount": 12,
      "pantryCount": 0,
      "shoppingCount": 3,
      "familyJoined": false,
      "byok": false,
      "premium": false,
      "aiRemaining": 5,
      "platform": "android",
    },
  },
  "catalog": "…カタログを平文にしたもの（requires で絞った後・suggestedQuestions は含めない）…",
  "catalogVersion": "2026-09-10",
}
```

`state` があるから「なぜ広告が出るの」「同期されないんだけど」に**その人の状態で**答えられる
（`familyJoined:false` なら「家族グループにまだ入っていません → [家族設定を開く]」）。
レシピ名・材料・写真は**送らない**。質問文以外に個人の内容は出ない。

**カタログの大きさ**（レビューで訂正）: 1 件 ≈125 字 × 40 件 ≈ **5,000 字 ≈ 4〜6k トークン**（当初の 1.5k は過小）。
サーバーの `zValidator` 上限は固定値を手で決めず、**端末側テストで「上限の 80% 以下」を assert** する
（55 件に伸びた時点で日本語版だけ 400 で落ちる腐り方を防ぐ）。
カタログは `systemInstruction` の先頭に固定配置する — locale × requires の組み合わせは数種なので内容が同一になりやすく、
Gemini 2.5 系の implicit caching（1,024 トークン以上）で入力が自動的に割引される。

### 6-3. レスポンス（サーバー → 端末）

```jsonc
{
  "ok": true,
  "data": {
    "reply": "できます。在庫の右上の「レシート」から撮影します。",
    "actions": [{ "id": "pantry.receipt", "tier": "navigate" }],
    "suggestions": ["読み取れなかったときは？"], // 次の候補チップ。0〜2 個
    "offTopic": false, // 料理の話だったら true ＋ consult への navigate（質問文を seed に載せる）
  },
}
```

Gemini には `responseSchema` で固定させる（相談と同じ手法。function calling は**使わない** —
1 往復で終わり、実行は端末側でタップ後に行うので、モデルに「呼ばせる」必要が無い）。

### 6-4. システムプロンプトの骨子（サーバー `lib/assistant.ts`）

```
あなたは、料理レシピ手帳アプリ「だいどこ」の使い方を案内する係です。
- 答えられるのは **カタログにある機能だけ**。無いものは「この機能はありません」と言う。作らない。
- 返事は 3 文以内。質問は一度に 1 つまで。
- 画面を開けば済むことは、説明を短くして actions に navigate を入れる。
- データを変える操作（追加・切替）は actions に mutate を入れる。**実行するのは利用者**。
- 料理そのもの（何を作るか・レシピの中身）の質問には答えず offTopic=true にし、「相談しながらつくる」へ送る。
- context.state を使って、その人の状態に合わせて答える（家族未参加・枠切れ・鍵なし）。
- アレルギー・栄養・カロリーには触れない。
```

### 6-5. サーバーと上限

| 項目           | 内容                                                                                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| エンドポイント | `POST /api/v1/infer/assist`（`infer.ts` に追加。`messages` 12 件・`catalog` の上限は §6-2 のテストと連動）                                                                                |
| モデル         | **gemini-2.5-flash-lite**（案内文は短く、推論は要らない。思考オフ既定は `thinking-budget.ts` を踏襲）                                                                                     |
| レート上限     | `rate-limit.ts` に**独立プール** `ASSIST_POOL`（`ASSIST_GLOBAL_DAILY_LIMIT` / `ASSIST_DAILY_LIMIT`）。相乗りのさいえん帳の教訓: 単価が違うものに 1 本のカウンタを共有しない               |

| 同意           | **新設しない**。送るのは質問文と件数だけなので免責 1 行で済ませ、`hasCloudInferenceConsent()`（定義のみ・未配線）の配線は写真系と一緒に Issue #265 で扱う                                 |
| 計測           | 端末内に**件数だけ**（聞いた／候補を開いた／候補ゼロ）を `app_meta` に持ち、設定画面のデバッグ表示で見られるようにする。質問文は残さない。`growth-analyst` の材料                         |

**無料枠を消費しない理由**: 「使い方を聞く」に課金の枠を使わせると、初めての人が最初に触る AI が
「あと 4 回」を減らす体験になる。フリーミアム設計 §1 の「価値を先に見せる」に反する。

## 7. 端末内フォールバック（Phase 0 の中身であり、常設の保険）

入力中に走る `catalogSearch()` は AI とは無関係の**端末内の検索**。

- 対象: `title` / `summary` / `suggestedQuestions` を NFKC＋カナ統一（`normalizeItemName` と同じ正規化）
- 手法: 単純なトークン含有スコア。FTS5 は不要（40 件）
- 出す: 上位 3 件を「開く」カードとして即時表示
- 効き目: **オフライン・サーバー停止・枠切れ**でも「機能を探して開く」は動く。
  けんじ（ペルソナ）「Phase 0 が本体で AI は飾り。40 件のカタログなら端末内検索で 8 割解ける」

## 8. 常駐ボタンの表示ルール（登録表）

判定は `useOverlayVisibility()`（新設・`CookingResumeBar` と共用）に寄せる。セグメント一致（`pathHasAnySegment`・Issue #285）。

| 状態                                                  | 表示                                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 料理中 `/cook`・撮影 `/import-photo`・相談 `/consult` | 出さない                                                                                 |
| バーコード `/scan-barcode`・冷蔵庫写真 `/fridge`      | 出さない（カメラ全画面）                                                                 |
| `presentation:'modal'` の画面（`recipes/[id]/edit`）  | 出さない（iOS で下に沈む — §3-1）                                                        |
| Web（`isNativePlatform` が false）                    | 丸ごと出さない（`r/b/j` をルートで除外するより漏れない）                                 |
| `CookingResumeBar` 表示中                             | その**上**に積む（+56px）                                                                |
| **広告バナーのある画面**（在庫・買い物・レシピ一覧）  | バナーの高さぶん上へ積む。**バナーに被せない**（AdMob ポリシー: 広告を他要素で覆わない） |
| 下端 CTA のある画面（フォーム系・ペイウォール）       | CTA の高さぶん上へ（表で指定）                                                           |
| `EXPO_PUBLIC_DISABLE_ASSISTANT=1`                     | 出さない（ストア用スクショ）                                                             |

削った行（レビューで）: 「空状態のとき出さない」「コーチマーク中は出さない」。前者は画面→ルートの信号が無く 43 画面に配線が生える。
後者は overlay が Modal なので下のピルは押せず、誤タップは起きない。
