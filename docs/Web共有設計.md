# Web 共有設計 — レシピの共有リンク（S1）

> 2026-08-12 起草。家族（iPhone）や SNS へ、**アプリなしで読めるレシピページ**を渡すための設計。
> 背景: 共有・招待型の成長はリンクの受け手がアプリを入れられないと連鎖が切れる。
> 日本は iPhone 多数派のため、Android アプリ単体では共有がほぼ毎回断線する — Web ページはその断線を塞ぐ。

## 2. 方針（運用と権利の 2 大リスクを構造で潰す）

### 2-1. 限定公開のみ — 「公開の場」を作らない

- ページは **URL を知っている人だけ**が見られる（スラッグ = 暗号乱数 12 文字。列挙不可能）
- サイト内に一覧・検索・発見の面を**作らない**
- `<meta name="robots" content="noindex">` ＋ `X-Robots-Tag: noindex` で検索エンジンに載せない
- 共有はユーザーの明示操作のみ・**いつでも取り消し可**（取り消し後は 404）
- 通報窓口は LP の連絡先を使う

これで当サイトは「不特定多数に見せる場」ではなく「手渡しリンクの置き場」になり、
モデレーション面がほぼ消える。

### 2-2. 出所ゲート — 転載をサーバーに保存しない

公開可否は**レシピの出所（sources.type）で機械的に**決める。人の注意力に頼らない。

| 出所                                            | Web 共有                           | 理由                                                                                                            |
| ----------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| URL 取り込み（`type='url'`）                    | **不可**（メニュー自体を出さない） | 他サイトの文章表現の転載になり得る。サーバーに保存もしない                                                      |
| それ以外（手動・写真AI・OCR・テキスト取り込み） | 確認つきで可                       | 「自分で作成した内容」の確認ダイアログ（attestation）を挟む。テキスト取り込みは出所不明のため特にこの確認が担保 |

- 判定はレシピの**全リビジョン**の sourceId → sources.type を見る（編集で出所が消える抜け道を塞ぐ）
- 本設計に合わせ、URL 取り込みは保存時に `sources(type='url', url)` を記録するようにした
  （それまでは記録なし。既存の URL 取り込みレシピは判定できないが、確認ダイアログが最後の担保）
- サーバー API は `attested: true` を必須にする（クライアントの確認を通った証跡）

## 3. データモデル（サーバー・SQLite）

**初の永続ストレージ。** Railway ボリューム（`/data`）上の SQLite ＋ better-sqlite3 ＋ Drizzle。
Postgres にしない理由: 月数十円で済み、サービスが増えず、クラウド同期（#65）本格化時に
Drizzle スキーマごと移行できる。

```
shared_recipes
  slug              TEXT PK   -- 暗号乱数 12 文字（base64url）。これが「限定公開」の鍵
  delete_token_hash TEXT      -- 取り消しトークンの SHA-256（平文は端末にのみ保存）
  locale            TEXT      -- 'ja' | 'en'（ページの表示言語）
  title / servings / cook_time_min / description
  ingredients       TEXT(JSON) / steps TEXT(JSON) / tags TEXT(JSON)
  photo             BLOB?     -- 圧縮済み JPEG（長辺 1200px）
  photo_mime        TEXT?
  created_at        TEXT
  revoked_at        TEXT?     -- 取り消し（soft delete）。ページ・写真とも 404
```

- DB パス: `SHARE_DB_PATH` → 既定 `/data/share.db`（`/data` が無いローカルは `.data/share.db`）
- 個人情報は**持たない**（投稿者名・端末情報・アカウントなし）

## 4. API / ページ

| メソッド | パス                          | 内容                                                                                       |
| -------- | ----------------------------- | ------------------------------------------------------------------------------------------ |
| POST     | `/api/v1/share/recipes`       | 公開。`attested: true` 必須 → `{ slug, url, deleteToken }`                                 |
| DELETE   | `/api/v1/share/recipes/:slug` | 取り消し。ヘッダ `x-share-delete-token`                                                    |
| GET      | `/r/:slug`                    | レシピページ（HTML・noindex・OGP・「アプリで開く」導線）                                   |
| GET      | `/r/:slug/photo`              | 写真（immutable キャッシュ）                                                               |
| GET      | `/api/v1/share/export`        | バックアップ用全件ダンプ。ヘッダ `x-export-token` = `SHARE_EXPORT_TOKEN`（未設定なら 404） |

- レート制限は AI 系と別枠（`SHARE_DAILY_LIMIT` 既定 20/日/IP・`SHARE_GLOBAL_DAILY_LIMIT` 既定 500/日）
- ページの HTML は全フィールドをエスケープ（XSS）。OGP は写真があれば `summary_large_image`
- ベース URL は `SHARE_BASE_URL`（既定 = Railway 本番）

## 5. アプリ側

- レシピ詳細メニュー: 出所ゲート通過時のみ「Web ページで共有」を表示
  - 未共有 → 確認ダイアログ（自分で作成した内容か）→ 公開 → OS 共有シートで URL を渡す
  - 共有済み → 「共有リンクを送る」「Web 共有を停止」
- 共有状態は `app_meta` の `web_share:<recipeId>` に JSON（slug / url / deleteToken / sharedAt）で保存
  （テーブル追加なし・マイグレーション不要。deleteToken は端末外に出さない）
- 写真は表紙（無ければヒーロー）を長辺 1200px / JPEG q0.7 に圧縮して同送

## 6. 運用

- 費用: ボリューム 1GB ≒ $0.15〜0.25/月。1 共有 ≒ テキスト数 KB ＋ 写真 100〜200KB
- バックアップ: `export` エンドポイントで全件 JSON を取得できる（公開リンクはユーザーとの約束なので、
  リリース運用に日次退避を組み込むのが次の宿題 — R2 無料枠を想定）
- プライバシーポリシーに「Web 共有」の節を追加（共有時のみサーバー保存・取り消しで削除・個人情報なし）

## 8. 共有リンクをアプリで開く（#198・2026-08-22 実装）

共有リンク（`/r/:slug`・`/b/:slug`）を、**インストール済みのアプリ**が受け取って取り込み画面を出す。
入っていない人はこれまでどおり Web ページ（App Links / Universal Links はインストール済みのときだけ
アプリへ行くので、既存の体験は壊れない）。

| 層       | 何をしたか                                                                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| app.json | `android.intentFilters`（`autoVerify`・host = 共有サーバー・`/r/`・`/b/`）と `ios.associatedDomains`。**config 変更なので `--prebuild` が要る**                             |
| サーバー | `GET /api/v1/share/recipes/:slug`・`GET /api/v1/share/books/:slug`（JSON。閲覧ページと同じ公開範囲。帖のパスコードは `x-share-passcode` ヘッダ・同じロック）                |
| サーバー | `/.well-known/assetlinks.json`（`APP_LINKS_SHA256_FINGERPRINTS`）と `/.well-known/apple-app-site-association`（`APPLE_TEAM_ID`）。**未設定なら 404** ＝ OS はブラウザで開く |
| アプリ   | `app/r/[slug].tsx`・`app/b/[slug].tsx` が受け口 → `recipes/import-share`（取り込み画面）へ。レシピは RecipeForm で確認して保存、帖は一覧から**まとめて保存**                |
| 出所     | `sources.type = 'share'`。出所ゲートは `'url'` だけを見るので、家族から受け取ったレシピは再共有できる（共有した側の attested で担保）                                       |

**決めたこと**: 取り込んだレシピは**自分の蔵書庫に普通のレシピとして入れる**（別のまとまりにしない）。
「どこから来たか」は出所（`share`・URL）で残る。帖ごと取り込んでも帖は作らない（受け取った側が
自分の帖を作ればよい — 作るなら蔵書庫の棚から）。

同じ仕組みに **家族共有の招待リンク `/j/:code`** も載っている（2026-09-02・1.13.0。
`docs/クラウド同期設計.md` §2-2b）。intentFilter・AASA の `paths` は `/r/`・`/b/`・`/j/` の 3 つ。

**まだ利用者側でやること（環境変数を入れるまで App Links は効かない）**:

1. Play Console → アプリの完全性 → **アプリ署名鍵証明書**の SHA-256 を `APP_LINKS_SHA256_FINGERPRINTS` に
   （Railway の環境変数・複数はカンマ区切り）。**アップロード鍵ではない**（Google が配布時に署名し直す鍵）。
   ローカルの検証ビルドで試すなら、その APK の署名鍵の SHA-256 も足す
2. Apple Developer の **Team ID** を `APPLE_TEAM_ID` に。iOS は次のビルドから `associatedDomains` が効く
3. 実機で `adb shell pm get-app-links com.daidoko.app` が `verified` になることを確認（検証は
   インストール時に OS が非同期で行う。`pm verify-app-links --re-verify com.daidoko.app` で再検証）

## 7. レシピ帖を「モノ」にする（S4）

> 2026-08-13 起草（ユーザー提案「まずレシピ帖を作成して、それを共有する。共有する時に権限を設定する」）。

### 7-1. 何が問題か

S2 の帖は**アプリの中に存在しない**。`publishRecipeBookToWeb(title, recipes)` が
「選んだレシピ＋題名」を丸ごと送って公開ページを作る、一回きりの操作になっている。
手元（`app_meta` の `web_share_books`）に残るのは共有の控えだけで、
**どのレシピが入っていたかすら保存していない**（slug / url / deleteToken / title / recipeCount / sharedAt）。

結果として:

- **中身を 1 品足すには作り直すしかなく、slug が変わる＝配ったリンクが死ぬ。**
  「わが家のレシピ帖」を育てていく、という一番やりたい使い方が成立しない
- 管理画面に題名と冊数しか出せない（中身を見せられない・直せない）
- 共有しない限り帖は存在しないので、ローカルの整理棚として使えない

### 7-2. 変えるのは操作ではなく成果物の格

**既存の「選んで即共有」は残す。** パッと 3 品送りたいときに「まず帖を作る」を挟むと遅くなる。
その操作が結果として帖を作り、続けて共有もする、という形にする（帖の作成が主・共有は任意の後続）。

導線は 2 つになる:

| 入口                                  | 動き                                                                |
| ------------------------------------- | ------------------------------------------------------------------- |
| 蔵書庫で複数選択 →「レシピ帖」        | 帖を作る（既存どおり）＋その場で共有するかを選べる                  |
| **蔵書庫の棚（2026-08-22 追加）**     | 既にある帖を開く／「＋ 新しい帖」で空の帖を作る → 後から足す → 共有 |
| 帖の一覧（設定 → Web 共有の管理）から | 共有の停止・更新の反映（管理用。入口としては棚が主）                |

### 7-3. データモデル（アプリ・SQLite）

```
recipe_books
  id                 TEXT PK
  title              TEXT NOT NULL
  created_at         TEXT
  updated_at         TEXT
  -- 共有状態（NULL = 未共有）。S2 の app_meta 相当をテーブルへ移す
  share_slug         TEXT?
  share_url          TEXT?
  share_delete_token TEXT?   -- 取り消し＋更新の鍵。端末外に出さない
  shared_at          TEXT?
  share_locale       TEXT?
  is_legacy_share    INTEGER NOT NULL DEFAULT 0  -- S2 で公開した帖（中身が不明）

recipe_book_items
  book_id            TEXT NOT NULL
  recipe_id          TEXT NOT NULL
  position           INTEGER NOT NULL
  PRIMARY KEY (book_id, recipe_id)
```

**S2 からの移行**: `app_meta.web_share_books` の各要素を `recipe_books` に写す。
収録レシピは記録されていないので `recipe_book_items` は空、`is_legacy_share=1` を立てる。
UI では「この帖は以前の形式です。中身を編集するには作り直してください（リンクが変わります）」と出し、
**停止だけできる**ようにする。取りこぼしを黙って消さないための措置で、
1.7.0 の利用者はまだ本人だけなので影響は小さい。

### 7-4. 更新 API — リンクを変えずに中身を差し替える

| メソッド | パス                        | 内容                                                                |
| -------- | --------------------------- | ------------------------------------------------------------------- |
| PATCH    | `/api/v1/share/books/:slug` | 題名・収録レシピ・公開の強度を**まるごと差し替える**（slug は不変） |

- 認証は**既存の削除トークン**（`x-share-delete-token`）。**編集トークンを兼ねる**。
  アカウントを増やさずに更新できるのがこの設計の肝。トークンは端末にしか無い
- ボディは POST と同形（`attested: true` 必須・出所ゲートは毎回効かせる）
- 実装は「同じ slug で書き直す」= 既存の帖レコードと収録行を消して入れ直す（差分更新はしない。単純さを取る）
- レート制限は POST と同じ枠で数える（編集の連打も費用になるため）

### 7-5. 「権限」= 公開の強度（人ベースにはしない）

**アカウントレス（個人情報ゼロ）が土台**なので、「この人だけ見られる」という人単位の権限は持てない。
人を識別するにはアカウントが要り、それは `docs/クラウド同期設計.md`（#65）の範囲。
持てるのは**リンクそのものの強度**だけ。

| 設定                  | 実装                                                    | 効き目                                                 |
| --------------------- | ------------------------------------------------------- | ------------------------------------------------------ |
| 有効期限              | `expires_at` を持ち、超えたら 404（取り消しと同じ扱い） | 貼りっぱなし事故を防ぐ。既定は無期限                   |
| パスコード（数字6桁） | `passcode_hash`（SHA-256＋slug をソルト）・入力フォーム | リンクが漏れても中身は読めない＝「家族だけ」が実質成立 |
| 停止                  | 既存（`revoked_at`）                                    | 即 404                                                 |

パスコードの注意点:

- **総当たり対策が必須**（6 桁 = 100 万通り）。slug ごとに失敗回数を数え、
  一定回数で一定時間ロックする。数え方はサーバー側のみ（クライアントを信用しない）。
  **初版は 4 桁（1 万通り）だった**が、レート制限（5 回失敗で 15 分ロック）を掛けても
  平均 10 日ほどで割れる計算だったため、実装ロジック（ハッシュ・比較・レート制限）は
  変えずに桁数だけ 6 桁へ上げた（2026-09-01）。ロック状態を DB で永続化する案は
  意図的に採らない — 再起動でカウンタが消えるのは許容し、桁数で底上げする方針
- **6 桁必須は新規発行（`createBookShare`/`patchBookShare` の zod）だけ。**
  既に 4 桁で公開済みの帖は、そのまま開ける必要がある——ハッシュ照合
  （`hashPasscode`/`verifyBookPasscode`）は桁数を見ないので通るが、**入力ゲートを
  一律 6 桁専用にすると、正しいパスコードを持っている閲覧者が弾かれる。**
  JSON API・HTML の unlock フォーム（`<input pattern>`）・モバイルの入力欄、
  いずれも「4 桁 or 6 桁」を通す形に揃えてある。入力側の文言も桁数を名乗らない
  （「6桁を入力してください」と出すと、4 桁の持ち主が混乱する）
- 認証後は**署名付き Cookie**（slug スコープ・短期）で読み直しを許す。毎回入力させない
- パスコード付きのページは **OGP を出さない**（プレビューで中身が漏れるため。
  タイトルも「保護されたレシピ帖」に落とす）
- 写真エンドポイント（`/b/:slug/photo/:index`）も同じ Cookie で守る。**ページだけ守っても写真が直リンクで読めては意味がない**

### 7-7. 落とし穴（先に潰す）

- **バックアップ対象に新テーブルを足す。** 在庫まわりで一度漏らしている（PR#109）。
  `BACKUP_TABLES` に `recipe_books` / `recipe_book_items` を入れ、復元時に共有トークンをどう扱うか決める
  （**別端末に復元した帖の共有を止められると困る**ので、トークンごと復元する）
- **出所ゲートは共有時に効かせる。** URL 取り込みレシピは帖に入れられてよい（手元の整理は自由）が、
  共有時に除外し、除外した件数を伝える（S2 の既存挙動と同じ）
- **写真は共有・更新のたびに送り直す。** サーバーは端末の写真を参照できない
- 帖から消したレシピ、あるいは削除されたレシピの扱い（収録行は消す。共有中なら次の更新で反映）

### 7-8. 実測（2026-08-13・ローカルサーバーで確認）

サーバー側は実際に起動して全経路を通した。**アプリからの共有往復は、サーバーが本番へ出る
リリース時に確認する**（新エンドポイントの本番先行デプロイはしない方針 — `docs/リリース手順.md` §1）。

| 経路                   | 結果                                                |
| ---------------------- | --------------------------------------------------- |
| 公開 → ページ表示      | 200・中身が出る                                     |
| PATCH で差し替え       | **URL 不変**のまま追加レシピが反映される            |
| パスコードあり・未認証 | 401・**題名も収録レシピも漏れない**                 |
| 写真の直リンク・未認証 | 404（ページだけ守っても意味がないため同じ鍵で守る） |
| 解錠 → 再訪            | Cookie 発行 → 200・写真は `private, max-age=3600`   |
| 4桁を5回失敗 → 正解    | 401（ロック中は正解でも通さない）                   |
| 有効期限 7 日          | `expiresAt` が 7 日後に設定される                   |
