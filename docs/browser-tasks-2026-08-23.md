## A. Play Console — データセーフティ申告の更新【最優先・リリースのブロッカー】

**なぜ必要か**: 現行申告は「収集はすべて一時的処理（解析後破棄）・サーバー保持なし・データ削除リクエスト=いいえ」。
クラウド同期はレシピ・買い物・在庫をサーバー（PostgreSQL）に**保持する**ので、この前提が崩れる。
申告と実装の不一致は審査で弾かれるため、**アプリを提出する前に**申告を変更し審査に通す必要がある。

**場所**: Play Console → だいどこ（`com.daidoko.app`）→ アプリのコンテンツ → データセーフティ
（URL 直行可: `.../app-content/data-privacy-security`）

**現行申告（2026-07-05 送信・変更前の状態）**

| 項目                 | 現在                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| データの種類         | ウェブ閲覧履歴（URL 取り込み）／写真／その他のユーザー作成コンテンツ |
| 収集・共有           | いずれも「収集」のみ（共有なし）                                     |
| 処理                 | **すべてエフェメラル（一時的処理）**                                 |
| 必須/任意            | 任意                                                                 |
| 目的                 | アプリの機能                                                         |
| 暗号化               | はい                                                                 |
| データ削除リクエスト | **いいえ**                                                           |
| アカウント作成       | なし                                                                 |
| 広告 ID              | 使用する（2026-07 の広告有効化で申告済み）                           |

**変更する点（ここだけ直す。他は触らない）**

1. **「その他のユーザー作成コンテンツ」**（レシピ・買い物リスト・在庫が該当）
   → **エフェメラルのチェックを外す**（サーバーに保持されるため）
   → 目的は「アプリの機能」のまま
2. **「写真」**
   → **エフェメラルのままでよい**。クラウド同期は写真を送らない（S3 は次のリリース）。
   ※ Web 共有では写真をサーバーに保存するが、これは 2026-08-14 に申告済み（「一時的に処理」を いいえ に変更済み）。
   **画面上で写真が既に「エフェメラルでない」状態なら、そのまま触らない**
3. **「デバイスまたはその他の ID」を追加**
   → 収集する／共有しない／**必須**／目的=**アプリの機能**／エフェメラルではない
   （同期は端末ごとのランダム ID と Expo Push トークンをサーバーに保持する。氏名・メールは一切収集しない）
4. **データ削除リクエスト = はい**
   → 削除方法の説明: アプリ内の「家族グループ」画面から
   「共有グループを削除」（サーバー上の共有データを全消去）または「このグループから離脱」で行える
   → 削除リクエスト用 URL を求められた場合はプライバシーポリシーの gist URL を入れる:
   `https://gist.github.com/keisato848/49fb9a73f3a1c9952548388f288c383c`
5. **アカウント作成 = なし のまま**（アカウントレス設計。氏名・メール・電話番号は収集しない）
6. **暗号化 = はい のまま**（HTTPS）

**手順**

1. 5 ステップのウィザードを進める: 概要 → 収集とセキュリティ → データの種類 → 使用と処理 → プレビュー
2. **各ステップの画面を都度ユーザーに見せて確認を取る**
3. 保存しただけでは審査に載らない。**「公開の概要」→「変更を審査に送信」まで実行**
   → ここは**ユーザーの明示承認が必要**（`console-browser-ops` §1 の承認ゲート）

**注意**: プライバシーポリシーの gist は**まだ更新されていない**（原本 `docs/privacy-policy.md` は更新済みだが、
main へのマージ待ち）。**申告の送信は gist 更新後**にするのが望ましい。順序が前後しそうならユーザーに確認すること。

**終わったら**: `docs/リリース手順.md` §4 の「現行申告」の記述を新しい内容に更新する（次に見る人のため）。

## B. App Store Connect — さいえん手帳の「マーケティング URL」を登録

**なぜ必要か**: さいえん手帳（iOS・`com.saientecho.app`・App ID `6801141151`）は
**デベロッパー Web サイトが未登録**（iTunes Lookup API の `sellerUrl` が空）。
AdMob はストア掲載のデベロッパー Web サイトを見て app-ads.txt をクロールするため、
未登録だとクロール対象が無く、アプリ確認が永久に完了しない。

**場所**: App Store Connect → さいえん手帳 → App 情報（または該当バージョン）→ **マーケティング URL**

**入れる値**: `https://keisato848.github.io/`
（だいどこ iOS は `https://keisato848.github.io/daidoko/` が入っている。
さいえん手帳の LP があるならそのパスでよい。無ければルートで可）

**注意**: 公開中バージョンのメタデータ変更は審査対象になる場合がある。
「App 情報」側の変更で済むか、次バージョンでの反映になるかを画面で確認し、**ユーザーに判断を仰ぐこと**。

## C. AdMob — app-ads.txt の再クロール（待つだけ・急がない）

**現状**: だいどこ iOS / さいえん手帳（Android・iOS）で

が出ている。**別セッションの調査で「単なるクロール待ち」と結論済み**。

**確認済みの事実（再調査は不要）**

- `https://keisato848.github.io/app-ads.txt` は AdsBot-Google / Googlebot のどちらでも **200・text/plain**
- 中身は AdMob が提示するスニペットと 1 バイト違わず一致（BOM・CRLF なし）:
  `google.com, pub-2633806931583277, DIRECT, f08c47fec0942fa0`
- `robots.txt` は 404（クロール制限なし）

**やること**: 各アプリの「app-ads.txt のステータス」で **「アップデートを確認」を押すだけ**。
反映に最大 24 時間かかる。押しても状態が変わらなくても、**それ以上の調査や設定変更はしないこと**
（ファイル側は正常であることが確認済み）。

**重要**: だいどこ iOS は**ストアリンクの登録自体は成功済み**（2026-08-23）。
app-ads.txt の警告はプログラマティック需要に関わるもので、広告配信を完全に止めるものではない。
