## 症状 → 原因 → 対処

### 1. 100 字要約では 2 往復目が劣化する

- **症状**: S1 で下書きが出ず質問に戻る。S2 で袋の分量・手順を持っていないのに「作り方どおり」の下書きを捏造する。
- **原因**: 設計 §7-4-1 の例（「冷蔵庫上段: 鶏むね肉2パック、卵10個、牛乳。下段: 玉ねぎ3個」）は品目の列挙で、**パッケージの文字・料理の細部が落ちる**。
  相談の 2 往復目は「写真に写っていた○○」を前提に進むので、そこが無いと会話が成り立たない。
- **対処（設計への提案）**: `imageReadings[].reading` の**粒度を設計書で決める**。「品目＋数えられた数量」に加えて
  「パッケージの文字（材料・作り方・人数・内容量）は読めたまま」「料理写真は具材・麺や米・スープの色・薬味まで」。
  長さ上限は置かない（S2 裏面で 693 字・出力 ¥0.28 相当）。試験で使ったプロンプトは本ファイル末尾。

### 2. 読み取りの誤りが会話の間ずっと固定される

- **症状**: S1 の読み取りが容器の丸鶏を「メロンのような果物」、柑橘を「アボカド」「洋梨」と読んだ。
  full の「紫色の野菜」がそのまま材料名 **「紫色の野菜 1/4 個」** として下書きに入った。
- **原因**: 写真再送なら往復ごとにモデルが見直せるが、テキスト代用では**1 往復目の読み取りが唯一の真実**になる。
  曖昧語（「緑色の液体のボトル」「紫色の野菜」）は写真があれば具体化されるが、テキストでは具体化のしようがない。
- **対処（設計への提案）**: (a) 読み取りの指示に**曖昧なカテゴリ語を材料名に使わない**を入れる（`fridge-vision.ts` の「カテゴリ名は品目として返さない」と同じ規約）。
  (b) **読み取りを利用者に見せる**。端末は `imageReadings` を保持するのだから、1 往復目の返答に「写真から読み取ったもの: …」として折りたたみで出せば、
  2 往復目に「それメロンじゃなくて鶏肉」と直せる。サーバーは写真を持たないので、**直せるのは利用者だけ**。

### 3. 読み取りに無いことを聞かれたとき

- **症状**: S1「写真に写ってたチーズ」— 読み取りにチーズは無いが、text 腕は両方とも利用者の言葉に従って追加した。
  S3「麺は太めだった？」— short は「お好みでしたら」と写真を根拠にせず、full は読み取りを根拠に「確かに太め」と答えた。
- **原因**: 本番プロンプトには「見えないことを見えたことにしない」があり、それが効いている（捏造は起きなかった）。
  ただし利用者の主張を**検証できない**ので、間違った主張もそのまま通る。
- **対処**: 許容範囲（決めるのは利用者、の原則どおり）。設計に「読み取りに無いものを利用者が言ったら、読み取りに無かったことを一言添えて従う」を足すかは判断待ち。
  プロンプトに `imageReadings` は**写真そのものではなく前回の記録**だと明示すること。

### 4. 3 往復目の「言われた点だけ変える」

- **症状**: text-full の S1 で塩こしょう追加・手順の組み替え・題の変更。S3 で返事と下書きが食い違う。
- **原因**: 読み取り方式に固有か、温度 0.6 の揺れかは **n=1 では区別できない**（photo 腕でも 2 往復目の #1/#2 で塩こしょうの有無が揺れている）。
- **対処**: 本測定では言い切らない。実装後に同じ 3 会話を各腕 3 回以上回して差を見る。

## 判断

| 観点                     | 判定                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| 写真の内容と矛盾しないか | text-full: 3/3 矛盾なし。text-short: S2 で袋の作り方を捏造（矛盾）                                        |
| 材料の一貫性             | 3 往復目の共通下書きに対し、材料の**削除・入れ替えは全腕なし**。text-full に足し過ぎ 1 件（揺れの可能性） |
| 下書きの精度             | text-full は photo と同等（S3 は麺の種類で上回る）。text-short は S1 で下書きなし・S2 で分量誤り          |
| 送信量                   | 5〜9KB（写真再送の 1/25〜1/200）。受入基準 A「1/3 以下」を大きく満たす                                    |

**成り立つ条件**: (1) 読み取りは詳細（品目・数量・パッケージ文字・料理の細部）で、100 字要約にしない。
(2) 曖昧なカテゴリ語を材料名にしない規約を読み取りに入れる。(3) 読み取りを利用者に見せて直せるようにする（提案）。
(4) プロンプトで `imageReadings` を「前回の記録」と位置づける。

## 測れていないこと

- 日本の家庭の冷蔵庫写真（利用者のもの）。米国の冷蔵庫で代用した
- 読み取りを**同じ応答で**生成したときの品質（設計の形）。別呼び出し・temperature 0.2 で作った
- 各腕 1 回ずつ（photo のみ 2 回）。温度 0.6 の揺れと方式の差を分離できていない
- 4 枚添付（R2）。最大 2 枚で試した
- 1 往復目に下書きが出る会話（3 会話とも質問で返った）

## 試験で使った読み取りプロンプト（提案の下書き・本番には無い）

```
あなたは家庭料理の相談アシスタントです。利用者が相談に添えた写真を、
**あとで写真を見返せない状態でも会話を続けられるように**、文章で記録します。
写真ごとに 1 件、readings に書いてください（index は 0 始まりの何枚目か）。
数や量は数えられた・読めたものだけ書き、見えないことは書かない。
各写真について、写っている食材・食品・料理・容器の中身を**見えた範囲で漏れなく**列挙する。
パッケージに文字があれば、作り方・分量・原材料・人数など**読めた文字はそのまま**書く。
料理の写真なら、具材・麺や米の種類・スープの色や見た目・薬味・盛り付けまで書く。
長さの上限は設けない。
```

これに「調味料・野菜・飲料のようなカテゴリ語や色だけの表現（紫色の野菜）を品目にしない」を足すのが対処 2-a。
