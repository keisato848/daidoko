## 2. 判断（2026-09-05）

| 打ち手                                      | 判断           | 理由                                                                                                                     |
| ------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Apple Ads の増額                            | **しない**     | 効果を読む数字（訪問者・到達率）が無い。現状予算で 4 週固定して CPT・TTR・CR を見る                                      |
| Google 広告アプリキャンペーン               | **今はしない** | 収益は広告 1 表示 ¥2.4。有料獲得は構造的に元が取れない。やるなら「入れた人が AI 導線に到達するか」を知る上限つき実験のみ |
| アナリティクス SDK 導入                     | **しない**     | 母数 9 では 9 人分しか取れず、データセーフティ申告変更のコストの方が大きい（`docs/fcm-setup.md` の方針を維持）           |
| 掲載スクショの改修（けんじレビュー 4 指摘） | **保留**       | 訪問者が居なければ効かない。§3 の訪問者数を見てから                                                                      |
| ストア外の獲得作業（§5）                    | **やる**       | ストア内の作業は一通り済んでおり、残っているのはここだけ                                                                 |

### 判断の閾値

- 4 週後、Play 掲載訪問者数 < 100 → 流入の問題。掲載改修より記事・外部導線を優先
- 4 週後、訪問者 ≥ 100 でインストール率が 1 桁 % → 掲載改修（けんじレビュー `docs/reviews/value-review-2026-09-05.md`）
- 累計インストール 100 に達するまで継続率は読まない
- Apple Ads: 4 週で CPA が日本相場（CPT $0.8〜1.0 前後、[AppTweak](https://www.apptweak.com/en/aso-blog/apple-ads-benchmarks)）から大きく外れたら止める

## 3. 2026-09-05 に確認できたこと（Web 検索。ストア API はリモート環境から遮断されていて未確認）

### 3-1. 「だいどこ」は既存ブランドと衝突している

Web で「だいどこ アプリ レシピ」を検索すると、**パルシステムの「だいどこログ」**（レシピサイト＋Android アプリ＋Instagram）が上位を占める。
2011 年頃からあるサービスで、検索エンジン上では「だいどこ」の語をほぼ独占している。

- 影響: アプリ名で検索した人が「だいどこログ」に流れる。口コミで名前を聞いた人が辿り着けない可能性がある
- 対処（案）: 掲載名・記事・SNS では常に **「だいどこ - お店の味を再現」** のように補語をつけて呼ぶ。単独の「だいどこ」では名乗らない。改名は保留（App Store 側の名前変更は済んだばかり。`docs/store/app-store/SUBMISSION.md`）
- 未確認: App Store / Play の検索でも同じか。**§4 の順位確認で確かめる**

### 3-2. 掲載文の語は競合が押さえている

「レシピ管理 買い物リスト 献立」で Web 検索すると、App Store / Play の結果はレピッタ・レピモ・クックスルー・レシパル・買いさぽが上位。
だいどこのストアページは、アプリ名の完全一致で検索しても Web 検索結果に出てこなかった（検索エンジンの索引に載っていないか、順位が低い）。

- 影響: 掲載文（`docs/store/*/listing-ja.md`）の一般語ではストア内でも並べない前提で動く
- 対処: 勝負する語は「〇〇 再現」「お店の味 再現」「写真 レシピ AI」の 3 系統に絞る

### 3-3. 「〇〇 再現レシピ」は検索される語だが、レシピ自体は既に大量にある

「サイゼリヤ 再現」「丸亀製麺 再現」はクックパッド特集・Yahoo ニュース・個人ブログ・YouTube Shorts・TikTok が既に埋めている。
レシピそのものを出しても埋もれる。**だいどこで出せる固有の内容は「写真 1 枚から AI が出した下書きを、感想で 2〜3 回直して近づけた過程」**。
この「過程」を書いた記事は見当たらなかった（2026-09-05 時点の Web 検索の範囲）。

## 4. ユーザーにしかできない作業（順番どおりに）

1. **順位確認（30 分・費用 0）** — シークレットウィンドウ（未ログイン）で以下を検索し、だいどこが何位に出るかをこの表に記入する

   | 検索語          | App Store 順位 | Play 順位 | 確認日 |
   | --------------- | -------------- | --------- | ------ |
   | だいどこ        |                |           |        |
   | お店の味 再現   |                |           |        |
   | 再現レシピ      |                |           |        |
   | 料理写真 レシピ |                |           |        |
   | 写真 レシピ AI  |                |           |        |

   自分の名前で出なければ、掲載改修より先に名前の呼び方（§3-1）を直す。

2. **Play Console の数字を取る** — 「統計」（インストール・国別）「ストア掲載情報のパフォーマンス」（訪問者・インストール率）「Android vitals」を CSV で `analytics/` に置き、要約値を §1 に足す
3. **App Store Connect の App Analytics** — インプレッション・製品ページ表示・ダウンロード・ソース別（検索 / ブラウズ / リファラー）
4. **Apple Ads のレポート** — 種別（Basic / Advanced）・開始日・日予算・累計支出・対象国・キーワード指定か Search Match か・インプレッション・タップ・CPT。§1 に転記する
5. **iOS 6 件 / Android 3 件のうち自端末・身内・TestFlight 移行分の数**を書く（残りが本当の外部流入）
6. **レビュー 5 件** — 実際に使った家族・知人に正直な評価を頼む。評価 0 件は順位要因でもあり転換率も落とす。文面の指定はしない（ガイドライン違反になる）
7. **家族ループを自分で 1 組回す** — 招待 → 家族の端末で受諾 → 相手が 1 件作る → 自分の端末に届く、までを通し、詰まった箇所を `docs/クラウド同期設計.md` か Issue に書く
8. **記事を 1 本出す** — `docs/growth/記事/` の下書きを、実際に作った結果で埋めて note に出す。URL と公開日をこのファイル §5 に記録する

### 記事の方針

- 題材: 「お店で食べた〇〇を、写真 1 枚から AI で下書き → 感想で直す → 3 回目で近づいた」の**過程**。完成レシピの羅列にしない（§3-3）
- 1 本目はリポジトリに実物がある料理（プロモ用シード: 明太釜玉うどん・麻辣うどん・スクランブルエッグトースト）から選ぶと、スクショと差分画面をそのまま使える
- 表記: 「だいどこ - お店の味を再現」で統一（§3-1）
- 導線: 記事末尾にストアリンクを両方。Play 側は UTM 付き（`&referrer=utm_source%3Dnote%26utm_medium%3Darticle`）にすると Play Console の獲得レポートで記事経由を分けられる
- YouTube: ストア用プロモ動画の更新は掲載素材であって流入経路ではない。流入にするなら記事と同じ「過程」をショートにする（`.claude/skills/promo-video` の収録手順は使えるが、内容は別）
