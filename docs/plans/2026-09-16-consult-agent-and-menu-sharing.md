## 受け入れ基準

### A. 相談の送信（R1〜R6）

- [ ] 写真 2 枚を添えて 1 往復目を送ったあと、文字だけ追記して 2 往復目を送ると、リクエストボディに画像 base64 が**含まれず**、`imageReadings` 文字列が含まれる（サーバーログの `rxBytes` が 1 往復目の 1/3 以下）
- [ ] 1 メッセージに写真を 4 枚添付できる（添付ボタンが 4 枚目まで有効）
- [ ] 回線速度を測る・分岐するコードが**無い**（grep で `NetInfo`／帯域判定が相談経路に増えていない）
- [ ] BYOK 経路とサーバー経路で、タイマー開始が両方とも `toWireMessages` の**後**である（テストで固定）
- [ ] 在庫 300 件の状態でサーバー経路の相談を送ると、ペイロードの pantry が 200 件に切られている
- [ ] 相談以外の経路（写真からレシピ・冷蔵庫・レシート）の `TIMEOUT_MS` は変更されていない

### B. エージェント化 v1（R10〜R16）

- [ ] 相談で「玉ねぎ切らしてる」と送ると、返答に確認カードが出て、**タップするまで買い物リストは変わらない**（テストで `run` が呼ばれないことを固定）
- [ ] ［足す］をタップすると買い物リストに「玉ねぎ」が 1 行増え、Toast に［取り消す］が出る。8 秒以内にタップすると行が消える
- [ ] 買い物リストに未チェックの「玉ねぎ」が既にある状態で同じ操作をすると、Toast は「足しました」ではなく「既にあります」相当の文言で、取り消しボタンが出ない
- [ ] 相談で「在庫はどこで足すの」と聞くと、相談の中で場所を答える（別画面に飛ばない）
- [ ] 設定で候補数を 3 にして「鶏むねで何か」と送ると、候補が 3 件並び、1 件選ぶと下書きになる。相談画面で 1 に上書きすると 1 件になる
- [ ] ホームに相談の常設ボタンがある（既存の位置。空状態以外でも出る）
- [ ] 家族の端末で、相談経由で足した行と手で足した行の見た目に差が**無い**
- [ ] 上記を AQUOS 実機で確認した記録が `docs/verification/` にある（写真 4 枚・3 往復）

### C. 献立の家族共有（R19〜R27・D2・D3・R29）

- [ ] 端末 A で夕の献立を変えると、端末 B を開いたとき同じ献立が出る（1 分以内）
- [ ] 1 日の夕に主菜 1 品＋副菜 2 品＋汁物 1 品を登録でき、週ビューに 4 品すべてが出る
- [ ] 設定で枠の種類（副菜・汁物・サラダ…）と数を変えると、一括生成の対象枠がそれに従う
- [ ] 「在庫・蔵書から組む」「一括 AI 生成」の両方で、1 週間分が枠付き（主菜＋設定した枠）で出る
- [ ] 一括 AI 生成 1 回で、`INFER_GLOBAL_DAILY_LIMIT` を超えない回数の推論で 1 週間分が返る（Phase 1 で「1 推論あたり何品」を決め、試算を残す）
- [ ] 週ビュー（案 1）で 7 日が縦に並び、主菜が 15px・副菜が 13px 以上で表示される。記号でなく「予定」「済み」の文字が出る
- [ ] 献立に入っている日に「作った」を記録すると、その枠が「済み」になる。端末 B でも「済み」が出る（`cooking_logs` 同期）
- [ ] 家族が献立を変えたとき、既存の家族 push（固定文）が届く。**通知に名前は出ない**（D2）
- [ ] 設定で「共有する時間帯」を夕だけにすると、週ビューに朝・昼のチップが出ない
- [ ] 英語ロケールで 1 日のセルが横に切れない（`numberOfLines` と省略）。`+ Add` は半角
- [ ] `SYNC_PAYLOAD_SCHEMA_VERSION` を上げた版で、既存端末が一度全量を取り直したあと、献立・買い物・在庫・レシピが欠けていない（2 台で確認）

### D. ウィジェット（R30〜R33）

- [ ] Android 小/中サイズで今日の主菜＋副菜・汁物が出る。大サイズで週 7 日の主菜が出る。さらに大きいサイズで週の主菜＋副菜が出る
- [ ] ウィジェットの行をタップすると、その日のレシピ詳細が開く
- [ ] 端末 A で献立を変えると、端末 B のアプリを**開かずに**ウィジェットが新しくなる（push → 背景同期 → スナップショット再書き出し）。買い物ウィジェットも同じ。**iOS はベストエフォート（配信保証なし。2026-09-17 決定）**
- [ ] iOS に献立ウィジェットがある。**iPhone は 2 段まで（今日の主菜＋副菜／週の主菜のみ）。iPad のみ週の主菜＋副菜の 3 段目（2026-09-17 決定）**

### E. 一括生成の非同期化（R34・2026-09-17 追加）

- [ ] 一括生成（枠付き 3 分割・既存の主菜のみ一括生成の両方）をリクエストすると、即座に受理応答が返り、画面をブロックしない
- [ ] アプリを閉じても生成は継続し、完了すると push 通知が届く。通知をタップすると生成結果が反映された状態でアプリが開く
- [ ] 生成中にアプリを再度開いても進行状況が分かる（少なくとも「生成中」であることが分かる）
- [ ] ジョブの一時保存に TTL が設定されており、一定時間後に自動的に消える

## スコープ外

- 相談の**初回送信**の軽量化（3〜4 枚で 1.4〜2.0MB のまま）
- 回線速度による分岐、利用者に「写真を小さくして送りますか」と聞く UI
- サーバー側での写真の保持
- 相談以外の経路のタイムアウト統一、共通入口 `image-payload.ts` への寄せ
- 「言ったらそのまま実行」（確認カード無し）、料理そのものの質問に答えること、使い方専用の入口
- v1 の操作は「買い物リストに足す」のみ。献立に入れる／作った記録／在庫を減らす・使い切ったは**後続**（取り消し基盤の完全版が前提）
- 家族端末への「相談で足された」印
- 掲載文（リリース時に別途）
- **「誰が変えたか」の表示・通知**（D2。`createdBy` 同期・同期設計 §0-2 の撤回・プライバシーポリシー更新・データセーフティ再申告は**今回やらない**）
- 献立を各自で持つ形、決める人 1 人・他は閲覧、献立だけの別カレンダー、月グリッド、OS カレンダーへの書き出し、固定 3 枠
- ウィジェット内の切替トグル、タップで週ビューを開くこと、Android 先行・iOS 後
- ウィジェットの存在をアプリ内で案内すること（要求されていない。第 4 部「まだ聞けていないこと」）
- 「128kbps で通ること」を合格条件にすること（要求されていない）

## 決定待ち（eval-inference の測定結果・2026-09-16）

R1 の品質確認が完了した（[docs/eval/consult/2026-09-16-r1-image-readings.md](../eval/consult/2026-09-16-r1-image-readings.md)）。
**結論: 条件付きで成り立つ。** 設計書の例（100字要約）だと2往復目で劣化する（下書きが出ない・作り方を捏造）。
品目・数量・パッケージの文字をそのまま書いた詳細な読み取りなら、写真再送と同等の精度が出た。
送信量は5〜9KB（受入基準Aの「1/3以下」を大きく満たす）。ただし**読み取りの誤りは会話の間ずっと固定される**
（実測: 丸鶏を「メロンのような果物」と誤読→材料名に混入）。

- **imageReadings の粒度**: 100字要約ではなく、品目・数量・パッケージの文字・料理の細部まで書く詳細版にする。**利用者判断**（設計への反映は要合意）
- **読み取りを利用者に見せるか**（新規論点）: サーバーが写真を持たないため、誤読を直せるのは利用者だけ。1往復目の返答に「写真から読み取ったもの」を折りたたみで出す案。**要求されていなかった新しい UI 要素なので、利用者判断が要る**
- **読み取りに無いことを利用者が言った場合の扱い**: 現状は本番プロンプトの「見えないことを見えたことにしない」により捏造はしないが、利用者の主張を検証できない。「読み取りに無かったことを一言添えて従う」を足すかは**利用者判断**
- `docs/レシピ推論の評価設計.md` に相談（consult）の採点軸が無い。追加する提案（軸: 矛盾／一貫性／精度、比較対象: 写真再送、初回の合格ラインは「写真再送と同等」を仮に置く）
- 測れていないこと: 日本の家庭の冷蔵庫写真（米国の写真で代用）、読み取りを同一応答で生成したときの品質（今回は別呼び出しで検証）、各腕1回のみ（温度の揺れと方式差を分離できていない）、4枚添付（R2）
