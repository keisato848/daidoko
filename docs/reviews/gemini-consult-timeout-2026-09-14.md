### A. 1〜6の診断の検証

1. **正しい**
   - **根拠**: `recipe-consult.provider.ts` で `TIMEOUT_MS = 45_000` と定義されています。一方、サーバー側 `recipe-consult.ts` では `REQUEST_TIMEOUT_MS = 30_000`、`MAX_ATTEMPTS = 4`、`BACKOFF_MS = [0, 1_500, 4_000, 8_000]` と定義されており、最悪実行時間は `30s×4 + 13.5s = 133.5秒` となります。
2. **正しい**
   - **根拠**: サーバー側で1回目が30秒でタイムアウトし、バックオフ1.5秒を経過した時点で31.5秒。クライアントは45秒で打ち切るため、2回目の通信には実質13.5秒しか残されていません。
3. **正しい**
   - **根拠**: `cover-image.provider.ts` は `CLIENT_TIMEOUT_MS = 75_000`。サーバー側 `cover-image.ts` は `REQUEST_TIMEOUT_MS = 55_000`、`MAX_ATTEMPTS = 1`。常にクライアント側の待機時間が長く、逆転は起きていません。
4. **正しい**
   - **根拠**: `consultViaServer` では `setTimeout` を宣言した**後**の `fetch` のbody内で `await toWireMessages(...)` を実行していますが、`consultViaByok` は `setTimeout` の**前**に実行しています。
5. **正しい**
   - **根拠**: `toWireMessages` 内で、履歴メッセージ(`messages`)に紐づくローカルURI(`imageUris`)から毎回 `preprocessImageForOcr` と Base64 読み込みを行っており、一度処理した画像を再利用するキャッシュ機構がありません。
6. **正しい**
   - **根拠**: `expo-image-preprocess.adapter.ts` の `getInfo` が `renderAsync` と `saveAsync` を実行しています。さらに `resize` の中で `this.getInfo` を呼び出し、その後自身でも `renderAsync` と `saveAsync` を行っているため、1枚のリサイズにつき「重いデコードとエンコード」が合計3回走る実装になっています。

### B. 見落とされている別の原因（「1往復目は成功し2往復目で失敗する」理由）

原因は**「画像再処理コストの累積による、45秒予算の圧迫」**です（事実と推測を含みます）。

`consultViaServer` はタイマー開始後に `toWireMessages` を呼び出します。この関数は、過去のターンに添付された画像（最大4枚）を**毎ターンすべてリサイズ・Base64化し直します**。

- **1往復目**: 画像1枚の処理（デコード/エンコード3回）のみで済むため、通信に十分な秒数が残ります。
- **2往復目**: ユーザーが新たに画像を添付しなくても、1往復目の画像が履歴(`messages`)に含まれているため、再び重いリサイズ処理が走ります。
  もし画像前処理に合計5〜10秒以上かかった場合、ネットワーク通信の実質的な持ち時間は30秒台前半に減少し、1度目のAPI通信が少し遅延しただけで容易に45秒のクライアントタイムアウトに到達します。

### C. 表紙画像生成のコードへの懸念

**あなたの「無関係」という判断は正しいです**。
`generateViaServer` に渡される `CoverImageInput` にはテキスト（タイトル、材料、タグ）しか含まれていません。端末側で重い画像前処理やBase64化は発生しないため、相談機能と同じタイムアウト問題は潜んでいません。

---

### D. 修正案（サーバー予算41.5秒）の問題点

1. **根本原因（前処理による予算消費）が直っていない**: 前述の通り、`consultViaServer` ではタイマー開始後に画像処理が走ります。画像前処理に3.5秒以上かかった場合、通信に使える時間は41.5秒を下回り、結局「端末(45s-3.5s=41.5s) < サーバー(41.5s)」の逆転が発生します。
2. **AI生成自体の成功率低下**: レシピの構造化出力は時間がかかることがあり、サーバーのタイムアウトを20秒に切り詰めると「25秒待てば成功したはずの正常な通信」まで自ら捨ててしまい、機能全体の成功率が低下するリスクがあります。

---

### E. その他、ソースを読んで気づいた重大な問題

1. **`getInfo` の実装が異常に重い**
   画像の寸法を取得する目的だけで画像をレンダリング・保存（`saveAsync`）すべきではありません。React Nativeの `Image.getSize` など、ファイルをデコードせずにヘッダから寸法だけを取得する軽量な手段に変更すべきです。
2. **リサイズ結果がキャッシュされていない**
   「StateにBase64を置かない（重くなるため）」という方針は正しいですが、代わりに**「リサイズ・圧縮完了後の軽量な画像のローカルURI」**をState（またはメッセージ履歴）に保持すべきです。毎ターン原寸大画像から処理をやり直すのはバッテリーと時間の大きな無駄です。
3. **タイマーの開始位置の修正**
   `consultViaServer` の `setTimeout` は、前処理が終わった後、つまり `fetch` の直前に開始するように移動すべきです。これにより純粋なネットワーク通信に対して45秒を保証できます。
