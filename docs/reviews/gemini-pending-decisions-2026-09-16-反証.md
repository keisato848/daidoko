## 採用 3 / 見送り 3 / 未確認 2

### 1. 【当たり・重大】「エミュレータ固有だから実機では通る」は成り立たない

**指摘**: 実測 13.7KB/s は約 110kbps。日本の携帯キャリアの速度制限（128kbps = 16KB/s）とほぼ同じ帯域であり、
「エミュレータ固有の環境問題」として片付けると、同等の速度で通信する実ユーザーを切り捨てることになる。

**調査**: 単位換算は正しい（13.7KB/s × 8 = 109.6kbps）。Play は 177 か国に配信済みで、速度制限・混雑した公衆
Wi-Fi・海外ローミングの利用者は確実に存在する。**9/15 の AQUOS 実機検証は自宅 Wi-Fi 環境であり、低速回線は一度も
試していない**。したがって「実機なら通る」は「速い回線なら通る」を言い換えただけで、#331 の症状が出た利用者の
回線速度は分かっていない。

**判断**: 当たり。android-verifier の結論（環境固有・PR の欠陥ではない）は、**帯域という変数を固定せずに
「エミュレータ」と「実機」を比べた**ことによる誤りだった。私がその結論をそのまま docs §4-0c に書いた点も同じ誤り。

**対応**: §4-0c の記述を「エミュレータでは E2E できない」から「**低速回線では実機でも同じ症状が出る**」へ書き換える。
帯域を 128kbps に絞った実機テストを、マージ判断の前提条件に追加する。

### 2. 【当たり・重大】#337 は往復ごとに全画像を再送しており、低速回線では 45 秒に収まらない

**指摘**: キャッシュしているのは前処理済み URI だけで、`FileSystem.readAsStringAsync` による base64 化と送信は
往復ごとに毎回行われる。低速回線では通信だけで 45 秒を超えるため、#337 は対症療法にとどまる。

**調査**: `apps/mobile/src/services/recipe-consult.provider.ts` の `toWireMessages()` を読んだ。
キャッシュヒット時も `readAsStringAsync` を呼んで `images.push({ imageBase64 })` しており、**指摘のとおり毎回フルで載る**。
実測値もこれを裏づける — 文字だけ追記した 2 往復目のエッジログが `rx=290,216`（1 往復目 `rx=288,242` とほぼ同じ）。
**写真を足していないのに同量が再送されている。**

数字を詰めると:

| 項目                                   | 値                  | 出典                                                  |
| -------------------------------------- | ------------------- | ----------------------------------------------------- |
| クライアントのタイムアウト             | 45 秒               | `recipe-consult.provider.ts:27` `TIMEOUT_MS = 45_000` |
| 写真の上限                             | 4 枚                | 同 `:49` `MAX_CONSULT_IMAGES = 4`                     |
| 縮小後の 1 枚                          | 約 350KB（1280px）  | 9/16 実測 357KB / 390KB                               |
| 2 枚の base64 ペイロード               | 約 1.0MB            | 実測「ボディ全体は約 1.0MB」                          |
| サーバー処理                           | 3〜4 秒             | 9/12 以降の本番 20 件すべて 0.66〜4.4 秒              |
| **2 枚を 45 秒に収めるのに必要な上り** | **約 200kbps 以上** | 1.0MB ÷ 41 秒                                         |
| **4 枚なら**                           | **約 400kbps 以上** | 2.0MB ÷ 41 秒                                         |

速度制限中（128kbps）の利用者は 2 枚でも 64 秒かかり、**確実にタイムアウトする**。

**判断**: 当たり。#337 は「前処理をタイマーの外へ出す」ことで**速い回線での**症状を消したが、
遅い回線では同じ症状が残る。#338 のサーバー側予算 133.5 秒も、クライアントが 45 秒で切る限り到達しない。

**対応**: #331 に「往復ごとの再送量と必要帯域」を数字で追記した上で、恒久対応（初回だけアップロードして
画像 ID で参照する）を別 Issue として起票する。#337 自体は前進なので破棄はしない。

### 3. 【当たり・中】クライアント 45 秒とサーバー 133.5 秒の逆転が #337/#338 では解消していない

**指摘**: クライアントが 45 秒で abort する限り、サーバー側の再試行予算 133.5 秒は意味を持たない。

**調査**: #331 のタイトル自体が「端末 45 秒 < サーバー再試行予算 133.5 秒の逆転」であり、この逆転こそが起票理由。
#337 は前処理をタイマー外に出しただけ、#338 は計測ログを足しただけで、**どちらも 45 秒という値を変えていない**
（`TIMEOUT_MS = 45_000` は差分で変更されていない）。

**判断**: 当たり。3 本をマージしても #331 の表題どおりの逆転は残る。

**対応**: #331 をクローズ可能とみなさない。タイムアウト値の決定（延長するのか、送信量を減らすのか）を
#331 の残作業として明記する。

### 4. 【外れ】「不完全な JSON で 500 になるのは放置された脆弱性（DoS）」

**指摘**: クライアント切断で中途半端な JSON が届くとサーバーが 500 を返す。悪意ある不完全リクエストで
リソースを破壊できる。

**調査**: 500 はレスポンスであってプロセスのクラッシュではない（Hono のボディパース失敗時の通常動作）。
41 秒かかったのは低速アップロードの待ち時間であり、パーサの問題ではない。

**判断**: 外れ（wontfix）。ただし**関連する本物の問題が別にある** — #333 の調査で判明済みのとおり
「端末の abort はサーバーに伝播しない（`req.signal` を見ている箇所が 0 件）」ため、**利用者が諦めた後も
Gemini 呼び出しは最後まで走り、課金だけ発生する**。低速回線で abort が増えるなら、この浪費も増える。
こちらは指摘 2 と併せて対応する価値がある。

### 5. 【外れ】「base64 を配列に展開するので低スペック端末が OOM で落ちる」

**調査**: 上限 4 枚 × 縮小後 350KB → base64 で 1 枚約 470KB、合計約 1.9MB。
RN の JS スレッドが落ちる規模ではない（原寸 6MB を載せているなら別だが、載せているのは縮小後）。

**判断**: 外れ。ただし「往復ごとに 1.9MB の文字列を作り直している」という無駄は指摘 2 と同根。

### 6. 【外れ】「`daidoko-modal-wt` の 302 ファイルが android-verifier を誤動作させる」

**調査**: `daidoko-modal-wt` は独立した worktree ディレクトリで、android-verifier が使ったのはメインの
作業ディレクトリ。PR #330 が記録した罠は「未 push コミットが PR のマージを止める」であって、別 worktree の
ステージ状態とは別物。

**判断**: 外れ（両者を混同している）。ただし孤立ステージの整理自体は必要で、Issue #341 で追跡中。

### 7. 【未確認】`.claude/settings.json` の相対パス（`../claude-harness`）が使えるか

**指摘**: 絶対パス `C:/Projects/claude-harness` は他 OS を壊すので相対パスにすべき。

**調査**: 「CI が確実に壊れる」は**外れ** — CI の Q-7（`test-customizations.mjs`）は settings.json をパースするが、
`extraKnownMarketplaces` のパス実在は検査しない（grep 一致 0 件）。リポジトリ内のフック配線は
`scripts/agent/hook-*.mjs` のリポジトリ相対なので、プラグインが読めなくても既存のフックは動く。
壊れるのではなく**プラグインが読み込まれないだけ**に劣化する。

一方で「他マシンで無効になる」こと自体は事実。`extraKnownMarketplaces` が相対パスを受けるかは
**Claude Code 側の仕様であり、材料からは判定できない**。

**判断**: 未確認。案 a（絶対パスで揃える）は利用者が決定済みだが、相対パスが通るなら明らかに上位互換。

**対応**: 相対パスで動くかを 1 度試す。通れば案 a を相対パスに差し替える（利用者決定の趣旨「全マシンで揃える」を
壊さずに移植性が上がるため）。通らなければ案 a のまま。

### 8. 【未確認・B の論点】「相談だけを唯一の入口にするのは過大解釈」

**指摘**: ヒアリング F10「だいどこの中から Web のレシピを探したい」があるのに、設計は「無から作る唯一の道＝相談」
としている。

**調査**: F10 の見出しはヒアリング記録に実在する（`hearing-user-2026-09-14.md:159`）。
ただし PR #330 の設計は「蔵書庫への**2 本目の**入口」と書いており、「唯一」とは書いていない。
Gemini が §2 の「詰まりの構造」の記述を強く読んだ可能性がある。

**判断**: 未確認（文言の解釈差）。設計の意図と記述が食い違って読めるなら、記述を直す価値はある。

**なお F12（家族に伝えたい）の「過小解釈」指摘は外れ** — 設計 §7-6 は先送りの理由を明記している
（内容を push に載せるとプライバシーポリシーの変更になる／「誰かが何かを取り消しました」としか言えない通知は
不安を与える）。検討の上での判断であり、見落としではない。
