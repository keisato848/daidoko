## 分かったこと `F`

### 直したい振る舞いについて

- **F1**: あるべき挙動は「**写真を減らして速く返す**」。
- **F2**: その中身は「**2 往復目以降は同じ写真を送り直さない**」。
- **F3**: 判断は「**アプリが常にそうする**」。回線速度で分岐させない。
- **F4**: 適用範囲は「**相談だけ**」。
- **F8**: サーバーが写真を会話の間持つ案には「**保持は避けたい**」。
- **F13**: 「**クライアントからまとめて送るようにすればいいのでは？**」→ 確認したところ
  「1 メッセージで 4 枚まとめて添付」と「読み取り結果で代用」の**両方やる**。

### 実際の使い方（仮定ではなく実績）

- **F5**: 相談で「**3〜4 枚使う**」。
  実装で裏取り: `MAX_CONSULT_IMAGES_PER_MESSAGE` により**1 メッセージ 2 枚が上限**で、添付ボタンが
  無効化される（`apps/mobile/app/(tabs)/recipes/consult.tsx:427`）。**3〜4 枚使う人は必ず 2 回以上に
  分けさせられており、2 往復目には「新しい写真」が乗る。** 再送だけの問題ではなかった。
- **F6**: 9/13 にタイムアウトした後は「**その場で相談をやめた**」。＝ 再試行せず離脱している。
- **F7**: 9/13 の回線は「**覚えていない**」。→ **未解決のまま置く**（推測で埋めない）。

### 範囲について

- **F9**: 初回送信（3〜4 枚で 1.4〜2.0MB）は「**対象外でよい**」。1 往復目は実際に通っていたため。
- **F10**: #335（原寸デコード 3 回・画像 5 経路が遅い）は「**両方。ただし OCR 品質は絶対に変えない**」
  （速度とメモリの両方が目的、ただし読み取り精度が落ちるならやらない）。
- **F11**: #334 同梱の非タイムアウト項目のうち認めるのは「**BYOK とサーバー経路の非対称を揃える**」
  「**pantry の 200 件切りをサーバー経路にも入れる**」の 2 件。共通入口 `image-payload.ts` への寄せは
  選択肢に出したが**選ばれなかった**。
- **F12**: 私が勝手に作った Issue #342 は「**閉じて #331 に統合する**」。

### 目的そのものについて（最重要）

- **F14**: 「**相談機能をエージェントとして○○を買い物リストに追加のように使えるようにするって要望は
  どこに行った？**」→ **私が落としていた。** 実物は PR #330 の `docs/相談してレシピを作る設計.md` §7 に
  「2026-09-14 確定・実装前」として存在し、**その PR を私が止めていた**。
- **F15**: 「**タイムアウトだけが修正必要な要件じゃないからね**」。

## 詰まりの構造

設計書 §7-9 に依存が明記されている。

| 段階     | 中身                                                               | 前提 |
| -------- | ------------------------------------------------------------------ | ---- |
| **前提** | **#331（相談のタイムアウト）の解消**                               | —    |

「使ってみて価値を感じる」段階に到達しない。

## 要求されなかったこと

**ここに書いてあるものを次のセッションが設計し直さないこと。**

- **初回送信の軽量化**… F9 で「対象外でよい」

- **共通入口 `image-payload.ts` への寄せ**… 選択肢に出したが選ばれなかった
- **サーバー側での写真保持**… F8 で明示的に「避けたい」
- **「128kbps で通ること」を合格条件にすること**… **一度も要求されていない。私が勝手に置いた指標**
  （docs §4-0c と Issue #342 に書いてしまった。撤回対象）
