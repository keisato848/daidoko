## 分かったこと

### 報告トラック

**F1. 報告の受け皿は既にあるが、AI 生成コンテンツ限定**
`apps/mobile/app/(tabs)/recipes/report.tsx` → `apps/server/src/routes/report.ts`。
カテゴリは `inappropriate` / `inaccurate` / `other` の 3 種、本文 500 字まで、入口は 3 画面（cover-image プレビュー・相談・写真レシピ）。
Play の AI 生成コンテンツポリシー（"without needing to exit the app"）を満たすために作られたもので、**不具合報告・機能要望は想定されていない**。

**F2. 報告の保存先は「ログ＋運営者へのメール」だけ。DB もチケットも無い**
`apps/server/src/routes/report.ts` は `process.stdout.write` と `sendOperatorAlert()` を呼ぶだけ。専用テーブルは設計上あえて持っていない（`docs/レシピ表紙AI生成設計.md` §6「無ければログのみで可 — 過剰に作らない」）。
通知は Google Apps Script webhook か Resend 経由のメール（`apps/server/src/lib/usage-alert.ts`）。
→ **「届く」までは出来ているが、「残って追える」形になっていない**。

**F3. Claude のワークフローは 1 本も無い**
`.github/workflows/` にあるのは `ci.yml` と `vision-poc.yml` のみ。Issue から自動修正を回す経路はゼロから作ることになる。

**F4. リポジトリは PUBLIC**
`keisato848/daidoko` は public。利用者の自由記述をそのまま Issue 化すると、検索に載る公開ページに本人が想定しない文章が出る。

**F5. プライバシーポリシーは報告の送信先を限定列挙している**
`docs/privacy-policy.md:107-141` —「報告の内容は、サーバーの運用ログと運営者への通知メールに残ります」。
GitHub（第三者サービス）へ送るなら**記載の追記が要る**。ただし private リポジトリであれば「非公開の課題管理システムに記録されます」の 1 行で足り、**ポリシーは障害にならない**。公開 Issue（F4）だけが重い。

**F6. 開発者自身の気づきが、今どこにも残っていない**

> 「メモや頭の中にあるだけ」

選択肢にあった「その場で Claude に言って直している」「GitHub Issue にしている」ではなく、**残っていない**を選んだ。これが本ヒアリングで唯一、**既に起きている詰まり**。

**F7. 利用者からの報告はまだ 1 件も届いていない**

> 「まだ無い（先回りで作る）」

利用者向けの入口は、**既存の困りごとを解く要求ではなく、受け皿を先に置く要求**。

### テーマトラック

**F8. 動機の根拠は一般論であり、実利用者の証言ではない**

> 「一般論として知っている」

「ダークテーマは見づらいという人も多いようです」の出どころは、ストアレビューでも知人の発言でもない。**この点は要求の優先度に直接効くので、埋めずに残す**。

**F9. ただし「暗い画面が読めない」は現行実装で裏が取れる**（ヒアリングでは出ていない発見）
`Colors.muted` (`#5A4A34`) は現行の背景 `#0A0805` に対して **コントラスト比 2.35:1**。本文に必要な 4.5:1 どころか、大きい文字の 3:1 も下回る。
それが `apps/mobile/src/constants/theme.ts:15` に定義され、**文字色として 191 箇所**で使われている（`grep -rn "Colors.muted" apps/mobile/app apps/mobile/src --include=*.tsx | wc -l`）。
同種の問題への対処跡も残っている — `apps/mobile/app/fridge.tsx:483`「opacity 0.5 は背景 #0A0805 に沈んで視認不能だった」。
→ **F8 が推測でも、可読性の問題そのものは実在する**。ただし解が「白テーマ」であるとは限らない（F9 は現行ダークテーマの色設計の問題であり、ダークのまま直せる）。

**F10.「反転すればいい」は成り立たない**

- `apps/mobile/src/constants/theme.ts` の `Colors` は静的な `as const`。**75 ファイル**が import。
- **72 ファイル**が `StyleSheet.create` をモジュール直下で呼ぶ（＝実行時に色が切り替わらない構造）。
- `Colors` を通さない**ハードコードの hex が 125 箇所**（`#130E08` 22 件、`#1A1108` 18 件、`#FF6B6B` 13 件 ほか）。
- ウィジェットは色を別定義で持つ（`apps/mobile/src/widgets/MenuWidget.tsx:23-25`、`ShoppingListWidget.tsx:20-22`）。

**F11. ブランドのゴールドは白背景で読めない**
`#C9A16A` on `#FFFFFF` = **2.39:1**（`#0A0805` 上なら 8.37:1）。CLAUDE.md §4 はこの色を憲法として定めている。
白テーマ専用の暗い金の候補: `#8A6A3A` on `#FFFFFF` = **5.00:1**（AA 合格）。`#7A5C2E` なら 6.18:1。

**F12. 初回起動画面（オンボーディング）は存在しない**
初回はコーチマークのみ（`apps/mobile/app/(tabs)/index.tsx:97`、`add.tsx:118`、`pantry.tsx:166`、`recipes/index.tsx:92`、`shopping.tsx:118`、`settings.tsx:134`）。
「初回起動時に変更できれば」は**新規画面の追加**を意味する。

**F13. 目的は「選べること」ではなく「読みやすさ」**

> 「読みやすさ（暗い画面が読めない人がいる）」

選択肢の「選べること自体が価値」「インストール直後の印象」ではなく、可読性を選んだ。
→ **合格基準はコントラスト比で書ける**。テーマの数を増やす方向（複数配色の提供）は目的外。

## 詰まりの構造

```
[開発者]  実機で気づく ──→ メモ・頭の中 ──→ ✕ 消える          (F6)
                              ↑
                        ここで輪が切れている

[利用者]  不具合に遭う ──→ ✕ 送る先が無い（AI 生成物の報告しか無い） (F1)
                                    ↓ もし送れても
                            ログとメール ──→ ✕ 追えない        (F2)
```

報告トラックの本質は「**気づきが構造化されたチケットになって残らない**」の 1 点。
開発者側（F6）は既に起きている。利用者側（F7）はまだ起きていない。
「Claude が自動修正する」は、この輪が閉じた**後**の話であり、閉じる前に作っても流れるものが無い。

```
[テーマ]  現行ダークの muted が 2.35:1 ──→ 読めない  (F9・実在)
          「白にすれば読める」            ──→ 未検証   (F8・推測)
```

テーマトラックは、**実在する問題（F9）と、推測の解（F8 → 白テーマ）が別物**である点に注意が要る。

## 要求されなかったこと

**次のセッションがここを設計し直さないこと。** いずれも選択肢に出したうえで選ばれなかった、または明示的に否定された。

- **エラー発生時にその場で報告ボタンを出すこと** — 選択肢にあったが「設定画面に別項目を新設」を選択。クラッシュ情報の自動添付も含めて範囲外。
- **既存の AI 生成コンテンツ報告フォームへの統合** — 「2 本立て」を明示的に選択。カテゴリを足して 1 本にする案は**却下されている**。
- **公開リポジトリでの Issue 化** — private を選択。
- **マージまでの自動化** — 「マージは手動」と明示。テストが通れば自動マージ、は否定された。
- **テーマを「選べること」自体の価値として作ること** — 「読みやすさ」を選択。配色バリエーションを増やす方向の拡張は目的外。
- **テーマの段階的導入（主要画面から）** — 「全画面を今回やる」を選択。
- **配色案の見本を先に出すこと** — 「白テーマ専用の暗い金を作る」を直接選択しており、見本待ちにはしていない。
- **今回のリリース（献立トラック R1〜R34）に載せること** — 「献立トラックを出してから別リリース」。

## 追記 2（2026-09-19・5 往復目）— F8 の訂正と、根拠の格上げ

**F8 は誤りだったので訂正する。** 「一般論として知っている」という選択肢を選んでもらったが、その後の本人の説明で**出どころが実務での証言**だと分かった。

### F15. 動機は一般論ではなく、実務で複数人から言われたこと（F8 を置き換える）

> 「一般論は私が最近仕事をしていて実務で言われたことです。最近、若者はダークテーマが好きで目に優しいと思っているんですが、ある程度年を重ねた人は**ダークテーマ**にあまり慣れてなくて、ダークテーマそのものが見づらいという印象を感じたりするようでした。確かに大抵のアプリではダークテーマがなくてホワイトベースが多い時もあるなと」

※「抱く手間」は音声入力の変換ミスと判断し「**ダークテーマ**」と読み替えた（本人に明示して確認済み）。

分かれる点は 3 つ:

1. **年齢層で割れる。** 若年層はダークを好み「目に優しい」と考える。年齢が上がるとダークに**慣れておらず**、見づらいと感じる。
2. **問題は文字のコントラストではなく、黒背景そのもの**（下の訂正を参照）。

## 追記 3（2026-09-19・6〜9 往復目）— 読みづらさの正体が入れ替わった

モック（https://claude.ai/artifact/LzVp2ajucGNCreZSH7FRHw ）を見ながら 4 往復した結果、
**本ヒアリングで最も重要な訂正**が出た。

### F17. 読みづらいのはコントラストではなく、小さい文字だった

> 「私が読みづらいと思ってるのは、今が一覧で言うと白のメインテキストではなくて、**テーマカラーのちょっとちっちゃい文字**の方です」

続けて:

> 「細かいが、**個数の白字も小さい**な」

**実測**: 金 `#C9A16A` は **8.37:1**、`goldDim` `#A07A44` は **5.11:1**。
**どちらも WCAG AA（4.5:1）を通る。**

10〜13px の小さい文字に金を使っている箇所は **90 件**。代表例:

| 箇所 | 実装 |
| --- | --- |
| AI バッジ | `PhotoPickerField.tsx:281` `fontSize: 10, Colors.gold` |
| ホームの統計ラベル | `(tabs)/index.tsx:598` `fontSize: 10, Colors.goldDim` |
| 献立カードのラベル | `(tabs)/index.tsx:583` `fontSize: 12, Colors.gold` |
| 棚ラベル | `(tabs)/recipes/index.tsx:765` `fontSize: 11, Colors.goldDim, letterSpacing: 1` |
| 店バッジ | `(tabs)/shopping.tsx:415` `fontSize: 11, Colors.goldDim` |
| 在庫メモ | `fridge.tsx:486` `fontSize: 11, Colors.goldDim` |
| 設定セクションヘッダー | `settings.tsx:517-519` `fontSize: 12, Colors.goldDim`（大文字化＋字間） |

白系（`paperDim`）の小さい文字も同様:

| 箇所 | 実装 |
| --- | --- |
| 買い物リストの個数 | `(tabs)/shopping.tsx:414` `itemAmount: fontSize 12, Colors.paperDim` |
| 消費シートの数量 | `consume-meal.tsx:311` `itemQty: fontSize 13, Colors.paperDim` |

### 訂正: 「AA を満たせば読める」という前提は成り立たない

**追記 1・2 までの設計は、「読みづらい ＝ コントラストが低い」という私（AI）の推測の上に立っていた。**
F13 で「目的は可読性」と確認したところまでは正しいが、そこから**指標をコントラスト比だと決め打ちした**のが誤り。
これは `harness:refine-requirements` §2-1 が警告している罠そのもの（「推測した指標で判断を進める」）を、
同じセッション内で踏んだもの。

結果として何が起きたか:

- **R12（合格基準 = WCAG AA）と R13（パレット是正）を完遂しても、上の 90 箇所は 1 つも変わらない。**
  金は基準を通ってしまうため、対象に入らない。
- つまり**票の受入基準 B-5・B-6 を全部 Pass にしても、本人の体感は変わらない**可能性が高い。

**なぜ AA で検出できないか**: WCAG のコントラスト比は 2 色の相対輝度の比でしかなく、
**文字の大きさ・線の細さ・彩度を見ていない**。10px の細い金文字は、8.37:1 でも 15px の白文字より読みにくい。
字間を広げた大文字ラベル（設定のセクションヘッダー）はさらに読みにくくなる。

**R12・R13 は取り消さない。** `muted` 2.35:1 と星 1.32:1 は客観的に壊れており、直す価値がある。
ただし**体感を変えるのは R14 のほうだ**という優先順位を、次に読む人が取り違えないように残す。

### 決まったこと

> 「**金のままサイズを上げる**で、もうちょっとだけ小さく」
> 「**採用案でOK**です！」

**採用案 = 金の色も量も変えず、小さい段階だけ 1 つ上げる。**

| 現行 | 採用案 |
| ---: | ---: |
| 10px | 12px |
| 11px | 13px |
| 12px | 14px |
| 13px | 15px |

- **レシピ名・本文・統計の数値（15px 以上）は触らない。**
- 対象は金の小さい文字（90 箇所）＋ 分量・個数（白系）。
- 選ばれなかった案: 「小さい文字を白系にして金を装飾に降格する」（密度は失わないが、金の量が減りブランドの印象が変わる）。
- 一覧の件数は変わらない（カード高さがわずかに伸びるだけ）。

**実装方針**: 対象が金だけでなくなったため、「金に使うときだけ 1 段階上げる規則」ではなく
**`Typography.size` の段階そのものを上げる**方向。lint で規則を守る仕組みが要らない。

### 却下された案（記録として残す）

- **全画面を料理中モードのサイズにする** — 蔵書一覧が 6 件 → 4 件になり、一覧が一覧でなくなる。
  料理中モードが大きいのは「1 度に 1 手順しか出さない＝失うものが無い」ためで、
  件数が価値の画面には同じ理屈が通らない。
- **小さい文字を白系にする**（金を装飾へ降格）— 上記のとおり不採用。

### 新しく分かったこと（別軸）

- **`allowFontScaling` を落としている箇所が 0 件** → RN 既定で **OS の文字サイズ設定に既に追従している**。
  ただし固定高さで見切れないかは**未検証**。実機で「文字サイズ最大」にして 1 周すれば分かる。
- **料理中モードの手順テキストは既に 20px**（`cook.tsx:486`「料理中は大きく読みやすく」）。
  取り残されているのは同じ画面の**材料オーバーレイ 15px・タイマー 13px・ヒント 12px**。
- 利用者の言葉:
  > 「料理中にちょっと離れた位置から見るのは厳しいのかも」

  **この使用状況はヒアリング開始時には出ていなかった。** 実機で困ったのかモックを見て気づいたのかは**未確認**。
