推測をやめてユーザー本人に聞く、という指示（「ヒアリングして」）に応じたもの。5 往復・理想ではなく実際の行動を聞く形で実施。

## 1. 分かったこと（重要な順）

### F1. 蔵書が空だと、レシピサイトに負ける（最重要）

> **最初は空なので、レシピサイトをみたほうが早いと感じる**

**実装で裏が取れた事実**: 本番のだいどこは**レシピ 0 件から始まる**。
サンプルデータ（`db/seed.ts` の 7 レシピ）は `isSampleDataEnabled()`（`db/sampleData.ts:11-19`）が
`EXPO_PUBLIC_ENABLE_SAMPLE_DATA=1` かテスト実行時にしか true を返さないため、**本番ビルドには 1 件も入らない**。

### F2. だいどこの機能は、ほぼ全部が「蔵書があること」の下流にある

ヒアリング中に同じ形の答えが 3 回出た。

| 機能                      | 本人の言葉                                                   |
| ------------------------- | ------------------------------------------------------------ |
| 献立                      | 「使っているが、**レシピがない状態から使いづらい**」         |
| レシピ詳細 → 買い物リスト | 「**そもそもレシピがないと使い道がない**」                   |
| 在庫で作れるレシピ        | 「使っていて、**役に立っている**」（＝蔵書があれば機能する） |

**在庫で作れるレシピだけが「役に立っている」と答えられた。** 蔵書が満ちていれば輪は回る。回らないのは入口。

### F3. 無からレシピを作れる唯一の道が、ほぼ必ず壊れる

- レシピを無から作る経路は「相談しながらつくる」だけ（写真からレシピは**目の前に料理がある**ときの機能）
- 本人は「**たまに使っている**」が、タイムアウトの頻度は「**往復を重ねるとほぼ必ず**」
- 原因は **Issue #331**（端末 45 秒 < サーバー再試行予算 133.5 秒の逆転）。2026-09-13 に実機のスクリーンショットで再現済み

**「たまたま見つけた不具合」ではなく、詰まりの中心にある。**

### F4. 外の AI に聞いているのは「ある材料で作れるもの」

- 「今日何を作るか」を決めるとき、実際にしているのは「**他の AI や Web で探す**」と「いつもの定番から選ぶ」
- 外の AI に聞く内容は「**ある材料で作れるもの**」
- **だいどこは在庫を持っているのに、その質問を外でしている。** そして答えは何も残らない

オーナーが最初に挙げた不満（2026-09-14）と、ここで一致する:

> Gemini や Claude に「レシピを教えて」と聞くだけだと、それは何も残らない。買い物リストも作ってくれない。

### F5. 献立を決めることと買い物は、ひと続きの行為

- 開く場面は「今日何を作るか考えるとき」と「買い物の前・買い物中」
- 買い物中にしているのは「**作るものを決めながら買う**」
- 一番面倒なのは「**献立を決めてから材料を見るのが手間**」

決める → 買うものに変換する、の変換点で詰まっている。

### F6. 会話で最初に頼みたいのは「今日何を作るか決める」

選択肢は 4 つ（買い物リストをいじる / 在庫を記録する / 今日何を作るか決める / 料理そのものを相談する）で、
選ばれたのは「**今日何を作るか決める**」。

**司令塔はここまで「買い物リストに砂糖を足す」を主題に設計していた。** それは入口の例であって目的ではなかった。

### F7. 家族とは実際に共有している。「家族に伝わること」が足りない（本人も曖昧と留保）

- 「家族と共有している」と回答（机上の想定ではない）
- 仮説（材料から思いつく → レシピが残る → 買い物リストになる）に足りないものとして「**家族に伝わること**」を挙げたが、
  本人が「**ちょっと曖昧**」と留保している。**掘り切れていない**

## 2. 詰まりの構造

```
  蔵書が空（本番は 0 件から始まる — F1）
        │
        ├─▶ 献立が使えない（F2）
        ├─▶ 材料→買い物リストが使えない（F2）
        └─▶ 在庫で作れるレシピに候補が出ない（F2 の裏）
        │
        ▼
  レシピサイトの方が速いと感じる（F1）→ だいどこに戻ってこない
        │
        ▼
  無から作る唯一の道＝相談 → 往復を重ねるとほぼ必ずタイムアウト（F3・#331）
        │
        ▼
  外の AI で「ある材料で作れるもの」を聞く（F4）→ **何も残らない**
```

**輪が閉じていない場所は 2 つだけ**: 蔵書の立ち上がり（F1）と、相談の信頼性（F3）。
その 2 つが詰まっているせいで、下流の機能（献立・材料→買い物）が全部「使い道がない」と評価されている。

## 3. 設計への影響

### 優先順位が変わる

`docs/相談してレシピを作る設計.md` §7 は「会話の結果がアプリに残る」ことを主題に書いたが、
**残す先（レシピ・買い物リスト・献立）より前に、残すもの自体が生まれていない。**

| 順  | やること                                         | 根拠                                                 |
| --- | ------------------------------------------------ | ---------------------------------------------------- |
| 1   | **#331 を直す**                                  | F3。唯一の生成経路が「往復を重ねるとほぼ必ず」壊れる |
| 2   | **空の蔵書からの立ち上がり**                     | F1。レシピサイトに負けている状態を先に解く           |
| 3   | **「ある材料で作れるもの」に答えて、結果が残る** | F4・F6。外の AI でやっていることを中に取り戻す       |
| 4   | 決めた献立 → 買うものへの変換                    | F5                                                   |
| 5   | 家族に伝わる                                     | F7（ただし本人が曖昧と留保。掘り直しが要る）         |

### §7 で書いた「操作の代行」の位置づけが下がる

買い物リストに足す・在庫を記録する、といった操作の代行は**間違いではない**が、
オーナーが最初に頼みたいのは「今日何を作るか決める」（F6）。
操作の代行は**その会話の副産物として起きる**もので、単体の主題ではない。

### 変わらないもの

- 代行の線引き「日常の家事か」（§7-2・§7-3）
- 確認カードに聞き取り原文と合算先を出す（§7-4）
- 品名は発話そのまま（§7-4）
- 「買った」「使い切った」は取り消しを作ってから（§7-5）

## 5. 追加ヒアリング（同日・後半 3 往復）

前半（F1〜F7）で詰まりの構造が見えたので、**設計に落とせるところまで**掘った。

### F8. 在庫は正確ではない。そして本人が「追いつかなくていい」と言った

- 実態は「**買ったものは入るが、減らない**」。つまり在庫は**実際より多めに出る**
- 理由は「だいどこに聞かずに、登録せずに作るものが追いつかない」
- 「何があれば追いつきますか」への答えは「**追いつかなくていい**」

**設計への含意（重い）**: 「今ある材料で作れるもの」を、**在庫の正確さに依存した機能として作ってはいけない**。
在庫は「あるかもしれないもの」として扱い、提案は在庫だけに閉じない。
`/cookable`（在庫で作れるレシピ）が「役に立っている」と評価されているのは、**蔵書 6〜20 件に対する緩い絞り込み**として効いているからで、
厳密な引き当てが効いているからではない（推測）。

### F9. 蔵書は 6〜20 件。定番は 20 品以上あるが「入れ切れない」

- 保存済みレシピ: **6〜20 件**
- いつもの定番: **20 品以上。入れ切れない**

**定番の数（20+）が蔵書の件数（6〜20）を上回っている。** 頭の中にあるものが、アプリに移せていない。

### F10. だいどこの中から Web のレシピを探したい

「検索できないのが痛い」の中身は、蔵書の検索機能（料理名・読み・タグ・材料名で引ける。実装済み）のことではなく:

> **だいどこの中から Web のレシピを探したい**

欲しいものは「実在するレシピを探して取り込む」と「AI が作った提案」の**両方**。
さらに本人から追加の案が出た（**「かもしれない」と留保付き**）:

> 他の人がだいどこ内で作ったレシピを検索できてもいいかもしれない。

**これは規模が違う話**（利用者どうしの共有・公開範囲・不適切投稿の扱い・サーバー費用）。
既存の Web 共有（`app/web-shares.tsx`・レシピ単品の公開）とは別物として、**単独で判断する**。本ヒアリングでは「案として出た」までを記録する。

### F11. 定番の入れ方は「作ったときに 1 品ずつ」＋「写真からまとめて」

選ばれたのは 2 つ:

- **作ったときに 1 品ずつ残る**（日々の調理のついでに溜まる）
- **写真からまとめて**（作った料理の写真を撮っておけばレシピになる）

選ばれなかったもの: 「名前を列挙すれば AI が中身を埋める」「Web からまとめて取り込む」。
**一括投入より、日々の流れの中で 1 品ずつ溜まる形が選ばれた。**

### F12. 家族に伝えたいのは 3 つ

前半で「ちょっと曖昧」と留保された F7 の中身。3 つが選ばれた:

- **今日何を作るかを共有したい**
- **買い物を頼みたい**
- **作ったものを家族に見せたい**

選ばれなかったもの: 「誰が変えたのか分かるようにしたい」。
**「勝手に変わるのが気持ち悪い」は、少なくとも本人の関心ではない**（`sync-payload` が `createdBy` を同期していない件は、当面このままでよい）。

### F13. 提案は候補 3 つ

「今ある材料で何が作れるか」への返し方は「**候補を 3 つくらい並べてほしい**」。
「1 つ提案して会話で調整」（＝いまの相談機能の形）ではなかった。**相談の往復型とは別の返し方が要る。**

### F14. 在庫は「たまに冷蔵庫写真で棚卸し」でよい（2026-09-14 追加）

> 在庫はたまに冷蔵庫写真でたなおろしできればよい。

F8（買ったものは入るが減らない・追いつかなくていい）の**解き方**が本人から出た。
増減を 1 件ずつ追うのではなく、**ときどき現状に合わせ直す**。

**設計への含意**: 冷蔵庫写真（`app/fridge.tsx`・実装済み）は現在「写真から在庫を登録する」機能だが、
**「棚卸し」＝いまの在庫を写真の内容で突き合わせる**という位置づけを与えられる。
差分（写真に無いのに在庫にある＝使い切った可能性）をどう扱うかは設計事項。
在庫の正確さを日々の操作で担保しない、という方針がこれで完結する。
