#### A1. 初回ガイド2枚目が、設定の歯車を指して「このカートから」と説明する（high）

**症状** — 初回起動でホームに出る2枚のうち2枚目が、⚙設定ボタンをくり抜いてハイライトしながら「買い物リスト・家の在庫・レシート読み取り・「この在庫で作れるレシピ」は**このカートから**」と言う。画面上にカートは存在しない。設定＞使い方ガイド再表示でも同じものが出る。日英とも同文（en は "all live behind this cart"）。

**直し方** — 文言の差し替えのみ。ref 名も同時に直さないと同じ事故が再発する。

#### A2. 設定「クラウド同期」が、出荷済み機能を「今後追加予定」と表示して無効化している（high）

## 2. 献立 M1 / ウィジェット W0 が入る前に決めておくべきこと

**手遅れになる順**に並べる。マージ後に直しても、既存ユーザーには何も伝わらない（B5 のため）。

1. **ホーム最上部の順位を先に決める。** `origin/main` の復帰カードと `origin/feat/menu-m1` の献立カードが `index.tsx` の**同一ハンク**に別々の「最上部」を主張しており、`git merge` は必ず競合する。設計側の並び定義（`docs/画面設計.md` 付録「献立導入後の全体導線」）には**復帰カードが1行も出てこない**（献立設計 8/28 確定 ＞ 復帰カード同日実装、設計が実装に追いついていない）。決めずにマージすると競合解決者の判断で入る。**B1 で復帰カードを削除してバーに一本化すれば、この判断自体が消える。これが最短。**

2. **献立カードは「常時」か「保存時のみ」か。** 設計は「最上部・**保存時のみ**」、実装は無条件描画（プランが無いときは `menu.card.empty` を出す）。常時にすると献立を一度も使わない人のホームも1段増える。発見性を採る（決定変更A「4番目のタブを開かないと気づけないのは #182 の再演」）なら意図的な逸脱として通るが、**設計文を直さないと次の人がどちらが正か分からない**。

3. **設計が用意した緩和策「撮る/相談/作れるを1行に圧縮」が R1 で未実装。** これを入れずに献立カードを足すと、ホーム最上部の全幅ブロックは「献立→復帰→撮る→相談→在庫で作れる」の4〜5枚縦積みになる。**圧縮を入れるか、献立カードを条件付きにするか、どちらかは必須。**

4. **`COACH_MARK_SCREENS` に `'menu'` を足す枠を M1 のマージ PR で確保する。** M1 は coach を1行も触っていない（設計の R1 行は「コーチマーク1枚」と書いている＝未実装）。献立は在庫・買い物リスト・作りたいリストを横断する新しい概念で、`menu.tsx` は `href: null` の隠し画面（発見手段がホームのカードだけ）。説明が `menu.card.empty` の1文だけになる。**かつ B5 のため、後から足しても既存ユーザーには出ない。**

5. **献立カードのアイコンが `CalendarDays` で、ヘッダの「暦」アイコン（`index.tsx:295`）と同一。** 同じ絵で別の行き先（`/menu` と `/calendar`）が同一画面に並ぶ。B1 の暦／写真の畳み込みと同時に決める。

6. **`getMenuPlan()` の重さをマージ条件にする。** M1 はホームの `loadTimeline()`（`useFocusEffect` と `useSyncRefresh` の両方から走る）に `getMenuPlan()` を足した。プランがあると `menu-plan.service.ts:189-210` が status='active' の**全レシピ**＋**全在庫**＋署名計算を読む。設計自身が「ホーム側の追加読み出しは app_meta 1 read＋署名計算のみ」を前提にコールドスタート <3.0 秒（品質基準 §3）への影響測定を求めている。**設計が求めている実測を M1 のマージ条件にする**か、ホーム用に保存済み JSON の title/doneAt だけで描く軽量版を分ける。

7. **マージ順は #241 → #242。** W0 は #241 の1つ前のコミット上に積まれている。W0 自体は UI 変更ゼロ（土台のみ・誰も読まないファイルを書くだけ）なので急がない。ただし設計の5フックのうち**調理記録保存・同期 pull 完了後・AppState background の3つが未配線**で、W1 が出た瞬間に「HH:mm 時点」が古いまま出る面が生まれる。Issue #238 に書き足しておく。

8. **タブは5本のまま。** 献立タブを作らない判断は設計側で既に固めてある（Material「three to five destinations」、Apple HIG「Avoid overflow tabs」、現ラベルが 9px で既に最小クラス）。この判断を蒸し返さない。

## 3. やらない方がよいこと

1. **ヘルプを増やして解決しようとしない。** 今回見つかった誤案内2件は「ヘルプが足りない」ではなく「実装が動いてヘルプが取り残された」。ホームのカート文言も設定の「今後追加予定」も、**同じ導線を2つ持ったこと・機能を移したのに文言を移さなかったこと**が原因。文言を増やすほど同じ事故が増える。**先に B1（重複導線を削る）→ 残ったものだけ説明する**の順にする。

2. **初回の全画面チュートリアル／ウォークスルーを作らない。** NN/g は「avoid creating app onboarding whenever possible」「we don't recommend deck-of-cards onboarding」（ユーザーテストでタスク成績が改善しなかった）としている。Crouton は初回チュートリアル無しで出し、**空状態の弱さが実害として観測されてから** onboarding を足した（2025.5）。だいどこは既に 7画面のコーチマーク＋? を持っており、足りないのは枚数ではない。

3. **What's New を毎回・起動直後に出さない。** Material Feature discovery は「**Don't present upon opening an app**」「1セッション1件まで」「閉じられたら長期間出すな」「その機能をまだ使っていない人にだけ」を明示している。クックパッドは起動時プロンプト（「またこのレシピを作りたいですか？」）を苦情で廃止した実例がある（一次ページ未確認・二次情報）。もし What's New を入れるなら **(a) 既存ユーザー限定＝新規インストールには出さない**（WhatsNewKit などの定番実装はこの判定を持っていないので自分で塞ぐ必要がある）、**(b) オフにできる**、**(c) N回で自然消滅**、を最初から入れる。

4. **アプリ内に階層のあるヘルプ「画面」を作らない。** Paprika・Mela・クックパッド・クラシルはいずれも詳しいマニュアルを Web（またはサポートサイト）に置き、アプリ内は最小限に留めている。ビルドに縛られた説明は腐る — **今回の2件がまさにそれ**。書くなら `docs/` かリポジトリ外の1ページに置き、アプリからは該当箇所へ飛ばす。

5. **可視の「前／次」ボタンを消してスワイプに寄せない。** `cook.tsx:295-311` の併存は正しい形で、AnyList・Mealime・Mela も同じ（調理中は手が汚れていて誤スワイプの代償が大きい）。逆に、スワイプを説明するために枚数を増やすのではなく、**ボタンを押したときにスワイプと同じ方向へアニメーションさせる**（WWDC21 "Discoverable design" の hint at gestures）方が安い。

6. **コーチマークを1画面4枚以上にしない。** `recipes/[id].tsx:165-167` のコメントが「4枚あったが、初回に連続で出てまとめてスキップされていた（R5 問題4）」と実害を記録している。NN/g も「連鎖するヒントは早く閉じられ、アプリを複雑で威圧的に見せる」としている。なお現状スキップは1枚目でも画面全体を既読にする（`useCoachMarks.ts` の `dismiss` → `markCoachMarksSeen(screen)`）ので、枚数を増やすほど「1枚目で閉じて全部消える」確率が上がる。

7. **感覚で機能を折りたたまない。** progressive disclosure の典型的失敗は「実データ上よく使われている機能を隠す」「情報設計の悪さを階層の深さで覆う」。B1 で削る候補（復帰カード・在庫ボタン・FAB）は**重複しているから削る**のであって、使われていないから隠すのではない。
