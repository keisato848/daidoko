## 1. iOS の現況確認（ASC の GET）は、この Mac では実行できない

**症状**: `scripts/release/` の ASC 系スクリプト（`update-appstore-listing.mjs` 等）が Mac で動かない。

**原因**: `scripts/release/lib/asc-api.mjs` の `readAscConfig()` は鍵のパスを
`apps/mobile/eas.json` の `submit.production.ios.ascApiKeyPath` から読む。値は
**`C:/secure/AuthKey_8C387NYC2T.p8`（Windows のパス）**で、**環境変数による上書き口が無い**。

- 対照的に Play 側の `scripts/release/lib/play-api.mjs:15` には `PLAY_SERVICE_ACCOUNT_KEY` の
  上書き口が**ある**。ASC 側だけ非対称に欠けている
- Mac 上に `.p8` は 1 つあるが（`~/Downloads/AuthKey_34FRT6NUR2.p8`）、
  **キー ID が `8C387NYC2T` と異なる別の鍵**。同一視できない
- `asc-api.mjs` の冒頭コメントに **「`.p8` は再ダウンロード不可」**と明記されている
- Play のサービスアカウント JSON も Mac 上に存在しない

**対処**: **Windows 側で GET して結果を共有してもらう。** アップロードが Windows 側の担当である以上、
現況確認も同じ側でやるのが自然で、鍵を機械間で複製しなくて済む。

知りたい値（ブリーフ §4-1）: アプリ名・サブタイトル・スクショの現在の枚数と構成・`promotionalText`・
**`appStoreVersions` の状態**（全部 `READY_FOR_SALE` なら、次バージョンを作るまで名前・説明・
スクショは変えられず、審査なしで変えられるのは `promotionalText` だけ。2026-09-17 時点はこの状態）。

> **鍵を Mac へ複製する道は取らない。** 再ダウンロード不可の秘密鍵を増やすのは、
> 得られるもの（GET 1 回）に対して割に合わない。

### 2-1. この機体固有の制約（8 GB・Intel）

- **ビルドとシミュレータを同時に走らせない。** 共倒れする（過去にシミュレータ起動が 2 時間終わらず、
  システムデーモンが連鎖クラッシュした実績あり）
- Release ビルドは `ONLY_ACTIVE_ARCH=YES` を渡す（既定の `NO` は 2 スライス作って時間が倍）
- **空きディスクが 17 GB しかない。** DerivedData 12 GB ＋ CoreSimulator デバイス 13 GB が回収可能。
  iOS ビルドの前に掃除が要る（**利用者の確認待ち**）
- 撮影前に `ios/` が古い prebuild でないか確認する。古いと後から入った依存がリンクされず即死し、
  **全ショットが同じ絵になる**（`expo prebuild -p ios --clean` で解決）

## 3. 撮影経路の判断 — 寸法をどちらに寄せるか（**要・利用者判断**）

**症状**: 既存 8 枚は 1080×2400 だが、`extras/11-shopping-list.png` だけ **1080×2432**。
`update-play-screenshots.mjs` は**寸法の混在を弾く**ので dry-run が止まる。

**原因**: **エミュレータは 1080×2400、AQUOS 実機は 1080×2432**。11 だけ実機で撮られた。
`phone-screenshots/README.md` に既に
「**混ぜられない。片方に寄せて 8 枚とも撮ること**」と結論が書かれている。

### 3-1. Android SDK は要らない（今回の最大の発見）

撮影・収録スクリプトが外部に呼ぶコマンドは **adb だけ**だった。

| スクリプト                      | 使う外部コマンド                                                         |
| ------------------------------- | ------------------------------------------------------------------------ |
| `capture-store-screenshots.mjs` | `adb exec-out screencap` / `am start`（ディープリンク）/ `adb root` のみ |
| `record-promo-video.mjs`        | `adb push` / `adb shell screenrecord` / `adb shell wm size` のみ         |
| `edit-promo-video.mjs`          | `ffmpeg`（`which ffmpeg` で解決。Mac では PATH 解決で通る）              |

`emulator` / `sdkmanager` / `avdmanager` / gradle は**一度も呼ばれない**。
adb は既に `/usr/local/bin/adb`（v37.0.1）にある。

**ただし 1 か所だけ詰まる**: `capture-store-screenshots.mjs` の `resolveAdb()` は
`ANDROID_HOME/platform-tools/adb` しか見ず、**PATH の adb を拾わない**（`:328-334`）。
→ `ANDROID_HOME` に `platform-tools/adb` を持つディレクトリを用意して渡せば、**コード改修なしで通る**。

### 3-2. 三つの道

| 案                                                           | 追加で要るもの                                | 利点                                                | 欠点                                                                            |
| ------------------------------------------------------------ | --------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------- |
| **(ア)** AQUOS に `adb shell wm size 1080x2400` を掛けて撮る | 無し（adb のみ）                              | 既存 8 枚と同寸法。撮り直しは必要な枠だけで済む     | 密度の調整が要る。レイアウトが実機と変わる可能性 → **1 枚撮って目視確認が要る** |
| **(イ)** Mac に Android SDK ＋ エミュレータ（1080×2400）     | SDK 数 GB のダウンロード（遅回線）＋ ディスク | 既存 8 枚と完全に同条件。文書化された既定の手順     | **8 GB 機でエミュレータは重い**（共倒れの実績あり）。ディスクも厳しい           |
| **(ウ)** 全 16 枚（ja 8 ＋ en 8）を 1080×2432 で撮り直す     | 無し（adb のみ）                              | SDK 不要。実データが AQUOS にあるので移送が要らない | 作業量が最大。「撮影不要」だった `02-recipe-library` も撮り直しになる           |

**推奨: (ア) を 1 枚試し、崩れるなら (ウ)。** (イ) はこの機体には重い。

> **(イ) を選ぶ場合の追加の罠**: 撮り直しには**実データが要る**。シードには料理写真が 1 枚しか無いので、
> README の「AQUOS → エミュレータの再現手順」で機種変更バックアップを復元することになる。
> このとき **AI 無料枠も復元される**ため、AQUOS で消費済みだと `07` が「あと 0 回」になり `08` が撮れない。
> エミュレータなら `adb root` が効くので SQLite を直接戻せる（README §AQUOS → エミュレータ 手順 4）。
> **(ア)(ウ) は実機で撮るのでこの移送自体が不要**という利点がある。

## 4. 既存素材の欠陥 3 件 — 是正計画

3 件とも 2026-09-18 に実物で再現を確認した。

### 4-1. 欠陥①: `extras/11-shopping-list.png` だけ寸法が違う

- **確認**: `file` で 13 枚を検査。`extras/11-shopping-list.png` のみ **1080×2432**、他 12 枚は 1080×2400
- **是正**: §3 の判断に従って**撮り直す**。単独でリサイズして辻褄を合わせない
  （引き伸ばしになり、帯の文字がぼやける）
- **なお §6-2 の「中身」の問題も同時に直る** — 現行の買い物リストには**玉ねぎが入っている**が、
  §6-1 の設計では玉ねぎは「在庫にあるから献立に選ばれた」品なので、
  **買い物リストに並んでいてはいけない**。寸法と中身は同じ撮り直しで両方直す

### 4-2. 欠陥②: en 側に買い物リストのスクショが無い

- **確認**: `phone-screenshots-en/extras/` は `03-recipe-detail.png` と `04-cooking-mode.png` の **2 枚のみ**。
  `11-shopping-list` は**一度も撮られていない**
- **是正**: ja を撮り切ってから `--locale en-US --out docs/store/google-play/phone-screenshots-en` で撮る。
  **訳し下ろしにしない**（帯の文言は en 用に別途起こす）
- **順序の制約**: README のとおり、言語切り替えは**全テーブルを空にして再シード**する。
  ja を完成させてから en に移る（§6-5 手順 7）

### 4-3. 欠陥③: `12-fridge-to-recipe.png` の読み取り結果が調味料だらけ

- **症状**: 読み取り結果が豆板醤・焼肉のたれ・マヨネーズ・チューブ類・乳製品ばかりで、
  **野菜も肉も無く、玉ねぎが入っていない**
- **なぜ困るか**: §6-1 の撮影データセットは**玉ねぎ 1 個が 4 枚を貫く**ことで
  「つながっている」を見せる設計。3 枠目に玉ねぎが無いと**輪の起点が成立しない**
- **是正**: **野菜と肉が写った実際の冷蔵庫写真で撮り直す**（要・利用者提供 → §6）。
  撮り方は README「`12-fridge-to-recipe.png` の撮り方」のとおり:
  BYOK で無料枠を使わない／**確認シートの状態で撮る**／「在庫に追加」を押さずに閉じる／
  **使った実写真は撮影後に削除する**
- **検証点**: §6-5 手順 2 のとおり、ここで**玉ねぎが読み取れたことを確認してから先へ進む**。
  ここを飛ばすと 4・5 枚目まで撮ってから輪が繋がっていないことに気付く

## 5. 動画台本（40 秒・10 カット）の実現性

### 5-1. 実現できる

- 収録は `record-promo-video.mjs`（**adb のみ**）→ §3-1 のとおり Mac で動く
- 編集は `edit-promo-video.mjs`（ffmpeg）。**ffmpeg は未インストール**だが `which ffmpeg` で
  解決する作りなので、`brew install ffmpeg` すれば**改修なしで通る**
  （ハードコードされているのは Windows の winget パスのみ。`:252`）
- 字幕は `drawtext` で焼き込む。**動画生成 AI・TTS は使えない**ことは実測済み（ブリーフ §6-1）ので、
  **ナレーション無し・字幕のみ**という現行方針のままでよい

### 5-2. 収録条件として引き継ぐもの

- **カット 6・7 はタップの操作が画に写っていること。** 字幕「買ったら、タップで食材に戻る」は
  自動の含みがあるため、**画にタップが写っていなければ §1-4 と同じ掲載事故になる**（けんじの指摘）
- 実尺は screenrecord が要求より短く終わるので、**`ffprobe` で実測してから `CUTS[].seconds` を合わせる**
- en 版はロケールを切り替えて**別収録**（字幕も別途起こす）
- 見せるデータはコードで再現できる形にする（`seed.ts` / `scripts/release/promo-assets/`）。
  UI を手で作り込んで状態を作らない

### 5-3. ⚠️ 台本に不整合が 1 件ある（**要・確認**）

`docs/store/刷新案-2026-09-17.md` §4 の中で、**実装待ちのカット番号が 2 か所で食い違っている**。

| 記述箇所                     | 実装待ちとされているカット |
| ---------------------------- | -------------------------- |
| カット表の 🚧 マーク         | **3・5・8**                |
| 「収録前に決めること」の本文 | **4・7・8**                |

カット 3（献立の週ビュー）と 5（家族に「済み」が伝わる）は、ブリーフ §3 の
「待っている実装」と一致するので、**カット表の 3・5・8 が正しいと思われる**。
カット 4（料理中モード）と 7（買い物リスト → 在庫）は既存機能で撮れるはず。

**→ 解決済み（2026-09-18）。Windows 側の確認で「表の 3・5・8 が正、本文の 4・7・8 が誤り」と確定した。**
原因は §4 冒頭の改訂 6 で**「作る」をカット 4 に挿入して以降の番号がずれた**のに、
「収録前に決めること」の行が挿入前の番号のまま残ったこと。`刷新案-2026-09-17.md:456` を訂正済み。

**カット 4（料理中モード／作った料理の写真）とカット 7（チェック → 在庫の数が増える）は

## 7. 「実機 2 台の検証」は、記録の器が無い

**症状**: ブリーフ §3 は「献立と『済み』の家族同期は、**実機 2 台での検証が済むまで掲載文に書けない**」
としているが、その検証を記録する手段が無い。

**原因**: `docs/verification/*.json` は全 14 件すべて **単一の `device` オブジェクト**しか持たない
（直近の `1.13.2-10036.json` も AQUOS SH-RM19s 1 台のみ）。
`scripts/agent/record-device-verification.mjs` の記録形式が 1 台前提になっている。
**2 台で検証した記録は 1 件も無い。**

**対処（案）**: 次のどれかを Windows 側と決める。

1. 記録形式を `devices: []` に拡張する（`scripts/agent/` の変更。**実装側の担当**）
2. 2 台ぶんを 1 件の `checked` 配列に文章で書く（器は変えない・最小の手当て）
3. **2 台目が用意できないなら、掲載文から家族同期の行を落として出す**（ブリーフ §3 の但し書き）

**決定（2026-09-18・Windows 側）**: **1 を採る。** `scripts/agent/` の記録形式を Windows 側で拡張する
（Wave 2 で同期を検証するときに必要になるため）。

**掲載文を書く側としては、それでも 3 を前提に組む。** 器ができても、
**実際に 2 台で検証が通るまで家族同期の行は書けない**（ブリーフ §3 の但し書き）。
検証が間に合ったら行を戻す。
