# お店の味を再現（再現ループ）設計

> だいどこの主役機能。「お店で食べたあの味を、家で」。
> 実装前にこのファイルと `docs/料理写真レシピ推論設計.md` を読むこと。

---

> **前提: 主役への格上げは測定結果を待って判断する（2026-08-02）。**
> 現行のシステムプロンプトは 8 行の汎用指示で、店 → 家庭への翻訳・思考順序・店名の活用・
> confidence の基準がいずれも入っておらず、**出力品質を測る仕組みも存在しない**。
> 評価設計は `docs/レシピ推論の評価設計.md`（R0）。合格ラインを満たすまで **R4（ストア訴求の刷新）は凍結**する。
> R1・R2・R3・R5 はプロンプト品質と独立に価値があるため、測定と並行して進めてよい。

## 1. なぜやるか

- **エンジンは既にこれをやっている**: サーバーのシステムプロンプトは「料理写真からレシピを再現する」であり、
  感想・文脈テキストを味の方向性に反映する指示も入っている（`apps/server/src/lib/vision-recipe.ts`）。
  不足しているのは能力ではなく、**体験の言語化と導線**。
- **訴求が競合と重ならない**: 「レシピ管理・買い物リスト・食材管理」は既存アプリと同じ土俵。
  「お店の味の再現」は検索意図が明確で競合が薄い。リーチが律速の現状（2026-07 実績）への打ち手を兼ねる。
- **再訪問の動機が構造として生まれる**: 再現は一度で終わらない。「近づける」たびにアプリに戻る理由がある。

## 2. ループ

```
① 食べた（店で）  写真＋店名＋一言 → AI がレシピ化 → 「再現したい」棚へ
       ↓
② 作った（家で）  料理中モード → 調理記録
       ↓
③ 近づける       「甘すぎた」「もっと香ばしく」→ AI が調整 → 新リビジョン
       ↑___________________________|  （何度でも）
```

**③ で終わらず ① に戻れることが芯**。「Rev.3 でやっと店の味になった」という履歴自体が価値になる
（バージョン履歴 S13・`recipe_revisions.author_note` を流用）。

## 3. データモデル

既存テーブルの拡張のみ。新規テーブルは作らない。

### cooking_logs の拡張（v9）

| 列           | 型   | 意味                                                         |
| ------------ | ---- | ------------------------------------------------------------ |
| `kind`       | TEXT | `'cooked'`（家で作った・既定） / `'eaten_out'`（店で食べた） |
| `place_name` | TEXT | 店名（`kind='eaten_out'` のとき。任意）                      |

> **なぜ cooking_logs に乗せるか**: 「食べた」も「作った」も _その料理を体験した記録_ であり、
> ホームのタイムラインは一本のままにしたい。別テーブルにすると一覧の結合・バックアップ・
> 将来の同期がすべて二重になる。区別は列一本で足りる。

- マイグレーションは `migrate.ts` の `ADD_COLUMN_MIGRATIONS` に追記（ALTER TABLE ADD COLUMN 方式）し、
  `CURRENT_SCHEMA_VERSION` を 8 → 9 に上げる。
- **`backup.service.ts` の `BACKUP_TABLES` の `cooking_logs` の列にも必ず追加する**
  （追加し忘れると復元で欠落する。`docs/買い物リスト・在庫設計.md` のバックアップ節も参照）。

### 既存の流用

| 用途         | 使うもの                                              |
| ------------ | ----------------------------------------------------- |
| 再現したい棚 | `recipes.pinned_at`（作りたいリスト）                 |
| 調整の履歴   | `recipe_revisions`（`author_note` に感想を残す）      |
| 元写真・出典 | `sources`（`type='photo'`）                           |
| 店の写真     | `cooking_photos`（`kind='eaten_out'` のログに紐づく） |

## 4. 画面と導線

### 4.1 ①「お店で食べた」の記録

`import-photo.tsx` を拡張する。現状は**無条件で「作った」記録を作っている**が、これを出し分ける。

- 撮影後の**感想を書く画面**に「どこで食べた？」＝ **お店 / 家で作った** の選択（既定＝お店）。
  **2026-08-25 に置き場所を変えた**: 以前はプレビュー最上部にあったが、
  「どこで食べたか」を思い出しているのは感想を書いている最中なので、そこへ移した。
  あわせてホームの入口を「お店の料理を撮る」→「**料理の写真を撮る**」に中立化した —
  追加タブと同じ機能なのに文言が違うと、別物に見えて分かりづらいため。
  既定はお店のまま（この機能の主役の流れ）。**間違えても後から直せる**ことで釣り合いを取る:
  レシピの編集画面に「お店の料理 / 家の料理」の切り替えを置き、
  お店を選んだときだけ店名の欄を出す（家に戻したら店名は消す —
  「家の料理なのに店名がある」状態を作らない）。
  なお**調理記録（履歴）の kind は書き換えない** — 記録はその日の事実であって、
  レシピの性格とは別物。履歴側の個別編集が要るかは実地で判断する。
- 「お店」を選んだら店名の任意入力欄を出す。
- 保存時: `kind` と `place_name` を付けて `createCookingLog`。「お店」なら
  `recipes.pinned_at` を立てて **再現したい棚に自動で入れる**（＝次の行動が用意される）。
- 店名・一言は従来どおり推論の `context` にも渡す（味の方向性に効く）。

### 4.2 ③「味を近づける」

レシピ詳細（S05）に「味を近づける」を置く。調理記録を保存した直後にも同じ導線を出す。

1. 感想を自由入力（例:「少し甘すぎた。お店のはもっと酸味があった」）
2. 現在のレシピ（材料・手順）＋感想をサーバーへ送る
3. 返ってきた調整済みレシピを **差分プレビュー**（何が変わるかを見せてから確定）
4. 確定で `updateRecipe` → 新リビジョン。`author_note` に感想を保存

**差分を見せてから確定する**こと。AI が黙って手を入れると、育ててきたレシピが壊れる不安が残る。

### 4.3 起動後の導線（2026-08-02 UX 監査を反映）

> **2026-08-28 決定変更 B**: 空ホーム・主役ボタンの主語を「お店の味」→「献立」へ。
> お店の味系（#111/#112/#115）は検索需要ゼロで凍結済み・訴求の主語は変えてよい
> （本人決定 2026-08-26）。撮影ボタンは残すが主役の座を献立カードに譲る。
> 詳細は `docs/画面設計.md` 末尾「献立導入後の全体導線」。
> （**2026-08-28 本人確認済み** — 主語変更に留まらず「ホーム全体を再定義」する）

主役を入れ替えるということは、**起動してから最初の 1 タップで何が起きるか**を変えるということ。
現状の導線を全数確認した結果と、目標の形を以下に定める。

#### 現状の問題（監査結果）

| #   | 問題                                                                                        | 影響                                             |
| --- | ------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1   | 記念ボーナス +3 の付与が**完全に無言**（`_layout.tsx` で fire-and-forget、UI 表示なし）     | 初回の掴みとして最も強い材料を黙って捨てている   |
| 2   | 写真からレシピが **3 タップ目**、しかも追加画面の 5 択中 4 番目（上に手動・テキスト・URL）  | 主役が埋もれている。起動即カメラだけでは届かない |
| 3   | 写真から保存した直後、**レシピ一覧**に着地する（`router.replace('/(tabs)/recipes')`）       | いま作ったものを探す羽目になる。ループが途切れる |
| 4   | 初回コーチマークが **7 画面・計 18 枚**（ホーム2/一覧2/詳細4/追加2/買い物2/在庫3/設定3）    | 初回に連続で出て、まとめてスキップされる         |
| 5   | ホームの空状態が「まだ調理記録がありません」                                                | 初回の第一印象。最大の広告面が何も語っていない   |
| 6   | ホームヘッダーが無ラベルアイコン 4 つ（カレンダー / ギャラリー / カート / ヘルプ・各 19px） | カート以外はほぼ発見されない                     |
| 7   | 撮影画面が `(tabs)` 配下のためタブバーが残る                                                | 店内で集中して撮る画面としてノイズ               |

> **8. 在庫が 2 階層目（買い物リスト経由）は修正しない。** 主役が再現ループに変わるなら、
> 在庫・買い物リストが一段奥にあるのはむしろ整合する。ストア訴求の変更（R4）とセットで妥当になる。

#### 目標の形

```
起動 → ホーム
        ├ [お店の料理を撮る]        ← 1 タップでカメラ。ホーム最上部
        ├ 再現したい（棚）           ← 「つくりたい」を改称
        └ 食べた / 作った のタイムライン
```

- **ホーム最上部に撮影ボタン**を置く。FAB（＋ → 追加方法選択）は残すが、主役だけは直行させる。
- **「つくりたい」→「再現したい」に改称**（`recipes.pinned_at` はそのまま）。
- 空状態は「お店で食べたあの味、撮っておきませんか」＋撮影ボタン。**空のときこそ主役を語る**。
- 追加画面（S08）の並びを **写真からレシピを先頭**に。手動入力は最後でよい。
- 撮影画面はタブバーを出さない（`(tabs)` 配下から出すか `tabBarStyle: {display:'none'}`）。
- 保存後は**そのレシピの詳細**へ着地する（一覧ではなく）。「再現したい」に入ったことも併せて伝える。

#### 初回体験

初回起動で伝えることは **1 つだけ**にする。

1. ホーム初回のみ: 「AI レシピ 3 回分をプレゼントしました。お店で食べた料理を撮ってみてください」
   （記念ボーナスの告知を兼ねる。`launch_bonus_2026_07` の付与成功時に一度だけ）
2. 残りのコーチマークは**その画面に初めて来たとき**に出す現行方式を維持する。
   ただしホームの 2 枚は上記 1 に統合し、レシピ詳細の 4 枚は 2 枚に減らす（`cook` / `logShortcut` を残す）。

コーチマークを全部消さないのは、`?` ボタンからの再生導線が既にあり、
その画面に来た人にだけ出る仕組み自体は正しく働いているため。**初回に連続で出ることだけが問題**。

### 4.4 起動即カメラ

- 設定「アプリを開いたらすぐ撮影」（**既定オフ**）。オンなら起動時に `import-photo` へ直行。
  既定オンにしない理由: 店を出た直後には最適だが、レシピを見に来た人には邪魔になる。
- Android はアイコン長押しのショートカット（「お店の料理を撮る」）も用意する。
  設定に依存せず最短経路を持てる。
- アプリ起動広告のガード（撮影復帰時は出さない）は `app-open-ad.service` に既存。
  起動即カメラの経路は **cold-start と sensitive-screen の二重ガード**で広告が出ない。

**起動経路の優先順位**（`utils/launchDestination.ts`）: 通知タップ ＞ 起動即カメラ ＞ ホーム。
通知タップはユーザーの明示的な操作なので、設定より必ず優先する。
取り違えると「押したのと違う画面が開く」といういちばん困る壊れ方をするため、1 か所に固定した。

**撮影画面のタブバー非表示は親タブ側で切り替える。** `recipes/` 配下は入れ子スタックなので、
`(tabs)/_layout.tsx` の `Tabs.Screen name="recipes/import-photo"` に `href: null` や
`tabBarStyle` を書いても効かない（実機で確認済み）。
`recipes` タブの options を関数にして `getFocusedRouteNameFromRoute(route)` で
いま開いている子ルートを見る。

## 5. サーバー: レシピ調整エンドポイント

`POST /api/v1/infer/refine`

```jsonc
// request
{
  "recipe": { "title": "...", "servings": 2, "ingredients": [...], "steps": [...] },
  "feedback": "少し甘すぎた。お店のはもっと酸味があった",
  // 任意。家で作った結果の写真（＋あれば店の写真）
  "images": [
    { "imageBase64": "...", "mimeType": "image/jpeg", "role": "cooked" },
    { "imageBase64": "...", "mimeType": "image/jpeg", "role": "target" }
  ]
}
// response: 既存の photo 推論と同じ RecipeDraft 形 ＋ changeSummary
```

**写真は任意で添えられる（`images`）。** 言葉にしにくいズレ——焦げ色が足りない、とろみが強い、
色が濃い、具が大きい——は**写真の方が速く正確に伝わる**。特に次の 2 枚が効く。

| `role`   | 何の写真                  | AI に何を判断させるか                        |
| -------- | ------------------------- | -------------------------------------------- |
| `cooked` | 家で作った結果            | 目標との見た目の差（焼き色・とろみ・色・量） |
| `target` | 店の料理（①で撮ったもの） | 目指す状態。R1 の記録から自動で添えられる    |

`target` は**ユーザーに撮らせない**。R1 で「お店で食べた」記録に紐づいた写真がすでにあるので、
アプリが自動で添える。ユーザーが撮るのは `cooked` の 1 枚だけでよい。

- 写真なし（テキストのみ）でも動く。**写真は精度を上げる任意入力**という位置づけを崩さない。
- 送る画像は既存の前処理（長辺 1600px / JPEG q80）を通してから。2 枚でも入力トークンは
  出力に比べて誤差（[[gemini-api-quota-and-cost]] の実測より）。
- レート制限・グローバル日次上限（`INFER_GLOBAL_DAILY_LIMIT`）は既存の仕組みに相乗り。
- クライアントの無料枠は**写真レシピと同じ枠を消費**する（AI 呼び出しであることに変わりはなく、
  別枠にすると上限管理が二重になる）。
- プロンプト方針: **感想で指示された点だけを変える**。関係ない材料・手順は原文を保つ。
  写真がある場合は「作った結果と目標の差」を根拠に使い、**写真に写っていないこと（味・香り）は
  感想テキストだけを根拠にする**。変更点の要約（`changeSummary`）も返し、差分プレビューに使う。

## 7. 決めたこと

- 「食べた」と「作った」は **1 テーブル 1 列**で区別する（別テーブルにしない）。
- AI の調整は **必ず差分を見せてから**適用する。
- 起動即カメラは **既定オフ**。代わりにホーム最上部の撮影ボタンで既定 1 タップを確保する。
- 在庫・買い物リストは畳まない。再現ループの脇役として残す
  （店の味に必要な材料 → 買い物リスト、という接続はむしろ強い）。
  **在庫が買い物リスト経由の 2 階層目にあることも変えない**（主役交代と整合するため）。
- 初回起動で伝えることは **1 つだけ**。コーチマーク自体は残すが、初回に連続で出さない。
- 空状態は主役を語る面として使う（「記録がありません」で終わらせない）。
