## 1. 背骨: 共通スナップショット JSON・DB 直読みしない

`widget-snapshot.service.ts`（新設）が JSON 1 本（version/writtenAt/locale/shopping/menu）を組み立て、iOS は `ExtensionStorage`（App Group UserDefaults）＋`reloadWidget()`、Android は `documentDirectory/widget/snapshot.json`＋`requestWidgetUpdate()` へ書く。書くタイミングは買い物書き込み系・献立保存・調理記録保存・**同期 pull 完了後**・background 遷移の 5 フック（500ms デバウンス）。

DB 直読み（iOS App Group への DB 移動 / Android Headless からの expo-sqlite）は両案とも落とす — 既存全ユーザーの DB ファイル移動はデータ消失リスクの新設であり、表示に要るのは高々 10 行。

**検証反映**: 初稿の「スナップショットをクラウドバックアップ除外に足す」は**不要（no-op）** — `withDaidokoBackupRules` のクラウド規則は include 方式で documentDirectory は最初から対象外。D2D 移行では運ばれるが派生データなので無害（除外作業は書かない）。

## 7. R5 Android スパイクの結果（2026-08-29・実測）

**§6-1 の答え: 読める。フォールバック不要。**
Headless タスクから `expo-file-system/legacy` で `documentDirectory/widget/snapshot.json` を
読めることを emulator-5554 で確定（logcat: `WIDGET_ADDED snapshot: remaining=19`）。
ウィジェット表示 → タップ → `daidoko://shopping` → 買い物リスト画面まで一気通貫を確認。

実機まわりの発見（症状 → 原因 → 対処）:

- **`adb shell cmd appwidget` は使えない**（AQUOS・エミュレータとも "No shell command
  implementation"）→ ウィジェットの配置はランチャーの長押し → Widgets → アプリ行を展開 →
  **プレビューをタップして出る「+ Add」ボタン**で追加できる（ドラッグ不要）
- **`adb shell input text` は日本語で NullPointerException** → テストデータは
  シードのチェックボックス操作で代替する
- **AQUOS は暗証番号ロック中はスパイク不可**（screencap 真っ黒・既知）。arm64 APK は
  インストール済み・起動確認は未了 → **1.13.0 の一括実機検証（#243）でロック解除の上で確認**
- `build-android.mjs` は既定 arm64-v8a。**エミュレータには `--arch x86_64` で組み直す**
  （arm64 をエミュに入れると SoLoader UnsatisfiedLinkError で即クラッシュ）
- **AQUOS SH-RM19s の Sharp ランチャー（`jp.co.sharp.android.launcher3`）は上記フローに乗らない**
  （1.13.0 実機検証で発見）。「ホーム長押し → ウィジェット」は Play ストアの詳細ページへ
  直行してしまい、§7 冒頭の「アプリ行を展開 → プレビューをタップして＋Add」に到達しない。
  到達経路は**アプリ一覧でアイコン長押し → ウィジェット**のみ。配置もタップでは受け付けず
  **長押しドラッグ**が要る（adb では `input draganddrop`）

## 8. R5 iOS スパイクの結果（2026-08-31・実測）

### 通ったこと

- **SDK 54 の prebuild で `@bacons/apple-targets` 5.0.0 は動く。** 内部依存が
  `@expo/prebuild-config ~55.0.6`（SDK 55 世代）でも衝突しない。pnpm が
  `node_modules/@expo/cli/node_modules/` にネストして共存させる（`node-linker=hoisted` でも）。
  **overrides も patch も要らない**
- ウィジェットターゲットが生成され、`.appex` が `app.app/PlugIns/` に同梱される。
  `WidgetKit.framework` もリンクされる
- **App Group に書いた JSON をウィジェットが実際に読んで描画する**ところまで確認した
  （ギャラリーのプレビューは拡張プロセスによる実描画）

### 症状 → 原因 → 対処

#### 1. `ExtensionStorage` が autolink されず、App Group に書けない

**症状**: `expo-modules-autolinking` は検出するのに `Podfile.lock` に入らない。
`pod install` はエラーも警告も出さない。アプリからは書けたつもりで、ウィジェットは
永久に「アプリを開くと表示されます」のまま。

**原因**: `@bacons/apple-targets` の `expo-module.config.json` が旧い表記。

```
@bacons/apple-targets   "platforms": ["ios"]     ← 単数。リポジトリ内で唯一
他の全 22 モジュール      "platforms": ["apple"]
```

SDK 54 の autolinking は `"apple"` を期待する。`resolve` は互換で拾うが、
`use_expo_modules!` が Podfile へ流す段階で**黙って消える**。

**さらに厄介なのは JS 側**。`ExtensionStorage.js` はネイティブ不在時に例外ではなく
**no-op のスタブ**へ落ちる:

```js
const nativeModule = ExtensionStorageModule ?? {
  setString() {},
  reloadWidget() {}, // 何もせず成功したふりをする
};
```

`try/catch` にも掛からず、ログにも出ない。

**対処**: **書き込みだけ自前のローカル expo モジュールで持つ**
（`apps/mobile/modules/daidoko-widget-storage`）。ターゲット生成は apple-targets の
まま使う。npm 上 5.0.0 が最新で**上げ先が無い**ため、版上げでは解決しない。
patch-package は版が上がると黙って剥がれ、同じ「静かに壊れる」を再生産するので採らない。

自前側は**同じ轍を踏まない作り**にした:

- ネイティブ不在なら `console.warn` を 1 回（毎回は出さない — 買い物リストの連打でログが溢れる）
- Swift の `setString` は App Group を開けなければ **`false` を返す**。
  「ネイティブは居るが entitlement が無い」も検知できる
- サービス側は書けなかったら `reloadWidgets()` を呼ばない（古い姿を出し直すだけなので）

#### 2. `expo-target.config.js` に `entitlements: {}` が無いと拡張側の App Group が空になる

**症状**: 本体には App Group が入るのに、ウィジェット拡張側の entitlements ファイルが
生成されない。ビルドは通るので**実機で見るまで気づけない**。

**原因**: README は「App Group を使えるターゲットは `app.json` の配列を自動でミラーする」と
書いているが、`entitlements` オブジェクト**自体**が無いと `generated.entitlements` が
書き出されない。

**対処**: `entitlements: {}` を空で書く。中身は書かない（app.json 側から写るので、
両方に書くと片方だけ直したときに食い違う）。

#### 3. `CODE_SIGNING_ALLOWED=NO` でビルドすると App Group が使えない

**症状**: すべて正しく組み込まれているのに `UserDefaults(suiteName:)` が nil を返し、
App Group コンテナが作られない。

**原因**: 署名が無いと **entitlements が埋め込まれない**（`codesign -dv` が
`code object is not signed at all`）。App Group は entitlement で許可される。

**対処**: シミュレータ向けでも **`CODE_SIGN_IDENTITY="-"`（アドホック署名）**でビルドする。
`xcrun simctl get_app_container <udid> com.daidoko.app groups` にパスが出れば効いている。

#### 4. `-derivedDataPath` を `ios/` の中に置くと `pod install` が壊れる

**症状**: 次の `pod install` が
`invalid byte sequence in UTF-8`（`set_RCTNewArchEnabled_in_info_plist`）で落ちる。

**原因**: ビルド成果物の**バイナリ plist**（`bplist00`）を post-install フックが
テキストとして読む。

**対処**: `ios/` の外に出す。

#### 5. iOS の中サイズは 6 行を 1 列で積めない

**症状**: `systemMedium` でタイトルと「HH:mm 時点」が上下に押し出されて見切れる。

**原因**: iOS の `systemMedium` は縦が約 158pt しかない。Android の中サイズは
縦長なので 1 列で入るが、iOS は横長。

**対処**: **中サイズは 2 列に割る**。「6 件見える」という §2 の約束は保つ。

### 未検証

## 10. W2 献立ウィジェット（Android）の実装メモ（2026-09-04・実装時）

ペルソナ確定設計（由紀・美咲ら 5 人の総意）で実装。既定は「今日の一品」を大きく、
週間一覧は大サイズのときだけ。実装は W1 を踏襲（純関数＋テスト、`snapshot.json` 共通）。

### スナップショット契約の拡張（版は上げない・§1）

`menu` に**省略可フィールドを 2 つ**足した（`widgetSnapshot.ts`）:

- `recipeId?: string | null` — 今日/次の一品のタップ先（`daidoko://recipes/<id>`）
- `week?: { title, recipeId, doneAt, isToday }[]` — 週間表示（大）用の先頭 7 日分

**買い物側のフィールド・挙動は一切変えていない。** `parseWidgetSnapshot` は旧アプリが
書いた（`week` の無い）JSON を `week: []`・`recipeId: null` として読む（前方・後方とも互換）。
`SnapshotInput.menuDays` に `recipeId?`・`day?`（自動モードの日番号）を足しただけで、
**`widget-snapshot.service.ts` の抽出コードは変更不要だった** — `getMenuPlan()` が返す
`MenuDayView` が既に `day`/`recipeId`/`title`/`doneAt`/`missing` を全部持っているため、
`menuDays: menu.days` がそのまま新契約を満たす。

**2026-09-05 追加（献立の結果フィードバック・`docs/買い物リスト・在庫設計.md` §10.7-a）**:
`menu` に省略可フィールド **`requestedDays?: number`** を足した（同じ流儀・版は上げない）。
「組む」で要求した日数で、週間表示（大）は `week.length < requestedDays` のとき末尾に
1 行「残り◯日分はレシピが足りません」を出す（由紀の案・`menuWidgetContent.ts` の
`shortfallMessage`）。**旧アプリ・旧プラン（要求日数を保存していない）が書いた
スナップショットには無い** — 無ければ不足行を出さない。壊れた値（非整数・0 以下）は
書く側（`buildWidgetSnapshot`）・読む側（`parseWidgetSnapshot`）の両方で落とす。
実の献立が 1 行も無いときも出さない（noMenu の案内に一本化）。小/中（今日の一品）には出さない。

### サイズ→表示の出し分け（ウィジェット内トグルは使わない）

react-native-android-widget では**ウィジェット内トグルが困難**なので、`widgetInfo` の
幅・高さ（dp）で出し分ける（`menuWidgetContent.ts` の `menuWidgetSize`）:

- **高さ 250dp 以上 → 大（週間 7 日）。** 週間は縦に 7 行積むので**高さで判定する**
  （横に広げるだけでは週間にしない — 1 行の今日を大きく出す方がペルソナの既定）
- 高さがそれ未満のとき、幅 250dp 以上 → 中、未満 → 小（どちらも今日の一品）

週間の色分け: 今日 `#C9A16A`（金・太字）／調理済み `#6B5B40`（薄く・§2 の「#2E2418 系」だが
真っ黒だと読めないので少し起こした）／未定・削除済みは「—」＋グレー `#8A8175`。
各行は行ごとに `clickAction=OPEN_URI`（レシピがあればその詳細、無ければ献立画面）。

### 罠: 写真サムネは file:// URI では出せない（今回は名前のみ）

**症状**: ペルソナ設計の「料理名＋あれば写真サムネ」を Android ウィジェットで出そうとすると、
ヒーロー写真（`documentDirectory` の `file://` URI）が描画できない。

**原因 2 つ**: ①`react-native-android-widget` の `ImageWidget.image` の型は
`require() | http(s): | data:image` のみで、**`file://` を受け付けない**。②仮に渡せても
ランチャー（ホスト）プロセスは他アプリの private な `documentDirectory` を読めない
（RemoteViews の既知の制約）。

**対処**: **今回は料理名のみ**にした（タップ＝レシピ詳細は問題なく動く）。写真を出すなら
base64 データ URI をスナップショットへ載せる（肥大化）か、iOS W2b と同じ**共有コンテナ
書き出し**が要る。W2b（§3）と同じ課題なので、写真対応は**両 OS まとめて後続**とする。
スナップショットにも `heroPhotoUri` は入れていない（描けないデータを載せない）。

### --prebuild 必須

`app.json` の `react-native-android-widget` プラグインに 2 つ目のウィジェット `Menu`
（label「献立」・`maxResizeHeight` は週間のため 320dp）を足した。**config plugin 変更なので
反映には `--prebuild` が要る**（実機ビルドはメイン側）。Headless ハンドラは 1 本
（`daidokoWidgetTaskHandler`）で `widgetInfo.widgetName` により `ShoppingList`/`Menu` を
出し分ける（`index.js` の登録も更新済み）。
