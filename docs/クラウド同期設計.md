## 0. 目的と非目的

**目的**: 家族グループ内でレシピ等のデータが「何もしなくても」全端末に行き渡る自動同期。
Android⇄iOS 混在の家族で成立すること（1.5.0 で iOS 初回リリース後の最重要ギャップ）。

**非目的（やらないこと）**:

- メールアドレス・パスワード等の**個人情報を伴うアカウント制**（→ §2 アカウントレス）
- リアルタイム共同編集（WebSocket/CRDT）— ポーリング＋プッシュ通知トリガーで十分
- Memo のマージ UI（原案 §4.2 の Vector Clock 案は **LWW に簡素化**。件数・重要度に対して過剰）
- E2E 暗号化（将来オプション。v2.0 は TLS＋グループトークン分離まで）
- Web 版同期

**設計原則**:

1. **ローカルファースト温存** — SQLite が常に真実。同期は「後ろで走る差分転送」で、オフラインでも全機能が動く現状を壊さない
2. **個人情報ゼロ** — サーバーが持つのは乱数 ID・表示名（任意・ニックネーム）・暗号化された push トークンのみ
3. **コスト上限** — 増分ランニングコストは月 $5 以内（§8）。プッシュ通知は Expo Push で ¥0

### 0-2. ユーザー間の通信機能は搭載しない（2026-08-21 決定）

ユーザー同士が自由文をやりとりする機能（チャット・DM・コメント・利用者が文面を書く
プッシュ通知）は、他人の通信の媒介として**電気通信事業法の届出**が必要になり得るため
**搭載しない**。

- 同期は**アプリデータ（レシピ・帖・買い物・在庫）の転送に限る**
- プッシュ通知は**利用者名・共有データの内容を含まない、サービスからの状態通知のみ**
  （「家族の共有データが更新されました」まで。理由は下記の該当性判定 — ファイル共有サービスの但書）
- 自由テキストは**共有オブジェクトの属性**（レシピのメモ・品目名など）に限る
- 将来この線を越える機能を検討するときは、届出の要否を先に確認する

**該当性の自己判定（総務省「電気通信事業参入マニュアル［追補版］」の判定フローに沿う・2026-08-21）**

判定フロー（マニュアル p.10〜15）への当てはめ:

1. 電気通信役務か → **該当**（サーバ＝電気通信設備を他人（利用者）の通信の用に供する）
2. 電気通信事業か → **該当として扱う**（同期はレシピ管理の付随機能とも整理し得るが保守的に）
3. 「営む」か → **該当**（名目上無償でも広告収入により利益を上げていれば「営む」— p.12）
4. 適用除外 1号（単一提供先）・2号（同一構内）→ 非該当
5. 登録 → 不要（電気通信回線設備＝伝送路設備を設置しない）。届出の要否は**媒介該当性**で決まる:
   媒介 = 「ア 加工・編集を行わない」∧「イ **送信時の通信の宛先として受信者を指定**」（p.15）。
   本設計の同期は書き込み時に宛先を指定しない（グループの保存領域へ保存し、各端末が pull する）
   → **イ不成立 → 媒介でない**

事例集への当てはめ（p.22〜28）:

| 本設計の機能                 | マニュアルの事例                                             | 判定                  |
| ---------------------------- | ------------------------------------------------------------ | --------------------- |
| 家族グループのデータ同期     | **ファイル共有サービス**（互いに共有する目的で受信・保存）   | 3号事業・**届出不要** |
| Web 共有ページ（稼働中）     | 電子掲示板／各種情報のオンライン提供                         | 3号事業・届出不要     |
| チャット・DM（**作らない**） | クローズド・チャット／利用者間メッセージ媒介（付随機能でも） | 作れば**届出必要**    |

**この判定から出た設計ガードレール**: ファイル共有サービスの但書 —
「利用者間で、データを保存したことや保管先を通知するメッセージ機能を提供する場合は媒介＝届出必要」（p.23）。
プッシュ通知はこれを踏まないよう:

- **通知文言に利用者名・共有データの内容を含めない**（「家族の共有データが更新されました」まで。
  送信主体はサーバ＝サービスからの状態通知であり、「利用者間の」通知ではない）
- **「誰が何を追加したか」の表示・通知は v1 では持たない**（ユーザー決定 2026-08-21 —
  端末側生成なら適法だが、そもそも持たない方が明快）。`created_by` / `updated_by_device`
  等の**記録**は同期データの属性として続ける（表示と記録は別 — #199 の決定どおり、
  列が無い間の行は後から復元できないため。表示を足すかは将来の判断）

残る義務（3号事業でも適用される）: **検閲の禁止（3条）・通信の秘密の保護（4条）** —
payload を不透明なまま扱い、ログ・エラー通知に内容を出さない実装で担保する。
外部送信規律（27条の12）は対象類型（メッセージ媒介・SNS 等・検索・ニュース配信等）に当たらず非該当と判断。

**結論: 届出不要（法 164 条 1 項 3 号事業）と自己判定。** 疑義照会は必須ではない。
それでも確認する場合の質問文: 「家族グループ内でレシピ・買い物リスト等のアプリデータをサーバ経由で
同期する。書き込み時に宛先の指定はなく、各端末がグループの保存領域から取得する。ユーザー間の
メッセージ機能は無く、プッシュ通知は利用者名・内容を含まないサービスからの更新通知のみ。
ファイル共有サービス（3号事業）と同様に届出不要という理解でよいか」

https://www.soumu.go.jp/main_content/000477428.pdf

## 1. 全体像

```
デバイスA(Android)              Railway サーバー                 デバイスB(iOS)
  SQLite(真実)                  Hono + PostgreSQL                SQLite(真実)
     │ 書き込み時に sync_queue へ積む      │                            │
     │── POST /sync/push ───────────>│ LWW マージ・seq 採番        │
     │<─ {applied, serverSeq} ───────│                            │
     │                               │── Expo Push "変更あり" ──> │ (無料・ベストエフォート)
     │                               │<────── GET /sync/pull?since=seq ──│
     │                               │─ {changes[]} ────────────>│ ローカル適用(LWW)
```

- **push**: ローカル書き込みのたびに `sync_queue` へ積み、オンライン時にまとめて送る（既存設計 §4.3 踏襲）
- **pull**: `前回受信した seq 以降の変更をくれ` 方式（グループ単位の単調増加シーケンス）。起動時・フォアグラウンド復帰時・push 通知受信時に実行
- サーバーは変更を受けたら同グループの他端末へ Expo Push を投げる（**内容を持たない同期トリガー** —
  文言に利用者名・データ内容を含めない。§0-2 の該当性判定を参照。「誰が何を追加したか」の
  表示・通知は v1 では持たない）

## 2. アカウントレス認証とグループモデル

既存の家族機能（S16: ローカルの家族プロフィール＋招待コード）をそのままクラウドの「同期グループ」に昇格させる。

### 2-1. 識別子

| もの          | 実体                                                     | 保存場所                                                         |
| ------------- | -------------------------------------------------------- | ---------------------------------------------------------------- |
| device_id     | UUID（初回起動時生成）                                   | 端末 SQLite + サーバー                                           |
| device_secret | 乱数 32byte。API 認証に使用                              | **expo-secure-store**（Keystore/Keychain）+ サーバー（ハッシュ） |
| group_id      | UUID                                                     | 端末 + サーバー                                                  |
| invite_code   | 短い英数字（既存 UI の招待コード。**ローテーション可**） | サーバー（有効期限つき）                                         |

### 2-2. フロー

- **グループ作成**: `POST /sync/groups`（device 登録と同時）→ `{group_id, invite_code}`。既存家族画面の「招待コードを共有」がそのまま入口
- **参加**: `POST /sync/groups/join {invite_code}` → 端末がグループに紐づく。以後の API は `Authorization: Bearer <device_id>:<device_secret>`
- **退出/端末除名**: `DELETE /sync/devices/me` / オーナー端末からの `DELETE /sync/devices/:id`（2026-08-22 実装。除名と同時に invite_code をローテーションして再入場を防ぐ — 応答に新コードが返る）。端末の整理と所有権の引き継ぎは §5-4
- **機種変更**: 既存の移行 ZIP に device 資格情報は**含めない**（secure-store 方針踏襲）。新端末は招待コードで再参加すれば全データが pull で戻る — **移行 ZIP なしの機種変更も成立するようになる**副次効果

### 2-3. 脅威モデル（割り切り）

- 招待コードが漏れると第三者がグループに入れる → 有効期限（例: 72h）＋手動ローテーション＋参加時に全端末へ通知で緩和。家庭内データの機微度に対して十分
- サーバー管理者（=開発者）は平文データを読める → プライバシーポリシーに明記。E2E は将来オプション

## 3. サーバーデータモデル（PostgreSQL 16 + Drizzle）

```
sync_groups   (id, invite_code, invite_expires_at, created_at)
devices       (id, group_id, secret_hash, display_name, expo_push_token, last_pull_seq, created_at)
entities      (group_id, entity_type, entity_id,         -- 複合PK
               payload JSONB, updated_at, deleted_at,
               seq BIGINT,                               -- グループ内単調増加（変更のたび採番）
               updated_by_device)
photos        (id, group_id, r2_key, bytes, created_at)  -- 実体は R2
```

- **最新状態方式**（オペレーションログは持たない）: `entities` は各行の最新版のみ保持。pull は `WHERE group_id=? AND seq > :since ORDER BY seq`
- 削除は `deleted_at` の**トゥームストーン**（クライアントはローカル行を削除）。90 日で物理削除のバッチ
- `payload` はクライアントのテーブル行をそのまま JSONB 化（サーバーはスキーマの意味を知らない＝**サーバー改修なしにアプリ側のカラム追加が可能**）
- インデックス: `(group_id, seq)` と `(group_id, entity_type, entity_id)`

## 4. クライアント側の変更

- `sync_queue` テーブル追加（schema v14・**実装は印だけ**: `entity_type` / `entity_id` / `queued_at` / `retry_count`。
  主キーは (entity_type, entity_id)。payload は送信時に DB から作り直すので持たない — 原案 §4.3 の
  `operation`/`payload` 列は廃止。**バックアップ対象には入れない**（他人のバックアップを復元した端末が
  その人の送信待ちを自分のグループへ流してしまう））
- 各サービスの書き込みパスに「queue へ積む」を追加（recipe/tag/shopping/pantry/cooking-log/…。**書き込み API は不変**なので画面側の改修はゼロ）
- 実装の分割（S1）: `sync-payload.ts`（純関数: JSON 化・検証・LWW）/ `sync-queue.service.ts`（送信待ち・受信適用中の抑止）/
  `sync-entities.service.ts`（DB ⇄ payload）/ `sync-runner.service.ts`（実行と 4 つのきっかけ）。
  **DB を掴む経路は jest でテストできない**（動的 import 不可の既知制約）ので、判断のいる部分を純関数側へ寄せている
- 適用時の LWW: 受信 `updated_at` > ローカル `updated_at` なら上書き。同値はサーバー優先。**時計ずれ対策**: push 時にサーバーが `updated_at` を自分の時計で上書きし単調性を保証（クライアント時計を信用しない）
- FTS・作りたい・派生データはローカル適用後に既存のフックで再構築

## 5. エンティティ別戦略（原案 §4.2 を v2.0 スコープに更新）

| エンティティ                                 | 方式     | 競合解決                                                  | フェーズ |
| -------------------------------------------- | -------- | --------------------------------------------------------- | -------- |
| Recipe / Ingredient / Step / Tag / RecipeTag | 差分同期 | LWW（レシピ単位。材料・手順はレシピの子として丸ごと置換） | **S1**   |

> **LWW かつサーバーに履歴が無いので、送信側で欄を落とすと全端末から消える。**
> 受信側の `onConflictDoUpdate` は payload の値をそのまま採るため、
> **家族の誰か 1 人が 1 回編集しただけで、その欄が全員の端末から失われる**。
> `sync_entities` は (group, type, id) の 1 行上書きなので、過去の payload も残らない。
> #220（更新で読みがな・店名が消える）が家族全体に伝播したのはこの経路。
> **レシピを書く経路は必ず `resolveRecipeUpdate` を通す**（`docs/レシピ作成フロー.md` §2）。
> | RecipeBook / RecipeBookItem | 差分同期 | LWW（帖単位。共有トークン類は同期しない） | **S1** |
> | ShoppingList / ShoppingItem | 差分同期 | LWW（項目単位 — チェック操作が主なので実質競合しない） | **S2** |
> | PantryItem / NameAlias | 差分同期 | LWW。ただし**数量のみデルタ同期**（§5-1） | **S2** |
> | CookingLog / CookingPhoto / RecipeRevision | 追記のみ | 競合なし（INSERT のみ） | **S3** |
> | Memo | 差分同期 | LWW（Vector Clock 案は廃止） | S3 |
> | 写真バイナリ | R2 へ遅延アップロード/ダウンロード | — | **S3** |
> | users / families（プロフィール） | **同期しない**（v1） | — （下の注を参照） | — |
> | 設定・BYOK キー・AI 利用カウント | **同期しない**（端末ローカル） | — | — |

**プロフィール（表示名）を v1 で同期しない理由**（2026-08-21・実装時に確定）:
ローカルの利用者行は全端末で `users.id = 'user-kei'`、家族行も `families.id = 'family-001'` に固定されている。
このまま行単位 LWW に載せると、**お互いの「自分の名前」を上書きし合う**（パパの端末とママの端末が同じ行を
奪い合う）。そもそも §0-2 の決定で「誰が何を追加したか」を v1 では表示しないので、他端末の表示名を
配る必要が無い。端末ごとの利用者 ID を導入するのは調理記録の `cooked_by` 等に波及するため、
必要になった時点（S3 で「誰が作ったか」を出すとき）に併せて設計する。

### 5-1. 在庫数量のデルタ同期（#199 決定・2026-08-19）

在庫の数量は LWW では合わない。同時に「卵を 1 個使った」と記録すると 5→4 と 5→4 が
競合して 4 になる（正しくは 3）。**数量の変更だけ「+2」「−1」という操作として同期**し、
受信側で全部適用する。名前・単位・グループ（置き場所）・期限など他の列は LWW のまま。

- push/pull の封筒は「行更新（LWW）」と「デルタ操作」の**2 種類を最初から運べる形**にする
- フル操作ログは持たない（履歴表示・「誰が使ったか」までは要らない。要るとなったら拡張）
- **（2026-08-22 確定）** +2/−1 を操作として運ぶのではなく、**端末ごとの累計増減（持ち分）を状態として**
  行 LWW に載せる方式で実装する（§5-3）。収束結果は同じで、操作ログを再生しないので復元・版更新との
  相互作用（§5-2b）が消える。`sync_deltas` 表は書き手を作らず温存

### 5-1b. S1 プロトコル詳細（2026-08-21 確定）

**エンティティの粒度**（§5 の「丸ごと置換」の具体化）:

| entityType    | payload の中身                                         | LWW の単位 |
| ------------- | ------------------------------------------------------ | ---------- |
| `recipe`      | レシピ本体＋材料＋手順＋タグを 1 つの JSON に          | レシピ単位 |
| `recipe_book` | 帖＋所属レシピ ID 列（**Web 共有トークンは含めない**） | 帖単位     |
| `profile`     | 表示名（users / families）                             | 行単位     |

**payload の約束**:

- クライアント行の JSON 化。サーバーは解釈しない（§3）。`schemaVersion` を含める（将来の互換判定用）
- **写真パスは含めない** — 写真は S3 の領分で、パスは端末ローカルの値。
  **受信適用時もローカルの写真列は保持する**（丸ごと置換で受信側の写真参照を消さない）。
  つまり S1 では「テキストは同期・写真は各端末のまま」。S3 で写真が付く

**push**: `POST /sync/push { changes: [{entityType, entityId, payload, clientUpdatedAt, deleted}] }`
→ `{ applied, latestSeq }`。サーバーは LWW 判定して採用分に seq 採番。
LWW の基準は **clientUpdatedAt（端末の時計）** — サーバー到着順にしない
（オフライン編集の勝敗が「後でつないだ方が勝つ」になるのを防ぐ。家族用途の時計ずれは許容）。
同時刻は deviceId の辞書順で決定的に。

**pull**: `GET /sync/pull?since=<seq>&limit=500` → `{ changes, deltas, latestSeq, hasMore }`。
グループ内単調 seq 順。クライアントは `last_pull_seq` を進める。自端末由来（updated_by_device 一致）はスキップ。

**クライアント**:

- `sync_queue`（schema v14）: 書き込みのたび `{entity_type, entity_id}` を積む。
  **payload は送信時に最新の DB から作る** — 連続編集が自然に 1 回の送信へ合流する
- 実行タイミング: 起動時・フォアグラウンド復帰・ローカル書き込み後（数秒デバウンス）・push 通知受信時
- 削除は tombstone（deleted=true）→ 受信側はローカル行を削除…**だが、レシピは例外**（下記）

**実装で確定した詳細（2026-08-21・S1 モバイル実装時）**:

- **レシピの削除は行を消さない。** アプリの削除は `status='archived'` の論理削除で、リビジョン・材料・
  手順・調理記録・メモが `recipes.id` を外部キーで参照している（`PRAGMA foreign_keys = ON`）。
  受信側で行を DELETE すると外部キー違反で落ちるので、**受信 tombstone も archived に倒す**。
  送信側も archived を普通の payload として配る（tombstone を使うのは行ごと消えていたときだけ）。
  **帖は元々物理削除**なので設計どおり tombstone → DELETE（子 `recipe_book_items` → 親の順）
- **出所（`sources`）は payload に含める。** Web 共有の出所ゲート（`getUrlImportedRecipeIds` は
  `sources.type='url'` で判定）が出所の無い受信側で素通しになり、**URL 取り込みのレシピを他端末から
  公開できてしまう**ため。運ぶのは種別・URL・サイト名・ページ題・取得日時だけで、**OCR の生テキストは運ばない**
- **`familyId` / `createdBy` は運ばない。** 全端末で `family-001` / `user-kei` 固定なので運ぶ意味が無く、
  運べば受信側で外部キー違反になりうる。適用側がローカルの値を入れる
- **タグは名前で運ぶ**（ID は端末ごとに別物なので、受信側で名前から引き当てるか新規作成する）
- **手順写真は「手順 ID が一致する分だけ」引き継ぐ。** 他端末が編集して新しいリビジョンになると
  手順写真の参照は外れる（表紙写真はレシピ行なので保たれる）。S3 で写真が乗れば解消する
- **同期カーソル**（`last_pull_seq`）は `app_meta.sync_cursor` に **groupId とセットで** JSON で持つ。
  app_meta はバックアップに含まれるので、グループ ID が違えば 0 から取り直す
- **グループ参加時**: カーソルを白紙にして、いまある**レシピ・帖を全件**送信待ちへ積む（v1 は全量同期）。
  **離脱・グループ削除時**: 送信待ちとカーソルを捨てる。
  **バックアップ復元後**: カーソルを 0 に戻して全件積み直す（どちらが残るかは通常どおり LWW が決める）
- **詰まり対策**: 300KB を超える 1 件は送らない。バッチがサーバーに弾かれた（SERVER）ときは
  1 件ずつ送り直し、通らない 1 件だけ捨てる — 壊れた 1 件で以後の同期が永久に止まらないようにする
- **受信適用中は `sync_queue` に積まない**（受け取った変更を押し返す往復を作らない）。
  ただし止めるのは**適用しているその 1 行だけ**。全体を止めると、適用の待ち時間に
  利用者が別のレシピを保存したときに、その編集が積まれず永久に送られない

**多面レビューで見つけて直した落とし穴（2026-08-22）**:

実装後に 4 観点（DB 整合・収束性・既存機能・プライバシー）で機械レビューを回し、
確認できた 14 件を直した。同じ穴を掘り直さないために要点を残す。

- **カーソルは受け取った変更の seq までしか進めない。** サーバーの `latestSeq` まで
  飛ばすと、「変更一覧を読んだ後・最新 seq を読む前」に他端末が push した分を飛び越す。
  サーバーは 1 エンティティ 1 行なので、飛ばした変更は**その行が再編集されるまで
  二度と届かない**（無音の恒久欠落）
- **書き込みに失敗した受信より先へカーソルを進めない。** 適用はトランザクションを
  張っていない（材料・手順は delete → insert）ので、途中で落ちると欠けたまま残る。
  進めなければ次の pull でやり直せる（同時刻の再適用は LWW が同値で通す）
- **カーソルに payload の版を持たせる。** 自分より新しい版は読み飛ばす仕様なので、
  版が上がったら 0 から取り直して読み飛ばした分を拾う
- **一時障害では送信待ちを捨てない。** HTTP 400（内容の拒否）だけを `SERVER_REJECTED`
  として捨て、502/504/HTML 応答（Railway の再デプロイ中）は捨てずに残す。
  ここを一緒くたにすると、再デプロイ中にたまたま同期した端末の編集が丸ごと消える
- **削除の時刻は「消した時刻」**（`sync_queue.queued_at`）を使う。送信時刻にすると、
  オフライン中の削除が、その後に他端末がした更新に勝ってしまう
- **ピン留め（作りたいリスト）は同期しない。** 人ごとの都合であるうえ、ピンで
  `updated_at` を進めるとブックマーク 1 タップがレシピ丸ごとのスナップショットを
  LWW で勝たせ、オフライン端末のピン 1 回で他端末の編集が巻き戻る
- **共有中の帖は受信 tombstone で消さない。** 共有の鍵（`share_delete_token`）は
  共有した端末のローカル行にしか無く、消すと**公開中のページを二度と止められない**。
  先に停止（revoke）を試み、止められたときだけ削除する
- **共有・停止では `updated_at` を触らない。** 帖の内容の変更ではないのに LWW の
  時計だけが進み、しかも同期に積まないのでサーバーと片方向に食い違う
- **編集でも出所（`sources`）を引き継ぐ。** URL 取り込みのレシピを一度編集すると
  新リビジョンの `source_id` が消え、受信側で Web 共有の出所ゲートが外れて
  他人のサイト由来のレシピを公開できてしまっていた
- **カーソルを 0 から取り直すときは自端末由来も適用する。** バックアップ復元後は
  ローカルが古いのに、サーバーは自分の古い push を LWW で捨てるため、
  取り直さないと**その端末だけ永久に食い違う**
- **push は待ち行列が空になるまで繰り返す**（1 回 200 件・最大 20 バッチ）。
  1 バッチで止めると、蔵書の多い端末の参加直後に一部だけ家族に見える状態が続く
- **push トークンは DB（app_meta）に残さない。** app_meta はバックアップ・移行 ZIP に
  入るので、端末へ通知を送れるトークンが端末外に出てしまう。起動ごとに 1 回登録する
- **端末の表示名をサーバーへ送らない。** サーバーは返しもしないので使い道が無く、
  「サーバーに個人情報を置かない」（§2）に反するだけだった

### 5-1c. S1 検証ゲート（2026-08-22 実施・通過）

**実機 Pixel 9a ＋ エミュレータ**（と、先行してエミュレータ 2 台）で一気通貫を確認した。
サーバーはローカル（`PORT=3210`）＋ docker の PostgreSQL（`daidoko-sync-pg` / localhost:5433）。

実機側で追加に確認できたこと:

- **まっさらな実機**（Play 版をアンインストールした状態でローカルビルドを新規インストール）に、
  家族グループへ参加した他端末の**蔵書が丸ごと届く**（レシピ 5・帖 1・タグ）。
  実機には元データが 1 件も無いので、**表示されたものは全部同期で届いたもの**
- **実機で作ったレシピ（`PIXELSYNC` / 材料 `PIXELTOFU` / 手順 `MIXONPIXEL`）が他端末に現れる**
- サーバー側のグループを消した端末が、次の起動で **401 から「未参加」へ自己修復**して
  招待コードで入り直せる（`GET /me` 401 → `POST /groups/join` → 全件 push → pull）
- 写真は実機にも渡らない（他端末の表紙写真は届かず、テキストだけが揃う＝ S1 の仕様）

以下はエミュレータ 2 台で確認した内容（実機でも同じ経路を通っている）。

| 確認したこと                       | 結果                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------- |
| グループ作成 → 招待コードで参加    | ○（同意ダイアログ経由・`sync_devices` に 2 台）                            |
| 参加時の全件積み直し               | ○（作成側の蔵書 5 レシピ＋帖 1 が seq 1〜6 で載った）                      |
| **A で新規レシピ → B に現れる**    | ○（`SYNCGATE`。材料 `TOFU to`・手順まで届いた）                            |
| **B で削除 → A から消える**        | ○（archived が seq 8 で伝わり、A の一覧から消えた）                        |

| 写真はローカルに留まる             | ○（A の表紙写真は A に残り、B の同じレシピには付かない＝ S1 の仕様どおり） |
| push トークンが取れない環境        | ○（登録されないまま同期は成立。通知が来ないだけ）                          |
| **変更通知（Expo Push）**          | **×（FCM 未設定のため実機でもトークンを取れない — 下記）**                 |

**検証時の落とし穴**（`.claude/skills/emulator-verify` にも追記済み）:

- **リリースビルドは平文 HTTP を遮断する**（targetSdk 28+ の既定。`localhost` も同じ）。
  ローカルサーバーへ向ける検証ビルドは `AndroidManifest.xml` に
  `android:usesCleartextTraffic="true"` を手で足してから組む（`android/` は gitignore
  対象。**検証後は必ず戻す** — 戻さないとローカル生成の release APK に残る）
- 端末 → ホストは `adb reverse tcp:3210 tcp:3210` を**端末ごとに**張る
- 実機で `input text` を使うと**日本語 IME がかなを混ぜる**（`PIXELSYNCまPIXELTOFUゆ` になった）。さらに**キーボードに隠れた入力欄を叩くと
  キーボードのキーが押される**（打鍵が別の欄に入る）。`uiautomator dump` で毎回
  bounds と `focused` を確かめてから叩くこと
- レシピの保存は**材料 1 行と手順 1 行が埋まっていないと通らない**（zod の `min(1)`）。
  エラーは画面下の「手順」節に出るので、上部の保存ボタンだけ見ていると
  「押しても何も起きない」に見える
- AQUOS は暗証番号ロックのため使えなかった（`screencap` が真っ黒になる）。今回は
  Pixel 9a で代替した。**リリース時の実機検証（リリースビルドでの通し確認）は別途必要**

**この検証で見つかった未成立: Android の変更通知（Expo Push）が飛ばない**

実機でも `expo_push_token` が登録されなかった。原因はアプリ側のコードではなく
**FCM が未設定**であること（`google-services.json` がリポジトリに無く、`app.json` にも
`android.googleServicesFile` が無い）。実機ログに次が出る:

```
W FirebaseApp: Default FirebaseApp failed to initialize because no default options were found.
I FirebaseInitProvider: FirebaseApp initialization unsuccessful
```

- **同期そのものは成立する**（起動時・フォアグラウンド復帰・書き込み後デバウンスの 3 つで動く）。
  設計どおり「通知はベストエフォート」に倒れているだけで、データは失われない
- ただし「家族が変えたら（アプリを開いていなくても）気づける」という §7 の価値は**出ない**
- 解消には Firebase プロジェクト作成 → `google-services.json` を `app.json` の
  `android.googleServicesFile` に配線 → EAS に FCM v1 の資格情報を登録、が要る。
  **利用者の Google アカウント作業を含むのでリリース前の別タスク**
  （→ §10 の未決 / [#207](https://github.com/keisato848/daidoko/issues/207)）

### 5-2. 個人/家族の行単位フラグ（2026-08-21 決定）

`shopping_items` / `pantry_items` に `shared`（0 = 自分だけ / 1 = 家族と共有）を追加する。

- **同期に乗るのは shared=1 の行だけ**（sync_queue に積むのも shared=1 のみ）。
  0→1 でサーバーへ挿入、1→0 はトゥームストーンで他端末から消す
- **グループ未参加のあいだ、このフラグは UI に出さない**（全行 shared=1 のまま・
  現行と同じ見た目 — 使わない人の画面を変えない）
- グループ参加時に一度だけ「今ある買い物リスト・在庫を家族と共有しますか？」と聞き、
  既存行を一括で倒す（後から行単位で変更可）。参加後の追加行の既定は「家族」
- レシピ・帖は v1 では**全量同期**（参加時の同意画面に明記する）。
  個人レシピの分離要望が出たら同じ機構を流用する

### 5-2b. S2 の実装方針（2026-08-22 確定・**破壊的変更ゼロ**が制約）

S2 に入る前に、設計 §5・§5-1・§5-2 に書かれていなかった穴を潰して決めた。
**上位の制約は「既に入っているデータと、いまの使い勝手を壊さない」**こと。

#### 守る約束（この 5 つを破る変更はしない）

1. **列の追加だけ**（`ALTER TABLE ADD COLUMN`）。列の削除・改名・型変更はしない
2. **同期に参加していない端末の挙動を変えない**。既定値は現行の見た目と同じになるよう選ぶ
3. **バックアップの相互互換を保つ**。古い ZIP を新しいアプリで復元でき、
   新しい ZIP を古いアプリでも復元できる
4. **S1 のプロトコルを壊さない**。レシピ・帖の payload の形は変えない
5. **サーバーの既存 API を壊さない**。追加は任意フィールドのみ

##### 3 について（実際に踏みかけた罠）

`backup.service.ts` の `replaceDatabase` は
`table.columns.map((column) => row[column] ?? null)` で **NULL を明示的に渡す**。
SQLite の `DEFAULT` は「列を省略したとき」にしか効かないので、
**`NOT NULL` 列を `BACKUP_TABLES` に足すと、その列を持たない古い ZIP の復元が丸ごと失敗する**
（1 行目の INSERT で制約違反 → ROLLBACK）。

→ **S2 で足す列はすべて nullable にし、NULL を「現行どおり」と読む**。
`shared` は `NULL = 共有する`（`shared !== 0` で判定）、
`shopping_items.updated_at` は `NULL` なら `checked_at ?? created_at` で代用する。
新しい ZIP を古いアプリで復元しても、古い `BACKUP_TABLES` は新列を読まないので無害。

#### 決めたこと

| 論点                                        | 決定                                                                                                               | 理由                                                                                                                                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`shopping_items` に `updated_at` が無い** | **v15 で nullable 追加＋バックフィル**（`COALESCE(checked_at, created_at)`）。以後すべての UPDATE 経路でセットする | LWW の基準が無いと同期そのものが成立しない。`checked_at` はチェックを外すと NULL に戻るので代用不可                                                                                       |
| **`shared` フラグの判定場所**               | **enqueue は無条件**。payload を組むときに `shared = 0` なら **tombstone** を送る                                  | 設計 §5-2 の字面（「積むのも shared=1 のみ」）だと **1→0（共有をやめる）が送れず、他端末に残り続ける**。組み立て時なら「行が消えた」と「共有をやめた」を同じ形で扱え、判定も 1 箇所で済む |
| **数量のデルタ同期**                        | **S2 を 2 段に分ける。今回（S2-A）は数量も LWW**。デルタは S2-B へ                                                 | 下記の「なぜ 2 段か」を参照                                                                                                                                                               |
| **`jan_catalog` / `store_group_aliases`**   | **同期する**（設計 §5 の表に無かったが追加）                                                                       | `shopping_items.store_group` だけ同期されて対応表が端末ごとに別、バーコードで覚えた名前が片方にしか無い、という半端な状態になる                                                           |
| **買い物の即時通知 vs 5 分デバウンス**      | 買い物・在庫を含む push は**デバウンス窓を短くする**（1 分）。レシピは 5 分のまま                                  | 「片方が買ったら伝わる」が買い物リストの価値そのもの（§9）。通知の中身は変えない（§0-2）                                                                                                  |
| **2 端末で同じ「牛乳」を足したとき**        | **v1 では 2 行のまま**。名寄せ統合はしない                                                                         | 別 id の行を機械的に 1 つへ畳むと、片方の数量・店・期限が消える。**消えるより並ぶ方がまし**                                                                                               |
| **payload の版**                            | **2 へ上げる**                                                                                                     | 段階的公開で版が混ざったとき、古い端末が新種別を読み飛ばしたまま**カーソルだけ進んで二度と届かない**のを防ぐ。版を上げれば更新時に 0 から取り直して拾い直す（行の再適用は LWW で冪等）    |

#### なぜ数量デルタを 2 段目にするか

#199 の決定（数量はデルタ同期）は変えない。**順序だけを変える。**

- デルタは**再生すると二重に足し引きされる**。S1 で決めた「バックアップ復元後はカーソルを 0 に
  戻して全件取り直す」（§5-1b）と正面から噛み合わない。行の LWW は再適用しても同値なので
  無害だったが、`+2` `−1` は違う
- 絶対値の上書き（`updatePantryItem({quantity: 3})`）とデルタが同じ列に同居するので、
  「どちらが権威か」を決めないと、あとから来た絶対値がデルタを踏み潰す
- つまりデルタは**それ自体が独立した設計問題**で、S2 の他の部分（行の同期・shared フラグ）と
  混ぜると、どちらの不具合か切り分けられなくなる

**S2-A（今回）**: 行を LWW で同期する。数量も行の一部として LWW で運ぶ。
→ **同時に別々の端末で「1 個使った」を記録すると、片方の減算が失われる**（5→4 と 5→4 で 4。
正しくは 3）。これは既知の割り切りとして残す。家族が同時刻に別々の端末で在庫を減らす頻度は
低く、失われても**在庫の数がずれるだけ**で、レシピや記録は壊れない。

**S2-B（確定・§5-3）**: 数量を行 payload の権威から外し、`quantity_base`/`quantity_epoch` と端末ごとの `pantry_quantity_parts` に分ける。payload 版 3。復元・冪等性・絶対値との合流は §5-3-4 / §5-3-2 を参照。

**S2-A だけでもリリースできる**形にしてある（数量がずれても壊れない）。S2-B を同じリリースに
含めるかは、S2-A の実機検証が終わってから判断する。

#### 同期するエンティティ（S2-A）

| entityType          | 何を運ぶか                                                                                 | 削除                 |
| ------------------- | ------------------------------------------------------------------------------------------ | -------------------- |
| `shopping_item`     | 名前・正規化名・分量・チェック状態・出所・並び順・買う場所・**数量ではない**・`updated_at` | 物理削除 → tombstone |
| `pantry_item`       | 名前・正規化名・**数量**・単位・しきい値・JAN・置き場所・期限                              | 物理削除 → tombstone |
| `name_alias`        | 正規化名 → 正規食材名                                                                      | 物理削除 → tombstone |
| `jan_catalog`       | JAN → 名前・単位                                                                           | 削除経路なし         |
| `store_group_alias` | 店名 → 買い物グループ                                                                      | 物理削除 → tombstone |

`shopping_items.recipe_id` は当初 payload に**含めなかった**（受信側に無いレシピを指すと
外部キーで落ちる）。**2026-08-26 に「あるときだけ繋ぐ」形で足した**:

- 送信側は素直に `recipeId` を載せる
- **受信側は手元にそのレシピがあるときだけ設定する**（`localRecipeIdOrNull`）。
  無ければ null。**品目が丸ごと入らないより、レシピへ飛べない方がまし**
- 更新経路では**解決できたときだけ書く**。解決できないからといって、
  既に繋がっている行を切らない（送信元にあってこちらに未着なだけのことがある）
- **`SYNC_PAYLOAD_SCHEMA_VERSION` は 3 のまま上げない。** `parseSyncPayload` は
  自分より新しい版を**丸ごと捨てる**ので、v4 にすると公開済みの 1.11.0（v3）で
  **買い物の変更が 1 件も届かなくなる**。zod は非 strict なので、古い端末は
  知らないキーを無視して残りを適用する。版を上げるのは
  「古い端末に解釈させては困る」破壊的変更のときだけ
  `created_by` / `checked_by` も運ばない（全端末で `user-kei` 固定なので区別が付かない — §5-1b と同じ理由）。

### 5-2f. AI 由来の印を運ぶ（#266・2026-09-01）

**`recipe` payload のトップレベルに `aiGenerated?: boolean` を足した。**
`urlImported` の隣で、性質もほぼ同じ（レシピ単位・省略可・単調に立つだけ）。

- **`SYNC_PAYLOAD_SCHEMA_VERSION` は 3 のまま。** 上の規則どおり、省略可の追加は
  破壊的変更ではない。上げると公開済みの端末がレシピを 1 件も受け取れなくなる
- **送信は真のときだけ**（`...(recipe.aiGenerated === 1 ? { aiGenerated: true } : {})`）。
  `false` を送っても意味が無いうえ、受信側に「AI ではないと確かめた」と誤解する余地を作る
- **受信の `set` にも、立つときだけ含める。**
  ここが肝心で、素直に `aiGenerated: payload.aiGenerated ? 1 : null` を `set` に書くと、
  **印を知らない古い端末が `aiGenerated` の無い payload を後勝ちで送ってきたときに印が潰れる。**
  `pinnedAt` を `set` から外しているのと同じ考え方（受信で消さない列）
- 回帰テストは `sync-payload.test.ts` の「AI 由来の印（#266）」と
  `recipe-update.test.ts` の「false を明示的に渡しても印は下がらない」

**なぜリビジョンではなくレシピ単位か**は `docs/レシピ表紙AI生成設計.md` §4-1。
要点だけ書くと、「編集しても落とさない」印なので、編集のたびに新しい行を作る
リビジョンに置くと引き継ぎを書き忘れた瞬間に消えるため。レシピ単位にしたことで、
**リビジョンの行ごと LWW で旧端末の後勝ちによりバッジが表示上消える**副作用も消えている
（これは #266 固有ではなく、行ごと LWW・フィールド単位マージをしないという
この同期設計が最初から持っている性質。材料も手順も同じ）。

### 5-2c. S2 検証で見つけた欠陥（2026-08-22・実機/エミュレータ）

#### D1. 参加プロンプトが家族の買い物リストと在庫を消していた（データ損失）

**再現**（エミュレータ2台・ローカルサーバ）:

1. 端末 A に買い物1件・在庫2件がある状態でグループ作成 → 「共有する」を選ぶ → サーバーに 3 件が載る
2. 端末 B が招待コードで参加 → 参加処理の中で A の 3 件を pull（B のローカルに入る）
3. B が参加プロンプトで**「自分だけにする」**を選ぶ
4. → B のローカル**全行**が `shared = 0` になる。**A から降りてきた 3 件も含まれる**
5. → 共有をやめた行は push 時に tombstone になるので、A の 3 件がサーバーで墓標化
6. → **A の買い物リストと在庫が空になった**（実機の画面で確認）

**原因**: `askShareExistingItems()` を参加処理の**後**に呼び、`setAll*ItemsShared()` が
無条件に全行を更新していた。「いまある品目」に他端末由来の品目が混ざる。

**副次の穴**: 参加してから聞くので、「自分だけ」を選んでも**一度サーバーへ出てしまう**
（`onSyncGroupJoined` が全件を送信待ちへ積んだ後に答えを聞いていた）。

**直し方（2 段構え。どちらか片方では不十分）**:

| 直し                                         | 何を防ぐか                                                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **参加より先に聞き、答えを反映してから参加** | 「自分だけ」の品目がサーバーに一度も出ない（`listRowSyncableEntities` が共有中の行だけ返すため） |
| **対象を `shared IS NULL` の行だけに限る**   | 他端末から降りてきた行（`shared` 決定済み）を巻き込まない。離脱→再参加でも同じ                   |

関数名も `setAll*ItemsShared` → `setUndecided*ItemsShared` に変えた（「全部」を触る関数を
残すと同じ事故が再発する）。新規作成行は `shared` が NULL のままなので、次に聞かれたときの対象になる。

#### ⚠ ダイアログを差し替えるときの注意（PR #210 でアプリのデザインへ統一済み）

参加プロンプト（`askShareExistingItems`）は**「答えを待ってから参加する」ことが安全装置**であり、
見た目の話ではない。`await askShareExistingItems()` → `joinSyncGroup()` の順序が D1 を防いでいる。

**2026-08-23 に `dialog.confirm()`（`docs/画面設計.md` §7）へ移した。** 移し方と、次に触る人が
守るべき条件:

| 守ること                                              | 理由                                                                                                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **答えが返るまで await する**                         | state を立てて即 return する形にすると、答える前に参加処理が走り D1（家族の買い物リストと在庫が消える）が復活する。`dialog.*` は Promise なのでそのまま待てる |
| **「共有しない」を第 1 ボタン（キャンセル側）に置く** | §7-2 で背景タップ・戻るキーは**第 1 ボタン**に倒れる。ここを逆にすると、確かめないまま手元の品目が家族へ出る                                                  |
| **§5-2e の #2 と #4 を 2 台で取り直す**               | 順序が守られたことは単体テストでは示せない（`dialog.service` を mock すると、待たない実装でも緑になる）                                                       |

`Alert.alert` の `cancelable: false` に相当するものは `dialog.*` には無い。閉じられること自体は許し、
**倒れる先を安全側（共有しない）にする**ことで同じ安全性を得ている。ホスト（`DialogHost`）が
画面に居ないときも `confirm` は `false` を返すので、やはり共有されない側に倒れる。

#### 併せて直したこと

参加時に**待ち行列を捨ててから**積み直すようにした（`onSyncGroupJoined`）。参加より先に
「自分だけ」を選ぶと、その時点で待ち行列に id が積まれる。捨てないと、共有しないと決めた
品目の id が墓標としてサーバーへ出てしまう。

#### 離脱時に `shared` を NULL に戻さない理由

「離脱したら決定も無効」に見えるが、**戻すと D1 が別経路で復活する**。離脱→同じグループへ
再参加した端末には、以前 pull した家族の品目が残っている。NULL に戻すとそれらも
「まだ決めていない」に化け、「自分だけ」を選んだ瞬間にまた墓標になる。
離脱後も決定を保持するのが安全側。

#### 学び

- **参加直後に一度だけ聞く UI は、pull より前に聞く。** 後に聞くと「いまある品目」の定義が
  「自分のもの」から「自分のもの＋他端末のもの」に変わってしまう
- 一括更新は「全部」ではなく**まだ決めていないもの**を対象にする。決定済みを触らないという
  制約が、離脱→再参加のような後から出てくる経路も同時に守る
- この欠陥はテストが全部緑のまま入っていた（サービス層は動的 import で jest から触れない）。
  **2 台の実機/エミュレータで実際に参加させないと出ない**類の不具合

**D2: 前のグループの持ち分が残り、あとから届いた品目の数量が端末ごとに食い違う（2026-08-24 実機で検出・同日修正 #213）**

**症状**: 家族の 1 人だけ在庫の数が違う。同期しても直らず、増減すると差が open したまま平行に動く。

実機 2 台（AQUOS = グループ作成者 / Pixel = あとから参加）＋本番サーバーで再現した:

|                              | RiceA            | SaltA |
| ---------------------------- | ---------------- | ----- |
| サーバー（`base + Σ持ち分`） | 2                | 4     |
| Pixel                        | 2                | 4     |
| **AQUOS**                    | **0** ← 食い違い | 4     |

- RiceA は **Pixel が参加時に持ち込んだ品目**（サーバー上は `quantityBase=2`・持ち分なし）
- SaltA は最初から AQUOS にあり、行と持ち分が一緒に動いたので**全端末で一致**（同時減算でも一致・上の表）
- コールドスタートしても直らない。AQUOS で「＋」を 1 回押したら、送られた持ち分が **`net=+2`**
  （`+1` ではない）だった。`effectiveDelta(raw, +1) = +2` になるのは `raw = −1` のときだけなので、
  **AQUOS のローカルは raw = −1**、サーバーの 2 より**ちょうど 3 低い**

**原因（コードから）**: `pantry_quantity_parts` は**行が消えても残る**。

- `onSyncGroupLeft` はキューとカーソルしか消さない（持ち分は「状態なので持ち越す」のが §5-3 の設計）
- 行が無いのに持ち分だけ残っている状態＝**孤児の持ち分**を掃除する経路が無い
- `applyPantryItem` の**新規挿入の経路**は、受信した `quantityBase` を入れたあと `rematerialize` を呼ぶ。
  ここで孤児の持ち分が Σ に入り、**受信 base が既に反映済みの消費をもう一度引く**

持ち分が行と一緒に動いているかぎり冪等（SaltA が一致したとおり）だが、
**行だけが別経路で戻ってきたときに二重計上になる。**

**直した内容**: `deleteOrphanParts()`（`pantry-quantity-db.ts`）を新設し、
**グループの境目**で行の無い持ち分を捨てる。呼ぶのは 3 か所:

| 呼ぶところ            | 理由                                                       |
| --------------------- | ---------------------------------------------------------- |
| `onSyncGroupJoined`   | 前のグループから持ち込ませない（作成も参加もここを通る）   |
| `onSyncGroupLeft`     | 離脱の時点で捨てる。次にどのグループへ入っても残っていない |
| `onLocalDataReplaced` | 復元で行が入れ替わり、前の中身の持ち分が孤児として残る     |

**セッションの途中では呼ばない。** `applyPantryQuantity` は行が無くても持ち分を upsert する
（§5-3-3「持ち分が行より先に届く」窓）ので、途中で掃除するとその正常な順序を壊す。
境目で捨ててよいのは、**行の無い持ち分はそもそも送信対象に入らない**から
（`listRowSyncableEntities` は共有中の行がある品目の持ち分しか積まない）——持ち越して得をする場面が無い。

**残る狭い穴**: 同じグループの中で「持ち分だけ届いて行が永久に来ない」状態が続き、
そのあとで行だけが届くと二重計上は起こりうる。境目を越えないので実害は小さいと判断して今回は見送った。

**回帰の押さえ**: `sync-runner.service.test.ts` の「グループの出入り」3 ケースで
`deleteOrphanParts` が呼ばれることを assert している（DB 層は jest から実行できないため、
呼ばれているかだけを機械で押さえ、値の正しさは実機で見る — `docs/品質基準.md` §2.3）。

**実機で確かめたこと（2026-08-24・AQUOS・本番サーバー）**: 直す前と同じ条件を API で組み立てた。

| 確かめたこと                                                            | 結果                                                 |
| ----------------------------------------------------------------------- | ---------------------------------------------------- |
| グループ作成が通る（`deleteOrphanParts` が実 SQLite で落ちない）        | 通った。**ここが最大のリスクだった**                 |
| 持ち分だけ届いた品目 X を抱えたまま、削除 → 別グループ作成 → 行だけ届く | **2**（＝受信 base どおり。直す前は 0 に見えていた） |
| 同じセッションで「持ち分 → 行」の順に届く品目 Y                         | **2**（順序の窓を壊していない）                      |

**落とし穴（次に検証する人へ）**:

- `scripts/agent/build-android.mjs` の `--arch` 既定は **arm64-v8a**。x86_64 エミュレータに
  そのまま入れると**インストールは成功して起動時に落ちる**（`libreactnative.so` が見つからない）。
  エミュレータ用は `--arch x86_64` で作り直す
- **Pixel には `daidoko://` を横取りする別アプリが入っている**。実機では deep link を使わず、
  `monkey -p com.daidoko.app` で起動して画面をタップで辿る
- **Wi-Fi 経由の adb（`adb connect IP:5555`）では `adb reverse` が中継しない**（Pixel 9a で再現。
  端末側の `nc 127.0.0.1 3210` は接続を受け付けるのに何も返らず、参加ボタンが 20 分以上
  「処理中」のまま固まった）。実機を無線でつなぐときは **PC の LAN アドレスを焼き込む**
  （`EXPO_PUBLIC_SERVER_URL=http://192.168.0.XX:3210`・Windows のファイアウォールは node を通していた）。
  USB なら reverse で足りる
- 無線 adb は端末が Wi-Fi を落とすたびに `offline` になり、**IP も変わる**（.46 → .216 → .84）。
  `ForEach-Object -Parallel` で 5555 番が開いている IP を総当たりすれば 1 秒で見つかる
- **横向きに持たれているとキーボードが全画面モードになり `input text` が入らない**。
  `settings put system accelerometer_rotation 0` で縦固定してから打つ（終わったら戻す）
- 日本語 Gboard は `input text` の英字を**未確定（下線）**で入れる。候補バー（y≈1517）をタップして確定してから次へ
- 利用者の端末なので**操作の衝突**が起きる。検証は「5 分触らないで」と宣言してから一気に通す
- 同期の fetch に **30 秒の上限**を入れた（この固まりで見つけた）。上限が無いと、応答の無い経路で
  UI が永久に「処理中」になる

### 5-3. S2-B 数量デルタ同期（確定・2026-08-22）

**解く問題**: 2 台が同時に「卵を 1 個使った」と記録すると、行 LWW では 5→4 と 5→4 が競合して 4 になる（正しくは 3）。数量の増減を全端末で収束させる。

**結論（一行）**: 数量の増減は「操作ログ」ではなく、**端末ごとの累計増減（持ち分 = part）を 1 行の状態として既存の行 LWW に載せる**。
`pantry_items.quantity`（表示値）は `quantity_base + Σ parts.net` から**導出**する。part は書き手が 1 台だけなので LWW が競合せず、状態なので何度再適用しても同じ値 → カーソル 0 の取り直し・復元・版更新で二重計上が**構造的に**起きない。サーバーの `sync_deltas` 表は使わない（書き手を作らない）。サーバーの必須変更はゼロ。

**3 案の審査から取り込んだもの**（案 0 を土台に）:

| 出所           | 取り込んだもの                                                                                                                                                                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 案 1           | 起動時の再導出（`rematerializeAll`）で実体化値を自己修復する。決定的 ID（part の entity_id）。「raw ≠ 表示値なら差を埋める」の規則（set ではなく δ で）                                                                 |
| 案 2           | 合算経路で `updated_at` を進めるのは他列が実際に変わったときだけ。判断部分を純関数へ寄せて jest で固定                                                                                                                  |
| 審査（致命点） | ①バックフィルが実体化値から base を作って二重計上する → **「v16 未移行」の印を `quantity_epoch IS NULL` で持ち、実体化値を基準にしない**                                                                                |
| 審査           | ②参加時の epoch 繰り上げが家族の減算を消す → **参加・再参加では epoch を上げない**（上げるのは 0→1 の真の遷移と絶対値セットだけ）                                                                                       |

#### 5-3-0. 用語と不変条件

| 用語         | 意味                                                                                                                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **base**     | `pantry_items.quantity_base`。その品目の「ベースライン」。作成時の数量、または共有を始め直した／数え直した時点の数量                                                                                 |
| **epoch**    | `pantry_items.quantity_epoch`。ベースラインの世代。**ミリ秒の整数**（作成時は `Date.parse(createdAt)`、繰り上げ時は `max(前 + 1, now)`）。**NULL = v16 未移行**（`quantity` をそのまま base と読む） |
| **part**     | `pantry_quantity_parts` の 1 行 = `(item_id, device_id)` ごとの累計増減 `net` と、それがどの `epoch` の持ち分か                                                                                      |
| **raw**      | `(base ?? 0) + Σ net（part.epoch == 行 epoch のものだけ）`。base が NULL かつ part が無ければ NULL（＝数量未管理）                                                                                   |
| **実体化値** | `pantry_items.quantity` = `raw == null ? null : max(0, raw)`。表示・在庫判定・残量通知・バックアップはこの列を従来どおり読む                                                                         |
| **繰り上げ** | base := raw、epoch := 新しい値、その品目のローカル part を全削除、`updated_at := now`、行を送信待ちへ。0→1 と絶対値セットだけが行う                                                                  |

不変条件:

- **I1** 行 `quantity` は導出値。書くのは `rematerialize(itemId)` だけ（`updated_at` を触らず、`sync_queue` に積まない）
- **I2** 数量だけの変更は行の `updated_at` を進めない（§5-1b ピンの教訓）。例外は「part に載せない経路」（未参加・自分だけ）で、これは現行どおり
- **I3** part の entity は `(item, device)` で**単一書き手**。entity_id = `${itemId}:${deviceId}`（UUID 36 + `:` + base64url 22 = 59 字）
- **I4** part の `updated_at` は端末内で単調（`max(前の値 + 1ms, now)`）。時計を戻しても自分の part が自分に負けない
- **I5** base と epoch を書くのは「作成」「繰り上げ」「受信した行からの採用」の 3 つだけ。epoch は下がらない
- **I6** `quantity_epoch IS NULL` の行に part を書く前に必ず `ensureBaseline(行)`（epoch := `Date.parse(updated_at)`、base := `quantity`）。**base は実体化値から作り直さない**（NULL 判定の印は epoch。quantity から base を再生成する経路は移行・復元直後の epoch NULL 行に限る）

#### 5-3-1. モバイルのデータモデルと復元（答え 1）

**schema v16**（`migrate.ts` の `CURRENT_SCHEMA_VERSION` を 16 に。`CREATE TABLE IF NOT EXISTS`・`ADD COLUMN` のみ。既存列の型変更・NOT NULL 化・表の作り直しは無し）

新表 `pantry_quantity_parts`（外部キー無し — 行が part より**後の seq** で届くことがある。§5-2d S1 の「負けた push の seq 採り直し」で行の seq が後ろへ動くため）:

| 列           | 型      | 備考                                                                 |
| ------------ | ------- | -------------------------------------------------------------------- |
| `item_id`    | TEXT    | PK の一部                                                            |
| `device_id`  | TEXT    | PK の一部。同期の deviceId（secure-store。バックアップに入らない値） |
| `net`        | REAL    | nullable。NULL = 0。この端末がこの品目に加えた累計増減               |
| `epoch`      | INTEGER | nullable。NULL = 0。どの世代の持ち分か                               |
| `updated_at` | TEXT    | nullable。part の LWW 基準（I4 の単調スタンプ）                      |

索引 `idx_pantry_quantity_parts_item (item_id)`。**以後この表に足す列も nullable のみ**（`replaceDatabase` の `?? null` 束縛のため — §5-2b 約束 3 と同じ規律）。

`pantry_items` に追加（`ADD_COLUMN_MIGRATIONS`）:

| 列               | 型      | 意味                                                                                      |
| ---------------- | ------- | ----------------------------------------------------------------------------------------- |
| `quantity_base`  | REAL    | nullable。NULL = 数量未管理（epoch が非 NULL のとき）／v16 未移行（epoch が NULL のとき） |
| `quantity_epoch` | INTEGER | nullable。**NULL = v16 未移行**。非 NULL なら base が権威                                 |

**ベースライン化 `ensureQuantityBaseline()`**（JS で実行。`Date.parse` の結果を全端末で一致させるため SQL の `julianday` は使わない）:
`quantity_epoch IS NULL` の行だけ → `quantity_epoch := Date.parse(updated_at)`（NaN なら 0）、`quantity_base := quantity`。
**走らせる場所は 3 つ**: v16 移行時（`runMigrations`）・バックアップ復元直後（`replaceDatabase` の後、`rebuildFts` と同じ場所）・`onLocalDataReplaced`。条件が epoch NULL なので、v16 以降に作られた／受信した行（必ず epoch を明示して書く）は**二度と触らない**。審査①の経路（他端末の part が届いて実体化された 2 を base に焼き付ける）は、その行の epoch が既に非 NULL なので起きない。

**起動時 `rematerializeAll()`**: epoch 非 NULL の全行を `base + Σ` で再実体化（数百行・数 ms）。part の upsert と quantity の UPDATE が 2 文で、間でアプリが落ちても次の起動で直る（案 1 の `rederiveAll` を採用）。

**復元 — `BACKUP_TABLES` に入れる**（`backup.service.ts`）:

- `pantry_items` の columns に `quantity_base`, `quantity_epoch` を追加（nullable なので `defaults` 不要）
- `pantry_quantity_parts` を `optional: true` で追加（旧 ZIP にキーが無ければ 0 件）
- `sync_queue` を同一トランザクションで捨てる（R1）・`sync_cursor` を捨てる（#7）は**不変**

**入れる理由（`sync_cursor` / `sync_queue` と扱いが逆になる理由 — 隣の人が「sync 系だから捨てる」と直さないように書く）**:
`sync_cursor` は「サーバーのどこまで受けたか」という**位置**、`sync_queue` は他人の送信待ちを自分のグループへ流す**印**で、どちらも中身と無関係だから捨てる。part は `quantity` と対になる**中身そのもの**。捨てて `quantity` だけ戻すと `base + Σ ≠ quantity` になり、次に何か 1 件受信して再実体化した瞬間に表示が巻き戻る。表ごと戻せば `(quantity, base, parts)` は同じ時点の対で、復元後のカーソル 0 取り直しは「バックアップより新しい part」を LWW で上書きするだけ（自分の古い part を push してもサーバー LWW に負けて seq だけ採り直され、pull で新しい方が降りる）。表名を `sync_*` にしない（`pantry_quantity_parts`）のもこの区別のため。

**互換**: 旧 ZIP（列も表も無い）→ part 0 件・epoch NULL → 復元直後のベースライン化で `quantity` を base に → 現行どおり。新 ZIP を旧アプリで → 旧 `BACKUP_TABLES` は新列・新表を読まない → 無害（§5-2b 約束 3）。

#### 5-3-2. 送信 — 何を part（デルタ）にし、何を行（LWW）に載せるか（答え 2）

**規則**: 数量の「差」は、参加中かつ `shared ≠ 0` の行ならすべて自端末の part へ。数量以外は従来どおり行 LWW。行 payload から数量の**権威**を外す（base/epoch を運ぶ。`quantity` は目視用）。

新設 `adjustPantryQuantity(id, δ)`（`pantry.service.ts`。**`updatePantryItem` の patch 型から `quantity` を削除**し、呼び手を全部こちらへ）:

```
row = 読む; ensureBaseline(row)
parts = この品目の part で epoch == row.epoch のもの
raw = (base ?? 0) + Σ net   （base NULL かつ part 無しなら NULL）
displayed = raw == null ? null : max(0, raw)
target = max(0, (displayed ?? 0) + δ)
if (raw != null && target == displayed) return        // 見た目が変わらないタップは書かない
effective = target − (raw ?? 0)                       // raw が負なら「+」1 回で表示値+1 まで埋める（審査④）
if (資格情報あり && row.shared != 0):
    own = part(id, myDevice)
    net = (own && own.epoch == row.epoch ? own.net : 0) + effective   // epoch 不一致なら 0 から（審査③）
    upsert part(net, epoch=row.epoch, updated_at=max(own.updated_at+1ms, now))
    enqueueSyncEntity('pantry_quantity', `${id}:${myDevice}`)
    // 行は積まない・updated_at も進めない（I2）
else:
    base := (base ?? 0) + effective; updated_at := now   // 未参加・自分だけ = 現行の絶対値更新と同じ挙動
    enqueueIfShared(id, shared)                           // shared=0 なら積まない（R8）
rematerialize(id)
```

UI から**絶対値を渡さない**（`pantry.tsx` の `handleAdjust` は React の `item.quantity` が pull 直後に古いことがある。δ だけ渡し、現在値は service が DB から読む）。

| ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **±ボタン** `pantry.tsx handleAdjust`                                                                       | `adjustPantryQuantity(item.id, ±1)`。楽観表示は従来どおり、`refresh()` で DB の実体化値に揃う                                                                                                                                                |

| **共有 1→0**                                                                                                | base := raw に畳む・ローカル part 全削除・epoch はそのまま（次の 0→1 で上がる）・tombstone（従来）                                                                                                                                           |

#### 5-3-3. 受信 — part の適用と行 LWW の共存（答え 3）

**`pantry_item` payload（版 3）**: `quantity`（実体化値・目視用）は残す。`quantityBase?: number | null` と `quantityEpoch?: number` を足す。**送信側は必ず解決して書く**（`quantityBase = epoch == null ? quantity : quantity_base`、`quantityEpoch = epoch ?? Date.parse(updatedAt)`）。受信側の互換判定は **`quantityEpoch` が数値か**（v2 payload は未定義）。`SYNC_PAYLOAD_SCHEMA_VERSION = 3`（全端末が一度カーソル 0 から取り直す）。

**`pantry_quantity` payload（新）**: `{ schemaVersion: 3, entity: 'pantry_quantity', item: { id: '<itemId>:<deviceId>', itemId, deviceId, net, epoch, updatedAt } }`。`item.id` を封筒の `entityId` と一致させるので `applyIncomingChange` の既存チェック（`payload.item.id !== change.entityId`）がそのまま効く。`isRowEntityType` / `SYNC_ENTITY_TYPES` に追加。

**行の適用 `applyPantryItem`**（`sync-row-entities.service.ts`）:

```
inEpoch = item.quantityEpoch ?? Date.parse(item.updatedAt)          // v2 互換: 旧端末の行は「その時刻の世代」
inBase  = item.quantityEpoch == null ? item.quantity : item.quantityBase
local = 読む（updatedAt, shared, base, epoch）
if (local && local.shared == 0) → skipped                             // §5-2d #3/#4 不変
if (!local):
    INSERT（base=inBase, epoch=inEpoch, shared=1, 他列）→ rematerialize（保留 part のうち epoch==inEpoch を足す）
else:
    ensureBaseline(local)
    lwwWins  = incomingChangeWins(item.updatedAt, local.updatedAt)
    adoptQty = inEpoch > local.epoch || (inEpoch == local.epoch && lwwWins)
    if (!lwwWins && !adoptQty) → skipped
    UPDATE { lwwWins ? 他列 + updatedAt : {} , adoptQty ? {base: inBase, epoch: inEpoch} : {} }   // shared は書かない
    if (inEpoch > local.epoch) DELETE parts WHERE item_id = id AND epoch != inEpoch              // 審査③
    rematerialize
→ applied
```

要点: **base/epoch の採用は行 LWW から独立**。繰り上げ（epoch が大きい）は、別端末の「名前だけ直した新しい行」に負けない。逆に epoch の古い行が名前で勝っても base/epoch は動かない。同 epoch 内で base が違うのは「未参加・自分だけの δ」と合算以外に無く、そこは行 LWW に従う。

**v2 行の意味**: 「旧端末が見ていた絶対値 q を、その行の `updatedAt` を世代にしたベースライン」と読む。旧端末の q が新しければ全端末で q に揃う（v3 端末の part は epoch 違いで除外 = 混在期間の LWW 品質の損失）。v2→v3 に更新した端末の移行ベースライン（epoch := `Date.parse(updated_at)`、base := quantity）と**同じ値**になるので、更新後に端末間で食い違わない。

**part の適用 `applyPantryQuantity`**:

```
(itemId, deviceId) = payload; local = 行を読む
if (local && local.shared == 0) → skipped（保存もしない）
existing = part(itemId, deviceId)
if (existing && !incomingChangeWins(part.updatedAt, existing.updated_at)) → skipped
upsert part(net, epoch, updated_at)                // 行が無くても保存（行が後から来る）
if (local) { ensureBaseline(local); rematerialize(itemId) }
→ applied
```

Σ は `epoch == 行 epoch` で絞るので、まだ行が来ていない新 epoch の part も、離脱端末の古い part も、保存するだけで効かない。

**tombstone**: `pantry_item` の tombstone → 行削除＋その品目の part 全削除（既存の `shared = 0` ガード・LWW 判定は不変）。`pantry_quantity` の tombstone は設計上送られないが、受けたら part 1 行削除→再実体化（防御）。

**`rematerialize` は `db.update` 直書き**（`pantry.service` を経由しない）。`withRemoteApply` の抑止キーは `pantry_quantity::<id>:<dev>` で、行のキー `pantry_item::<id>` は抑止されていない。service 経由で書くと行を積んで押し返しループになる。

`pullAndApply`（`sync-runner.service.ts`）は**無変更**。`result.deltas` は引き続き無視（書き手が無い）。自端末由来スキップ・カーソル 0 では自分も適用・`failed` で止める・`cursorEpoch`、すべてそのまま。

#### 5-3-4. 二重計上の防止（答え 4）

**仕組みは一つ: 操作ではなく状態を運ぶので、再適用は冪等。** 「適用済み seq の表」「seq と端末の対応」「その表を復元でどう戻すか」は**存在しない**。

- **seq と端末の関係**: seq はグループ単調の**位置**（`sync_entities` と同じ採番空間）。part の同一性は entity_id `${item}:${device}` で、seq にも端末の再参加にも依らない。カーソルをどこに戻しても、届くのは「その entity の現在値」だけ（1 entity 1 行・§5-2d S1 の seq 採り直しで古い版が後から届くことも無い）
- **適用済みの記録の置き場**: **無い**。part の行そのものが状態で、それは `pantry_quantity_parts` にあり、バックアップと一緒に戻る（§5-3-1）。復元後は `(quantity, base, parts)` が同時点の対なので、取り直しは「バックアップより新しい part を上書き」するだけ

| 経路                                                        | 何が起きるか                                                                                                                                                                                                                                               |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 初参加（端末に何も無い）                                    | 行＋全 part を pull → `base + Σ`。順序不問（行が後でも `rematerialize` で揃う）                                                                                                                                                                            |
| 離脱→同グループ再参加（新 deviceId）                        | ローカル part（自分の旧 deviceId 分・他端末分）を押す → サーバーと同値か古いので LWW で捨てられ seq 採り直し → pull で現在値。旧 deviceId の part は**永久の貢献として残る**（実際の消費）。新 deviceId の part は別 entity。**epoch は上げない**（審査②） |
| 別グループへ参加                                            | 行（base/epoch）＋**全 part**（他端末分も）を押すので、新グループの端末の Σ がこの端末と一致する                                                                                                                                                           |
| バックアップ復元（v16 以降の ZIP）                          | part も戻る → 全件 push（古い part は負ける）→ pull で新しい part が降りる。途中で落ちても次の同期が同じことをやり直すだけ                                                                                                                                 |
| バックアップ復元（v15 以前の ZIP）                          | part 0 件・epoch NULL → 復元直後にベースライン化（base := quantity・epoch := `Date.parse(updated_at)`）→ pull で行（同 epoch なら LWW・新 epoch なら採用）と全 part が降りる。ZIP の quantity は pre-v16 の LWW 絶対値で part を含まないので二重にならない |
| payload 版更新（2→3）                                       | カーソル 0 → 全件取り直し。行は LWW 同値で冪等、part は状態で冪等。自分の tombstone が戻る #3b は既存ガードで止まる                                                                                                                                        |
| push 応答の喪失                                             | 印が残り再送。サーバー LWW で同値以上なら seq 採り直しだけ                                                                                                                                                                                                 |
| ページ境界で同じ part が二度返る                            | 同値 → `incomingChangeWins` の `>=` で upsert（同じ値）                                                                                                                                                                                                    |
| 復元中に走っていた同期（§5-2d #6）                          | `cursorEpoch` がそのまま効く                                                                                                                                                                                                                               |
| #209 で端末が整理され新 deviceId で入り直す                 | `sync_entities` は端末行に外部キーを持たないので part は消えない。上の「再参加」と同じ                                                                                                                                                                     |
| 1→0→1 を**した端末**と**していない端末**の組（審査③の経路） | 繰り上げた行を受けた端末は当該品目のローカル part を全削除。万一残っても adjust 時の epoch 不一致で net を 0 から始める。サーバーに残る旧 epoch の part は Σ から除外                                                                                      |

**なぜ op-log（`sync_deltas`）にしないか**: 未送信の `+δ` を待ち行列に持つと、「送信成功と印の削除の間」「push 応答と次の pull の間にバックアップを取った」窓で二重送信・二重適用が起きる。塞ぐには端末ごとの適用済み op 表（push 応答に seq を返す改修つき）をバックアップと一緒に戻す必要があり、§5-2d で「直しても隣が残る」と学んだ種類の状態を 1 つ増やすことになる。履歴（誰がいつ使ったか）が要件になった時点で op-log へ移る余地は残す（§5-1「要るとなったら拡張」）。

#### 5-3-5. 後から参加した端末のベースラインと、それ以前のデルタ（答え 5）

- ベースライン = 行の `quantity_base` と `quantity_epoch`。作成時の数量（epoch = 作成時刻）か、繰り上げ時の数量
- **「共有前のデルタ」は存在しない**（作成・繰り上げの時点で base に畳まれている）。参加端末は行＋全 part を seq 順に pull して `base + Σ` するだけ。row が part より後に届いても FK 無しで保存し、行が来た時点で再実体化
- 旧 epoch の part（繰り上げ前の持ち分・離脱端末の持ち分）はサーバーに残るが epoch 違いで除外。行数は品目数 × 端末数（≤ 10）で有界。同じ端末が再びその品目を触れば同じ entity_id で上書きされる
- ページング: part は小さく、`MAX_PULL_PAGES = 20` × 500 件で初回参加は足りる。足りなくてもカーソルはページごとに保存されるので次回の同期で続く（既存）

#### 5-3-6. 自分だけ（`shared = 0`）の行と part（答え 6）

- **作らない・送らない**: δ は base へ（`updated_at` も進める — 現行の絶対値更新と同じ）。`enqueueIfShared` が 0 を弾く（R8）。`listRowSyncableEntities` も `shared = 0` の行とその part を積まない。part の組み立てで行が `shared = 0` なら捨てる
- **受けない**: 受信した part は、ローカル行が `shared = 0` なら保存もしない。受信した行・tombstone が `shared = 0` を動かさない既存規則（§5-2d #3/#3b/#4）と同じ側に倒す
- **1→0**: base := raw に畳み、ローカル part を全削除、tombstone（従来）。以後この端末では base だけが動く
- **0→1**: 繰り上げ（新 epoch）。共有をやめていた間にサーバーに残った旧 epoch の part は二度と効かない。他端末はこの行を「新着」（tombstone で消していた）として受け、`base + 0`
- **参加プロンプト**（D1）: NULL→1 / NULL→0 は epoch を触らない。`revertUndecided*` も触らない
- **合算・寄せの境界**（R5）: 不変。δ は合算相手（同じ共有側）の part にだけ載る

#### 5-3-7. サーバー（答え 7）

**必須の変更は無い。** part は `sync_entities` の普通の行（entity_type `'pantry_quantity'`・payload ≈ 150 B）。`pushChanges` の LWW・seq 採番・負けた push の seq 採り直し・グループ行 `FOR UPDATE`・`clampClientUpdatedAt`・通知・レート制限（端末日次 20000。1 タップ = 最大 1 件、デバウンスで合流）はそのまま。pull 応答の `deltas: []` は互換のため残す。`sync_deltas` 表は**休眠のまま**（書き手を作らない。将来 op-log が要るときの置き場として温存）。

**任意の変更 2 行**（旧サーバーのままでもモバイルは動く — 「新経路はサーバー未デプロイでも落ちない形にする」の方針どおり。Play リリースと同時デプロイで足りる）:

### 5-4. 端末の整理と所有権の引き継ぎ（#209・2026-08-22 確定）

**問題**: クレデンシャルは secure-store だけにある（§2-2）ので、紛失・初期化・機種変更した端末は
**二度と戻らない幽霊**になる。幽霊がオーナーだと招待の再発行もグループ削除もできず、
「グループ削除＝サーバーデータ消去」というデータ削除手段の約束（§10）が果たせない。

**決めたこと**（cron を持たず、誰かの操作のついでに行う）:

| 事項                   | 値             | 動き                                                                                                                       |
| ---------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 最終同期時刻           | `last_seen_at` | pull のたびに更新。**時刻しか持たない**（何をしたかは記録しない — §0-2）                                                   |
| オーナーの引き継ぎ     | **14 日**      | オーナーが 14 日同期していなければ、最も古い生存端末へ所有権を移す。元オーナーは外さない（戻ってくればメンバーとして続く） |
| 休眠端末の整理         | **90 日**      | 90 日同期していない端末を消す（自分以外）。消された端末は招待コードで入り直せば全データが戻る（§2-2）                      |
| 端末を外す（オーナー） | 即時           | `DELETE /sync/devices/:id`。同時に招待コードを回す（外した端末が同じコードで戻れないように）                               |
| いつ整理するか         | —              | `/me`・参加・端末を外すとき。参加は定員チェックの前に整理する（幽霊が 10 台の定員を食わないように）                        |

**画面**（家族グループ）: 端末一覧を「この端末 / 端末 N」＋「最終同期: N 日前」だけで出す。
名前を持たない（§0-2）ので、利用者は最終同期の古さで幽霊を見分ける。外せるのはオーナーだけ。

**注意**: `DELETE /devices/:id` は **`/devices/me` より後ろに登録する**。Hono は登録順に照合するので、
前に置くと `:id` が `me` を食って離脱が 403 になる（テストで検出）。

## 6. 写真（Cloudflare R2）

- バケット非公開。クライアントは `POST /sync/photos/presign` で PUT/GET の署名付き URL を取得して直接転送（サーバーを太らせない）

## 7. プッシュ通知（コスト ¥0）

- **Expo Push Notifications** を採用 — アプリは expo-notifications 導入済み（タイマー・残量通知）で、追加 SDK なし・**無料・Android/iOS 両対応**。FCM/APNs 資格情報は EAS が管理
- devices に `expo_push_token` を保存（同期のたびに確認し、変わっていれば `PATCH /sync/devices/me`）
- サーバーは push 受領後に同グループの**他**端末へ送信。**中身は載せない** — 文面は
  「家族の共有データが更新されました」固定で、**利用者名も件数も種別も入れない**（§0-2 の判定。
  内容を載せると「他人が入力した情報を媒介して伝える」側に寄り、電気通信事業の判定が変わりうる）。
  当初案の「⚡ 家族がレシピを 2 件追加しました」式のダイジェストは**取り下げ**（2026-08-21）
- 文面は端末の表示言語（`sync_devices.locale`・ja/en）で選ぶ。通知の言語を選ぶためだけに持ち、
  他の用途では使わない
- **同じグループへは 5 分に 1 回まで**（サーバー内のメモリで間引く）。通知は同期のきっかけに
  過ぎないので、連続編集のたびに鳴らす意味が無い。間引いた分は次に開いたときの pull で追いつく
- 受け取った端末は通知を**同期のきっかけ**としてだけ使う（内容ではなく `data.type = 'sync'` で判別）
- 通知はベストエフォート — 届かなくても起動時・フォアグラウンド復帰の pull で追いつく（通知を同期の前提にしない）

## 10. リスクと未決事項

- **無料ユーザーの写真容量**: R2 10GB 超過後は $0.015/GB/月と安価だが、1 グループあたりの写真上限（例: 2,000 枚）をサーバー側に置くのが安全
- **サーバー障害時**: ローカルファーストなのでアプリは動き続ける。queue が溜まるだけ（上限＋古い順破棄を設ける）
- **Expo Push の信頼性**: ベストエフォート前提の設計なので致命的ではない。将来量が増えたら FCM/APNs 直叩きへ移行可能
- **未決（S1 検証で判明・2026-08-22）**: **Android の Expo Push が未設定**で変更通知が
  飛ばない。Firebase プロジェクト＋`google-services.json`＋EAS への FCM v1 資格情報の
  登録が要る。同期は 3 つのきっかけで成立するので**リリースの絶対条件ではない**が、
  「開いていなくても気づける」を謳うなら先に片付ける（§5-1c /
  [#207](https://github.com/keisato848/daidoko/issues/207)）。
  **コード側は済んでいる**（2026-08-22）: サーバーは Expo が `DeviceNotRegistered` を返したトークンを消す。
  アプリは許可済みのときだけトークンを登録する（§5-2f N3）。残りは利用者の作業のみ:
  ① Firebase プロジェクト作成 → ② `google-services.json` を `apps/mobile/` に置き `app.json` の
  `android.googleServicesFile` に配線（`--prebuild`）→ ③ `eas credentials` で FCM v1 を登録 → ④ 実機で
  `sync_devices.expo_push_token` が入ることを確認。**ファイルの置き場所は EAS のファイルシークレット推奨**
  （`eas secret:create --scope project --name GOOGLE_SERVICES_JSON --type file` ＋ `app.config.js` で
  `process.env.GOOGLE_SERVICES_JSON` を参照）。リポジトリは private だが、API キーを履歴に残さない方が
  `docs/開発ハーネス.md` §6 の方針と揃う
- **確定済み（2026-08-21 実装時）**: 招待コードの有効期限 = **24 時間**・グループの最大端末数 = **10**
  （`apps/server/src/lib/sync-auth.ts`）。**未決**: トゥームストーン保持期間（案: 90 日）—
  現状はサーバー側で消していない（レシピは archived で残り、帖の tombstone 行も残る）。
  行数が問題になってから決める。消すときは、品目の tombstone と同時に `entity_id LIKE '<itemId>:%'` の持ち分（§5-3）も消す
- **Play データセーフティ申告の見直しが必須**（2026-08-08 確認）: 現在の申告は
  「データ削除リクエストの提供 = いいえ」「収集はすべて一時的処理（解析後破棄）」で、
  **サーバーがデータを保持しない前提**になっている。クラウド同期はレシピ・記録・写真を
  サーバー（PostgreSQL / R2）に**保持する**ため、この前提が崩れる。リリース前に
  ①データ削除手段の提供（グループ削除 = サーバー側データの消去）を実装し、
  ②データセーフティの申告（削除リクエスト = はい・写真等の一時的処理フラグ解除）と
  ③プライバシーポリシー §5（保存場所と保持期間）を更新すること。

### 11-2. AWS 移行を再検討するトリガー（いずれか該当で）

1. **コスト**: Railway 合計（Hobby $5＋PG 従量）が**月 $10 を超えた**（AWS 化でほぼ ¥0 に落とせる差が月 ¥1,500 相当を超える）
2. **スケール**: 同期ユーザー増で Railway PG の使用量課金が伸び始めた（DynamoDB 常時無料 25GB/25RCU/25WCU が効く規模）
3. **厳密なレート制限が必要になった**: in-memory カウンタ（再起動で消える・単一インスタンス前提）では不足する事態（複数インスタンス化・悪用対策の強化）— DynamoDB 共有ストア化とセットで移行が自然
4. **キャリア判断**: AWS の実務経験を職務経歴に積みたいタイミング（転職完了後など） — 学習目的だけでも移行の正当な理由とする

### 11-3. 移行しない・見送る基準

- リリース直前など **+1〜2 週の工数**を割けない時期
- 同期サーバー側に **SQL 前提の要件**（横断集計・複雑な検索・アドホッククエリ）が生まれた場合 — PostgreSQL 継続が有利
- 旧 AWS アカウント（2021 年頃使用）の棚卸しが済んでいない場合 — 移行前にログイン可否・請求履歴 $0 確認・残骸リソースの掃除が前提（または別メールで新規アカウント: $200 クレジット対象）

### 11-4. 移行する場合の原則

- **ハイブリッドで段階移行**: まず同期バックエンド（新規開発）を AWS で構築し、稼働中の AI サーバー（Railway）は触らない → 同期が安定してから AI エンドポイントを Lambda へ移し Railway を解約
- 写真は R2 → S3 に置き換え（presigned URL 方式は共通なのでクライアント改修は最小）
- プッシュ通知（Expo Push）と GAS 利用量アラートは構成に依存しないためそのまま
