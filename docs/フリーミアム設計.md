# フリーミアム設計 — AI 写真レシピ

> 「写真からレシピ」（Vision 推論）を**フリーミアム機能**として提供するための設計。
> 実装前・課金まわりの変更前に必ず参照すること。関連: `docs/レシピ作成フロー.md` / `docs/アーキテクチャ設計.md` / `infra/README.md`

---

## 1. なぜフリーミアムか

「写真からレシピ」は唯一**変動コスト**が発生する機能（Gemini Vision API は呼び出し従量課金）。
無制限に無料提供するとコストが青天井になるため、

- **無料枠**: **月あたり N 回**（既定 5。2026-08-12 に日次からライフタイムへ、
  2026-08-28 に月次へ変更 — §7・§11。実装は `usage.service.ts`）
- **プレミアム**: 月額サブスクで無制限

とする。コスト源は AI 呼び出しだけなので、**課金対象は AI 写真レシピのみ**。
手動入力・URL 取り込み・OCR・調理記録・家族共有などは**すべて無料・無制限**のまま。

---

## 2. プラン定義

| 項目                     | 無料（Free）                                         | プレミアム（Premium）           |
| ------------------------ | ---------------------------------------------------- | ------------------------------- |
| AI 写真レシピ            | **月 N 回**（既定 5、AI 献立並べ替えと共通の全体枠） | **無制限**                      |
| 手動入力 / URL / OCR     | 無制限                                               | 無制限                          |
| 調理記録・家族共有・検索 | 無制限                                               | 無制限                          |
| 課金                     | なし                                                 | **月額サブスク**（例: ¥300/月） |

- 無料枠は**暦月でリセットされる**（`ai_photo_recipe_free_used:YYYY-MM`・端末ローカル時刻の月。
  2026-08-28 まではリセットしない生涯カウンタだった — 旧キー `ai_photo_recipe_free_lifetime_used`
  は移行せず放置。月次キーは月が変われば 0 から始まるので移行という概念自体が無い）。
- 無料ユーザーは**リワード広告 1 本で 1 回ぶんをトークンとして獲得**（無期限で貯まる・失効しない）。
  **視聴回数の上限は無い**（2026-08-14 に撤廃 — 詳細と経緯は §7）。
- 価格はストア側（Play / App Store）で設定する（コード非依存）。

## 3. アーキテクチャ方針

本アプリは**アカウント／認証を持たない**（ローカル SQLite のみ）。
そのため freemium は次の二層で構成する。

```
┌──────────────────────── 端末（クライアント）────────────────────────┐
│  エンタイトルメント  : RevenueCat（端末匿名 App User ID／レシート検証）│
│  無料枠カウント      : SQLite app_meta（端末ローカル・日次）          │
│  ゲート              : import-photo 画面で canInfer を判定           │
└────────────────────────────────────────────────────────────────────┘
                                  │ 課金状態の真実 = ストアのレシート
                                  ▼
┌──────────────────────── サーバー（コスト天井）──────────────────────┐
│  グローバル日次上限  : INFER_GLOBAL_DAILY_LIMIT（全体のコスト上限）  │
│  Gemini クォータ     : Google AI Studio 側で requests/day を上限化   │
└────────────────────────────────────────────────────────────────────┘
```

### なぜクライアント側でエンタイトルメントを判定するのか

- アカウントが無いため、サーバーで「誰が何回使ったか」を厳密に紐付けられない。
- **プレミアム判定は RevenueCat**（＝ Google/Apple のレシート検証）に委ねるため、
  端末ローカルでも**なりすましは困難**（無料ユーザーが prem を詐称できない）。
- **無料枠カウントは端末ローカル**＝再インストールでリセットされる「ソフト」な上限。
  これは許容する。理由は、**全体のコスト上限はサーバーの global cap が担保**するため。
  「無料枠の厳密な個人単位カウント」が必要になったら、アカウント＋サーバー集計（DynamoDB 等）へ拡張する（将来）。

## 4. データモデル（端末ローカル）

新規テーブルは作らず、既存の `app_meta`（KV）を再利用する。

| key                                | value      | 意味                           |
| ---------------------------------- | ---------- | ------------------------------ |
| `ai_photo_recipe_usage:YYYY-MM-DD` | 整数文字列 | その日の AI 写真レシピ成功回数 |

- 日が変わると参照キーが変わる ⇒ 実質的に**自動リセット**。
- 旧日のキーは残るが微小（1 日 1 行）。

## 5. 判定ロジック

```
FreemiumStatus = {
  isPremium,                       // RevenueCat entitlements.active['premium']
  used,                            // 当日の成功回数
  tokenBalance,                    // 広告で貯めたトークン残高（無期限。§7）
  limit = FREE_DAILY_LIMIT + tokenBalance,
  remaining = max(0, FREE_DAILY_LIMIT - used) + tokenBalance, // premium は Infinity
  canInfer = isPremium || remaining > 0,
  canWatchAdForMore = adAvailable && remaining === 0,   // 視聴回数の上限は無い（§7）
}
```

### フロー（import-photo 画面）

1. 画面表示時に `getFreemiumStatus()` を取得し、
   - プレミアム／BYOK → 「使い放題」
   - 無料 → 「無料作成：あと N 回」（生涯枠なので「今日」とは書かない）
     を表示。
2. 「撮影」「ギャラリーから選ぶ」タップ時、`ensureInferenceCredit()` を通す（`inference-gate.service.ts`）。
   枠切れなら**その場で広告視聴を持ちかけ**、見終わればそのまま続行する。
   ペイウォールへ遷移するのは**広告を出せないとき**だけ（§7）。
3. **クラウド推論が成功**したときだけ `recordCloudInference()` を呼ぶ。無料枠が残っていれば生涯カウントを
   +1、使い切っていればトークン残高を -1（§7）。
   - **料理でない（not_a_dish）** や **AI に繋がらず端末内フォールバック**したケースは**カウントしない**
     （ユーザーは AI 結果を受け取っていない／コストも実質発生しないため、ユーザーフレンドリーに）。
4. サーバーは引き続き global cap で全体コストを抑える（多重防御）。

> **写真送信の同意**: 写真は解析のためサーバー（AI 提供元）へ送信される。ブロッキングの同意ダイアログは廃止し、
> 画面内に常時その旨を明示する方式に変更（毎回確認しない）。プライバシーポリシー／ストアの Data safety で開示する。

## 6. 課金（RevenueCat）

- ライブラリ: `react-native-purchases`（Expo dev/release ビルドで autolink。設定プラグイン不要）。
- エンタイトルメント識別子: **`premium`**。
- 月額サブスクの **Offering**（current）から `monthly` パッケージを取得して購入。
- 復元: `restorePurchases()`（ストアアカウントに購入が紐づく）。

### プロバイダ抽象（差し替え可能）

```
EntitlementProvider {
  configure(): Promise<void>
  isPremium(): Promise<boolean>
  getOffering(): Promise<PremiumOffering | null>   // 価格表示用
  purchasePremium(): Promise<{ success: boolean }> // ユーザーキャンセルは success:false
  restore(): Promise<boolean>
}
```

- `RevenueCatEntitlementProvider`: 公開 SDK キーがある & ネイティブ環境のときに使用。
- `StubEntitlementProvider`: キー未設定 / Web / テスト時のフォールバック。
  `isPremium=false`、購入系は「準備中」エラー（＝アプリは**無料枠だけで完全に動く**）。

### 公開 SDK キーはストアごとに別（2026-08-14）

RevenueCat のキーは **Play = `goog_…` / App Store = `appl_…`** で完全に別物で、
片方のキーでもう片方のストアを叩くと購入フローは必ず落ちる。
`eas.json` の production プロファイルは**同じ env を全プラットフォームへ配る**ため、
変数 1 本ではどちらかが必ず壊れる（AdMob のユニット ID で同じ罠を踏んでいる）。

| 変数                                 | 対象    |
| ------------------------------------ | ------- |
| `EXPO_PUBLIC_REVENUECAT_API_KEY`     | Android |
| `EXPO_PUBLIC_REVENUECAT_API_KEY_IOS` | iOS     |

無印 = Android・`_IOS` = iOS の対応は広告ユニットと揃えてある（`src/config.ts` の `platformValue`）。

### ペイウォールに置く法務リンク（App Store 審査 3.1.2）

自動更新サブスクの画面には、タイトル・期間・価格に加えて
**利用規約とプライバシーポリシーへの「機能するリンク」**が要る。文言だけでは足りない。
URL は `src/constants/legal.ts` に集約し、**ストアに登録した値と一致させる**
（プライバシーポリシー = ASC / Play に登録済みの gist、利用規約 = Apple 標準 EULA）。
見た目の整理でリンクが消えると審査で止まるので、`paywall-legal.test.tsx` で描画とタップを固定している。

## 7. リワード広告（広告を見てトークンを貯める）

無料枠を使い切った無料ユーザーは、**リワード広告を 1 本見ると「トークン」を 1 個獲得**できる。
トークンは**無期限で貯まる**（暦日をまたいでも失効しない）— 例えば旅行前にまとめて広告を見て
貯めておき、後日の無料枠切れの日にいつでも使う、という使い方ができる。
消費順は**無料枠を先に使い切ってからトークン**（`recordCloudInference()`）。
プレミアムは広告なし・無制限。バナー／インタースティシャルは世界観に合わないため**使わない**
（opt-in のリワード ＋ 強ガード付きのアプリ起動広告のみ — §7-2、2026-07-12 決定）。

### 広告視聴の回数に上限は無い（2026-08-14・#173）

かつては**1 日 3 回まで**の獲得レート制限（`AD_BONUS_DAILY_LIMIT=3`）を置いていた。
無限ファーミング防止のつもりだったが、実際に困るのは無料ユーザーの方だった —
4 本目を見ようとすると `canWatchAdForMore` が false になり、
`decideInferenceGate()` がペイウォールへ流す。課金（プレミアム）が未提供の現状では、
そこに落ちた人は BYOK で自分の Gemini キーを入れる以外に手段が無く、その日は事実上使えない。
**「無料でも使い続けられる」ことを優先し、上限を撤廃した**（ユーザー判断）。

- コストの歯止めは**サーバーの global cap** が担う（`apps/server/src/lib/rate-limit.ts`・§3）。
  端末側の速度制限は多重防御としても効きが悪く（再インストールでリセットされる）、
  外しても全体コストの上界は変わらない。
- 撤廃後、`decideInferenceGate()` が `'paywall'` を返すのは
  **広告そのものを出せないとき**（no-fill・広告無効ビルド・オフライン）だけになる。
- 広告視聴は引き続き**利用者が選んで見る**形式（自動再生しない・AdMob ポリシー）。
- 日次の視聴回数カウンタ（`ai_photo_recipe_ad_watch:YYYY-MM-DD`）と
  `FreemiumStatus.adWatchLimit` は用途が無くなったので削除した。
  旧キーが端末に残っていても参照されないだけで、害はない。

- 算定: `usage.service.ts`。
  - `app_meta` キー: `ai_photo_recipe_token_balance`（トークン残高、**日付キーなし＝無期限**）
  - `grantAdBonus()`（視聴 1 回でトークン+1・上限なし）／
    `spendToken()`（トークン-1、下限 0）／`getFreemiumStatus().canWatchAdForMore`
- ~~リリース記念ボーナス（2026-07-28 追加・端末ごと一度だけ +3 トークン）~~ →
  **2026-08-13 に撤去（ユーザー判断「初回の無料枠は1回でいい」）**。iOS の TestFlight で
  初回に 4 回（無料枠 1 ＋ ボーナス 3）使えることに気づいたのが発端。Android でも同じ挙動だった。
  `grantLaunchBonusOnce()` とホームの告知カード・`app_meta` キー `launch_bonus_2026_07` /
  `launch_bonus_announced` はすべて削除済み。**新規インストールは無料枠 1 回だけで始まる**。
  再導入するなら git 履歴（`fix/remove-launch-bonus` の親）から戻せる。
- 抽象: `AdRewardProvider`（`ad-reward.types.ts`）— `isAvailable()` / `showRewardedAd(): Promise<{ rewarded }>`。
- プロバイダ: `ad-reward.service.ts` の factory が `EXPO_PUBLIC_ADMOB_ENABLED=true` & ネイティブ時に
  `AdMobRewardProvider`（`ad-reward.admob.ts`／web は `.web` スタブ）を返す。**既定 false ＝ 広告 UI 非表示**で挙動不変。
- 導線: ペイウォール（`paywall.tsx`）に「広告を見て 1 回ぶん貯める」ボタン（`canWatchAdForMore` のとき表示）
  → 完了で `grantAdBonus()` → 貯まったトークン残高を画面に表示。

### AdMob の状態と本番化（配線済み）

`react-native-google-mobile-ads` は**導入・配線済み**。`app.json` の設定プラグインには Google の
**テスト アプリ ID** を入れてある（未設定だと起動クラッシュするため必須）。実装は `ad-reward.admob.ts`。

- **開発で動かす**: `EXPO_PUBLIC_ADMOB_ENABLED=true` でビルド → ペイウォールの「広告を見て…」で Google の
  **テスト広告**が出る（`EXPO_PUBLIC_ADMOB_REWARDED_UNIT_ID` 未設定なら `TestIds.REWARDED`）。
  app.json のプラグイン変更を反映する場合はローカルビルドに `--prebuild` が必要。
- **同意管理（UMP / GDPR）— 実装済み（2026-07-05）**:
  - 広告初期化前に `AdsConsent.gatherConsent()` を実行（`ad-reward.admob.ts`）。GDPR 対象地域では
    同意フォームが表示され、日本など対象外地域ではフォームなしで進む。`canRequestAds` が立たない場合は
    `AdUnavailableError` で広告ボタンのエラーメッセージに落ちる。
  - パーソナライズは UMP/TCF の同意状態に SDK が従う（`requestNonPersonalizedAdsOnly` の固定は廃止）。
  - 設定 → プランに「広告のプライバシー設定」行（`privacyOptionsRequirementStatus === REQUIRED` の
    ユーザーのみ表示）→ `showPrivacyOptionsForm()` で同意をいつでも変更可能。
  - `app.json` プラグインに `delayAppMeasurementInit: true`（同意前の SDK 計測開始を防ぐ）と
    iOS ATT 用 `userTrackingUsageDescription` を設定済み。
- **本番化（あなたの作業）**: `docs/リリース手順.md` §6 参照（AdMob 本番 ID・AD_ID 権限の解除・
  Play 広告申告/データセーフティ・課金サンドボックス検証）。
  ネイティブのリンク確認はこのビルドが初回（JS の typecheck/lint/test は緑）。

> リワードで増えた利用もサーバーを叩く。広告で件数が伸びるなら `INFER_GLOBAL_DAILY_LIMIT` を引き上げる（広告が原資）。
> 採算目安: Gemini(flash) 1 回 ≈ 0.1 円未満 ＜ リワード広告 1 本 ≈ 0.7〜2 円。

### 7-2. アプリ起動広告（App Open — 2026-07-12 追加）

リワードだけでは表示機会が「無料枠を使い切った人」に限られ収益母数が小さいため、
**フォアグラウンド復帰時のアプリ起動広告**を 1 枠だけ追加（ユーザー要望「使い勝手を著しく損なわない範囲で最適化」）。

- 実装: `app-open-ad.service.ts`（判定の純関数 `evaluateAppOpenAdGate` ＋ 配線は `app/_layout.tsx` の AppState リスナー）。
  プロバイダは `app-open-ad.admob.ts`（/`.web` スタブ）。ユニット ID は `EXPO_PUBLIC_ADMOB_APP_OPEN_UNIT_ID`（未設定 = テスト ID）。
- **表示ガード（全部 AND・どれか欠けたら出さない）**:
  1. Android の広告有効ビルド、かつプレミアムでない
  2. 写真の撮影/ギャラリー往復からの復帰ではない（`photo-capture.service` がフラグ連動）
  3. タイマーが `idle`（調理中は出さない）かつ調理・カメラ系画面（/cook, /receipt, /import-photo, /import-ocr, /consume-meal, /scan-barcode）にいない
  4. **60 秒以上**アプリを離れていた（アプリ切替の往復では出さない）
  5. 初回起動から **24 時間**の猶予期間を過ぎている
  6. 前回表示から **6 時間**以上（≒ 1 日最大 2〜3 回が上限）
- コールドスタートでは出さない（起動を遅らせない）。表示状態は `app_meta`
  （`app_open_ad_last_shown_at` / `app_open_ad_first_eligible_at`）に永続化。
- 失敗は全て握りつぶすベストエフォート — 広告都合でアプリの動作を妨げない。
- **ユニット ID 未設定なら完全オフ**（本番にテストユニットが紛れる事故防止）。実機検証は
  `EXPO_PUBLIC_ADMOB_APP_OPEN_UNIT_ID` に Google のテスト ID を明示指定してビルドする。
- **本番有効化済み（2026-08-10・1.5.0 から / #92）**: AdMob に App Open ユニット `app-open-return`
  （`ca-app-pub-2633806931583277/2735127473`）を作成し、`eas.json` の production env に配線した。
  これで production プロファイルのビルドは上記ガードを満たしたときに実広告を出す。
  ローカル検証ビルド（`build-android.mjs`）は env を渡さない限り従来どおりオフのまま。

## 7-3. 方針の更新（2026-08-12・ユーザー判断）

3 つまとめて変えた。**収益の柱を「初回無料→広告」へ寄せる**方向。

1. **無料枠は初回 1 回のみ**（それまでは毎日 1 回）。日次リセットをやめ、
   生涯カウンタ `ai_photo_recipe_free_lifetime_used`（日付キーなし）で数える。
   既存ユーザーは生涯カウンタが 0 から始まるため更新後に 1 回だけ無料枠が
   復活するが、害はなく実装が単純なのでよしとした。
   `EXPO_PUBLIC_FREE_DAILY_LIMIT` は名前のまま**生涯回数**の意味に変わった
   （0 = 常時広告、の E2E ビルド技はそのまま使える）。
   **2026-08-28 に月次へ再変更**（AI 献立並べ替え M2 の実装に合わせてユーザー決定。
   §10.10.7-1・§11 参照）。生涯カウンタ→月次カウンタ（キー
   `ai_photo_recipe_free_used:YYYY-MM`）、既定値 1→5。`EXPO_PUBLIC_FREE_DAILY_LIMIT` は
   名前も「0 = 常時広告」の挙動も変えていない。旧・生涯キーは読まない（移行不要 —
   月が変わればどのみち同じ状態になる）。
2. **枠切れ → 即ペイウォールをやめた。** プレミアムが存在しない現状で毎回
   課金画面を経由させる意味がない。AI を使う全導線（写真レシピ・感想調整・
   食事写真・相談・**紙面レシピ**）で `ensureInferenceCredit()` を通し、**その場で広告視聴を
   持ちかけ、見終わったらそのまま続行**する。リワード広告の自動再生は AdMob
   ポリシー違反なので、確認ダイアログを 1 つだけ挟む。ペイウォールは
   「広告を出せないとき」（視聴上限・no-fill・広告無効ビルド）の逃げ道に降格
   （BYOK の案内がそこにあるため画面自体は残す）。
3. **バナー広告を採用**（それまで世界観優先で不採用）。置くのは**眺める画面**
   （蔵書庫一覧・買い物リスト・在庫）の下部だけ。**料理中モードには絶対に
   出さない** — ストア掲載文で「広告なし」を約束している。レシピ詳細・撮影・
   AI 系画面にも出さない。実装は `src/components/AdBanner.tsx`。

**iOS も広告を出す方針に転換**（それまで iOS = 無料・広告なし）。
ユニット ID は config がプラットフォームごとに解決する（無印 = Android・
`_IOS` 付き = iOS）。**ID が空のフォーマットは丸ごと無効** — 空をプロバイダに
渡すとテスト ID にフォールバックして本番にテスト広告が出るため、
isConfigured 側で空を弾く。iOS の AdMob アプリ・ユニットは未作成
（作成して env を足せば有効になる。それまで iOS は自然に広告なし）。

## 8. 残る境界（あなたの作業）

コード（無料枠・ペイウォール・課金抽象・リワード広告・**UMP 同意管理**・BYOK）は実装済み。
以下は**ストア側のアカウント・商品設定が必要なため必ず手元に残る**作業。
手順の詳細と申告変更（AD_ID）は `docs/リリース手順.md` §6。

1. **RevenueCat** アカウント作成 → プロジェクト → Android の public SDK key 取得。
2. RevenueCat で **エンタイトルメント `premium`** と、月額サブスクを含む **Offering** を作成。
3. **Google Play Console** で支払いプロファイルを設定し、月額サブスク商品を作成して RevenueCat に紐付け。
4. **AdMob** でアプリ＋リワード広告ユニットを作成。
5. ID が揃ったら eas.json / app.json に設定注入（リリース手順 §6-2）→ ライセンステスターで
   **実購入フローとリワード広告を検証**（§6-4）。
   - ※ `react-native-purchases` のネイティブリンク確認はこのビルドが初回。JS レベル（typecheck/lint/test）は緑。

### iOS で有料化する場合の残り（2026-08-14 時点）

**Play とは前提が違う。** 課金を保留した理由は「個人アカウントで販売を有効化すると
自宅の完全住所が Play ストアに自動公開・不可逆」という **Google Play 固有の制約**だった。
App Store Connect の「ビジネス」を実地で確認したところ:

- **有料アプリ契約はステータス「新規」**（未締結）。無料アプリ契約のみ有効
- 「法人情報の更新が必要」と案内が出るが、**開くと種類は「個人」が選択済み**。
  法人化も開業届も求められていない（「法人」は Legal Entity の訳語）
- EU の DSA トレーダー申告のバナーは出るが、**EU/英国は配信除外済み**なので該当しない
  （申告ダイアログ自体がエラーで開かない＝申告対象が無いためと見られる）

→ Issue #57 の「開業届 → D-U-N-S → バーチャルオフィス（約3週間）」は **iOS には不要の可能性が高い**。
ただし**住所が公開されないことは契約署名前に確定させる**こと。署名は不可逆な可能性がある。

| #   | 作業                                                                 | 担当                   |
| --- | -------------------------------------------------------------------- | ---------------------- |
| 1   | 有料アプリ契約への署名・銀行口座・税務情報                           | **ユーザー**           |
| 2   | サブスク商品の作成（グループ／月額／価格／ローカライズ／審査用画像） | 代行可                 |
| 3   | RevenueCat に **App Store アプリを追加** → `appl_` キー発行          | 代行可                 |
| 4   | App-Specific Shared Secret / In-App Purchase Key を RC に登録        | **ユーザー**（秘密鍵） |
| 5   | Monthly パッケージに iOS 商品 ID を紐付け                            | 代行可                 |
| 6   | Sandbox テスターで購入・復元・解約を検証                             | 代行可                 |
| 7   | 審査メモの更新（現在は「アカウント不要」のみ。購入手順を足す）       | 代行可                 |

### 有料化は iOS のみ（2026-08-14 ユーザー決定）

Play 側の住所公開が未解決なので、**プレミアムは iOS だけ**にする。Android は広告＋BYOK のまま。

判定は `isEntitlementConfigured()`（= 実行中のプラットフォームの RevenueCat キーがあるか）1 本に集約した。
**プラットフォーム名で分岐していない** ので、Android の条件が整えばキーを足すだけで有効になる。

| 画面          | キーがあるとき                                                   | 無いとき                                           |
| ------------- | ---------------------------------------------------------------- | -------------------------------------------------- |
| ペイウォール  | 見出し「DAIDOKO プレミアム」＋特典・価格・購入・復元・法務リンク | 見出し「AIレシピをもっと使う」＋**広告の導線だけ** |
| 設定 → プラン | 「プレミアムにする」                                             | 「無料プラン」                                     |

**買えないのに購入ボタンを出さない**のが要点（押した先で必ず失敗する）。
プレミアムの語も出さない —— 買えない商品を宣伝しないため。

**購入 UI を隠すと 2 か所が壊れる。実機で見つけた（2026-08-14・AQUOS）:**

- **画面が行き止まりになる。** 広告ボタンは `remaining === 0` のときしか出ないので、
  無料枠が残っている間は本文だけの空白画面になっていた。以前は購入ボタンが埋めていた。
  → **課金が使えないときは BYOK（自分の AI キー）への導線を常に出す。**
  Android で無制限にする唯一の手段なので、案内としても正しい。
- **「または」が孤立する。** 「購入する **または** 広告を見る」の接続詞なので、
  購入ボタンを消すと前段が無くなる。→ `premiumAvailable` のときだけ出す。

回帰は `paywall-legal.test.tsx` の「課金が使えないプラットフォーム」で固定している。
**要素の有無はテストで見られるが、空白や孤立した接続詞は描いてみないと分からない。**

## 9. BYOK（自分の Gemini キーを持ち込む）

ユーザーが**自分の Gemini API キー**を設定すると、アプリは**端末から Gemini を直接呼び出す**（サーバー不要）。
このとき**無料枠・課金・広告はすべてバイパス**（無制限）。ユーザーは Google に直接課金されるため、こちらにコストは発生しない。

- なぜサーバー不要か: 自分のキーをアプリに**埋め込むと抽出・悪用される**ためサーバーが要る（managed）。BYOK は
  各ユーザーが**自分のキー・自分の端末・自分の課金**で動かすので共有秘密が無く、サーバーが要らない。
- 保存: `byok.service.ts` が **expo-secure-store**（OS キーチェーン／キーストア、暗号化）に保存。`getUserApiKey()` /
  `setUserApiKey()` / `clearUserApiKey()`。Google 以外には送信しない。
- 直接呼び出し: `vision-recipe.provider.ts` の `inferRecipeFromVision` が、キーがあれば `inferViaByok`（Gemini 直叩き＋
  `normalizeGeminiRaw`）、無ければ `inferViaServer`（managed）に分岐。
- 無制限化: `usage.service.ts` が `hasUserApiKey()` を見て `isByok` を立て、`canInfer=true`／カウントしない。
- 設定 UI: `app/(tabs)/ai-key.tsx`（設定 → プラン → 自分のAIキー）。キー貼り付け・削除・取得方法リンク。
  管理方法・削除方法・制約（機種変更で引き継がれない・Gemini専用）は `InfoTooltip`（タップ展開式の補足行）で明記（2026-07 追記）。
- モデル: `EXPO_PUBLIC_GEMINI_MODEL`（既定 `gemini-2.5-flash`）。
- 前提（あなたの作業）: ユーザー各自が Google AI Studio でキーを取得（アプリ内にリンクあり）。アプリ側の実装は完了。

> **方針メモ**: BYOK と「サブスク／広告で稼ぐ managed」は方向が逆。サーバー運用を完全にやめたいなら
> **純 BYOK**（managed・課金・広告を撤去）も選べる。両立させる場合は本実装のまま（managed 既定＋上級者は BYOK）。

## ATT（トラッキング許可）は要求しない — 申告と実装を一致させる（2026-08-14）

**`NSUserTrackingUsageDescription` を app.json から外した。** 文字列があるだけで
**Apple はバイナリを「トラッキングする」と判定**し、App Privacy の「トラッキングしない」と
矛盾して審査提出がブロックされる（`STATE_ERROR.BINARY_INDICATES_APP_TRACKS_USERS`）。

実装は ATT を一度も呼んでおらず（同意管理は UMP のみ）、IDFA も取得していないので、
**「トラッキングしない」が実態**。文字列の方が誤りだった。

将来パーソナライズ広告（IDFA）を使いたくなったら、**3点をセットで変える**:
`userTrackingUsageDescription` を戻す／`requestTrackingAuthorization` を実際に呼ぶ／
App Privacy のデバイス ID を「トラッキングに使用する」に変更。どれか欠けると審査で止まる。
