## 2. Google Play リリース（アプリ本体）

### 2-1. バージョンバンプ

`apps/mobile/app.json` の `version` と `android.versionCode`、**`ios.buildNumber`（versionCode と同じ値に揃える）** を上げる。
**app.json が唯一のソース**（`android/` は prebuild 生成物で gitignore。EAS は app.json から prebuild する）。

> **iOS のビルド番号は同一バージョン内で一意かつ増加**でなければならない（App Store Connect の制約）。
> 未設定だと EAS は `1` を使い、同じ `version` で2回目のアップロードが
> 「Build number 1 for app version 1.7.0 has already been used」で落ちる（1.7.0 で実際に踏んだ）。
> versionCode と同値にしておけば、リリースごとに1箇所直すだけで両プラットフォームとも一意になる。
> 同じ version のまま作り直して再提出する場合は buildNumber だけさらに上げる。

> **Android 自動バックアップの範囲**は `plugins/withDaidokoBackupRules.js` が制御している
> （クラウド自動バックアップ = SQLite＋設定のみで 25MB 枠に常時収まる / 端末間転送 = 写真込み全部。
> 写真のクラウド退避はアプリ内の SAF 書き出し・移行ファイル共有が担う — #79）。
> このプラグインや app.json を変えたら、ローカル検証ビルドは **`--prebuild` 必須**。

> **アイコン長押しのショートカット**（「お店の料理を撮る」）は
> `plugins/withDaidokoShortcuts.js` が生成する（R3 / #114）。
> `res/xml/daidoko_shortcuts.xml`・`strings.xml` のラベル 2 件・**LAUNCHER activity 配下**の
> `meta-data` の 3 点が揃って初めて出る。application 直下に meta-data を置いても効かない。
> これも app.json 変更を伴うため **`--prebuild` 必須**。

### 2-5. 本番構成の実機 E2E（マージ前検証の原則）

ローカル release ビルドは **必ず** `node scripts/agent/build-android.mjs` で行う
（`EXPO_NO_METRO_WORKSPACE_ROOT=1` を設定。生 gradlew は "Unable to resolve ./index.js" で失敗する）。

> **`EXPO_PUBLIC_*` を変えて連続ビルドするとき**（例: 広告オフ→オンの検証）は自動でキャッシュ破棄される。
> Gradle の bundleRelease タスクは JS ソースが不変だと前回のバンドルを再利用するため、フラグだけ変えても
> 反映されない実績があった（Pixel での広告テストで ADMOB*ENABLED=true が無視された）。
> build-android.mjs が `EXPO_PUBLIC*\*`の組をフィンガープリントとして記録し、変化していれば`createBundleReleaseJsAndAssets`の生成物を破棄してから叩く。手動で怪しいときは`apps/mobile/android/app/build/generated/{assets,res}/createBundleReleaseJsAndAssets` を消してもよい。

> **Expo パッケージの版が SDK とずれていたらビルドを止める。**
> ずれたまま組むと、**ビルドもインストールも成功するのに起動直後に落ちる**。
> しかも JS のテストは native を読まないので全部緑のまま通ってしまい、CI でも捕まらない。
> 実例（2026-08-09）: 多言語対応で `expo-localization` を `^57.0.1`（遥かに新しい SDK 用）で
> 入れてしまい、`expo-modules-core@3.0.30` に無い `getDirectConverter` を呼んで
> `java.lang.NoSuchMethodError` で即クラッシュした。SDK 54 の想定は `~17.0.9`。
> build-android.mjs が `expo/bundledNativeModules.json` と突き合わせ、**宣言と実際の両方**を
> メジャー単位で検査する（宣言だけだと手で node_modules を触った状態を、実際だけだと
> 宣言がずれたまま古い版が残っている状態＝EAS の新規インストールで壊れる状態を見逃す）。
> `npx expo install --check` はこのリポジトリの tooling では動かないので自前で見ている。

> **ネイティブモジュールを足したら prebuild が要る。**
> prebuild 陳腐化の検知は `app.json` と `plugins/` に加えて **`apps/mobile/package.json`** も見る。
> モジュールの追加・削除は app.json に出ないので、package.json を見ないと気づけない。

> **エミュレーターで試すときは `--arch x86_64` を付ける。**
> 既定は実機向けの `arm64-v8a`。ABI が食い違うと、**インストールは成功するのに起動時に**
> `SoLoaderDSONotFoundError: couldn't find DSO to load: libreactnative.so` で落ちる。
> 原因が直前の JS 変更に見えるので紛らわしい。`--arch` を明示していないときは
> build-android.mjs が接続中の端末の主 ABI（`ro.product.cpu.abi`）を見て警告する。
> なお x86_64 エミュレーターの `abilist` には `arm64-v8a` が載るので、abilist で判定しても
> この食い違いは見つからない。

```powershell
adb reverse --remove-all     # localhost ブリッジを排除（本番 Railway に向ける）
adb install -r apps\mobile\android\app\build\outputs\apk\release\app-release.apk
# AI 機能（食べた/名寄せ）を操作 → railway logs で 200 を裏どり
```

## 2b. iOS は App Store Connect API で提出まで行ける（2026-08-24 に確立）

**「審査へ提出は画面操作でしかできない」は誤り。** `eas.json` の `submit.production.ios` にある
ASC API 鍵（`ascApiKeyPath` / `ascApiKeyId` / `ascApiKeyIssuerId`）で、次がすべて API から行える:

| やること                               | エンドポイント                                          |
| -------------------------------------- | ------------------------------------------------------- |
| バージョンを作る                       | `POST /v1/appStoreVersions`                             |
| 「このバージョンの新機能」             | `PATCH /v1/appStoreVersionLocalizations/{id}`           |
| ビルドを選ぶ                           | `PATCH /v1/appStoreVersions/{id}/relationships/build`   |
| **審査へ提出**                         | `POST /v1/reviewSubmissions` ＋ `reviewSubmissionItems` |
| App ID の権限（Associated Domains 等） | `POST /v1/bundleIdCapabilities`                         |
| プロビジョニングプロファイルの削除     | `DELETE /v1/profiles/{id}`                              |

Git Bash から叩くときは **`MSYS_NO_PATHCONV=1` を付け、URL は絶対 URL で書く**。
付けないと `/v1/apps/...` が `C:/Program Files/Git/v1/apps/...` に化けて `InvalidURL` で落ちる。

**App Privacy（栄養ラベル）だけは API に無い**（`appDataUsages` 等の関係は存在しない＝画面専用）。
ただし**変更が要るかどうかは公開ページで確かめられる** — `https://apps.apple.com/jp/app/id6800964382`
の「データの取り扱い」に、申告済みの種類がそのまま出る。
2026-08-24 時点の申告は「ユーザコンテンツ（写真・その他）」「ID（デバイスID）」が
**すべて“あなたに関連づけられないデータ”**。クラウド同期が増やすのはこの 2 種類そのもので、
Apple の申告には Play のような「一時的処理か否か」の区別が無いため、**同期の追加では変更不要**だった。

**App Store の掲載は日本語のみ**（Play は ja/en の 2 言語）。「新機能」も ja だけ入れる。

### 2b-1. iOS の権限を足したらプロファイルを作り直す（1.11.0 で被弾）

`app.json` の `ios.associatedDomains` を足した（#198 共有リンクをアプリで開く）だけで、
EAS の iOS ビルドが**プロビジョニングプロファイルの権限不足で落ちる**:

```
Provisioning profile "*[expo] com.daidoko.app AppStore ..." doesn't support the Associated Domains capability.
```

手順:

1. `POST /v1/bundleIdCapabilities` で App ID に `ASSOCIATED_DOMAINS` を足す
   → Apple が既存プロファイルを **`INVALID`** にする
2. **`INVALID` のままでは EAS は作り直さない。** `--non-interactive` だと同じプロファイルを使い続け、
   2 回目も同じエラーで落ちる（実測）。`DELETE /v1/profiles/{id}` で**消してから**ビルドし直す
3. **それでも足りない。** `eas build --non-interactive` は Apple に認証しないので
   （`Skipping Provisioning Profile validation on Apple Servers because we aren't authenticated`）、
   Apple 側で消しても**自分が保存している古いプロファイルを使い続ける**。実測で 3 回とも同じエラー

### 2b-2. EAS の保存分が古いまま直せないときは、ローカル署名に逃がす（1.11.0 で実施）

`EXPO_ASC_*` を渡すと **`eas credentials:configure-build` は認証する**（capabilities も同期される）。
そこまでは進むが、最後に

```
Generate a new Apple Provisioning Profile?
```

という **TTY 必須の確認**で止まる。`printf 'y\n' |` でも `Input is required, but stdin is not readable`
で弾かれる（`isTTY` を見ている）。**利用者にこの 1 回だけ y を押してもらうのが本筋。**

押してもらえないときの逃げ道が `credentials.json`（ローカル署名）。EAS の保存分を完全に迂回する:

```bash
# 1) 鍵と CSR（Git Bash では MSYS_NO_PATHCONV=1 が要る。付けないと -subj が化ける）
MSYS_NO_PATHCONV=1 openssl req -new -key dist.key -out dist.csr -subj "/CN=... /O=... /C=JP"
# 2) POST /v1/certificates（IOS_DISTRIBUTION・csrContent は PEM をそのまま）→ certificateContent は base64 DER
# 3) openssl x509 -inform DER → PEM → openssl pkcs12 -export で .p12
#    （Git Bash の OpenSSL 1.1.1 に -legacy は無い。付けると Unrecognized flag で落ちる）
# 4) POST /v1/profiles（IOS_APP_STORE・**この新しい証明書に紐づけて**作る）→ profileContent は base64
# 5) apps/mobile/credentials.json に .p12 とプロファイルの絶対パス＋パスワード
# 6) eas.json の production に "ios": { "credentialsSource": "local" }
```

**代償を承知で使うこと**:

- Apple アカウントに**配布証明書が 1 本増える**（上限内。既存は失効させない）
- **EAS の保存分は古いまま**なので、次に iOS を出すときも同じ迂回が要る。
  本筋に戻すには、利用者のターミナルで `eas credentials:configure-build -p ios -e production` を
  1 回走らせて `y` と答える
- `credentials.json` は **`.gitignore` 済み**（パスワードを含む）。秘密は `C:/secure/ios-1110/` に置く

**2026-08-24 の顛末**: 1.11.0 はこの迂回で提出まで通した。そのあと利用者が
`eas credentials:configure-build -p ios -e production` を実行して `y` と答えたところ、
EAS が自前のプロファイル（`*[expo] com.daidoko.app AppStore ...`）を作り直したので、
`eas.json` の `credentialsSource: "local"` と `credentials.json` を**外して通常経路に戻した**。
ローカル署名用の証明書とプロファイルは `C:/secure/ios-1110/` に残っているが、**もう使っていない**。
不要になったら Apple 側の新しい方の `IOS_DISTRIBUTION` 証明書とプロファイル
`daidoko AppStore local 1.11.0` を消してよい（**古い方の証明書は消さない** — EAS が使っている）。

## 3c. 本番での動作確認と、そのあとの後始末（2026-08-23 ユーザー指示）

本番サーバーで同期の疎通を確かめたら、**テストデータは速やかに本番から消す**。
残すと、他人が同じグループに入ったときに知らないデータが出てくるし、
データセーフティ申告の「保持するのは利用者のデータだけ」という説明とも食い違う。

消し方（グループごと・アプリからが正）:

1. アプリの「家族グループ」→ **共有グループを削除**（オーナーのみ）。
   サーバー側は `ON DELETE CASCADE` で `sync_devices` / `sync_entities` / `sync_deltas` まで消える
2. アプリから消せない残骸（過去の検証で作った孤立グループなど）は Railway の psql で:

   ```bash
   railway connect Postgres   # 本番。実行前に必ず対象 group_id を目視確認する
   -- select id, created_at, (select count(*) from sync_devices d where d.group_id=g.id) from sync_groups g;
   -- delete from sync_groups where id = '<確認した group_id>';
   ```

   **`delete from sync_groups` を条件なしで打たない。** 利用者のグループが増えた後では取り返しがつかない

3. 消したら `select count(*) from sync_groups;` で残数を確認し、結果をこの節に追記する

## 3d. 実績（ストア・広告の数字）の取り方（2026-08-26 に一通り実施）

「いま何人入れてくれたか / 広告はいくらか」を毎回さがし直さないための経路表。
**Play とアプリ内実績は API で取れず、ブラウザが要る**（下の理由）。

| 欲しい数字                             | 取り方                                                                                       | 認証                                  |
| -------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------- |
| Play のインストール・表示回数・評価    | Play Console をブラウザで開く（URL 直打ちで指標指定可 — 下記）                               | Google ログイン（ブラウザセッション） |
| App Store のインプレッション・DL 数    | App Store Connect → アプリ分析（ブラウザ）                                                   | **Apple ID ログインが要る**（下記）   |
| App Store の評価数・平均評価・公開日   | `https://itunes.apple.com/lookup?id=<appId>&country=jp`（公開 API・認証不要）                | なし                                  |
| AdMob の収益・表示回数・eCPM           | AdMob コンソールのホームと「広告アクティビティ レポート → AdMob ネットワーク」               | Google ログイン（ブラウザセッション） |
| アプリの公開状態・バージョン・審査状況 | ASC API（`scripts` の ASC ヘルパーと同じ鍵）`GET /v1/apps`, `/v1/apps/{id}/appStoreVersions` | `C:/secure/AuthKey_8C387NYC2T.p8`     |

### 3d-1. API で取れないもの（試して 403 だったもの）

- **ASC の App Analytics / 売上レポートは、いまの API キーでは取れない。**
  `GET /v1/apps/{id}/analyticsReportRequests` も `GET /v1/financeReports` も
  `403 FORBIDDEN_ERROR "The API key in use does not allow this request"`。
  鍵のロールが **App Manager** で、これらは Admin / Account Holder（財務系は Finance）を要求するため。
  `GET /v1/apps` や `appStoreVersions` は同じ鍵で 200 なので、**鍵が壊れているわけではない**。
  → **恒久的な解は「Admin ロールの API キーを 1 本作る」**（下記 3d-1a）。作れば以後は API で取れる。

#### 3d-1a. Analytics を API で取れるようにする（利用者の作業・1 回だけ）

**毎回ブラウザでログインしてもらう必要は無い。** Admin ロールの鍵を 1 本作れば、以後は
`node scripts/release/asc-analytics.mjs` で取れる。**Account Holder 本人しか作れない。**

1. App Store Connect →「ユーザーとアクセス」→「**統合**」タブ →「App Store Connect API」
2. チームキーの「+」→ 名前は何でもよい（例 `analytics-readonly`）→
   **アクセス = Admin**（App Manager では 403 のまま。Analytics は Admin を要求する）
3. **`.p8` は 1 回しかダウンロードできない。** `C:/secure/AuthKey_<KeyID>.p8` に置く
4. その画面の **Issuer ID** と **Key ID** を控える
5. 実行:

```powershell
$env:ASC_KEY_ID="<新しい KeyID>"
$env:ASC_ISSUER_ID="<Issuer ID>"
$env:ASC_KEY_PATH="C:/secure/AuthKey_<KeyID>.p8"
node scripts/release/asc-analytics.mjs status     # 要求の一覧（状態を変えない）
node scripts/release/asc-analytics.mjs request    # 一度きりのスナップショットを要求
node scripts/release/asc-analytics.mjs fetch      # 生成後に落として docs/store/ios-analytics/ へ
```

#### いつ出るか — Apple の記述（逐語）

> "Once you make an `ONGOING` report request, you will receive your first report approximately 24-48 hours later."
> "Data for a given day is considered complete two days after the reporting date."

**24〜48 時間は `ONGOING` の初回についての記述。** `ONE_TIME_SNAPSHOT` の待ち時間は
Apple のこのページには**書かれていない**。2026-08-27 に要求した直後は両方とも `instances=0` だった。

#### ⚠ **5 ユーザー未満だとレポートが出ない**（この状況の本題）

> "Thresholding, for example, **omits rows with data from fewer than five users or five unique devices**.
> **Some usage reports are not generated if minimum thresholds are not met.** This means data may not
> appear for low-volume activities or new features."

**だいどこは MAU 3。しきい値の 5 を下回っている。**
つまり **Analytics を有効にしても、数字が出てこない可能性がある**。
「iOS 側を測ってから判断する」という計画は、**測れないかもしれない**という前提で立てること。

出てこなかった場合、それ自体が「5 ユーザー未満」という情報ではある（既に分かっていることだが）。
**iOS の表示回数・転換率を知りたいなら、ブラウザで App Store Connect の
「アプリ分析」を見るしかない**可能性が高い（UI 側のしきい値は別の可能性がある・未確認）。

実測でハマった点:

- **`attributes.name` は存在しない。** 付けると
  `409 ENTITY_ERROR.ATTRIBUTE.UNKNOWN "'name' is not an attribute"`。渡すのは `accessType` だけ
- **1 要求あたりレポートが 156 本ある。** 大半は `FRAMEWORK_USAGE`（AirPlay・CarPlay・Safari 拡張…）で
  このアプリには無関係。**全部落とすと無駄**なので、スクリプトは既定で 4 本だけ見る
  （`ASC_ALL=1` で全部）:

  | レポート                                     | 中身                               |
  | -------------------------------------------- | ---------------------------------- |
  | App Store Discovery and Engagement Standard  | **表示回数・製品ページ表示・転換** |
  | App Downloads Standard                       | ダウンロード                       |
  | App Store Installation and Deletion Standard | インストールと削除                 |
  | App Sessions Standard                        | セッション（定着）                 |

- **`reports` はページングが要る**（`limit=200` でも `links.next` が付く）
- **`ONE_TIME_SNAPSHOT` と `ONGOING` は別の要求**。前者が履歴、後者が以後の継続収集。
  2026-08-27 に**両方要求済み**（snapshot `e7190d2a…` / ongoing `eaffafe3…`）
- `ONGOING` は取りに行かない期間が続くと `stoppedDueToInactivity` になる

> **既存の submit 用キー（`8C387NYC2T`・App Manager）は消さないこと。** eas submit が使っている。
> Analytics 用は**別の鍵として足す**。

- **Play の統計は androidpublisher API に無い。** 一括レポートは GCS の
  `gs://pubsite_prod_4806763604853146902/stats/...` にあるが、
  publisher 用サービスアカウント（`play-publisher@pc-api-…`）は `storage.objects.list` を持たず 403。

## 6. 広告・プレミアム課金の本番化リリース

設計は `docs/フリーミアム設計.md`。コード（無料枠・ペイウォール・RevenueCat 抽象・リワード広告・UMP 同意管理・BYOK）は実装済みで、
**既定ではすべて無効**（広告 UI 非表示・購入はスタブの「準備中」）。本番化はビルド時の設定注入だけで有効になる。

### 6-0-a. 収益化方針の決定（2026-07-06）— ★プライバシー制約

**当面「方針A = サブスク課金なし・広告(AdMob)＋BYOK のみ」で運用する。Play の販売アカウント（Google Payments merchant）は設定しない。**

理由 = **自宅住所の公開回避**。確定した制約:

- **個人アカウントで有料アプリ/アプリ内課金（サブスク含む）を有効化すると、自宅の完全な住所が Play 掲載の「デベロッパーについて」欄に自動公開される**（Google 公式ポリシー: 販売アカウントは完全住所の表示が必須）。**個人アカウントのままでは回避不可・有効化は不可逆**。
- 現状のストア公開情報（実地確認済み）= 氏名・メール・"Japan"（国のみ）。**番地は未公開**。
- サブスクを実現するには**組織アカウント化**が必要（開業届＋D-U-N-S取得＋バーチャルオフィス契約 約3週間。住所は非自宅にできる）。将来ユーザーが決断したら着手。

### 7-4-3. 提出前に .ipa の中身を検査する（2026-08-14 に 1 件見つけた）

```bash
curl -sL -o app.ipa "<artifact URL>"
python -c "import zipfile,plistlib; z=zipfile.ZipFile('app.ipa'); p=plistlib.loads(z.read('Payload/app.app/Info.plist')); print({k:v for k,v in p.items() if 'UsageDescription' in k})"
```

用途説明を自動で足す（Android にも `RECORD_AUDIO` を足す — `recordAudioAndroid: false` で止まる）。

**ガイドライン 5.1.1 で指摘されうる**。

ほかに同じ方法で確認できること: バージョン/ビルド番号の整合・`ITSAppUsesNonExemptEncryption`・
`UIDeviceFamily`（iPhone 専用なら `[1]`）・プライバシーマニフェスト（`PrivacyInfo.xcprivacy`）の同梱。
