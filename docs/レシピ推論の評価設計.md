# レシピ推論の評価設計（R0）

> 「お店の味の再現」に振り切れるかを、**測ってから**決めるための設計。
> プロンプト本体の設計は `docs/料理写真レシピ推論設計.md` §7、主役交代の計画は `docs/お店の味を再現設計.md`。

---

## 1. なぜ必要か

現行のシステムプロンプトは 8 行の汎用指示で、**「お店の料理を家庭で再現する」に特化した要素がほぼ入っていない**
（`apps/server/src/lib/vision-recipe.ts`）。

| 再現に必要なもの                         | 現状                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------ |
| 店の厨房 → 家庭の台所への翻訳            | 「家庭で再現できる」の一言のみ。**機能の価値の中心が空白**                           |
| 思考の順序（料理特定 → 知識 → 差分補正） | 指定なし。いきなり材料を書かせている                                                 |
| 店名・メニュー名の活用                   | context は「味の方向性・辛さ・地域性・量に反映」のみ。料理の特定に使わせていない     |
| confidence の基準                        | 自己申告のみ。基準がない（なのに UI は high を「バッチリ読み取れました」と断定表示） |
| 見えない要素（下味・出汁・油）の扱い     | 「一般的な目安を用いる」の一言                                                       |
| few-shot                                 | なし                                                                                 |
| **評価セット**                           | **なし**                                                                             |

`docs/料理写真レシピ推論設計.md` §12 で「ゴールデン画像セット（10〜20 枚）で回帰評価」を計画していたが、
実施されていない。存在するのは `.github/workflows/vision-poc.yml`（**画像 1 枚を手動で流す PoC**）のみで、
サーバーテスト 35 件はルーティングとバリデーションの検証であり、出力の正しさは見ていない。

実利用のフィードバックもない（MAU 3・AI 実行はほぼ開発者のテスト）。
**つまり現在の品質は誰も知らない。** その状態でストア掲載を賭けるべきではない。

## 2. 測るもの

### 4 つの採点軸（各 0〜2 点・人手採点）

| 軸                    | 2 点                             | 1 点                                            | 0 点                           |
| --------------------- | -------------------------------- | ----------------------------------------------- | ------------------------------ |
| **A. 料理の特定**     | 料理名が一致                     | 系統は合っている（例: 麻婆豆腐→四川風豆腐料理） | 外れ                           |
| **B. 材料**           | 主要食材が揃い、余計なものがない | 欠け or 余計が 1〜2 個                          | それ以上ずれる                 |
| **C. 家庭で作れるか** | そのまま家庭の器具・食材で作れる | 一部に代替が必要                                | 業務用器具・入手不能食材が必須 |
| **D. 手順**           | そのまま実行できる               | 補完すれば作れる                                | 破綻している                   |

### confidence の校正

`confidence='high'` と申告した出力のうち、**A が 2 点だった割合**を測る。
UI は high を「バッチリ読み取れました」と断定表示しているため、ここが低いと信頼を壊す。

## 3. 合格ライン（測る前に決める）

測ってから基準を作ると必ず自分に甘くなるので、先に確定させる。

| 指標                        | 合格ライン                                            |
| --------------------------- | ----------------------------------------------------- |
| A 平均                      | ≥ 1.6 かつ 0 点が全体の 10% 以下                      |
| B 平均                      | ≥ 1.4                                                 |
| **C 平均**                  | **≥ 1.8**（この機能の肝。業務用器具を要求しないこと） |
| D 平均                      | ≥ 1.5                                                 |
| confidence=high の A 正答率 | ≥ 85%                                                 |

### ラインの意図（なぜこの高さか）

**失敗がどれだけ取り返しがつくかで決めている。** ユーザーが自分で直せる失敗は低く、直せない失敗は高くする。

| 軸  | 失敗したとき何が起きるか                                             | 取り返し             | ライン        |
| --- | -------------------------------------------------------------------- | -------------------- | ------------- |
| C   | 業務用器具や入手不能な食材が必須＝**そのレシピは存在しないのと同じ** | 不可能               | 最高（1.8）   |
| A   | 別の料理として出力される                                             | 0 点は不可・1 点は可 | 1.6＋0 点 10% |
| D   | 手順が破綻していて作れない                                           | 補完すれば作れる     | 1.5           |
| B   | 材料に過不足がある                                                   | **一番直しやすい**   | 最低（1.4）   |

- **C が最高**なのは、この機能の存在理由そのものだから。料理名が完璧でも家庭のコンロで作れなければ価値はゼロで、
  「お店の味を家で」の"家で"が成立しない。30 枚中、代替が必要なものは 6 枚まで、**作れないものはゼロ**という意味。
- **A は平均と 0 点率を分ける**。A=1（麻婆豆腐を「四川風豆腐料理」）は名前を直せば済み材料もだいたい合うが、
  A=0（全然違う料理）は「このAIは何も分かっていない」と伝わる瞬間で離脱に直結する。平均で薄まって見逃さないよう別枠にする。
- **B が最低**なのは、下味・隠し味・出汁の種類が写真に写っていないため。ここを高くするのは不可能の要求になる。
  加えて材料はユーザーが最も直しやすく、**R2（感想での調整ループ）が直すために作る機能そのもの**。
- **confidence 85% は精度ではなく「嘘をつかない」基準**。「バッチリ読み取れました」と表示する以上 7 回に 6 回は当たっていてほしい。
  ここだけが低い場合、直すべきはモデルではなく **UI の文言**。

> **数字自体に実証的な裏付けはない**（競合の水準も過去の測定値もない）。よって初回測定の一番の価値は合否ではなく
> **ベースラインが分かること**。v0 が最初から全部通ったら「合格」ではなく**基準が緩かった証拠**なので、
> 勝利宣言せずに難しい写真を足して測り直す。
> また 30 枚では統計的な精度は出ない（10% は 3 枚。1 枚のぶれで結果が変わる）。
> 「明らかに通っている／明らかに落ちている／際どい」の 3 値で読み、際どければ悩まずに枚数を増やす。

## 4. 判断ルール

- **全て満たす** → R4（ストア訴求の刷新）へ進んでよい
- **一部未達** → プロンプトを改良して再測定（**最大 2 周**）
- **2 周しても未達** → 主役交代を見送る。R2（感想での調整ループ）で補う路線に切り替え、
  ストア訴求は現行のまま据え置く

## 5. 評価セット

### 1 件の定義

**1 件 = 料理の写真 1 枚 ＋ 正解ラベル**（現行機能の入力形式と同じ）。これを 30 件そろえる。

| 1 件に含むもの           | 例                    |
| ------------------------ | --------------------- |
| 料理の写真（1 枚）       | 店で撮った麻婆豆腐    |
| 正解の料理名             | 麻婆豆腐              |
| ジャンル・撮影条件       | 中華 / 暗い店内・寄り |
| 店名・メニュー名（任意） | —                     |

- 内訳は **外食 20 / 家庭料理 10**。
- 分散させる観点: ジャンル（和洋中エスニック）／構成（単品・丼・鍋・複数皿）／
  撮影条件（明るい・**暗い店内**・寄り・俯瞰）。暗い店内は実利用で最も多い条件なので必ず入れる。

### 収集ルール（撮り始める前に決めておくこと）

**外食 20 件のうち 10 件は、3 枚セットで撮る**: ①全体 ②断面・取り分けた後 ③メニュー。
あとから「複数枚も試したい」と思っても撮り直しになるため、収集の時点で決めておく必要がある。

追加写真は種類によって期待値がまったく違う（枚数ではなく**別種の情報が増えるか**で決まる）。

| 追加する写真         | 何が新しく分かるか                                   | 期待できる効果                       |
| -------------------- | ---------------------------------------------------- | ------------------------------------ |
| **メニュー（文字）** | 料理名、説明文（「自家製ラー油」「〇〇産豚バラ」等） | **最大**。文字は情報密度が最も高い   |
| **断面・取り分け後** | 中の構造。層・餡・火の通り、煮込みか焼きか           | **大きい**。1 枚では原理的に見えない |
| 寄り（アップ）       | 香辛料の粒度、ソースのとろみ                         | 中                                   |
| 別角度（横から）     | ほぼ同じ情報                                         | **小さい**（画素が増えるだけ）       |
| 卓上全体             | 薬味・副菜からジャンルの補強                         | 小                                   |

**逆向きのコストも測る**: 店で複数枚撮らせるのは「撮るだけ」という売りと矛盾する（追加は必ず**任意**にする）。
断面は食べ始めてから撮るので撮影タイミングが分かれる。皿が複数写るとモデルが対象を取り違えて
**精度が下がる方向にも振れうる**ため、実測するまで良くなると決めつけない。

### 陰性ケース（拒否されるべき写真）5 枚

ガードレール（§7-2）の検証用に、**拒否されるべき写真を 5 枚**入れる。
食材だけ / レシピ本のページ / 風景 / 人物 / スクリーンショット。

厳しくすると正当な写真まで弾くため、**両方向を測る**。

- 弾くべきものを弾けているか
- **暗い店内の正当な料理写真を誤って弾いていないか**（実利用で最も多い条件のため、こちらが本命）

### プライバシー方針

**写真とマニフェストはリポジトリにコミットしない。** 個人の外食履歴＝行動データであり、容量も大きい。
ローカルの評価セットディレクトリ（gitignore）に置く。
**コミットするのは採点結果（スコア表）だけ**にして、プロンプト改良の履歴を追えるようにする。

## 6. ハーネス（実装済み）

`apps/server/scripts/vision-eval.ts`（既存の `vision-poc.ts` と同じ tsx 実行）

```bash
cd apps/server

# 1) 評価セットの manifest を用意（雛形: scripts/vision-eval-manifest.example.json）
#    <dir>/manifest.json ＋ 画像。**リポジトリにコミットしない**

# 2) 推論して採点シートを出す
npx tsx scripts/vision-eval.ts run --set <dir> --variant v0
npx tsx scripts/vision-eval.ts run --set <dir> --variant v1
npx tsx scripts/vision-eval.ts run --set <dir> --variant v1 --with name
npx tsx scripts/vision-eval.ts run --set <dir> --variant v1 --with cross
npx tsx scripts/vision-eval.ts run --set <dir> --variant v1 --with cross,menu
npx tsx scripts/vision-eval.ts run --set <dir> --variant v1 --model gemini-2.5-pro

# 3) 出力された md の A〜D 列を人が埋めてから集計
npx tsx scripts/vision-eval.ts summarize --file <dir>/results/latest-v1-default.md

# 4) コストの A/B（思考トークンを切ると品質はどれだけ落ちるか）
npx tsx scripts/vision-eval.ts run --set <dir> --variant v1 --thinking 0
npx tsx scripts/vision-eval.ts compare --files <a.md>,<b.md>
```

- `run` は `<dir>/results/` に **採点欄が空の Markdown 表**と生 JSON を書き出す
- `--with cross` を指定すると、断面写真を持たないケースは自動でスキップされる
  （3 枚セットで撮った 10 件だけが対象になる）
- `summarize` は §3 の合格ラインと突き合わせ、✅/❌ で表示する。
  **陰性ケースは A〜D を空のままにする**（拒否できたかだけを見る）。
  正当な写真を誤って拒否していれば警告が出る
- API キーは `apps/server/.env` の `GEMINI_API_KEY` を使う（既存の扱いを変えない）
- `--delay <ms>`（既定 6000）でケース間に待機。`--resume` で成功済みを引き継ぎ、
  失敗分だけ流し直す（クォータ切れで途中終了しても続きから回せる）

> **⚠ 評価は本番の AI 枠を食う（2026-08-02 実測）。**
> 本番の HTTP ルートは通さないのでサーバーの `INFER_GLOBAL_DAILY_LIMIT` は消費しないが、
> **Google 側のレート枠は本番と共有**で、そちらが本当の制約。
> しかも本番キーは**無料枠で gemini-2.5-flash が 1 日 20 リクエスト上限**（→ Issue #120）。
> 140 リクエストの評価計画は無料枠では 7 日かかり、**回した日は実ユーザーの AI が止まる**。
> 課金の有効化か評価専用キーの用意が前提になる。

### 本番への影響

プロンプト変種は `GeminiVisionRecipeProvider({ variant })` で切り替える。**既定は `v0`** であり、
`infer` ルートは変種を指定しないため**本番の挙動は変わらない**（`vision-prompt.test.ts` で固定）。
複数画像（`extraImages`）も評価ハーネス専用で、本番スキーマは単数の `imageBase64` のまま。

## 7. プロンプト v1（再現特化）

v0＝現行 8 行。v1 は以下の方針で書き直す。

1. **思考の順序を指定する**
   ① 料理を特定する（名前・ジャンル・地域）→ ② その料理の標準的な作り方を想起 →
   ③ 写真から読み取れる差分（具材・色・とろみ・焼き色・盛り付け）で補正 → ④ 家庭向けに翻訳
2. **店名・メニュー名は料理の特定に最優先で使う**
   補足テキストに含まれる場合、写真のピクセルより強い手がかりになる。
   現行は「味の方向性」にしか使わせていない
3. **家庭への翻訳を明示する（この機能の中心）**
   - 業務用器具を前提にしない。中華レンジの強火・コンベクションオーブン・真空調理・大型フライヤーは、
     家庭のコンロ・フライパン・オーブン・少量の揚げ油での代替手順に置き換える
   - 入手困難な食材は日本のスーパーで買えるもので代用し、`note` に本来の食材を書く
   - 何日も仕込む工程は、当日でも近づく方法を書く
4. **見えないものは「推定」と明示する**
   下味・隠し味・出汁の種類・油の種類は写真から確定できない。一般的な前提を置いたうえで、
   その材料の `note` に推定である旨を書く
5. **confidence を基準で判定させる**
   - high: 料理名を特定でき、主要な材料がほぼ確定できる
   - medium: 料理の系統は特定できるが、配合や具材に幅がある
   - low: 系統の推測どまり、または写真が不鮮明

## 7-2. ガードレールと改善ヒント

### 現状と穴

ガード自体は既にある（プロンプト 1 行＋`isDish`＋サーバーの `VISION_NOT_A_DISH`＋モバイルは
フォールバックせずエラー表示）。弱いのは中身。

| 穴                             | 具体例                                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| **食材と料理を区別していない** | プロンプトが「料理・**食品**が写っていない場合」なので、じゃがいも 3 個の写真でも `isDish=true` になりうる |
| 二値なので理由を返せない       | メッセージは常に「料理がはっきり写った写真でお試しください」の一択                                         |
| 判定が甘い方向に倒れる         | モデルは「料理っぽければ true」に寄る。**「迷ったら false」と書いていない**                                |
| 暗すぎ・ブレの扱いがない       | `isDish=true` / `confidence=low` になるだけで撮り直しを促せない                                            |

### 原則: 「もう一度」ではなく「何を足せば良くなるか」を返す

拒否も低確信も、**行き止まりにせず修復のループにする**。R2（感想で近づける）と同じ形であり、
アプリ全体の物語が「一発で当てる」ではなく「**近づけていく**」で一貫する。

### 型の拡張

```ts
isDish: boolean;
rejectReason?: 'not_food' | 'ingredients_only' | 'text_page' | 'too_dark' | 'blurry' | 'too_far';
improvementHints?: ('add_dish_name' | 'add_menu_photo' | 'add_cross_section' | 'brighter' | 'closer')[];
```

`unclear` の一語で済ませない。**暗い・ぶれた・遠いで、ユーザーが取るべき行動が違う**ため。

| 拒否理由           | 出す文言（アプリ側で固定）                 | ワンタップの導線                    |
| ------------------ | ------------------------------------------ | ----------------------------------- |
| `too_dark`         | 暗くて色や質感が判別できませんでした       | 撮り直す                            |
| `blurry`           | ぶれています                               | 撮り直す                            |
| `too_far`          | 料理が小さく写っています                   | 撮り直す（皿に寄る）                |
| `ingredients_only` | 食材が写っています。料理の写真から作れます | **在庫に登録**（スキャン/レシート） |
| `text_page`        | 文字が主体の画像です                       | **文字入り画像から作成**（OCR）     |
| `not_food`         | 料理が写っていません                       | 別の写真を選ぶ                      |

**成功時にも同じ仕組みを使う**。推論は通ったが確信が低いとき、何が足りなかったかを `improvementHints` で返し、
「料理名を入力」「断面を撮る」「メニューを撮る」をワンタップで出す。
**どのヒントが実際に効くかは §8 の測定で決まる**（料理名が効くなら `add_dish_name` を最優先で出す）。

### 文言をモデルに書かせない

自由文を出すと言い回しが毎回変わり、たまに的外れになり、テストできない。
モデルには **enum を最大 2 つ選ばせるだけ**にして、日本語はアプリが持つ。

### 検証と注意

- **モデルの自己診断は当てにならない**（「なぜ判断できなかったか」はそれらしい理由を作りうる）。
  陰性ケース 5 枚＋低確信ケースで**ヒントの妥当性も確認**し、的外れなら enum を減らすかヒント自体をやめる。
- プロンプトでは**判定を思考の第 0 段階**に置き、各カテゴリを定義したうえで「**迷ったら false**」を明記する。
- `AgentErrorCode` は増やさず、`error` に任意の `reason` を足す（省略可なので後方互換）。
- **暗さ・ぶれは端末側で送信前に判定できる可能性がある**。できれば API を呼ぶ前に返せて
  **ユーザーの無料枠を消費しない**。`image-preprocess.service` で画素にアクセスできるか要調査。

## 8. 比較する組み合わせ

| 変種                              | 何が分かるか                                         | 対象  | 採点           |
| --------------------------------- | ---------------------------------------------------- | ----- | -------------- |
| v0 × flash × 全体 1 枚            | **ベースライン**（現在ユーザーが受け取っている品質） | 30 件 | **4 軸すべて** |
| v1 × flash × 全体 1 枚            | プロンプト改良の効果                                 | 30 件 | **4 軸すべて** |
| v1 × flash × 全体＋**料理名**     | **名前の効果**（打つだけで済むなら複数枚は不要）     | 30 件 | A のみ         |
| v1 × flash × 全体＋**断面**       | 視覚情報を増やす効果                                 | 10 件 | A・B・D        |
| v1 × flash × 全体＋断面＋メニュー | 全部載せの上限                                       | 10 件 | A・B・D        |
| v1 × pro × 全体 1 枚              | モデル差（コスト増に見合うか）                       | 30 件 | A のみ         |

- v0 × pro は測らない（プロンプトを直す前提のため情報価値が低い）。
- **採点負荷を優先度で配分する**。4 軸を全部つけるのは判断に直結する 2 変種だけ。
  1 件 2 分として 2 時間。残りは A だけなら 1 件 15 秒。全変種を 4 軸で採点すると
  480 判定・4 時間コースになって続かない。

### 複数枚は「作るか」ではなく「測ってから決める」

現行実装は写真 1 枚が上限（サーバー `imageBase64` は単数、アプリも `capturedPhoto` は 1 枚）。
複数枚対応は**本番実装を変えずに検証できる** — 評価スクリプトから直接 Gemini に複数画像を投げればよい。

- **料理名テキストで十分に上がる** → 複数枚は作らない（`context` 欄で既に渡せる）
- **メニュー写真がテキストを上回る** → 店で文字を打つより撮る方が楽なので、メニュー撮影を作る価値が確定する
- **断面が効く** → 「食べ終わったら断面も撮る」導線（後から足せる形）を検討する

効果が確認できてから `images[]` に拡張する。

## 9. コスト

30 件 × 4 変種 ＋ 10 件 × 2 変種 = 140 回。flash は実測 ¥0.45/回、pro はその数倍。**合計 ¥200〜600 程度**。
複数画像は入力トークンが増えるが、出力（日本語のレシピ全文）が支配的なので影響は限定的（これも実測できる）。
実質のコストは採点の手間（上表の配分で 2.5 時間程度）。

### 実測コスト（2026-08-03・課金有効化後）

理由は **gemini-2.5-flash の思考トークンが出力として課金される**こと。実測で 1 推論あたり
出力 ≒4,800 トークンのうち大半が思考で、入力（≒480 トークン）は誤差の範囲。
