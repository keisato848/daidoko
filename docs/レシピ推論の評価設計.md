# レシピ推論の評価設計（R0）

> 「お店の味の再現」に振り切れるかを、**測ってから**決めるための設計。
> プロンプト本体の設計は `docs/料理写真レシピ推論設計.md` §7、主役交代の計画は `docs/お店の味を再現設計.md`。

---

## 1. なぜ必要か

現行のシステムプロンプトは 8 行の汎用指示で、**「お店の料理を家庭で再現する」に特化した要素がほぼ入っていない**
（`apps/server/src/lib/vision-recipe.ts`）。

| 再現に必要なもの                      | 現状                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| 店の厨房 → 家庭の台所への翻訳          | 「家庭で再現できる」の一言のみ。**機能の価値の中心が空白**               |
| 思考の順序（料理特定 → 知識 → 差分補正） | 指定なし。いきなり材料を書かせている                                     |
| 店名・メニュー名の活用                | context は「味の方向性・辛さ・地域性・量に反映」のみ。料理の特定に使わせていない |
| confidence の基準                     | 自己申告のみ。基準がない（なのに UI は high を「バッチリ読み取れました」と断定表示） |
| 見えない要素（下味・出汁・油）の扱い  | 「一般的な目安を用いる」の一言                                           |
| few-shot                              | なし                                                                     |
| **評価セット**                        | **なし**                                                                 |

`docs/料理写真レシピ推論設計.md` §12 で「ゴールデン画像セット（10〜20 枚）で回帰評価」を計画していたが、
実施されていない。存在するのは `.github/workflows/vision-poc.yml`（**画像 1 枚を手動で流す PoC**）のみで、
サーバーテスト 35 件はルーティングとバリデーションの検証であり、出力の正しさは見ていない。

実利用のフィードバックもない（MAU 3・AI 実行はほぼ開発者のテスト）。
**つまり現在の品質は誰も知らない。** その状態でストア掲載を賭けるべきではない。

## 2. 測るもの

### 4 つの採点軸（各 0〜2 点・人手採点）

| 軸                     | 2 点                                     | 1 点                             | 0 点                     |
| ---------------------- | ---------------------------------------- | -------------------------------- | ------------------------ |
| **A. 料理の特定**      | 料理名が一致                             | 系統は合っている（例: 麻婆豆腐→四川風豆腐料理） | 外れ                     |
| **B. 材料**            | 主要食材が揃い、余計なものがない         | 欠け or 余計が 1〜2 個           | それ以上ずれる           |
| **C. 家庭で作れるか**  | そのまま家庭の器具・食材で作れる         | 一部に代替が必要                 | 業務用器具・入手不能食材が必須 |
| **D. 手順**            | そのまま実行できる                       | 補完すれば作れる                 | 破綻している             |

### confidence の校正

`confidence='high'` と申告した出力のうち、**A が 2 点だった割合**を測る。
UI は high を「バッチリ読み取れました」と断定表示しているため、ここが低いと信頼を壊す。

## 3. 合格ライン（測る前に決める）

測ってから基準を作ると必ず自分に甘くなるので、先に確定させる。

| 指標                       | 合格ライン                     |
| -------------------------- | ------------------------------ |
| A 平均                     | ≥ 1.6 かつ 0 点が全体の 10% 以下 |
| B 平均                     | ≥ 1.4                          |
| **C 平均**                 | **≥ 1.8**（この機能の肝。業務用器具を要求しないこと） |
| D 平均                     | ≥ 1.5                          |
| confidence=high の A 正答率 | ≥ 85%                          |

## 4. 判断ルール

- **全て満たす** → R4（ストア訴求の刷新）へ進んでよい
- **一部未達** → プロンプトを改良して再測定（**最大 2 周**）
- **2 周しても未達** → 主役交代を見送る。R2（感想での調整ループ）で補う路線に切り替え、
  ストア訴求は現行のまま据え置く

## 5. 評価セット

- **30 枚目安**。外食 20 / 家庭料理 10。
- 分散させる観点: ジャンル（和洋中エスニック）／構成（単品・丼・鍋・複数皿）／
  撮影条件（明るい・**暗い店内**・寄り・俯瞰）。暗い店内は実利用で最も多い条件なので必ず入れる。
- 各画像のメタ: `id` / 正解の料理名 / ジャンル / 撮影条件 / 店名（任意）/ メニュー名（任意）

### プライバシー方針

**写真とマニフェストはリポジトリにコミットしない。** 個人の外食履歴＝行動データであり、容量も大きい。
ローカルの評価セットディレクトリ（gitignore）に置く。
**コミットするのは採点結果（スコア表）だけ**にして、プロンプト改良の履歴を追えるようにする。

## 6. ハーネス

`apps/server/scripts/vision-eval.ts`（既存の `vision-poc.ts` と同じ tsx 実行）

```bash
pnpm --filter server exec tsx scripts/vision-eval.ts \
  --set <評価セットのディレクトリ> --variant v1 --model gemini-2.5-flash
```

- 評価セットを順に推論し、**採点欄が空の Markdown 表**を出力する（人が埋める）
- 生の JSON はローカルのみ（gitignore）。集計は同スクリプトの `--summarize` で行う
- API キーは `apps/server/.env` の `GEMINI_API_KEY` を使う（既存の扱いを変えない）

## 7. プロンプト v1（再現特化）

v0＝現行 8 行。v1 は以下の方針で書き直す。

1. **思考の順序を指定する**
   ① 料理を特定する（名前・ジャンル・地域）→ ② その料理の標準的な作り方を想起 →
   ③ 写真から読み取れる差分（具材・色・とろみ・焼き色・盛り付け）で補正 → ④ 家庭向けに翻訳
2. **店名・メニュー名は料理の特定に最優先で使う**
   補足テキストに含まれる場合、写真のピクセルより強い手がかりになる。
   現行は「味の方向性」にしか使わせていない
3. **家庭への翻訳を明示する（この機能の中心）**
   - 業務用器具を前提にしない。中華レンジの強火・コンベクションオーブン・真空調理・大型フライヤーは、
     家庭のコンロ・フライパン・オーブン・少量の揚げ油での代替手順に置き換える
   - 入手困難な食材は日本のスーパーで買えるもので代用し、`note` に本来の食材を書く
   - 何日も仕込む工程は、当日でも近づく方法を書く
4. **見えないものは「推定」と明示する**
   下味・隠し味・出汁の種類・油の種類は写真から確定できない。一般的な前提を置いたうえで、
   その材料の `note` に推定である旨を書く
5. **confidence を基準で判定させる**
   - high: 料理名を特定でき、主要な材料がほぼ確定できる
   - medium: 料理の系統は特定できるが、配合や具材に幅がある
   - low: 系統の推測どまり、または写真が不鮮明

## 8. 比較する組み合わせ

| 変種            | 目的                                       |
| --------------- | ------------------------------------------ |
| v0 × flash      | **ベースライン**（現在ユーザーが受け取っている品質） |
| v1 × flash      | プロンプト改良の効果                       |
| v1 × pro        | モデル差の効果（コスト増に見合うか）       |

v0 × pro は測らない（プロンプトを直す前提のため情報価値が低い）。

## 9. コスト

30 枚 × 3 組 = 90 回。flash は実測 ¥0.45/回、pro はその数倍。**合計 ¥200〜500 程度**。
実質のコストは採点の手間（30 枚 × 4 軸 = 120 判定・1 時間程度）。

サーバーのグローバル日次上限（`INFER_GLOBAL_DAILY_LIMIT=600`）に相乗りするため、
評価実行が本番ユーザーの枠を圧迫しないよう、1 日の実行回数に注意する。

## 10. UI への波及（測定後）

- confidence の校正結果が悪ければ、`import-photo.tsx` の `CONFIDENCE_LABEL` の
  「バッチリ読み取れました」を弱い表現に変える
- C（家庭で作れるか）で代替が入った材料は、`note` の「推定」表示をユーザーに見せるか検討する
