## 1. モデルと原価（一次確認 2026-08-28）

- 既定 `gemini-3.1-flash-lite-image`（≒$0.0336/枚(1K) ≒**¥5.0**・¥150/USD 仮置き）。`gemini-2.5-flash-image`（$0.039・legacy）は廃止リスクで採らない。env `COVER_IMAGE_MODEL` で差し替え可（アプリリリース不要）
- 全画像モデル **Free tier なし** → BYOK も課金有効キー必須（byok 文言に 1 行追加）。SynthID 透かしは全数埋め込み（可視ラベルの代替にはならない）
- **1 枚=テキスト推論の 11〜17 倍**。無料枠に混ぜない根拠
- **検証反映（evidence の訂正 2 件）**: ①available-regions には **EEA 各国・UK も掲載されている**（「記載が無い」は誤り。本アプリは EU/英国に配信しないため結論は不変）。②0.5K の「ドキュメントと料金ページの食い違い」は**存在しない**（0.5K 対応は 3.1-flash で、Lite は 1K のみ。両ソースは整合）。1K だけ使う方針は不変
- Lite の料理写真品質は**未測定**。リリース前に和食 10 題 × Lite/3.1-flash の目視比較（≒¥150）で既定モデルを確定

## 2. フロー

- 入口は **PhotoPickerField（cover variant）の第 3 アクション「AI でイメージをつくる」1 箇所**。RecipeForm は手入力/URL 取り込み/相談 confirm/編集で共有されており、実装 1 箇所で全入口をカバー。タイトル空なら disabled
- タップ → ゲート判定 → 生成中（表紙欄内・画面は塞がない）→ プレビューシート（画像＋「AI が作ったイメージです」＋［この表紙にする］［作り直す（1 回ぶん使います）］［やめる］［報告］）→ 採用で `persistRecipePhoto` へ。**自動で表紙に設定しない**（採用は常に人間）
- **検証反映**: `persistRecipePhoto` は内部命名でプレフィックスを渡す口が無い → **シグネチャ拡張（options 引数に `filenamePrefix`）＋既存テスト追随を作業として計上**（+0.25 日）
- 失敗はフォームを壊さずトースト＋現状維持（サーバー未デプロイでも落ちない線）
- プロンプトはサーバー側自動組み立て（タイトル＋材料名＋タグ＋locale。手書きプロンプト入力は設けない）。「材料リストに無い食材を描かない」「文字・ロゴ・人物・手を入れない」を縛る

## 3. ゲート（別勘定・決定変更 G）

- **無料: 月 3 枚**（`app_meta` の端末ローカル月次カウント・成功時のみ加算）
- **枠は「採用」ではなく「生成」に対して消費する（裁定済み・実機検証で確認された挙動は仕様どおり）**:
  `PhotoPickerField.tsx` の `runGenerate()` は生成成功直後に `recordCoverImageUse()` を呼ぶ——
  プレビューシートで［やめる］を押しても、その 1 枚ぶんの枠は戻らない。理由はコストの発生点が
  生成時点にあるから（サーバー側の実費はプロンプトを投げた瞬間に発生し、採用するかどうかでは
  変わらない）。採用時消費にすると「気に入らなければ何度でも捨てて作り直す」が枠の外側で
  無制限にでき、実質的にゲートが無いのと同じになる
- 枠切れ → **広告 1 本=1 枚・即時消費・貯めない**（既存トークンと別勘定 — 単価 14 倍の裁定を防ぐ）
- BYOK: 無制限（利用者負担・課金有効キー必須）
- サーバー天井: `COVER_IMAGE_GLOBAL_DAILY_LIMIT` 既定 10/日（月最大 ¥1,550・MAU 3 に十分・0 で機能オフ）
- **検証反映（プレミアム枚数の再計算）**: 初稿の「月 30 枚で ¥300 に収まる」は**ストア手数料を無視した誤算**。手取りは ¥255（15%）〜¥210（30%）で、プレミアムの中身は毎日 AI（¥10.5/月）と枠を分け合う。**月 10〜15 枚から始める**（原価 ¥50〜75 → 毎日 AI と合算 ¥60〜88 で、手取り最悪 ¥210 に対し粗利 ¥120 以上を確保）。実利用を見て増枠
- `device_monthly_usage`（§10.10.7-1）へは将来 category='cover_image' で相乗り。先にテーブルを作った側（R2 想定）が CREATE TABLE を持つ
- **R4 実装時の決定（プレミアム枚数の確定値）**: 「月 10〜15 枚から始める」の範囲のうち、
  `PREMIUM_MONTHLY_COVER_LIMIT = 10`（下寄り）で実装（`cover-image-gate.service.ts`）。
  原価を保守的に見て開始し、実利用を見て増枠する方針どおり — 上げるのはこの定数 1 箇所
  （プレミアムが枠切れのときは §11 のとおり広告を出さず paywall 相当に落とす）
- **R4 実装時の決定（プレミアムの枠切れ表示）**: プレミアムが枠切れのとき、無料ユーザーと
  同じ「paywall」判定に落ちる（BYOK 案内画面へ）。プレミアム専用の「来月までお待ちください」
  画面は今回作らなかった — RevenueCat 未配線でプレミアムが実在しない現状では優先度が低い。
  プレミアムを実際に売る前に画面文言を見直すこと

## 4. AI 生成ラベル（**検証反映・重い問題の修正**）

初稿の「aigen- ファイル名だけでどこへでも運ばれる」は **Web 共有で偽**（共有は写真を base64 バイト列で送り、ファイル名はサーバーに届かない）。修正後は**二重持ち**:

1. **端末内・バックアップ・将来の同期**: ファイル名 `aigen-<id>.jpg`＋`isAiGeneratedPhoto(path)` ユーティリティ（DB マイグレーション不要・coverPhotoPath と一緒に運ばれる）
2. **Web 共有**: 共有 payload に**明示フィールド `coverIsAiGenerated: boolean`（省略可）を追加**し、サーバーが共有ページに「AI が作ったイメージです」表記を出す。省略可フィールドなので新旧相互互換（aiNote と同じ手法）。**アプリ側バッジと同じリリースに載せる**（他人の画面が最リスク面なのに無ラベル期間を作るのは §2 の軸に反する — 初稿の「後回しでも矛盾は生まれない」を撤回）

アプリ内は一覧カード・詳細ヘッダに小さな「AI」バッジ＋詳細に「実物とは異なります」1 行。

### 4-1. 中身が AI 由来かは**別のフラグ**（#266・2026-09-01 追加）

**表紙にはラベルがあるのに、材料と分量には無かった。** 安全に関わる度合いは逆なので、
この非対称は歪んでいた（`ai.disclaimer` は保存前に 2 秒で消えるトーストにしか出ておらず、
相談経路は一度も出していなかった）。

|              | 表紙が AI                              | 中身が AI                                  |
| ------------ | -------------------------------------- | ------------------------------------------ |
| 端末内       | ファイル名 `aigen-` から導出（列なし） | **`recipes.ai_generated` 列**（v17）       |
| 判定         | `isAiGeneratedPhoto(path)`             | `RecipeDetail.isAiGenerated`               |
| 共有 payload | `coverIsAiGenerated?: boolean`         | `aiGenerated?: boolean`                    |
| 文言         | 「AIが作ったイメージです」             | `ai.disclaimer` 全文（アレルギー警告込み） |

**両方立つことがある**（AI で作ったレシピに AI の表紙を付けた場合）。同じ「AI」でも
意味が違うので、フィールドも文言も分けている。**片方を他方で代用しない。**

**なぜ導出ではなく列か。** 表紙はファイル名という運ばれる実体があるが、中身にはそれが無い。
`sources.type` で代用する案は 4 つの理由で捨てた: ①相談・貼り付け・手入力は `sources` 行を
作らない（AI が全文を書いた相談レシピを表現できない）②`type='url'` は AI ではない
③`type='photo'` はクラウド Vision と端末内推定を区別できない ④web モックでは
`createShareSource` が行を作らない。

**なぜリビジョンではなくレシピ単位か。** 「編集しても印は落とさない」を採ったから
（分量を 1 つ直しただけで「人が作ったレシピ」に化けるのは、安全表示として逆方向）。
リビジョンは編集のたびに新しい行を作るので、あちらに置くと引き継ぎを書き忘れた瞬間に
印が落ちる（#220 と同型）。レシピ単位の列にすると、同期のリビジョン LWW で旧端末の
後勝ちによりバッジが消える副作用も**そもそも起きなくなる**。

**`NULL` は「AI ではない」ではなく「不明」。** v17 の移行で写真・紙面 OCR 由来のものは
遡って立てるが（`sources` に記録が残る）、相談・貼り付けテキスト由来は判定材料がゼロなので
`NULL` のまま残る。**この非対称は仕様であって漏れではない。**
`NULL` を根拠に「人が書きました」と断言する表示は作らないこと — それだけが嘘になる。

**共有ページにも同じリリースで出す。** §4 の「他人の画面が最リスク面なのに無ラベル期間を
作らない」と同じ理由。

## 5. サーバーとタイムアウト（**検証反映**）

- `POST /api/v1/infer/cover-image`（infer.ts の既存パターン・レスポンスは base64 JSON ≒2MB・Railway egress ¥0.02/枚未満で誤差）
- 初稿の「サーバー 60s×リトライ 2 回」は**モバイル 75s を超え、garden-vision.ts に明文化された教訓（リトライ予算 < クライアントタイムアウト。超えるとクライアントが諦めた後にサーバーだけ成功して課金）に違反** → **サーバー 55s・リトライなし**（または 30s×2 の合計 60s 台）に修正し、**garden-retry-budget.test.ts と同型の守衛テストを追加**する
- API 表面（`responseModalities` 等のフィールド名）は実装時に image-generation ドキュメントで再確認（表面が違えば見積りが膨らみ得ることを明記）

## 6. Play の AI 生成コンテンツポリシー（**検証反映**）

ポリシー原文は「**without needing to exit the app**」の報告機能を要求。mailto は外部メールアプリへ遷移するため厳格に読めば満たさない可能性がある → **アプリ内報告フォームを第一案にする**(既存サーバーへ POST する 1 画面・+0.25〜0.5 日)。mailto は代替案に降格。**既存の AI テキスト生成（相談・写真レシピ）にも同じ報告導線を同時に置く**(画像追加で審査の目が入るタイミングに安全側へ倒す)。
