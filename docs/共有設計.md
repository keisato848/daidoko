> 作成 2026-09-03。きっかけは利用者の連続した指摘:
> 「リンクによる共有が非常に使いづらい。OS共有でLINE等で共有できなかったか」
> 「誰に共有しているか把握できないのか」「共有方法と、今何が誰に共有されているのかが分かりづらすぎる」
> 「（対症療法の管理画面に対し）そんな単純か？共有は設計見直し必要では？」
>

> `docs/Web共有設計.md`（リンク公開の実装）と `docs/クラウド同期設計.md`（家族グループ同期）が正で、
> 本書はその**上に載る利用者向けの見せ方**と用語を決める。

## 1. 現状の棚卸し（2026-09-03・1.13.0 時点）

共有と呼べる仕組みは 4 つあり、**入口・画面・用語がすべて別**。

| 仕組み                   | 誰に見えるか                               | 入口                                  | 状態の置き場所                      |
| ------------------------ | ------------------------------------------ | ------------------------------------- | ----------------------------------- |
| テキスト共有             | 送った相手（取り込み書式で往復可）         | レシピ詳細メニュー「共有」            | なし（送りっぱなし）                |
| リンク公開（レシピ単体） | **URL を知る全員・無期限**                 | レシピ詳細メニュー「Webページで共有」 | app_meta（1.13.0 まで一覧手段なし） |
| リンク公開（帖）         | URL を知る全員（パスコード・期限は帖のみ） | 帖編集 / 設定→データ→レシピ帖         | recipe_books.share_url              |
| 家族グループ同期         | **グループのメンバーだけ**                 | 家族グループ画面・設定→クラウド同期   | secure-store ＋ サーバー            |

さらに買い物・在庫は品目ごとの「自分だけ」トグル（既定=共有）が各品目画面の奥にある。

## 2. 何が歪んでいるか

1. **機構中心 vs 相手中心。** 利用者は「妻に送りたい」「友達に見せたい」で考えるが、
   UI は仕組みごとに入口を分け、利用者に仕組みを選ばせている。
   「リンク共有が使いづらい」の正体。OS 共有シート自体は全経路に実装済みで、
   足りないのは機能ではなく**編成**。
2. **可視範囲が共有の瞬間に明示されない。** リンク=全員・無期限、グループ=メンバーのみ、
   という重大な差が、発行ボタンを押す瞬間に一度も表示されない。
   「誰に共有しているか把握できない」の本体は管理画面の不在より先にこれ。
3. **用語の揺れ。**「共有」「Webページで共有」「Web共有リンク」「共有グループ」「公開」が混在。
   同じ「共有」がテキスト送付とリンク公開と同期の 3 つを指す。
4. **全体を束ねる場所が無かった。** 設計書も Web共有とクラウド同期に分かれ、
   共有の全体像はグループ作成ダイアログの 2 文でしか語られない。

裏づけ: ペルソナ点検 `docs/reviews/persona-help-home-2026-09-03.md` P4（誰の記録か分からない）、
本書冒頭の利用者指摘 4 件。

## 3. 再設計 — 決定事項

### 3-1. 共有は「相手」で 2 つに再編する

利用者に見せる区分はこの 2 つだけにする:

- **家族と共有** — グループの端末どうしで自動同期。**メンバーだけに見える**。
- **リンクで渡す** — Web ページを発行して OS 共有シートで送る。**リンクを知る人は誰でも見られる**。

テキスト共有は「リンクで渡す」シート内の副項目（「テキストで送る」）に格下げする。
仕組み名（Web共有・クラウド同期）は利用者向け文言から消し、設計書内の用語として残す。

### 3-2. 統一共有シート

レシピ詳細・帖・買い物などの「共有」アクションはすべて同じボトムシートを開く:

```
このレシピを共有
● 家族と共有          … 参加済みなら「共有中（グループのメンバーだけに見えます）」
                        未参加なら「家族グループをつくる/参加する」へ
● リンクで渡す        … 「リンクを知っている人は誰でも見られます。新しく開けるのは
                        送ってから7日間（§3-6）」 [リンクを発行して送る]（発行済みなら [送る] [停止]）
○ テキストで送る      … 取り込み書式のテキストを共有シートへ
```

**可視範囲の 1 行は必ず表示する**（グレーの注記でよい。省略不可）。

### 3-3. 状態の一元化 —「共有の管理」

設定 → データ → **共有の管理**（1.13.1 で追加済み・share-status.tsx）を共有状態の正面にする:
家族グループの参加状態と共有範囲の常設表示・リンク公開中の一覧（単体＋帖件数）・
「自分だけ」品目の件数。帖の一覧は既存管理画面へ送る（一覧の二重化はしない）。

### 3-4. 用語統一表

| 使う                          | 使わない（廃止・設計書内のみ）     |
| ----------------------------- | ---------------------------------- |
| 家族と共有 / 家族グループ     | クラウド同期（利用者向け文言から） |
| リンクで渡す / リンクで公開中 | Web共有・Webページで共有           |
| テキストで送る                | 共有（単独で機構を指す用法）       |
| 自分だけ                      | 非公開・プライベート               |

### 3-5. やらないこと

- **閲覧者の個人追跡はしない。** リンクの閲覧者をサーバーに記録しない方針
  （`docs/Web共有設計.md` §0-2 の通信の秘密の整理）は維持する。「誰が見たか」は
  アカウント制とセットの別機能であり、本再編のスコープ外。
- 家族グループの複数化・役割（閲覧のみ等）は扱わない（需要が観測されてから）。
- 単体レシピへのパスコード追加は今はしない（必要なら帖を使う導線を出す）。期限は §3-6 で全リンク共通になった。

### 3-6. リンクの受け取り期限（2026-09-03 追加・利用者決定）

**無期限の URL は廃止する。** 帖の 6 桁パスコードは総当たりに弱く、リンクの防御を
パスコードに頼れない、という利用者の指摘が起点。家族の招待コード（24 時間）と同じ発想で:

- リンクを**新しく開けるのは送ってから 7 日間**（`expires_at`。サーバー側で最長 7 日に固定）
- **期限内に開いた閲覧者は、その後も見られる。** 開いた瞬間に署名付きアクセス Cookie
  （HMAC・鍵は share_meta に永続化 — 再起動で閲覧者を締め出さない）をブラウザに置く。
  サーバーは**誰が開いたかを記録しない**（Cookie は閲覧者の端末にだけ残る — §3-5 の方針のまま）
- **「リンクを送る」たびに期限を張り直す**（renew API。送る意思がある間だけ窓が開く）。
  帖の内容更新も送り直しとみなして張り直す
- 期限後の新規アクセスは **410 の期限切れページ**（「もう一度送ってもらってください」— 復旧手段を
  伝えるため 404 とは分ける。中身・タイトルは出さない）。写真も同じ鍵で閉じる
- パスコード付きの帖は、**パスコード通過後にだけ**アクセス Cookie を発行する。
  Cookie 保持者は期限後の再入力を免除（Cookie 自体が通過の証明のため）
- 既存の無期限リンクはデプロイ時に「そこから 7 日」で埋める（それまでに開けば継続）

実装: `share-store.ts`（expires_at / share_meta / renew / アクセス Cookie）・
`routes/share.ts`（410 判定・Cookie 発行・`POST /api/v1/share/{recipes,books}/:slug/renew`）・
アプリは各「送る」導線で renew をベストエフォート呼び出し。

## 5. 共有グループの一般化（2026-09-03 利用者提案 → **着手決定**）

> **状態（2026-09-03 再更新）**: 利用者（オーナー）の判断で前倒し着手が決定。
> **対象は 1.13.1**（一度 1.14.0 送りを提案したが、オーナー指示で 1.13.1 に確定。リリースは本実装の完了を待つ）。
> §5-2 の着手条件は「安定運用の実績」を待たずオーナー決定で上書きされた。
> ペルソナ 5 人の意見聴取を実施済み（§5-3）— 全員が概念を支持し、要件は §5-4 に落とし込んだ。

> 「グループ配下にレシピ・在庫・買い物リストを入れてグループを共有すればいいのでは。
> レシピだけ共有したいときはレシピだけのグループを作ればよい。後方互換性は要注意だが」

**評価: これが共有の最終形。** 「共有する＝グループに入れる」「誰に見えるか＝メンバー一覧」に
一本化され、§2 の歪み（機構中心・可視範囲の不明瞭さ）が構造的に消える。
家族＝全部入りグループ、友人＝レシピだけのグループ、のような**相手ごとのスコープ**も表現できる。

**今やらない理由**: 同期基盤（S0〜S2・2026-08〜09 出荷）は「1 端末 = 1 グループ」前提で、
認証情報・`sync_devices`・同期ランナー・LWW がすべて単一グループに紐づく。多グループ化は
全エンティティへの所属付与・グループ横断の競合解決・pull/push の多重化を伴う**同期の再設計**。
出荷直後の基盤を作り直すより、安定運用の実績を先に積む。

**後方互換の道筋（実現時）**:

- 既存の家族グループを「全部入りスコープのグループ」として読み替える（利用者の操作ゼロ）
- 品目の「自分だけ」（shared=0）は「そのグループからの除外」に写像
- サーバーはエンティティ行にグループ列を追加して段階移行（旧クライアントには従来ビューを返す）
- リンク共有（§3-6）は残る — アプリを持たない相手への受け渡しはグループでは代替できない

**着手条件**: ① v2.0 同期の安定運用（競合・消失の報告が落ち着いていること）、
② 「家族以外とレシピだけ*同期*したい」という実需要の観測（帖のリンク共有では足りないという声）。
それまでの「レシピだけ共有」の受け皿は、レシピ帖＋受け取り期限付きリンク（§3-6）。
→ **2026-09-03 オーナー決定により前倒し**（冒頭の状態欄参照）。

### 5-3. ペルソナ意見聴取（2026-09-03・5人・軽量モデル）

全員が概念を支持。「全部自動共有の方が実は気を使っていた」（律子・62・スマホ不慣れ）、
「品目ごとの『自分だけ』は設定が煩雑で実際には使い物にならない」（由紀・35・義母と同居）。
生活の中に分けたい場面が実在する: 家族=全部 / 娘・友人=レシピだけ / キャンプ仲間=買い出しだけ（健太・38）。

主な懸念（頻出順）:

- **「どのグループに何を入れたか忘れる」**（律子・健太・隆）— 文脈表示が生命線
- **金銭情報の漏洩不安**（隆・45・受け身）— 買い物リストは家計が見える。「見えて*いない*こと」を
  確認できないと、勝手に見えているのではと疑心暗鬼になる
- **既定の誤りによる漏洩**（由紀）— 新規レシピの既定が「全グループ」だと試作が義母に漏れる
- **移行でデータが勝手に分類されること**（隆）— 「実は見えていました」が起きたら信頼はゼロになる
