# 冷蔵庫写真設計 — 写真 1 枚から在庫と「作れるレシピ」へ

> オーナー要望「冷蔵庫の写真からレシピ作成、冷蔵庫の写真から在庫登録」を、
> **1 フローの両取り**として設計する。ペルソナ 5 人（由紀・美咲・律子・隆・健太）で
> 要件確定済み（2026-09-05）。

- 実装: サーバー `apps/server/src/lib/fridge-vision.ts` + `routes/infer.ts`（`POST /infer/fridge`）、
  モバイル `apps/mobile/app/fridge.tsx` + `src/services/fridge-vision.provider.ts` +
  `src/utils/fridgeReview.ts`
- 契約の正: `packages/shared/src/types/fridge.ts`
- 関連: `docs/フリーミアム設計.md` §7-3/§11（無料枠）、`docs/買い物リスト・在庫設計.md` §5.2/§6（在庫マージ・名寄せ）

---

## 1. 何を作るか（1 フローで 2 機能）

冷蔵庫の写真を撮る → AI が**食材の品名だけ**を読み取る → **確認シート**で修正・取捨 →
① 在庫へ「追加のみ」マージ（B: 在庫登録）→ ② そのまま「この材料で作れるレシピ」へ誘導
（A: レシピ作成）。途中で何度も聞かない、シンプルな一連（由紀の理想形）。

A のレシピ側は**新しい生成ロジックを作らない**。在庫が正しくなれば、既存の
「在庫で作れるレシピ」（`/cookable`・充足率ランキング）と AI 相談（`/recipes/consult`・
在庫を考慮するオプション）がそのまま答えになる — 既存資産への接続で済ませる。

## 3. フロー（モバイル `app/fridge.tsx`）

```
追加タブ「写真から」→「冷蔵庫からレシピ」
  │
  ▼
[select]  開示（A 階層・撮影前に常時表示）＋無料枠の残数表示
  │  撮影 / ギャラリー
  │  └─ ensureInferenceCredit()  … 枠切れ→その場で広告視聴 / 出せなければペイウォール
  ▼
[processing]  inferFridgeItems()（BYOK なら Gemini 直・無ければ POST /infer/fridge）
  │  成功（cloud）→ recordCloudInference()   … BYOK はカウントしない
  │  0 件 → [error]「読み取れませんでした」＋手入力（在庫画面）への誘導
  ▼
[review]  確認シート（必須・自動確定なし）
  │  ・品名は TextInput で修正できる（外すだけにしない）
  │  ・confidence low →「たぶん」バッジ（fridgeReview.classifyFridgeConfidence）
  │  ・既存在庫と同名（名寄せ済み比較 = alias 辞書＋normalizeItemName）
  │    →「すでに在庫にあります」＋既定オフ（行は消さない）
  │  「在庫に追加（n）」
  ▼
在庫へ追加のみマージ  addPantryItem(name, { quantity: null, unit: null, groupName: defaultGroupFor(name) })
  │  quantity=null = 数量未管理（読めない数字を 1 で埋めない — レシート §5.6 と同じ作法）
  ▼
[done] 「n 品を在庫に追加しました」
  ├─「この材料で作れるレシピを見る」→ /cookable（既存 P4）
  ├─「AIに相談してレシピを作る」→ /recipes/consult（既存・在庫考慮オプションあり）
  └─ 閉じる
```

## 4. スコープ外（やらないこと・理由つき）

| やらないこと                     | 理由                                                                                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **数量・分量の読み取り**         | 写真から数量は読めない（庫内の卵が 3 個か 7 個かは写らない）。推測した数字は在庫で合算されて「家に無いものが在庫にある」状態を静かに作る。契約（shared）に欄ごと持たせないことで、経路のどこでも混入しない（美咲・全員）         |
| **上書き・数量合算マージ**       | 「写真に写っている＝それが在庫の全て」ではない（隆の「真実の定義がない」問題）。ドアポケットの奥・野菜室・写らなかった棚がある以上、写真を根拠に既存在庫を上書きしたり消したりはできない。仕様は「追加のみ」に線を引いて回避する |
| **自動確定**                     | 誤読 1 件（味噌→ヨーグルト）で在庫そのものへの信用が壊れる（律子）。確認シートは省略可能なステップではなく、機能の一部                                                                                                           |
| **新しいレシピ生成ロジック**     | 在庫→レシピは既存の `/cookable`（充足率）・AI 相談・M3 一括生成が既に持っている。入口を増やさず接続で済ませる（美咲の「入口を増やしすぎない」と同根）                                                                            |
| **画像のサーバー保存・ログ出力** | 冷蔵庫は生活そのもの。既存 `/photo` と同じく、画像はリクエストの中でしか使わない。hono の logger は method/path のみでボディを書かない（実装確認済み 2026-09-05）                                                                |

## 5. API 契約（`POST /api/v1/infer/fridge`）

契約の正は `packages/shared/src/types/fridge.ts`。サーバー `routes/infer.ts` は同じ形の
zod の写し（サーバーは実行時に shared を取り込まない方針のため。**片方だけ直さないこと**）。

- リクエスト: `{ images: [{ imageBase64, mimeType(jpeg|png|webp) }]（1〜2 枚）, locale? }`
  - `unitSystem` は受けない — 分量を出力しない推論への単位系指示は「分量を書け」という圧力になるだけ（`/infer/menu` と同じ判断）
- レスポンス（AgentResult 形・常に 200）: `{ ok: true, data: { items: [{ name(≤50), confidence(0〜1) }]（≤60）} }`
  - `items: []` は「読み取れなかった」— エラーではない。文言と手入力への誘導はクライアント側
- 認可・枠（`/infer/menu-recipes` と同じ作法・チェック順が本質）:
  1. `x-device-id`（必須・書式チェック）
  2. 月次無料枠 `peekMonthlyQuota`（`x-quota-source: token|premium` で飛ばす）
  3. 共有レートプール `checkRateLimit`（`RECIPE_POOL`。専用プールは作らない — 視覚推論 1 回ぶん）
  4. 消費 `recordMonthlyUse` は **provider 成功時のみ**（空の items でも消費する — 推論は実行されコストは発生している）
- 検証 `sanitizeFridgeItems`（サーバーとモバイルで同じ規則の写し）: 捨てる方向のみ・埋めない。
  品名なしは捨てる・confidence は 0〜1 に丸め、無ければ **0（要確認側へ倒す）**・
  同名（正規化一致）は confidence が高い方を残す・60 品超は捨てる

## 6. 確認シートの判断ロジック（`src/utils/fridgeReview.ts`・純関数）

- `classifyFridgeConfidence`: 境界 **0.8 / 0.5**（以上で上の段）。`low` が「たぶん」表示。
  数値でない値は low へ倒す — 高く見せると確認されなくなる
- `buildFridgeReviewItems`: 在庫との重複は `canonicalNameKey`（`name_aliases` 辞書で正規名へ
  落としてから `normalizeItemName`）で判定。重複行は**消さず**に表示して既定オフ
- 在庫への追加はレシート P5 と同じ経路（`addPantryItem`）に乗る。名寄せ辞書は既存の
  自動経路（作れるレシピ表示時など・在庫設計 §6）が育てる — この機能から新経路は作らない

## 7. 無料枠（`docs/フリーミアム設計.md` §7-3 / §11 に追記済み）

- 読み取り 1 回 = 全体枠（月次 N・既定 5）を 1 消費。クライアントは
  `ensureInferenceCredit()` → 成功時 `recordCloudInference()`、サーバーは
  `x-device-id` の月次枠で二重に守る（M2/M3 と同じ二段構え）
- BYOK は無制限（自分のキーで Gemini 直・サーバーを通らない）
- レシート読み取り（無料・ゲートなし）とは扱いが違う: レシートは買った事実の記帳で
  在庫ループの入口として無料にした（2026-08-27 決定）。冷蔵庫写真は任意のタイミングで
  何度でも押せる能動的な AI 機能で、放置すると原価が青天井になるため通常の枠に入れる
