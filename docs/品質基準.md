## 1. セキュリティ

### 1.1 GitHub Security アラート（**ゼロトレランス**）

| アラート種別             | 重大度          | CI ゲート                               | SLA                                      |
| ------------------------ | --------------- | --------------------------------------- | ---------------------------------------- |
| Dependabot（依存脆弱性） | Critical / High | **マージブロック**                      | 検知から 24 時間以内に修正またはピン留め |
| Dependabot（依存脆弱性） | Medium          | 警告表示（ブロックしない）              | 検知から 7 日以内に対応                  |
| Dependabot（依存脆弱性） | Low             | 警告表示（ブロックしない）              | 次回スプリント内に対応                   |
| CodeQL SAST              | Critical / High | **マージブロック**                      | 検知から 24 時間以内に修正               |
| CodeQL SAST              | Medium / Low    | 警告表示（ブロックしない）              | 7 日以内に対応                           |
| Secret scanning          | 全重大度        | **マージブロック + 即時ローテーション** | 検知から 1 時間以内にシークレット無効化  |

**運用ルール:**

- Critical / High の未解決アラートが 1 件でも存在する場合、`main` ブランチへの PR マージを CI が自動的にブロックする。
- 誤検知（false positive）と判定した場合は、リポジトリ管理者（Kei）が GitHub UI から "Dismiss" し、理由をコメントに記載する。Dismiss なしのアラートを残したままマージすることは禁止。
- `npm audit --audit-level=high` を CI に組み込み、high 以上の脆弱性をビルドエラー扱いにする。

## 2. コード品質

### 2.1 静的解析

| 項目            | 基準                                                               | CI ゲート                           |
| --------------- | ------------------------------------------------------------------ | ----------------------------------- |
| TypeScript      | `strict: true`（`noImplicitAny`, `strictNullChecks` 等を全て有効） | エラー 0 件でなければマージブロック |
| ESLint          | `@typescript-eslint/recommended` + `eslint-plugin-react-hooks`     | エラー 0 件でなければマージブロック |
| ESLint warnings | 警告は蓄積しない。新規 warning は 1 週間以内に修正またはルール調整 | 警告表示のみ（ブロックしない）      |
| Prettier        | コード整形の統一（CI で `prettier --check` を実行）                | 差分あればマージブロック            |

> **Windows のローカルで `pnpm format:check` を全体に走らせない。** このリポジトリは
> `core.autocrlf=true`（`.gitattributes` なし）でチェックアウトが CRLF になるのに、
> Prettier は `endOfLine: "lf"` を要求する。そのため**1 行も触っていないファイルまで含めて
> 全件が warn になる**（2026-08-23 時点で 475 件。`README.md` すら落ちる）。壊したように
> 見えるが git 上の差分は無い。
>
> ローカルで見るべきなのは**変更したファイルだけ**:
> `git diff --name-only <base>..HEAD | xargs npx prettier --check`。
> pre-commit（`scripts/agent/format-staged.mjs`）が**ステージ済みファイルのみ**を整形するのも同じ理由。
> ここで全体に `pnpm format --write` を打つと、数百件の偽の差分が作業ツリーに出る
> （事故の経緯は `docs/開発ハーネス.md` §3）。CI は Linux（LF）なので影響を受けない。

### 2.3 テストを書くときの落とし穴（このリポジトリ固有）

#### 画像を Pressable で包むと、テストが緑のまま写真が消える（2026-08-25）

**症状**: レシピ詳細の表紙写真が真っ暗になった。ユニットテストは全部緑。

**原因**: `heroPhoto` は `StyleSheet.absoluteFillObject`（＝**親に対する**絶対配置）。
タップできるようにするため `Pressable` を挟んだが、その `Pressable` に大きさが無いので
画像が **0×0** に潰れた。`width: '100%'` の画像も同じで、親に幅が無ければ 0 になる。

**対処**: 包む側にも同じ大きさを持たせる（`style={StyleSheet.absoluteFill}` や `width: '100%'`）。

**なぜテストで捕まらないか**: jest（react-native の testing-library）は**レイアウトを計算しない**。
要素が描画ツリーに在ることは確かめられても、**潰れているかは分からない**。
画像・絶対配置・`flex` を触ったら、緑でも実機かエミュレータで目視する。

踏むと**テストが緑のまま本番の分岐が死ぬ**類のもの。見つけたらここに足す。

#### レビューが通っても、一度も実行されていないスクリプトは 1 行目から死ねる（2026-09-01）

**症状**: ストアスクショ撮影スクリプトが、どのショット指定でも 1 枚も撮れずに
`ReferenceError` で即死していた。#258（調理セッション汚染ガード）はロジックレビューを
通ってマージ済み・その後の監査のコードレビューも通過していたのに、である。

**原因**: `scripts/**` の host 側スクリプトは**テストも typecheck も CI も通らない**。
#258 は `let sessionGuardUsable` の宣言をファイル後半の節に置いたが、モジュールの
トップレベルで走る撮影ループが先にそれを参照する関数を呼ぶため TDZ で即死する。
`node --check` は構文しか見ないので通る。さらに直したら 2 匹目がいた:
wipe 直後は DB 未作成で初回クリアが失敗し、ガードが `false` に latch して
run 全体で黙って死んでいた（つまり**設計どおりの条件では一度も動けない実装**だった）。
マージから発覚まで 5 日・その間の撮影はゼロ回だったので、誰も気づかなかった。

**対処**: `scripts/**` を足したり直したりしたら、**マージ前に想定した使い方で
最低 1 回実行する**（アプリの「エミュレーターで動作確認」ルールと同じ扱いにする）。
レビューと `node --check` は実行の代わりにならない。修正は #262。
なお eslint の `no-use-before-define` はこの形（宣言は関数定義より前・**呼び出しだけ**が先）を
捕まえられない — 実測で確認済み。機械的な手前の網は専用検査
`scripts/agent/check-script-tdz.mjs`（CI Q-6・#263、`docs/開発ハーネス.md` §3）だが、
2 匹目（latch）のような論理の死角は実行でしか出ない。
**`check-script-tdz.mjs` が捕まえない形がもう 1 つある**（2026-09-05 実測）: 関数の**中からだけ**参照する
module スコープの `const` を、top-level `await` で呼ばれる関数より**後ろ**に宣言した形
（`test-customizations.mjs` に `BUILTIN_TOOLS` を足したとき、25 体全部が
`Cannot access 'BUILTIN_TOOLS' before initialization` で落ちた）。検査は「呼び出しが宣言より先」しか
見ないので、関数越しの参照は素通りする。対処は同じ — **足したら実行する**。定数はファイル先頭の
`failures` / `passes` の隣に置く。

## 7-2. 再発防止の規約 — 水平展開監査で見つかった 4 つの根本原因（2026-09-05）

冷蔵庫写真の実機 E2E で出た不具合（原寸送信 400・カテゴリ名の品目・無反応）を
根本原因まで遡って全機能を監査した結果、同根の穴が多数見つかった。個別修正では
再発するので、**原因の型ごとに規約**として固定する。

### ① 画像をサーバーへ送るときは必ず共通ヘルパーを通す

- **症状**: 実機カメラ写真（quality 1・6.5MB JPEG → base64 8.6MB）がサーバーの
  Zod 上限 8,000,000 字を超えて 400。「サーバーエラー (400)」しか出ない
- **原因**: 画像送信の共通入口が無く、縮小（前処理）が provider 任せだった。
  冷蔵庫・食事写真・レシート画像・感想調整の 4 経路で抜けていた
- **対処**: `apps/mobile/src/services/image-payload.ts` の `toInferImagePayload()`
  （縮小 → 失敗時は元画像 → JPEG 化）が唯一の入口。**新しい画像送信経路を作るときは
  必ずこれを通す。** 400/413 の保険は `ai-error.ts` の `serverErrorFor()` が変換する

### ② AI の出力・エラーを生のまま利用者へ流さない（語彙防御・文言変換）

- **症状**: 「調味料」「飲料」等のカテゴリ名が在庫の品目になる。英語の Java
  スタックや「サーバーエラー (400)」がそのまま画面に出る
- **原因**: サニタイズが構造（型・長さ）のみで**語彙の検証がゼロ**。エラーは
  provider ごとにばらばらに焼き込み
- **対処**: 語彙は shared `CATEGORY_NAME_WORDS` / `isCategoryName()`（サーバー写しは
  `lib/fridge-vision.ts` の `isCategoryItemName()`）。在庫へ流す全経路（冷蔵庫・
  レシート・食事写真・名寄せ）がこれを通す。エラーは `ai-error.ts` の
  `serverErrorFor()`（ステータス→文言）と `readableErrorMessage()`（userVisible の
  印が無い例外は fallback へ）を使う。**ルートは生出力を素通しで返さない** —
  sanitize 関数を必ず挟む

### ③ 契約の正（shared）と写し（server）は突合テストで縛る

- **症状**: base64 上限が写し（サーバー）にだけあり契約の正に無く、送信側の
  前処理漏れに契約テストで気づけなかった
- **原因**: サーバーは実行時に shared を取り込まない方針（tsconfig rootDir）で、
  写しのズレを検出する仕組みが無かった
- **対処**: 運命を分ける値（上限・語彙リスト）は shared に置き、サーバーの写しとは
  `apps/server/src/__tests__/shared-parity.test.ts`（shared ソースをテキストで読む）で
  突合する。**新しい写しを作ったら突合テストに 1 行足す**

### ④ 利用者の操作には必ず結果を言う（無反応の禁止）

- **症状**: 献立の差し替えで候補ゼロだと何も起きない。食事写真の在庫反映が
  失敗しても黙って戻る。グループ切替の失敗が無言
- **原因**: 「変化なし」と「成功」を同じ戻り値で返す・エラーの握りつぶし
- **対処**: 変化ゼロもエラーも**必ずトースト/文言で言う**。サービス層は
  「やらなかった理由」を戻り値で区別できる形にする（例:
  `replaceMenuDay` の `ReplaceMenuDayResult`）。`catch(() => undefined)` で
  利用者操作の結果を握りつぶさない

### ⑤ BYOK は「上限解除」のみ（オーナー決定・2026-09-05）

BYOK 前提の機能・BYOK と通常経路の挙動差を作らない。詳細と点検済みの意図した差の
一覧は `docs/フリーミアム設計.md` §9-1。両経路の同一性は
`byok-image-parity.test.ts`（画像縮小）と写し系テストで固定する。
