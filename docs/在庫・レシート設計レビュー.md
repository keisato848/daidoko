- `apps/mobile/plugins/withDaidokoOcr.js` が `play-services-mlkit-text-recognition-japanese` を

- `app.json` の `plugins` に `./plugins/withDaidokoOcr` が入っている

上の一文は #68（2026-07-12）で追記されたもので、**復活から3週間後に「休止中」と書かれた**。
症状2はまさにこの生きている経路が出しているので、記述を信じると原因に辿り着けない。

## 1. 症状と原因

### 症状1: 初回登録で名寄せの推論が走らなかった

**原因: 辞書を埋める処理の呼び出し元が「在庫で作れるレシピ」画面ひとつしかない。**

`resolvePantryNames()` を呼ぶのは `app/(tabs)/cookable.tsx` だけで、画面表示時に自動実行される。
在庫への登録（手入力・レシート・買い物リストからの移動）はどれも辞書に触らない。
**cookable を一度も開かなければ辞書は空のまま**で、これが「登録しても推論されない」の正体。

### 症状2: 初回のレシート読み取りがエラーになる（モジュールのダウンロード中らしき挙動）

**原因: 可用性の判定が実態を見ておらず、失敗時の逃げ道も無い。** 3つ重なっている。

1. `DaidokoOcrModule.kt` の `isAvailable()` が **無条件で `true` を返す**
   （`withDaidokoOcr.js` の Kotlin ソース内 `promise.resolve(true)`）
2. そもそも `receipt.tsx` は `isAvailable()` を呼んでいない。
   `createClientOcrRecognizer()` が「`NativeModules.DaidokoOcr` が存在するか」だけで判定し、
   存在すれば端末内 OCR 経路を選ぶ
3. ML Kit は unbundled 版なので**モデルは Play Services が必要に応じて配布する**。
   `com.google.mlkit.vision.DEPENDENCIES = ocr,ica,barcode_ui` の meta-data で
   インストール時ダウンロードを依頼してはいるが、これは**ベストエフォート**（インストール直後・
   通信が無い・Play Services が後回しにした、のいずれでも未取得のまま）

未取得のまま `recognizer.process()` を呼べば失敗し、`receipt.tsx` の catch が
**ML Kit の生のエラー文字列をそのまま画面に出す**。クラウド経路へのフォールバックは無い。

設計文書 §5.6 は「端末内 OCR が使える端末では優先し、無い端末ではクラウドへ自動切替」と
書いているが、**「モジュールはあるが今は使えない」という第三の状態を想定していない**。
現実にはこれが初回起動時の既定状態になる。

### 症状3（コードから発見・ユーザー未報告）: 表記違いが在庫に重複して積まれる

`pantry.service.ts` の upsert は `nameNormalized` の完全一致（＋単位一致）でマージ先を探し、
**辞書を一切参照しない**。`normalizeItemName` は NFKC（全半角）とカナ折り畳み（カタカナ→ひらがな）
までで、**漢字↔かなは吸収しない**。よって「人参」と「にんじん」は別レコードになる。
レシートからの一括追加はこの経路なので出やすい。

### 症状4（コードから発見）: 辞書が効いても片側しか寄らない

`utils/itemMatch.ts` は辞書を**両側**に当てる正しい作りになっている（`ca`/`cb`）。
しかし辞書に入るのは在庫側の名前だけなので、実際には片側しか canonical に移らない。

在庫「にんじん」・レシピ「人参」で、AI が canonical を「にんじん」と決めた場合:

|            | 元の名前 | 辞書適用後                       |
| ---------- | -------- | -------------------------------- |
| 在庫       | にんじん | にんじん                         |
| レシピ材料 | 人参     | **人参**（辞書に無いので素通り） |

一致しない。部分一致（3文字以上の包含）も効かない。逆に AI が「人参」を canonical に選べば
たまたま一致する。**AI が選んだ表記とレシピの表記が偶然揃ったときだけ効く**。

## 1.5 元の設計が守ろうとしていたもの

直す前に、何を意図していたかを押さえる。**どれも当時としては筋が通っており、
壊れたのは意図ではなく前提のほう**だった。

1. **同義語辞書をソースコードに持たない**（§7-4「表記ゆれ＝単純正規化のみ。同義語辞書は後追い」）。
   `itemMatch.ts` の冒頭も "the source carries no ever-growing synonym dictionary" と明言している。
   人が書き足し続ける表は必ず保守されなくなるので、ルール（NFKC＋カナ折り畳み＋部分一致）で
   行けるところまで行き、足りない分だけ AI に解かせてキャッシュする。辞書が無ければ
   ルールに自然に劣化する。**この判断は今も正しい。**
2. **AI コストを最小に**（§7-2「レシート＝端末内 OCR で無料。任意で Vision 高精度モード＝
   プレミアム特典」）。当時は収益化が広告のみで推論単価も今の倍以上だったので、
   無料・オフラインで動く経路を既定に置いた。
3. **保存する名前を汚さない**（正規化も辞書も読むときだけ当てる）。
   AI が誤って寄せても辞書を直せば過去の突合まで一斉に直り、データ移行が要らない。
   名寄せ辞書のメンテ画面はこの性質の上に成り立っている。**この判断も正しい**（§3.3）。
4. **包装商品は JAN で厳密識別**。名前突合は JAN を持たないもの（レシピ材料・バラ売り）の次善策。

### なぜ壊れたか

**辞書の範囲が、比較の相手が増えたあとも据え置かれた。**
`cdbabdd`（2026-07-01）で名寄せキャッシュが入ったとき、変更されたのは
`cookable.service.ts` と `shopping-list.service.ts` だけだった。目的は P4「在庫で作れるレシピ」の
充足率を上げることで、**在庫側の名前を寄せれば足りた**。辞書が在庫の形をしていて、
埋める処理が cookable 画面にあるのは、その出自そのもの。
その後 P5 でレシートが入り（#68）、レシピ材料が突合のもう一方の側になったが、範囲は据え置かれた。

**意図 2 は前提が変わった。** #68 でクラウド経路はプレミアム特典ではなく**無料の標準経路**になり
（§7-2 の記述と既に矛盾している）、PR#170 の思考オフで単価が ¥0.35 になった。
「無料だから端末内 OCR を既定にする」の根拠は薄れている。

## 3. 再設計案

### 3.1 名寄せ: 「両側を canonical 空間へ写す」に改める

辞書の定義を**「任意の食材表記 → canonical」**に広げる（在庫名に限定しない）。
解決対象に**レシピの材料名**を含める。データモデル（`name_aliases`）は変更不要 —
`source_normalized` に何を入れてよいかの解釈を広げるだけで済む。

### 3.2 埋めるタイミング: 「ルールで当たらなかった残り」だけを、突合する場所で解決する

**初版は「登録が確定した時点で解決する」と書いていたが、撤回する。** 登録のたびに投げるのは
無駄が多い。`itemMatch` は完全一致（NFKC＋カナ折り畳み）と部分一致（3 文字以上の包含）で
大半を拾えるので、「玉ねぎ」「にんじん」のような素直な名前は**辞書が無くても当たる**。
そこへ AI を投げるのは払い損で、意図 1（ルールで行けるところまで行き、足りない分だけ AI）
からも離れる。

正しくは:

- **登録時は AI を呼ばない。** 名前をそのまま保存するだけ
- **突合する場所**（作れるレシピ・足りない材料・レシピ検索）でまずルールと既存の辞書で照合し、
  **どれにも当たらなかった名前だけ**を解決対象にする。解決したらキャッシュに入れて再照合する
- 対象は在庫側に限らない。**当たらなかったレシピ材料名も同じ扱い**（§3.1）

直すべきは埋めるタイミングではなく、**埋める対象（両側）と、突合するすべての場所で解決が走ること**
だった。症状 1 の本質は「登録時に走らない」ことではなく、「cookable 以外のどこでも走らない」こと。

**この形なら枠の心配はほぼ消える。** 品目 20 点のレシートを読んでも、保存するだけなので AI は
呼ばれない。実際にレシピと突き合わせる段になって、なお当たらないものだけが対象になる。
呼び出し回数は「解決する価値があった名前の数」に自然に収束する。

（参考: 名寄せの無料枠は 1 日 30 件＋広告ボーナス 30 で**上限 90/日**。写真レシピ等のトークンとは
別枠で、そちらは #174 で広告視聴の 1 日上限が撤廃され無制限に貯められる。
名寄せ側の 90/日 が実際に当たるようなら上げればよい — 先回りしない）

### 3.3 重複在庫: 保存は生のままにし、統合は「提案」にする

**当初この節は「保存時に canonical へ寄せる」と書いていたが、撤回する。**
元の設計が「正規化も辞書も**読むときだけ**当て、DB には入力どおりの名前を残す」としていたのは
意図的で、実利がある:

- **AI が誤って寄せても、辞書を直せば過去の突合まで一斉に直る。**データ移行が要らない
- 設定の「名寄せ辞書」メンテ画面（§6 末尾）は、この性質の上に成り立っている

canonical を保存時に焼き込むと、この自己修復性が失われる。誤って「白ねぎ」を「ねぎ」に
寄せたあと辞書を直しても、**既に統合された在庫行は戻らない**。しかも在庫は数量を合算するので、
どの行が何を寄与したのかも失われる。**誤った統合は元に戻せない**。

書き込み時に辞書でマージ先を探す案（保存名は生のまま・マージ判断だけ辞書依存）も、
統合そのものは同じく不可逆なので同じ問題を持つ。程度が軽いだけで質は変わらない。

したがって:

- **自動では統合しない。** `addPantryItem` のマージ先探索は現状どおり
  `name_normalized` の完全一致（＋単位一致 / JAN 一致）のままにする
- **在庫画面で「同じものかもしれない」候補を提示し、統合はユーザーの確認を挟む。**
  判定には辞書＋既存の `itemNamesMatch` を使う。破壊的な操作なので、AI の推測を
  そのまま実行しない
- 突合（作れるレシピ・足りない材料）は今までどおり**読むときに**辞書を当てる。
  §3.1・§3.2 で辞書が両側に育てば、統合しなくても突合は正しくなる

**重複行が残ること自体は、突合が正しく効いていれば実害が小さい。**「にんじん」と「人参」が
2行あっても、どちらも在庫として認識されればレシピは作れる。困るのは数量の合算だけで、
そこは統合の提案で解けば足りる。

なお、毎回辞書を引く負荷が問題になった場合に限り、canonical を**再計算可能な派生列**として
持つ余地はある（辞書の変更時に再計算する前提。保存名は生のまま）。先回りしては入れない。

### 3.4 OCR: 端末内で文字にし、テキストだけを AI に構造化させる（決定 2026-08-15）

**端末内 OCR は畳まない。** レシート以外の 3 か所で使われており、畳むと巻き添えになる:

| 使い道                                 | 場所                                                                                  |
| -------------------------------------- | ------------------------------------------------------------------------------------- |
| レシート読み取り                       | `app/(tabs)/receipt.tsx`                                                              |
| S10 文字入り画像からのレシピ取り込み   | `app/(tabs)/recipes/import-ocr.tsx`（ここだけ `isClientOcrAvailable()` を呼んでいる） |
| 写真レシピのヒント（文字＋画像ラベル） | `app/(tabs)/recipes/import-photo.tsx` → `recipe-photo.agent.ts`                       |

そのうえで、レシート経路は**役割分担を変える**。今までは「端末内で読む**か**クラウドで読む」の
二択だったが、**端末内 OCR は文字起こしに専念し、構造化は AI に任せる**:

```
レシート写真
  ├ 端末内OCRが使える → 文字起こし → **テキストだけ**を AI へ → 構造化（品目・数量・単位）
  └ 使えない/読めない → 従来どおり**画像**を AI へ（Vision）
```

これを選ぶ理由:

- **安い。** 画像トークンが消えるので、同じ構造化を画像で解かせるより安く済む
- **精度が上がる。** `utils/receiptParser` のヒューリスティックを捨て、非食品除外・重複統合・
  数量抽出という**既にクラウド側に実装済みのロジック**（PR#179 含む）に一本化できる
- **画像が端末から出ない。** レシートは購入履歴そのものなので、送るものが減るのは実利がある
- **端末内 OCR の存在価値が残る。** 「無料だから」ではなく「前処理として速く安い」という理由に変わる

実装で必ず要ること:

1. **`isAvailable()` を本当の可用性にする。** 今は無条件 `true`。ML Kit の
   `ModuleInstallClient.areModulesAvailable()` でモデル取得済みかを問い合わせる
2. **失敗は必ず画像経路へ落とす。** モデル未取得・OCR 失敗・文字が取れない、のいずれでも
   画像を送る経路にフォールバックする。**生の ML Kit エラーを画面に出さない**
3. **`receipt.tsx` は `isAvailable()` を呼ぶ。** 今はモジュールの存在だけで経路を選んでいる

サーバー側は `POST /api/v1/infer/receipt` にテキスト入力の口を足す（スキーマと後処理は画像版と
共用し、プロンプトだけ差し替える）。S10 と写真レシピのヒントは今回触らない。

## 4. 決めてほしいこと

1. ~~**端末内 OCR を残すか、畳むか。**~~
   **決定済み（2026-08-15）: 残す。ただし役割を「文字起こし」に限定し、構造化は AI に任せる（§3.4）。**

2. **名寄せを入口で自動的に AI へ投げてよいか。** 体験は良くなるがコストと無料枠を消費する。
   投げない設計（辞書が育つのを待つ）は今と同じ症状を引きずる。
3. **既存の重複在庫をどうするか。** §3.3 のとおり自動統合は勧めない。
   放置（突合が効けば実害は数量の合算だけ）／在庫画面に統合の提案を出す、のどちらか。
