> 作成: 2026-08-07
> ステータス: 実装中（P2）
> 前提: `docs/海外展開の検討.md`（なぜ英語圏か・なぜ EEA を外すか）

---

## 1. なぜ今やるのか（**当初の着手条件は誤りだった**）

当初、着手条件を「**日本語版で再現ループが 1 周した実績**」とした。
摩擦の大きいループが回るかは言語に無関係で、回らないなら英語化しても回らない、という理屈だった。

**これは循環していた。**

- ストア掲載も機能も日本語のみ
- 到達可能な市場は日本語話者に限られる
- Play インプレッションは **約 5/日**、インストールは実質ゼロ

**日本語のサービスを、日本語圏以外の誰がインストールするのか。**
インストールがゼロなのは「ループが機能していない証拠」ではなく、
**誰も試していない証拠**にすぎない。検証できない状態を検証の条件にしていた。

律速は転換率ではなく**リーチ**である（2026-07-27 の実績確認で判明済み）。
多言語化はそのリーチを広げる施策であって、リーチが出てから着手するものではない。

### 現在の着手条件

| 段階   | 条件                                                                               |
| ------ | ---------------------------------------------------------------------------------- |
| P1・P2 | **なし**（§9 の実装準備が揃った時点で着手可）                                      |
| P3     | P2 完了 ＋ **R0 の英語での品質再測定**（これは市場ではなく品質のゲートなので残す） |
| P4     | P3 完了 ＋ ユーザー承認（公開物のため）                                            |

**P0（アレルギー）は機能として実装しない**ことになった（§5）。免責と注意書きで対応済み。

## 3. 技術選定

### 3-1. ライブラリ: `expo-localization` + `i18n-js`

| 候補                            | 判断                                                                                   |
| ------------------------------- | -------------------------------------------------------------------------------------- |
| **expo-localization + i18n-js** | **採用。** Expo 公式で SDK 54 に追従。依存が軽く、必要なのは辞書引き・補間・複数形だけ |
| react-i18next                   | 見送り。React Context・Suspense・プラグイン機構は本アプリの規模に対して重い            |
| 自前実装                        | 見送り。**複数形と数値・日付の書式**を自前で持つ価値はない                             |

`expo-localization` は端末のロケールと**地域**（`region`）を返す。地域は単位系の既定
（§4）に使う。

### 3-2. 辞書の置き場と形

```
apps/mobile/src/i18n/
├── index.ts            # 初期化・t() のエクスポート・ロケール解決
├── locales/
│   ├── ja.ts
│   └── en.ts
└── __tests__/
    └── parity.test.ts  # ja と en のキーが一致することを検証
```

**JSON ではなく TypeScript** にする。理由は**キーの型を効かせるため**。
`ja.ts` を `as const` で書き、`en.ts` に同じ型を要求すれば、
**キーの抜けと打ち間違いがコンパイルで落ちる**。

```ts
// ja.ts
export default {
  recipe: {
    refine: {
      title: 'お店の味に近づける',
      feedbackLabel: '作ってみてどうだった？',
      hint: '味の方向（甘い・辛い・濃い・薄い）を書くほど直しやすくなります。',
    },
  },
} as const;

// en.ts
import type ja from './ja';
const en: typeof ja = {
  /* 抜けがあればここで型エラー */
};
```

### 3-3. キーの命名

`<領域>.<画面または機能>.<用途>`。例: `recipe.refine.title` / `common.error.offline`。

**画面のファイル構成に合わせる**（`app/(tabs)/recipes/[id]/refine.tsx` → `recipe.refine.*`）。
どのキーがどこで使われるかを、辞書だけ見て追えるようにするため。

### 3-4. 複数形と補間

日本語には複数形が無く、英語にはある。**実測で数値を含む文言は多い**
（「写真${n}枚」「最新${n}件」「今日あと${n}回」など）。

i18n-js の複数形機能を使い、**辞書側で吸収する**。

```ts
// ja.ts
photoCount: { one: '写真%{count}枚', other: '写真%{count}枚' },
// en.ts
photoCount: { one: '%{count} photo', other: '%{count} photos' },
```

**文字列連結で文を組み立てない。** 語順が言語で変わるため、文全体を1キーにする。

## 4. 単位系（P1）— 翻訳ではなく「正しさ」

AI は「180度」「大さじ1」を出す。**米国利用者に 180°F と読まれれば料理が失敗する。**
tbsp も英 15ml / 豪 20ml で違う。R2 は分量を具体値で変える機能なので、
**単位系が曖昧だと機能の根幹が壊れる**。

### 実装（2026-08-11・1.5.0 の次のリリース向け）

| ところ       | 実装                                                                            |
| ------------ | ------------------------------------------------------------------------------- |
| 変換         | `apps/mobile/src/utils/unitSystem.ts`（純関数・表示のみ）                       |
| 設定の保持   | `app_meta.unit_system` ＋ `stores/unitSystem.store.ts`（描画から同期で引く）    |
| 既定         | 端末の地域（US/LR/MM → imperial、他 → metric）。**既定は保存しない**            |
| 設定 UI      | 設定 → 表示 → 単位（2 択なのでその場で選ばせる）                                |
| 表示への適用 | レシピ詳細・料理中モードの分量と手順本文                                        |
| AI への指示  | `output-locale.ts` の写し 2 つに `withUnitSystem()`。写真からレシピ・感想で調整 |

**メートル法では AI のプロンプトを一切変えない。** 本体がすでにメートル法前提で
書かれ、その内容で品質を測ってあるため（`docs/レシピ推論の評価設計.md`）。
指示を足すのは imperial のときだけ。

**変換は確実に分かるものだけ。** 「適量」「1個」「大さじ3」は原文のまま出す。
「度」は加熱の温度らしい範囲（40〜300）だけ変換する — 「2度揚げる」を温度と読むと
数字が化けるため。**間違った数字を出すくらいなら原文のまま出す。**

### 方針

| 対象         | 保存                         | 表示                                           |
| ------------ | ---------------------------- | ---------------------------------------------- |
| 分量         | **原文のまま**（変換しない） | 表示時に整形                                   |
| 温度         | 原文のまま                   | 表示時に ℃ ⇄ ℉                                 |
| 単位系の選択 | `app_meta` に保存            | 既定は端末の地域（US → imperial、他 → metric） |

**保存値を変換しない**のが要点。変換して保存すると、丸め誤差が版を重ねるたびに蓄積し、
`recipeDiff` が「変わっていないのに変わった」と表示する。R2 の安全装置を壊す。

### AI 側

プロンプトに**出力する単位系を明示する**。変換ではなくモデルに直接その単位で書かせる。
アプリ側の整形は既存レシピの表示用に留める。

## 5. アレルギー — 機能として実装しない（2026-08-08 決定）

**アレルゲンの検出・除去・警告は実装しない。** 免責（ポリシー）＋注意書きで対応する。

### なぜ実装しないのか

**保証できないものを、保証しているように見せる方が危険だから。**

AI 推論に基づいて「このレシピはナッツ不使用です」と示せば、外れたときに
**注意書きしかない場合より悪い結果**になる。誤った安心を与えるため。

材料は写真から判別できないもの（だし・油・調味料の原材料）を含み、
R2 では感想に応じて**材料が追加される**。この不確かさは仕組み上なくならない。

当初は「欧米では前提条件」として実装を計画したが、それは強すぎた。
**レシピアプリの一般的な扱いとしても、免責＋注意書きが標準**である。

### 実装したこと

| 場所                        | 内容                                                             |
| --------------------------- | ---------------------------------------------------------------- |
| `docs/privacy-policy.md` §7 | AI 生成物の免責。**アレルゲンの検出・警告を行わない旨を明記**    |
| 写真レシピの警告            | 「分量・手順」だけでなく**材料そのもの**の確認を促す文言に変更   |
| R2（お店の味に近づける）    | 差分プレビューに注意書きを追加。**材料が追加されうる**ことを明示 |

**R2 は写真レシピより強い注意を出す。** 材料を増やす経路であり、
「もっとコクを」という感想で乳製品が足されるといったことが起きるため。

### 英語版で必要になること

免責の**英訳**。§9 の P2（文字列外部化）と同時に行う。
ポリシーの英語版も P4（ストア掲載）に含める。

## 6. 意味の同一性をどう担保するか（**最重要**）

**英語が日本語と意味的に同一である**ことが要件。これは翻訳の丁寧さの話ではなく、
**意味が崩れると機能が壊れる**文言が実在するためである。

### 6-1. 型システムでは守れない

`en.ts` に `typeof ja` を要求すれば**キーの抜け**は落ちる（§3-2）。
しかし**中身が正しいかは一切見ていない**。空文字でも、意味の違う文でも型は通る。

さらに悪いことに、**既存テストは日本語文字列に固定されている**。

```ts
expect(result.error?.message).toContain('インターネットにつながっていません');
```

このままでは、英語側は**誰も検査しない**。i18n 導入時にこの手のテストを
「キーの一致」に置き換えるだけで済ませると、**#120 で作った区別が英語で失われても気づけない**。

### 6-2. 壊れると何が起きるか（実在する3つ）

| 崩れ方             | 実例                                                                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **区別が消える**   | 「つながらない」（再接続で直る）と「上限に達した」（待つしかない）。**取るべき行動が違う**。英語で両方 "Please try again" になれば #120 の作業は無に帰す          |
| **保証が変質する** | R2 の「**ここに出ていない材料・手順は変わっていません**」。これは AI が黙って書き換えないことの保証。英語で "may not have changed" 等に弱まれば**説明が嘘になる** |
| **免責が弱まる**   | 「**アレルゲンの検出・除去・警告を行いません**」。曖昧になれば免責として機能しない（§5）                                                                          |

### 6-3. 701 件を一律に扱わない

| 階層  | 中身                                                         | 扱い                                       |
| ----- | ------------------------------------------------------------ | ------------------------------------------ |
| **A** | **意味が崩れると機能が壊れる**（エラーの区別・保証文・免責） | **意図を併記**し、**両言語をテストで検査** |
| **B** | 体験に効く（ラベル・ボタン・ヒント）                         | 通常の翻訳                                 |
| **C** | 声（空状態・コーチマーク）                                   | **直訳しない**。英語として書き直す         |

**C を直訳しないのが要点。** 「お店で食べたあの味、撮っておきませんか」を逐語訳しても
英語として響かない。ここは意味の同一性より**同じ効果**を優先する。
逆に **A は効果より意味の正確さを優先する**。

### 6-4. A 階層は「意図」を辞書に持たせる

日本語文だけでは、翻訳者（将来の自分を含む）が**何を守るべきか分からない**。
何を伝え、**何と混同させてはいけないか**を併記する。

```ts
// locales/ja.ts — A 階層のみ intent を持つ
error: {
  offline: {
    text: 'インターネットにつながっていません。接続してからもう一度お試しください。',
    /** 必ず伝える: 再接続すれば直ること。混同禁止: 利用枠切れ（待つしかない） */
    intent: 'MUST convey: reconnecting fixes it. MUST NOT be confusable with quota exhaustion.',
  },
}
```

`intent` は**英語のまま書く**。翻訳する人が読むものであり、翻訳対象ではないため。

### 6-5. 機械的な検査（これが本体）

意図を書いただけでは守られない。**テストで縛る。**

既存の #120 のテストを**ロケール横断に書き換える**。

```ts
describe.each(['ja', 'en'])('%s: 失敗時の文言', (locale) => {
  it('オフラインと利用枠切れが別の文言になる', () => {
    expect(t('error.offline', locale)).not.toBe(t('error.quotaExceeded', locale));
  });
  it('オフラインは再接続を促す', () => {
    // 言語ごとの期待キーワードは辞書と別に持つ（翻訳と一緒に変わらないように）
    expect(t('error.offline', locale)).toMatch(EXPECTED_KEYWORDS[locale].reconnect);
  });
});
```

**キーワードの期待値を辞書と別ファイルに置く**のが肝。同じファイルに置くと、
翻訳を直すときに期待値も一緒に直してしまい、検査が意味を失う。

さらに `parity.test.ts` で次を検査する。

- ja と en のキーが一致（型でも落ちるが、実行時にも確認）
- **A 階層の全キーに `intent` がある**
- **A 階層の en が空文字でない**（型では通ってしまう）

### 6-6. A 階層の洗い出し結果（2026-08-09 実測）

`node scripts/agent/extract-critical-strings.mjs` で候補を機械抽出した。**30 件**
（949 件のうち約 3%）。目視だけでは必ず漏れるため、抽出は機械で行い、A/B/C の判定を人がする。

| 分類          | 件数 | 中身                                                    |
| ------------- | ---- | ------------------------------------------------------- |
| `user-action` | 20   | オフライン / 枠切れ / 混雑 / 「何を書けばよいか」の区別 |
| `destructive` | 7    | 削除・置き換えの確認文（誤読すると復旧できない）        |
| `ai-caveat`   | 2    | AI 生成物の注意書き                                     |
| `guarantee`   | 1    | R2 の「ここに出ていない材料・手順は変わっていません」   |

#### 抽出で分かったこと（**設計に反映済み**）

**JSX のテキストノードを拾わないと、最重要の文言が丸ごと漏れる。**
最初の実装はクォート内リテラルだけを見ていたため、`guarantee` が **0 件**だった。
R2 の保証文は `<Text>` の子テキストで、クォートに囲まれていない。
**いちばん守りたいものが、いちばん漏れやすい形で書かれていた。**

**「エラー文言＝ A 階層」ではない。** 当初 155 件が挙がったが、
「Base64 データが不正です」のような内部エラーは、英語が多少ぶれても
**ユーザーの行動は変わらない**（どちらにせよ復旧できず問い合わせるしかない）。
A 階層の基準は「意味が崩れるとユーザーが**違う行動を取る**か、**保証が嘘になる**」こと。

**ラベルと確認文を分ける。** 「削除」（ボタン）は B 階層、
「${count}件の調理ログを削除しますか？この操作は取り消せません」は A 階層。
前者は誤訳しても押す前に気づけるが、後者は**押した後では戻せない**。

**AI プロンプトは A 階層に混ぜない。** サーバーの `lib/*.ts` は P3 で
対象国ごとに書き換えるもので、翻訳対象の UI 文言とは性質が違う。
ただし `mobile/src/services/*.provider.ts` は**除外しない** —
BYOK 用のプロンプト写しと `visionErrorMessage()` が同居しており、
ファイル単位で外すと最重要の文言ごと消える。

#### 移行後に `intent` を書いた A 階層（2026-08-09 実績）

| キー                                            | 何を守るか                                           |
| ----------------------------------------------- | ---------------------------------------------------- |
| `error.offline` / `quotaExceeded` / `transient` | 取るべき行動の区別（再接続 / 待つ / 少し待つ）       |
| `error.notADish`                                | 写真の問題であること・どんな写真なら通るか           |
| `ai.disclaimer`                                 | AI 生成物であること＋アレルギーの注意（唯一の警告）  |
| `ai.error.apiKey`                               | 待っても直らない（キーを直すしかない）               |
| `ai.error.byokQuota`                            | 自分のキーの上限であって、アプリの上限ではない       |
| `recipe.refine.diffGuarantee`                   | 差分に出ていないものは変わっていない（絶対の保証）   |
| `recipe.refine.noChange`                        | 失敗ではなく入力不足 — 次に何を書けばよいか          |
| `recipe.refine.caution`                         | AI が材料を**増やす**ことがある／保存前に全部確認    |
| `recipe.photo.disclosure`                       | 写真が端末を離れること＋保存されないこと（両方必須） |
| `recipe.detail.deleteConfirm`                   | 削除は取り消せない                                   |
| `recipe.list.deleteConfirm`                     | 件数＋取り消せない                                   |
| `home.delete.confirm`                           | 件数＋取り消せない                                   |
| `backup.restore.confirm`                        | 現在のデータが**置き換わる**（統合ではない）         |
| `backup.migration.importConfirm`                | 同上（移行ファイルから）                             |
| `pantry.receipt.disclosure`                     | レシート写真がクラウドへ渡ること＋保存されないこと   |
| `byok.detail.storage`                           | セキュア領域に保存・自前サーバーへは送らない         |
| `byok.detail.destination`                       | Google へ直送・**利用者の Google アカウントに課金**  |
| `byok.detail.migration`                         | 移行ファイルに含まれない（新端末で貼り直しが要る）   |
| `paywall.terms`                                 | 自動更新・課金時点・解約方法（ストア規約の要求）     |
| `paywall.tokenHint`                             | 貯めた回数は**失効しない**                           |

### 6-7. 仕組みが効くことの実証（2026-08-09）

机上の設計で終わらせず、**わざと意味を壊してテストが落ちるか**を確かめた。
落ちなければ §6 は絵に描いた餅なので、着手条件に含めている（§9）。

| 実験                   | 壊し方                                                    | 結果             |
| ---------------------- | --------------------------------------------------------- | ---------------- |
| 保証を弱める           | `is unchanged` → `should be unchanged`                    | ✅ en だけ落ちた |
| 区別を潰す             | オフラインを `Something went wrong. Please try again.` に | ✅ 落ちた        |
| **最も紛らわしい崩れ** | 枠切れなのに `Check your connection` と促す               | ✅ 落ちた        |

いずれも **ja は通ったまま en だけが落ちる**。日本語を壊さずに英語だけ崩れる、という
実際に起こる形を再現できている。

#### 分かった弱点（**このまま放置しない**）

**「文言が互いに違う」だけの検査は弱い。** 実験2でオフラインと枠切れを
`Please try again.` / `Please try again later.` に潰したとき、
**文字列としては違うので、この検査は通ってしまった**。落としたのは
「再接続を促しているか」というキーワード検査のほうだった。

→ **意味を守るのはキーワード検査であり、差分検査ではない。**
A 階層を増やすときは「互いに違うこと」で満足せず、
**その文言が伝えるべき中身を1つずつキーワードで縛る**こと。

**キーワード検査は「言い換え」に弱い。** `reconnect` を
`/\b(offline|reconnect|connection|internet|network)\b/i` で見ているが、
`Check your Wi-Fi` のような表現は素通りする。完全ではない。
だからこそ §6-8 の逆翻訳（人手）を併用する。

### 6-8. 逆翻訳による確認（人手の工程）

A 階層は、英語を書いたあとに **EN → JA へ機械翻訳し、元の日本語と意味が一致するか**を見る。
安価で、直訳の崩れをよく捕まえる。B・C には行わない（C は直訳しないため無意味）。

## 7. AI プロンプトの英語化（P3）

サーバーの5ファイル（`vision-recipe` / `recipe-refine` / `meal-vision` /
`receipt-vision` / `name-resolve`）は**全文日本語**で、日本の家庭料理を前提にしている。

「家庭の台所で作れる形に翻訳する」の中身が
「**日本のスーパー**で買えるもので代用」「中華レンジではなく家庭のコンロ」である。
英語化は文字列置換ではなく、**対象国ごとの前提の書き換え**になる。

### 実装した範囲（2026-08-09）

**プロンプト全文の英訳はしない。** モデルへの指示であって画面には出ないし、
v1 の内容は日本語で品質を測ってある（`docs/レシピ推論の評価設計.md`）。
全文を訳すとその測定が丸ごと無効になる。

代わりに、**出力言語と入手性の前提だけ**をロケールで差し替える。
指示はプロンプトの末尾に置き、先に書かれた「日本語で出力する」を明示的に
打ち消す（`overrides any earlier instruction about Japanese`）。

| 実装 | 場所                                                           |
| ---- | -------------------------------------------------------------- |
| 規則 | `apps/server/src/lib/output-locale.ts`（サーバー）             |
| 規則 | `apps/mobile/src/services/ai-output-locale.ts`（BYOK・写し）   |
| 経路 | 写真レシピ・レシピ調整・食事写真・レシート・名寄せ の5つすべて |
| 既定 | `locale` 省略時は `ja` — **既存の呼び出しは挙動が変わらない**  |

サーバーは実行時に `@daidoko/shared` を取り込まない方針（tsconfig の `rootDir` が
`src` に閉じ、既存コードも型を各アプリで写している）。そのため同じ規則を
両側に置き、**文面が食い違わないようテストで固定**している。

### 残る手順（公開前に必要）

1. **R0 の評価ハーネス（`vision-eval.ts`）を英語で回して品質を測る**
2. 日本語版と同じ合格ラインを満たすまで公開しない

**1 を飛ばさない。** 出力言語を切り替えただけで英語の品質が担保される保証はない。
特に v1 の「日本のスーパーで買えるもので代用」は英語圏では前提が違う。

### P2 の結果（2026-08-09 完了）

**一括置換をしなかった。** 画面・領域ごとに 10 回に分けて進め、各回で
型チェック・lint・テストを通してからコミットしている。

移行中に**翻訳すると壊れる箇所**が見つかった。これは一括置換では気づけない。

| 見つかったもの                       | なぜ壊れるか                                              |
| ------------------------------------ | --------------------------------------------------------- |
| タグの絞り込みが固定の日本語リスト   | タグは DB の値。訳すと `tags.includes()` が一致しなくなる |
| `${期間}の記録がありません`          | 英語では "Week's records not found" になる                |
| 並び替えラベルがモジュール定数       | import 時のロケールで固定される                           |
| `localeCompare(title, 'ja')` 固定    | 英語のレシピ名が期待どおりに並ばない                      |
| Zod のメッセージ                     | スキーマ定義時に確定 → キーを持たせ `tDynamic()` で引く   |
| サーバー由来の失敗文言をそのまま表示 | サーバーは日本語固定。英語画面に日本語が出る              |
| `・` によるリスト連結                | 英語は `, ` — **lint が見つけた**                         |

同じキーに 2 つの別文言をまとめてしまった箇所も 2 件あり、**既存テストが捕まえた**
（差分の見出し「料理名」とフォームの「レシピ名」、OCR の「未設定」と「初期化失敗」）。

### 新規の埋め込み防止（稼働中）

`eslint.config.js` の `no-restricted-syntax` で、移行済み領域の
文字列リテラル・テンプレート・JSX テキストに含まれる日本語を **error** にする。
**放置すると外部化した端から増える**ので、これが本体。

除外は 3 種類だけ。辞書そのもの・日本語処理ロジック（§7・P5）・AI プロンプト本体。
意図的に日本語を残す行は `// i18n-ignore` と `// eslint-disable-next-line` に
理由を添える。

## 10. やらないこと

- **翻訳の外注・機械翻訳の一括適用** — 701 件は自分で書ける規模。
  ただし「声を守る」ことが理由になるのは **C 階層だけ**（§6）。
  A 階層に必要なのは声ではなく**正確さ**で、こちらは意図の記録とテストで縛る
- **日本語版の文言変更を伴う整理** — i18n はキーを外に出すだけ。
  文言を良くするのは別の作業として分ける（差分が読めなくなる）
- **RTL（アラビア語等）対応** — 対象言語に無い
