# 相談してレシピを作る（S18）

作成: 2026-08-11

## 1. なぜやるか

写真からレシピは、**目の前に料理がある**ときの機能。
「お店で食べた、あれを家で作りたい」に応える。

だが、料理を作りたいと思う瞬間の多くは**まだ料理が無い**。
「今日なに作ろう」「鶏むねが余っている」「子どもと作れる何か」。
そこには写真も、目標のレシピも無い。

この機能は、その状態から話しながらレシピの下書きに落とす入口。
**蔵書庫への 2 本目の入口**であって、再現ループの置き換えではない。

## 2. 「献立自動生成」との線引き

`docs/要件定義.md` §4 は「AIによる献立自動生成」を**非対象**としている
（**2026-08-28 決定変更**: オプトインの毎日自動モードを別途新設 — 買い物リスト・在庫設計
§10.11。**起点が利用者の設定である点で、この線は保たれる**）
（理由: 過度な自動化はアナログ感を損なう）。この機能はそれを覆さない。

|              | 献立自動生成（やらない） | 相談してつくる（これ）     |
| ------------ | ------------------------ | -------------------------- |
| 誰が決めるか | アプリ                   | **利用者**                 |
| 起点         | アプリが提案を並べる     | 利用者が「作りたい」と言う |
| 出るもの     | 献立の一覧               | **レシピ 1 つの下書き**    |
| 保存         | —                        | 必ず確認フォームを通す     |

守る一線は **決めるのは常に利用者**。モデルは提案と質問をするが、決め切らない。
プロンプトにもそのまま書いてある。

## 3. かたち

チャット（ユーザー判断・2026-08-11）。一度の入力で決め切る形も検討したが、
「作りたいもの」は言葉にしながら固まっていくため、往復できる方を採った。

```
利用者「鶏むねで、子どもと作れる何か」
  AI  「何人ぶんにしますか？」                    ← 質問は一度に1つだけ
利用者「4人」
  AI  「照り焼きはどうでしょう」＋ 下書き        ← 聞き切る前に下書きを出す
利用者「甘いのは苦手」
  AI  「みりんを減らして塩味に寄せました」＋ 下書き  ← 言われた点だけ変える
                                          → [下書きを確認して保存]
```

- **聞き切ってから作らない。** たたき台があった方が「そうじゃない」と言いやすい。
- **下書きは会話で言われた点だけ変える。** 関係ない材料・手順は一字一句そのまま
  （感想調整 R2 と同じ思想。勝手な書き換えは信頼を壊す）。
- 保存は必ず `RecipeForm` を通す。**AI が書いたものをそのまま保存しない**。

## 3-2. マスコットは入れない（2026-08-11 に試し、2026-08-12 に取り下げ）

「ただの AI アシスタントより、姿のある相手の方が話しかけやすいのでは」という案から、
コック帽をかぶった台所うさぎ（呼び名「おたま」）を試作して画面に載せた。取り下げた。

理由は 2 段階ある。

1. **名前が説明を要する。** 「おたまに相談する」と書くと「おたまって何？」となる。
   説明の要る名前は入口の妨げになる。まず名前を文言から外した。
2. 名前を外すと、絵だけが残る。**機能の説明にも世界観にも効いていない**ので、
   絵も外した。「深夜の私設レシピ蔵書庫」という静かな世界観と、
   キャラクターの愛嬌は素直には噛み合わなかった。

代わりに、**文言で機能が先に分かる**ようにしてある:

| ところ                 | 文言                                          |
| ---------------------- | --------------------------------------------- |
| ホーム・追加タブの入口 | 「AIと相談しながらつくる」/ "Plan it with AI" |
| 画面のヘッダー         | 「相談しながらつくる」/ "Plan with AI"        |

**「相談する」ではなく「相談しながらつくる」**。出口がレシピの下書きであることを
言葉でも示す（相談だけして終わる機能ではない）。

再挑戦するなら、名前より先に「どこで説明するか」を決めること。
意匠は 40px（吹き出し横のアバター実寸）まで縮めて判断する必要がある
— 細い線・目のハイライトはそこで最初に消える。

## 4. 在庫の扱い

**任意**（ユーザー判断・2026-08-11）。画面のスイッチをオンにしたときだけ送る。既定はオフ。

理由は、何を送ったか利用者に見えている状態を保つため。
毎回自動で送ると、買い物リストの中身まで含めて常に外へ出ることになる。

送るときは「在庫だけで無理に作らない」も一緒に伝える。
足りないものは足りないものとして材料に書かせる — 隠すと買い物リストへの接続が壊れる。

## 4-2. 写真を添える（2026-08-23）

相談は文字だけだったが、**冷蔵庫の中身・食材・参考にしたい料理**は言葉より写真の方が早い。
発言に写真を添えられるようにした。

**在庫と同じで任意。** 添えたときだけ送り、添えていない往復では写真の話をしない
（プロンプトにもそう書いてある）。何を送ったかが画面に見えている状態を保つ。

| 決めたこと                                         | なぜ                                                                                                                        |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 1 発言あたり **2 枚**まで                          | 冷蔵庫なら 1〜2 枚で足りる。増やすほど毎回の往復が重くなる                                                                  |
| 1 リクエストに載せるのは **新しい方から 4 枚**まで | 会話が伸びるほど過去の写真が積み上がる。古い写真は assistant の返答に言葉として残っているので、落としても文脈は途切れにくい |
| 長辺 **1280px** に縮小                             | 紙面（2000）より小さくてよい。**往復ごとに送る**ので 1 枚の重さがそのまま毎回の待ち時間になる                               |
| base64 は**送る直前**に作る                        | 画面の state に base64 を置くと、会話が伸びるほど state が重くなる。state は端末内パスだけ持つ                              |
| assistant の発言に付いた写真は**載せない**         | モデルに返させるものではない。境界で落とす                                                                                  |
| **送信先の開示を出す**（写真を添えたときだけ）     | 文字だけの相談では写真は出ないので、常時表示にはしない。添えた写真の隣に置く                                                |

絞り込みは**端末側とサーバー側の両方**で行う。サーバーだけだと、落とすと分かっている写真の
base64 を作って送ることになる（`toWireMessages()` / `pickRecentImages()`）。

| ところ                                         | ファイル                                                    |
| ---------------------------------------------- | ----------------------------------------------------------- |
| サーバー: プロンプトと Gemini 呼び出し         | `apps/server/src/lib/recipe-consult.ts`                     |
| サーバー: 正規化と AgentResult                 | `apps/server/src/agents/recipe-consult.agent.ts`            |
| サーバー: エンドポイント                       | `POST /api/v1/infer/consult`                                |
| モバイル: プロバイダ（BYOK 直 / サーバー経由） | `apps/mobile/src/services/recipe-consult.provider.ts`       |
| モバイル: 画面                                 | `apps/mobile/app/(tabs)/recipes/consult.tsx`                |
| 入口                                           | 追加タブ。**写真の次**（写真＝料理がある / 相談＝まだ無い） |

### 決めたこと

- **下書きが無い往復は正当**。まだ質問している段階では `draft: null` を返す。
  「下書きが無い＝失敗」にすると、質問だけ返す往復が全部エラーになる。
- **材料か手順が空なら下書きとして返さない。** 半端な下書きを出すと
  「保存できそうに見えるのに保存できない」状態になる。`ready` も同時に false にする。
- **会話は古い方から落とす**（上限 24 発言）。直近ほど効くので、頭を削る方が安全。
- 下書きと在庫は**最後の user 発言に添える**。古い turn に混ぜると効きが落ちる。
- 枠の数え方は写真レシピと同じ（成功した往復＝1 回）。
  **会話は往復するぶん枠を食う** — BYOK なら気にせず話せる、という整理でよい。

### アレルギー

`docs/多言語対応設計.md` §5 の決定を引き継ぐ。**アレルゲンの有無は保証しない。**
プロンプトで断定を禁じ、画面にも注意書きを出す。
「言われた範囲で避ける」までが機能の範囲。

### 下書きカードの更新が見えない（Issue #303, 2026-09-09）

**症状**: 本番 1.13.1 で「下書きを開いて中身を見る → 保存せず戻る → 要望を送る →
カードが更新されない」と報告。

**原因**: 下書きカードが**タイトルしか出していなかった**。サーバー単体とエミュレータで
8 往復確認したところ、2 回目以降の要望でも中身（人数・材料・手順）は毎回更新されて
いた。ただし同じ料理を深めていく会話ではタイトルは変わらないため、カードの見た目が
一切動かない。「更新されない」は実際にはデータの不具合ではなく**見え方の問題**だった。

**対処**: カードに 2 行目（人数 · 時間 · 材料数 · 手順数）を追加し、下書きが置き換わった
ときは「いま変えた点: …」も出す。差分は `apps/mobile/src/utils/consultDraftDiff.ts` で
**下書きの中身から決定的に**計算する。AI の reply の自己申告（「〜を変えました」という
文章）には頼らない — モデルが「変えました」と言いながら同じ下書きを返すことがあるため、
その場合は差分計算側で「前回と同じ下書きです（変わっていません）」と正直に出す。
項目は最大 4 件＋「ほか N 件」。**順は頼んだ変更が先**（料理名 → 追加 → 外した → 人数 →
時間 → 手順 → 分量・下ごしらえの件数）。分量はモデルが「ついでに」動かすことが多いので
名前を並べず件数だけにする（並べると「にんにくを外した」が「ほか N 件」に隠れる）。
材料の名寄せは買い物・在庫と同じ `normalizeItemName`（NFKC・カナ統一・空白除去）で、
「にんにく」→「ニンニク」の揺れを「追加＋外した」と誤検出しない。同名の材料が複数行
（下味の塩・仕上げの塩）あるときは出現順で対応づけ、余りを追加・不足を削除とする。
ペルソナ検証（2026-09-10・5 人）で反映したこと: 「分量・下ごしらえ N か所」の「下ごしらえ」は
初心者に通じない → 「分量 N か所」。2 行目は 13px の薄色だと老眼で読めない → 14px、
「材料5 · 手順5」は数字の意味が伝わらない → 「材料5品 · 手順5つ」。英語の unset → cleared。
見送り: 無料枠の残数表示（§10.10.4 の判断を維持）・前回との全文並べ比較・同じ料理の下書きが
並んだときの見分け（相談履歴の話）。
AQUOS 実機（2026-09-10）: 「にんにくを追加して」に AI は「追加しました」と答えたが、元の下書きに
おろしにんにくが既にあり差分ゼロ → カードは「前回と同じ下書きです」。差分表示は正しいが AI の
返事と食い違うので、文言に「頼んだことが元から入っていたか、反映されませんでした」を添えた。
AI 側で「既にあります」と答えさせる改善は Issue #304（出力言語）と同じプロンプトの話として別枠。

据え置き: §5「決めたこと」の**「下書きが無い往復は正当」は変更していない**。
応答に `draft` が無い往復では前回の下書きをそのまま保持する現行仕様のまま。

**確認済みの別件（未対応・Issue #303 に記録のみ、設計判断は保留）**: `RecipeForm` で
手直しした値はキャンセルで捨てられ、次の要望を送ったあとにフォームを再度開くと
手直し内容が消えている。

**未試験**: BYOK 経路（サーバー経由 / エミュレータでのみ確認）。

## 7. 拡張: 会話の結果をアプリに残す（2026-09-14 確定・実装前）

> 経緯: `docs/AIに聞く設計.md`（2026-09-10 起案・2026-09-14 中止）が、迷走の末にここへ吸収された。

### 7-1. なぜ広げるか

ユーザーの言葉（2026-09-14）:

> Gemini や Claude に「レシピを教えて」と聞くだけだと、**それは何も残らない**。買い物リストも作ってくれない。
> ただチャットで応答するだけ。そういったものに対して、**悩みを解決するという点は変えないが**、
> 料理のことについてはアプリの中で記録したり在庫管理したりできるように何でもしたい。

**差別化の中心は「答えが残ること」。** 汎用のチャットは答えを返して終わる。
だいどこは同じ悩みを解決したうえで、結果が**レシピ・買い物リスト・在庫・記録・献立**として残る。

§1 の「蔵書庫への 2 本目の入口」は維持する。広げるのは**出口**の方 — いまはレシピの下書きしか出ないが、
会話の中で決まったことを、そのまま他のデータにも落とせるようにする。

**手動操作はやめない**（ユーザー確認 2026-09-14）。画面で自分でタップして足す道はそのまま残る。
相反しない。会話は**もう 1 本の道**であって、置き換えではない。

### 7-2. 代行するもの — 線引きは「日常の家事か」

ユーザーが引いた線（2026-09-14）:

> 取り返しのつかない操作は代行しない。手順の説明のみ。**なぜなら日常の家事が楽にならないから。**

毎日起きる家事は代行する価値がある。日常の家事でない操作は、代行しても家事は楽にならず、
間違えたときの損だけが残る。**危険度ではなく頻度で引く。**

| 代行する（日常の家事）         | 呼ぶ既存サービス                                             | 備考                                                                            |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 買い物リストに足す             | `shopping-list.service.ts` `addShoppingItem`                 | 同名の未チェック行があると `null` を返して**何もしない**（§7-8）                |
| 買い物リストのチェック         | 同 `checkOffByNames`                                         | 複数行に一括で当たる。既存 UI のタップで戻せる                                  |
| 在庫に足す                     | `pantry.service.ts` `addPantryItem`                          | `defaultGroupFor` を先に引く（§7-8）。**合算先を確認カードに出す**              |
| 在庫を減らす                   | 同 `adjustPantryQuantity`                                    | 名前 → 行の解決が要る（§7-8）                                                   |
| 「買った」                     | 同 `moveShoppingItemToPantry`                                | **現状は物理削除で戻せない。取り消しを作ってから載せる**                        |
| 「使い切った」                 | `meal-consume.service.ts` `applyConsumption`                 | 残量 1 以下で**物理削除に化ける**。同上                                         |
| 「作った」の記録               | `cooking-log.service.ts` `createCookingLog`                  | `cookedAt` のみ必須。レシピ無しでも記録できる                                   |
| 献立を組む／差し替える         | `menu-plan.service.ts` `generateMenuPlan` / `replaceMenuDay` | **既存の献立を黙って上書きする。** 確認カードに「いまの献立を置き換える」と出す |
| レシピを作りたいリストに入れる | `recipe.service.ts` `setRecipePinned`                        | レシピの同定が要る（§7-8）。同期対象外                                          |

**v1 では載せないもの**: `addMissingRecipeIngredientsToList`（レシピの材料を一括で買い物へ）。
理由は 2 つ。(a) 現行 UI は #214 で「在庫にある材料も隠さず選ばせる」方式に変えたが、この関数は在庫にある材料を除く。
**会話経由と画面経由で結果が変わる。** (b) 内部で `resolveNames`（名寄せ・無料 30/日の別枠）を呼ぶので、原価の説明が合わなくなる。

### 7-3. 代行しないもの — 手順の説明だけする

日常の家事ではないので代行しない。**聞かれたら手順を説明する**（ここは新しくできること）。

レシピの削除／レシピ帖の削除／家族からの脱退・招待／Web への公開・公開取り消し／課金・解約／
API キーの保存・削除／バックアップの復元／データの初期化。

この線なら「なぜこれは取り消せないのか」という問いが発生しない。**そもそも代行しないから。**
実装は `docs/AIに聞く設計.md` §5 の denylist をそのまま引き継ぎ、**型で書けないようにする**
（`tier` に `destructive` を持たせない。テストで `@ts-expect-error` を固定する）。

### 7-4. 会話から操作が出るまで

§3 の往復はそのまま。下書きに加えて**操作の提案**が出るようになる。

```
利用者「鶏むねで、子どもと作れる何か」
  AI  「照り焼きはどうでしょう」＋ 下書き              ← §3 のまま
利用者「作る。玉ねぎ切らしてるかも」
  AI  「玉ねぎは在庫にありません。買い物に足しますか」
        ┌──────────────────────────────┐
        │ 〈玉ねぎ切らしてるかも〉        │ ← 聞き取った原文を必ず併記
        │ 買い物リストに「玉ねぎ」を足す  │
        │ 押すまで何も変わりません        │
        │ ［やめる］  ［足す］            │
        └──────────────────────────────┘
                                    → 実行 → Toast「足しました ［取り消す］」
```

決めたこと:

| 決めたこと                                            | なぜ                                                                                                                                                      |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **確認カードに聞き取った原文を併記する**              | 音声入力の誤変換（「砂糖」→「酢」）と AI の誤解釈を、利用者が区別できるようにする。併記が無いと「自分が何と言ったか」しか手がかりが無い                   |
| **何がどう変わるかまで出す**                          | 在庫は同名 × 同単位 × 同グループで**数量合算**する。「既存の『砂糖 500g・調味料棚』に足す」のか「新しい行を作る」のかを出して初めて誤りを目で捕まえられる |
| **品名は利用者が言った文字列をそのまま使う**          | 買い物・在庫の重複判定は正規化名の SQL 完全一致で、**名寄せは読み取りにしか使われていない**。AI が「さとう」を「砂糖」に整えると別行が生える              |
| AI が決めるのは「どの操作か」と「どの語が品名か」だけ | 文字列そのものは生成させない。`actions[].id` はカタログに無ければ黙って落とす（`docs/AIに聞く設計.md` §5 を継承）                                         |
| 1 回の返答に載せる操作は**最大 2 つ**                 | 並べるほど「どれ」が起きる                                                                                                                                |
| 実行後の Toast に**取り消しを置く**                   | ペルソナ 5/5 が「入れたものを自分で取り消せるか分からない」と答えた（`docs/reviews/persona-mock-assistant-2026-09-13.md` B2）                             |
| 保存は今までどおり `RecipeForm` を通す                | §3 の規約。**AI が書いたものをそのまま保存しない**は操作にも及ぶ（タップを 1 回挟む）                                                                     |

**「決めるのは利用者」（§2）は保たれる。** 起点は利用者の発話、決定は確認カードのタップ。
AI が勝手に実行する経路は作らない。テストで「タップ無しで `run` が呼ばれないこと」を固定する。

#### 7-4-1. 返答スキーマとリクエストの形（2026-09-16 設計）

##### 返答スキーマ（サーバー → 端末）

既存の `GEMINI_RESPONSE_SCHEMA`（`recipe-consult.ts L156-207`）に 3 フィールドを足す。
`draft` は既存のまま残し、**`actions` と `candidates` と `imageReadings` を同列に追加する**。

```ts

// 既存: reply(string, required), ready(boolean, required), draft(object, optional)
// ↓ 追加分
const GEMINI_RESPONSE_SCHEMA_V2 = {
  // ...既存の reply, ready, draft はそのまま...
  actions: z
    .array(
      z.object({
        id: z.string(), // カタログの id。v1 は 'shopping.add' のみ
        args: z.record(z.string()), // v1: { name: string }。品名は利用者の発話そのまま
        heardAs: z.string(), // AI が聞き取った原文（確認カードに併記する用）
      }),
    )
    .max(2)
    .optional(), // §7-4「1 回の返答に最大 2 つ」
  candidates: z
    .array(
      z.object({
        title: z.string(),
        description: z.string().optional(),
        // 下書きの中身は candidates には入れない。
        // 利用者が「これ」と言ったら draft に落とす
      }),
    )
    .optional(), // R13: 候補を複数返す（既定値は §7-12-2 で未決）
  imageReadings: z
    .array(
      z.object({
        originalIndex: z.number(), // 何枚目の写真か（0-based）
        reading: z.string(), // AI が読み取った内容の要約
      }),
    )
    .optional(), // R1: 2 往復目以降で写真の代わりに送る

| 決めたこと                                                               | なぜ                                                                                                       |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `actions[].id` は **カタログの id 参照**。カタログに無ければ黙って落とす | `docs/AIに聞く設計.md` §5 を継承。モデルの幻覚した操作を実行しない                                         |
| `actions[].args` の品名は **利用者の発話そのまま**                       | §7-4 の規約。AI が「さとう」→「砂糖」に整えると `addShoppingItem` の正規化名一致で別行が生える（§7-8）     |

| `candidates` は **タイトルと説明だけ**                                   | 選択前に下書きの全体を生成すると出力トークンが候補数倍になる。選んだ後に 1 件だけ `draft` に落とす         |

### 7-5. 取り消し

「買った」「使い切った」は**現状のコードに戻す手段が無い**（物理削除）。家族の端末からも消える。
**この 2 つを載せる前に取り消しを作る**（ユーザー判断 2026-09-13「戻せる仕組みを先に作る」）。

app-leader の設計（2026-09-14）:

- 方式は**逆操作**。操作の直前に消える行を控え、取り消しは逆向きの操作を既存サービス経由で実行する
- **同期プロトコルを 1 行も変えない。** サーバーは同じ行の復活を受け付ける作りになっている（`sync-store.ts` の `ON CONFLICT ... DO UPDATE SET deleted_at`）ので、**元の id のまま**復活させれば相手の端末では消えた行が戻る。新しい id を振ると相手に重複行ができる
- 台帳はローカルの専用テーブル（同期対象外・バックアップ対象外）
- 窓は 2 段: Toast の［取り消す］（破壊的な操作は 8 秒）と、設定 → データの「最近の変更」（直近 20 件 / 24 時間）
- redo は作らない。取り消しの取り消しは既存 UI で 1 タップでできる

**これはアプリ全体の削除の扱いを変える変更**なので、**別 Epic に切る**（app-leader 推奨）。
既存の削除系 i18n には「元に戻せません」が並び、英語側には翻訳者向けに「この表現を和らげてはいけない」という注記がある。
取り消せるようにした分だけ、文言の是正が要る（`audit-copy-drift` の対象）。
取り消し基盤は**会話の拡張が無くても単独で価値があり、単独で出荷できる**（今日は買い物・在庫の行を消したら戻せない）。

### 7-6. 家族にどう伝わるか

事実（app-leader が実装で確認）:

- 書き込み → 3 秒デバウンス → サーバー。買い物・在庫を含む変更は**急ぎ扱いで 1 分以内**に相手へ push
- 相手がアプリを開いていれば、**Toast も通知もダイアログも出さずに画面が黙って更新される**
- 閉じていれば固定文の push（「家族の共有データが更新されました」）のみ。**何が変わったかも誰が変えたかも含まない**（意図的）
- `createdBy` は同期しないので、**「誰がやったか」を相手端末で表示する手段が無い**

**これは会話の拡張とは無関係に、今日そうなっている。** ただし会話から操作できるようになると頻度が上がる。
相手への説明を出すかは未決（§7-10）。当面は出さない — 内容を push に載せるのはプライバシーポリシーの変更になり、
「誰かが何かを取り消しました」としか言えない通知は、静かに戻るより不安を与える。

### 7-8. 実装の地雷（着手前に必ず読む）

app-leader が実装を読んで確認したもの。**どれも型・lint・テストが通る壊れ方をする。**

- `addShoppingItem` は同名の**未チェック行があると `null` を返して何もしない**。「足しました」の Toast が嘘になる。戻り値で文言を分ける
- `addPantryItem` は upsert で既存行に**加算**する。合算の鍵は `familyId` ＋正規化名＋ `unit` ＋ `groupName` ＋共有境界。
  **`unit` と `groupName` を省くと「単位なし・グループなし」の行とだけ合算され、既存の『砂糖 500g・調味料棚』とは別行ができる。**
  既存画面（`receipt.tsx` / `fridge.tsx`）は先に `defaultGroupFor(name, unit)` を引いている。会話経由も同じ 2 段を踏む
- 取り消しは「行を消す」ではなく「同じ量を引く」。戻り値から新規か合算かが判別できないので、**呼ぶ前に行の有無を読む**
- `checkOffByNames` は複数行に一括で当たる。取り消しは当たった id を全部保持する
- **名前 → 在庫行を引く公開関数が無い**（`utils/shoppingPlan.ts` の `findStock` が非 export）。昇格させる
- **レシピ名を 1 件に決める関数が無い**（`searchRecipes` は部分一致の配列）。複数ヒット時の優先順位も未実装。**「どれ？」を返す**設計にする（先頭が勝つ現状を踏襲しない）
- 書き込み経路で**名寄せは効いていない**。「砂糖」と「上白糖」は必ず別行になる（合算の誤爆コストが高いため、とコード内にコメントあり）
- `Toast.tsx` に**ボタンの受け口が無く**、17 画面が各々ローカル state で持っている。取り消し付きの Toast はルートに新設する（既存 17 画面は触らない）
- `generateMenuPlan` は既存の献立を**黙って上書き**する
- 相談のサーバー往復は**端末 45 秒・サーバー再試行予算 133.5 秒**で逆転しており、本番でタイムアウトしている（**Issue #331**）。
  操作の提案を足すと往復が増えるので、**#331 の解消が前提条件**

以下は 2026-09-16 の設計作業で追加:

- **`toWireMessages` はキャッシュヒット時も `readAsStringAsync` で base64 を毎往復載せる**（`recipe-consult.provider.ts L198-232`）。R1 で `imageReadings` 方式に変えたとき、2 往復目以降で base64 生成をスキップするパスを確実に通す必要がある。スキップし損ねると「動くが遅い」という**計測しないと気づかない壊れ方**をする
- **BYOK 経路とサーバー経路でタイマー開始位置が違う**（`recipe-consult.provider.ts L334 付近`）。BYOK は前処理の後、サーバーは前処理の前にタイマーが始まる。R5 で揃える対象
- **`consultViaServer` は `args.pantry` を無加工で送る**（`recipe-consult.provider.ts L406 付近`）。BYOK 側は `buildContextText` で `.slice(0,200)` しているが、サーバー経路は切っていない。サーバー側の Zod（`infer.ts L716`）は `.max(200)` で弾くので 201 件以上で 400 エラーになる。R6 で端末側も切る
- **`GEMINI_RESPONSE_SCHEMA` に `actions` / `candidates` / `imageReadings` を足すとき、`required` 配列に入れてはならない**。`draft` と同じ理由で「まだ出さない」が正当な状態。`required` は `['reply', 'ready']` のまま維持する（`recipe-consult.ts L205`）

#### 7-12-1. 使い方に答える（R12）

##### 方針

`docs/AIに聞く設計.md` §4 の機能カタログ（`CatalogEntry`）をそのまま引き継ぐ。
カタログは操作カタログ（§7-9 段階 1）と同じデータで、`kind: 'screen' | 'setting'` のエントリを使い方の回答に使う。

**プロンプトへの渡し方**:

- カタログを `systemInstruction` の先頭に平文で固定配置する（`docs/AIに聞く設計.md` §6-2 と同じ）
- `requires` で利用者の状態に合わないエントリを除外してから載せる
- 大きさの目安: 1 件 ≈ 125 字 × 40 件 ≈ 5,000 字 ≈ 4-6k トークン（`docs/AIに聞く設計.md` §6-2 の見積を継承）
- Gemini 2.5 系の implicit caching（1,024 トークン以上の共通プレフィックスが自動的にキャッシュされる）でカタログ部分の入力コストが割引される

```
## 使い方の質問

- カタログに無い機能は「この機能はありません」と答える。作らない。
