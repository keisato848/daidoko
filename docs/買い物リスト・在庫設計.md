# 買い物リスト・在庫（パントリー）設計

> 「家の在庫を核にした食材ライフサイクル」の設計。買い物リスト単体ではなく、
> **在庫 ⇄ 買い物リスト ⇄ レシピ** のループとして設計する。実装前に必ず参照。
> 関連: `docs/データ設計.md` / `docs/レシピ作成フロー.md` / `docs/フリーミアム設計.md`

---

## 1. 狙い

- 家にある食材（在庫）を把握し、**足りないものだけ買う／あるもので作る／なくなりそうを知る**を回す。
- 入力の手間を下げる仕掛け（レシピ材料の一括取り込み、レシート読み取り、将来は食事写真）。

## 2. 全体像（3つのループ）

> **4 つ目のループ（設計中）**: 在庫 → **X 日分の献立** → 買い物リスト。§10（#215）。
> 「いま作れる 1 品」（§5.4）と「何日分の買い物」の間に橋を架ける。

```
        ┌──────────────┐   足りない材料を追加      ┌──────────────┐
        │   レシピ      │ ───────────────────────▶ │  買い物リスト  │
        │ (ingredients) │ ◀─ 在庫で作れる？ 判定 ── │  (shopping)   │
        └──────┬───────┘                           └──────┬───────┘
               │ 在庫で充足判定                            │ 「買った」→ 在庫へ
               ▼                                          ▼
        ┌─────────────────────────── 在庫 (pantry) ───────────────────────────┐
        │  家にある食材（数量・単位・残量しきい値）。残量低下で通知。           │
        │  入力: 手動 / 買い物リストから / レシート写真 / (将来)食事写真から推定 │
        └──────────────────────────────────────────────────────────────────────┘
```

## 3. 置き場所（UI / ナビゲーション）

- タブは現状の **4 つ（ホーム/レシピ/＋追加/設定）を維持**。
- **ホーム右上にカート🛒アイコン**（既存のカレンダー/ギャラリー アイコン横）→ 買い物リスト画面。
- 在庫画面へは、買い物リスト画面のヘッダ、または設定/ホームから。
- レシピ詳細に **「買い物リストに追加」**（足りない材料を一括追加）。

新規 2 テーブル。既存 `recipes/ingredients` は変更しない（突合は名前正規化で行う）。

| 列                     | 型      | 意味                               |
| ---------------------- | ------- | ---------------------------------- |
| id                     | TEXT PK |                                    |
| family_id              | TEXT    | 家族グループ                       |

`(family_id, store_name)` に一意インデックス。照合は**生の店名で完全一致**する。
「マックスバリュ松山店」と「マックスバリュ空港店」は別エントリになるが、どちらも
同じグループに向ければ目的には足りる。チェーン名への機械的な正規化は、ルール保守が必要な割に
「スーパー」のような粗いまとめにはならないので採らない。

### 4.1 グループ（v13）— 置き場所と買う場所

在庫の `group_name` と買い物の `store_group` は**名前が似ているが別物**。

| 何を束ねるか | 例                             | 効くところ                                         |
| ------------ | ------------------------------ | -------------------------------------------------- |
| 置き場所     | 冷蔵庫 / 〇〇の米 / 災害用備蓄 | 在庫の合算キー・作れるレシピ・相談に送る在庫       |
| 買う場所     | スーパー / ドラッグストア      | 買い物リストの絞り込み（**消し込みには使わない**） |

決めごと:

- **どちらも任意。** グループを 1 つも作っていない人にはチップを出さない（画面が変わらない）
- **「未設定」はそれ自体がひとつのバケツ**で、絞り込みからも常に覗ける。
  未設定を隠すと、振り分け忘れた品が埋もれて買い忘れ・二重買いになる
- **置き場所は在庫の合算キーに入る。** 同じ米が「パントリー」と「〇〇の米」に別々にあるのは
  正常なので、鍵から外すと勝手に 1 行へまとめられてしまう。JAN 一致でも同じ理由でグループを見る
- **置き場所を変えたら、移した先に同じ品があればそこへ寄せる**（`updatePantryItem`）。
  寄せないと、移した瞬間に同じ品が 2 行に並ぶ
- **賞味期限は行に 1 つだけ。** 合算時は**近い方（早い日付）を残す**。買った回ごとの
  ロット分割は、合算をやめる代償が大きすぎるので採らない。**通知では追い立てない**
- **使うグループは「そのとき選ぶ」**（グループ自身の属性にしない）。「普段は冷蔵庫だけ、
  旅行前は全部」のように、やりたいこと次第で変わるため

> マイグレーション: `migrate.ts` の `CREATE_TABLES_SQL` に 2 テーブルを追記し、
> `CURRENT_SCHEMA_VERSION` を 2→3 に上げる（`CREATE TABLE IF NOT EXISTS` なので既存 DB にも安全に追加される）。
> Drizzle 定義（`schema.ts`）は既存どおり object-style の index 設定で追加する。

### バックアップ対象（2026-07-30 に是正）

`pantry_items` / `shopping_items` / `jan_catalog` / `name_aliases` の 4 テーブルは
`backup.service.ts` の `BACKUP_TABLES` から漏れており、復元・機種変更で在庫と買い物リストと
名寄せ辞書が失われる状態だった。現在は 4 テーブルとも対象に含まれる。

新テーブルは `optional: true` を付けて登録する。旧バージョンが書き出したファイルには
そのキーが存在しないため、**欠けていれば 0 件として復元**し、`BACKUP_SCHEMA_VERSION` は上げない
（新旧どちらのアプリでも読める。写真同梱 `recipePhotos` と同じ互換方針）。
在庫系テーブルを増やすときは `BACKUP_TABLES`・`createEmptyBackupTables()` の両方に追記すること。

## 5. 機能別設計

### 5.1 買い物リスト（P1）

- 手動で品目追加（name ＋ 任意 amount）。チェック（永続）。並べ替え・削除・**チェック済み一括削除**。
- レシピ詳細「**材料を買い物リストに追加**」: そのレシピの材料を `source='recipe'`, `recipe_id` 付きで追加。
  **P1 は全材料を追加**（「足りない材料だけ」は pantry が要る **P2**）。
- 重複: 同名（正規化）が未チェックで既にあれば**重複追加しない**（amount は結合しない＝単位が多様なため）。
- 旧 per-recipe `shop.tsx`（このレシピ用・セッション限りのチェック、永続化なし）は**廃止済み**（Issue #66）。
  レシピ詳細のカートアイコン・「足りない材料を買い物リストに追加」テキストボタンはいずれも
  `addMissingRecipeIngredientsToList` に統一され、在庫判定つき・永続リストへの追加に一本化された。

### 5.2 在庫（pantry, P2）

- 一覧・追加・編集（数量・単位・しきい値）・削除。**数量は厳密管理（同一商品は合算）**。
- 買い物リストは**タップ＝買った＝即座に在庫へ**（Issue #66③、`moveShoppingItemToPantry`）。
  従来の「チェック→『在庫に入れる』ボタン押下」の2ステップを1タップに統合し、品目は
  pantry へ upsert（数量加算）された上でリストから消える。トースト通知で結果を表示。
  誤タップは pantry 側での削除／数量調整で復旧可能（不可逆ではない）。
  旧来の「チェック状態を保持して一括処理」機構（`setShoppingItemChecked`・
  `clearCheckedShoppingItems`）は用済みのため削除。`moveCheckedShoppingItemsToPantry`
  （旧チェック済みの一括移動）は移行互換のため残置。
- **バーコード(JAN)入力**: expo-camera で JAN をスキャン → 既知 JAN なら名前/単位を自動補完、未知なら**初回だけ名前入力 → `jan_code→名前/単位` をローカル記憶**（外部DB不要、使うほど賢くなる）。包装商品の厳密識別＋安全な合算に使う。

### 5.3 レシピの「足りない材料」→ 買い物リスト（P2）

- レシピ材料（正規化）のうち **pantry に無い／数量がしきい値以下**のものを抽出し、買い物リストへ一括追加。
- 数量の厳密比較はしない（単位が揃わないため、MVP は「在庫に存在するか」で判定）。

#### 5.3-a 「卵が 1 個あると、3 個要るのに追加されない」（2026-08-24 の指摘）

**症状**: 在庫に卵が 1 個でもあると、レシピが 3 個必要でも黙って除外される。
除外されたものを**あとから足す導線が無い**（`addRecipeIngredientsToList` は実装済みだが未配線）。

**類似アプリの調べ（2026-08-24）**:

| アプリ                      | レシピ → 買い物リストの作り                                                   | 数量の引き算         |
| --------------------------- | ----------------------------------------------------------------------------- | -------------------- |
| **Paprika 3**（有料の定番） | **確認画面＋チェックボックス。** 在庫のものは**チェックが外れるだけで見える** | **しない**           |
| **AnyList**（買い物の定番） | 材料を個別タップ or「すべて追加」。リストにある物は印。在庫の概念なし         | しない（合算はする） |
| **クラシル**（国内）        | 人数を調整して進み、**家にあるものは利用者がチェックを外す**                  | しない               |
| **Grocy**（在庫特化 OSS）   | **必要量 − 在庫**で不足だけをリストへ                                         | **する**             |
| 在庫特化の小規模アプリ群    | 「足りない物だけ」を謳う（＝だいどこと同じ作り）                              | 曖昧                 |

**読み取れたこと**:

1. **主流はどこも数量を引き算しない。** 引き算する Grocy は**製品マスタと単位換算**
   （「1dl 小麦粉 = 60g」を品目ごとに登録）が前提で、それでも複数レシピの引き当てが
   合算されない不具合が残っている。レシピの分量が自由文（「大さじ2」「少々」「1/2本」）の
   うちは、引き算は**自信を持って間違える**方に倒れる
2. **主流と決定的に違うのは「引き算の有無」ではなく「見せるか隠すか」。**
   Paprika もクラシルも、在庫にある材料を**画面には出して、チェックだけ外す**。
   だいどこは**一覧から消していた**ので、なぜ入らなかったのかが利用者に分からない
3. Paprika には**複数レシピ間で同じ材料の数量を合算**する機能がある（卵 2 個＋卵 3 個 → 5 個）。
   だいどこには無い

**決定**: 数量の自動計算はしない。**除外されたものを見せて選べるようにする**（下の #214）。
在庫にある物には「在庫 1個」を添える — 引き算はアプリではなく利用者がやる。

### 5.4 在庫で作れるレシピ（P4）

- 各レシピの材料に対する **pantry 充足率**（= 在庫にある材料数 / 全材料数）でランキング。
- 「ほぼ作れる（充足率高 ＋ 不足は調味料程度）」を上位表示。

### 5.5 残量通知（P3）

- pantry の `quantity <= low_stock_threshold` の品目を検出 → **ローカル通知**（先日実装の `notification.service` を流用）。
- トリガ: アプリ起動時／在庫更新時にチェックし、必要なら通知をスケジュール（1日1回まとめる等、頻度は要調整）。
- **通知タップ → 一括買い物リスト追加（Issue #66②）**: 確認画面を経由せず、タップ時点の低在庫アイテム全件を
  `source='low_stock'` で買い物リストへ即時追加し、買い物リスト画面へ遷移する。通知の `data.type` で識別
  （`addLowStockTapListener`＝生存中のタップ、`consumeLowStockLaunchTap`＝タップでのコールドスタート起動）。

### 5.6 レシート登録（P5）

**読み取りは2経路。端末内 OCR は文字起こしに専念し、品目化は必ず AI が行う**
（2026-08-15 / Issue #178。経緯と判断は `docs/在庫・レシート設計レビュー.md` §3.4）:

```
レシート写真
  ├ 端末内OCRが使える → 文字起こし → **テキストだけ**を AI へ → 構造化（品目・数量・単位）
  └ 使えない/読めない → **画像**を AI へ（Vision）
```

- **端末内 OCR（`withDaidokoOcr` / unbundled ML Kit・Android のみ）**：文字起こしまで。以前あった
  ヒューリスティック解析（`utils/receiptParser`）は廃止した — 品目名しか取れず、非食品の除外・重複統合・
  数量抽出をクラウド側と二重に持つことになるため。**画像トークンが要らず、レシート写真が端末から出ない**のが
  この経路の価値。
- **可用性は Play Services に問い合わせる**。unbundled ML Kit は「モジュールはあるがモデルが未取得」という
  状態があり、**インストール直後はたいていそれ**。`DaidokoOcrModule.isAvailable()` が
  `ModuleInstallClient.areModulesAvailable()` で実際に取得済みかを確認し、未取得なら `false` を返して
  deferred install を予約する。
- **失敗はすべて画像経路へ落とす**（モデル未取得・認識失敗・1文字も読めない・テキストからレシートと
  判定できない・品目が0件）。**生の ML Kit エラーを画面に出さない**。
- **クラウド AI（`POST /api/v1/infer/receipt`）**：Gemini の構造化出力から品目を直接抽出（半角カナ正規化・
  非食品/値引き行の除外・重複統合込み）。テキスト入力（`ocrText`）と画像入力でスキーマと後処理は共用し、
  プロンプトだけ差し替える。BYOK キー設定時は端末から直接 Gemini を呼ぶ。無料（クライアント側の回数ゲート
  なし）— コストはサーバーのグローバル日次上限＋利用量メール通知で管理。iOS は端末内 OCR を持たないので
  常に画像経路（Apple Vision は #58）。
- 画面（`app/(tabs)/receipt.tsx`）は**何が端末から出るのかを経路に合わせて明示する**。端末内 OCR が使える
  ときは「文字だけを送る・読めなければ写真を送る」、無いときは「写真を送る」。
- **数量・単位も読む（2026-08-15 / Issue #178-1）**: 構造化出力の品目を `{ name, quantity?, unit? }` に拡張し、
  読み取った数量・単位を確認画面（`app/(tabs)/receipt.tsx`）で編集してから在庫へ渡す。
  - **読めなければ `null` のまま通す**。1 で埋めない — 在庫は同一品目を合算するので、推測した数量は
    「家に無いものが在庫にある」状態として消えずに積もる。`addPantryItem` の「数量未管理（quantity=null）」に素直に乗せる。
  - 単位はレシート表記がばらつく（「2」「2個」「500g」「1P」）。`utils/receiptQuantity.ts` の
    `normalizeReceiptQuantity` で §6 の方針に沿って寄せる（NFKC → 別名表 →「個/本/袋/パック/g/ml」等、
    kg・L はグラム・ミリリットルへ換算、「点」「円」など単位でない付帯表記は捨てて数量だけ残す）。
    数量の妥当性も併せて見る（個数系は 99 まで・g/ml は 100,000 まで。単価や値引き額の紛れ込みを弾く）。
  - 同一レシート内の重複は **在庫と同じ規則（正規化名 × 単位）** でまとめる。片方でも数量が読めなければ合算せず `null`。
  - 単価・購入日・`store` は対象外（`store` は抽出しているが未使用のまま）。

**レシートで買い物リストを消し込む（v13）**

レシートは「何を買ったか」を持っているのに、買い物リストは手つかずのままだった。
在庫へ追加すると同時に、買った品を買い物リストから消し込む。

- **消さずにチェックを付ける。** 誤照合で行が消えると気づけないが、チェックなら取り消せる。
  買い物リスト側はチェック済みの行を打ち消し線で出し、タップで**取り消し**にする
  （そのまま「買った→在庫へ」に流すと在庫へ二重に積む）
- **照合は品目名（正規化＋名寄せ辞書）だけ。** 店では絞らない — 同じ品を別の店で買うのは普通で、
  店で絞ると取りこぼす
- **数量は不問。** 「牛乳2本」必要で1本だけ買った場合もチェックは付く（外すのは利用者の判断）
- **追加する前に「◯件を消し込みます」と見せる。** 黙って消すと誤照合に気づけない
- 在庫へ入れる置き場所は `defaultGroupFor`（その品が**1 か所だけ**にあるならそこ）。
  置き場所を使っている人の買い足しが「未設定」に別行で積まれるのを防ぐ
- 店名は初めてのときだけ買う場所と結び付けて覚える（`store_group_aliases`）。毎回選ばせない

### 5.7 毎食写真 → 消費推定（P6・実験的・プレミアム特典）

- 食事写真 → 料理推定 → 典型材料を推定 → pantry を概算で減らす。**Vision＝プレミアム特典**。
- **精度は未知**。あくまで補助（自動で減らしすぎない・確認を挟む）。opt-in。研究フェーズとして最後。

## 6. 食材名の正規化・突合（肝）

レシピ材料・在庫・レシート・手動入力を**名前で突合**するため、正規化が要。

- 正規化ヘルパ `normalizeItemName` を新設：`String.normalize('NFKC')`（全/半角統一）＋ 既存 `normalizeKana`（カナ→かな・小文字・trim）＋ 連続空白除去。
  ※ `normalizeKana` 単体は全/半角を統一しないため NFKC を併用する。
- 分量や修飾を除去（例: 「玉ねぎ 1個」→「玉ねぎ」、「みじん切り玉ねぎ」→ 要検討）。
- MVP は**完全一致（正規化後）**。表記ゆれ辞書（玉ねぎ＝玉葱＝たまねぎ）は段階的に。
- **包装商品は JAN コードで厳密識別**（名前突合より優先）。レシピ材料・バラ売りは JAN を持たないため名前正規化で突合（**JAN と名前正規化を併用**）。
- **数量は厳密管理＝同一商品は合算**（JAN 一致 or 同名(正規化)×同単位）。異なる単位は合算しない。
  **名寄せの対象と時機（2026-08 改訂）**

当初は「**在庫名** → canonical」の辞書として作り、埋めるのも「在庫で作れるレシピ」画面だけだった。
これだと突合が成立しない:

- 突合は **在庫 × レシピ材料**。片側（在庫名）しか canonical に写さないので、
  在庫「にんじん」・レシピ「人参」は、**AI が選んだ canonical とレシピの表記が偶然揃ったときだけ**当たる
- 辞書を埋める呼び出し元が cookable 画面ひとつだったので、**その画面を開かなければ辞書は空のまま**

改めた点は 2 つ:

1. **辞書は「任意の食材表記 → canonical」。** レシピ材料名も解決の対象にする
   （`collectUnmatchedNames` が在庫側・材料側の両方から集める）
2. **解決するのは「ルールで当たらなかった残り」だけ。** 完全一致・部分一致で当たる名前
   （「玉ねぎ」など）は AI に投げない。呼び出し回数は語彙数へ自然に収束し、無料枠を無駄に使わない

**突合が起きる場所では必ず育てる。** 現在の呼び出し元は「在庫で作れるレシピ」（表示時）と
「足りない材料を買い物リストへ」（追加前）。枠切れ・オフライン・AI 無効のときは黙って素通しし、
ルール 1〜2 だけで従来どおり動く。

- **`name_aliases`（AI名寄せキャッシュ）のメンテUI（Issue #66④）**: 設定画面「データ」→「名寄せ辞書」
  から一覧・編集・削除ができる（`getAliasEntries` / `updateAliasCanonical` / `deleteAlias`）。
  誤って解決された対応（例: 別の食材が同一視された）を手動修正でき、削除した項目は次回同じ表記が
  出た際に再度AIで解決される。

## 7. 決定事項（確定）

1. **数量・単位＝厳密管理**: 数量×単位を保持し、**同一商品は数量を合算**（**JAN 一致**、または 同名(正規化)×同単位）。異なる単位は合算しない。
2. **AI コスト**:
   - **食事写真→消費推定（Vision）＝プレミアム特典**。
   - **レシート＝端末内 OCR で無料**（既存 `withDaidokoOcr`/ML Kit 日本語）。任意で **Vision 高精度モード＝プレミアム特典**。
3. **共有範囲＝家族グループ単位**（`family_id`）。同期は未実装のため当面は端末ローカル。
4. **表記ゆれ＝単純正規化のみ**（かな/全半角統一＋トリム＋完全一致）。同義語辞書は後追い。**包装商品は JAN コードで厳密識別**。

## 10. 在庫から X 日分の献立を組む（#215）

### 10.1 狙い

**「何を作るか」で毎日詰まるのを、いま家にあるものから解く。**
`5.4 在庫で作れるレシピ` は**いま作れる 1 品**しか出さない。買い物は「何日分」で考えるので、
そこに橋が架かっていない。同時に、**蔵書庫に溜まったまま使われないレシピを在庫から逆引きで掘り起こす**。

**やらないこと**: 栄養・カロリー計算（データが無い）／好き嫌い・アレルギー（プロフィールに情報が無い）／
献立の自動確定（決めるのは常に利用者）。

### 10.2 いちばんの難所 — X 日分では在庫を食い合う

**症状**: 1 日目が卵 1 個を使い切ったら、3 日目の卵は「在庫にある」ではない。
なのに `rankByCoverage` も `buildShoppingPlan` も**レシピ 1 件ごと**に「名前が当たるか」で判定する。
§5.3-a で直したのとまったく同じ型の穴が、日数の軸で戻ってくる。

**引き算では解かない**（§5.3-a と同じ理由。分量が自由文のうち、推測した数量は自信を持って間違える）。
代わりに 2 つの仕掛けで扱う。

#### (1) 献立を組むとき — 「使った在庫」を候補から外していく

日を 1 つ決めるたびに、そのレシピが使った在庫の品名を `claimed` に入れ、
**次の日の候補はその品を在庫と見なさずに**採点する。

```
claimed = ∅
for day in 1..X:
    pick = argmax score(r, pantry \ claimed)   // r は未選択のレシピ
    claimed ∪= ingredients(pick) ∩ pantry
```

これは**引き算ではない**。「1 つの在庫の恩恵を受けられるのは 1 品まで」という
**採点上の割り切り**であって、数量には一切触れていない。
副作用として**献立が別の食材に散る**ので、変化を付ける効果も同時に得られる。

#### (2) 買い物リストに出すとき — 「2 品で使います」を見せ、既定を反転する

| 状態                           | 既定           | 見せ方                        |
| ------------------------------ | -------------- | ----------------------------- |
| 在庫に無い                     | ☑ チェック     | （§5.3-a のまま）             |
| 在庫にある・**1 品だけ**が使う | ☐ 外す         | 「在庫 1個」                  |
| 在庫にある・**2 品以上**が使う | **☑ チェック** | 「在庫 1個 ・ 2品で使います」 |

**2 品以上のときだけ既定を反転する。** 「1 個ある」が 2 品を賄える見込みは低く、
外したままだと週の途中で足りなくなる——利用者が最初に困ったのがまさにこれ。
逆に多めに買う損は小さい。**どちらの場合も理由は画面に出す**ので、判断は返したまま。

### 10.3 候補の採点（純関数・AI 不要）

`rankByCoverage` の `coverage = 在庫にある材料数 / 材料数` には既知の偏りがある——
**材料 3 個（全部常備品）のレシピが、材料 12 個で 10 個揃っているレシピに勝つ**。
これを打ち消すため、絶対数と買い足し数を別項として足す。

```
score(r) =  1.0 * coverage(r)         // 0..1  いまあるもので作れる度合い
          + 0.3 * useCount(r)         // 0..1  min(使う在庫の点数, 5) / 5
          + 0.6 * expiryUrgency(r)    // 0..1  期限が近い在庫を使うか
          + 0.2 * pinned(r)           // 0 / 1 作りたいリスト
          - 0.3 * missingCount(r)     // 0..1  min(買い足す材料数, 5) / 5
          - 0.8 * recency(r)          // 0..1  最近作った
```

| 項              | 定義                                                                                     |
| --------------- | ---------------------------------------------------------------------------------------- |
| `expiryUrgency` | 使う在庫の期限のうち**最も近いもの**で決める。≤1日:1.0 / ≤3日:0.8 / ≤7日:0.5 / 他:0      |
| `recency`       | 調理記録の最終日。≤7日:1.0 / ≤14日:0.5 / ≤30日:0.2 / 他:0                                |
| `useCount`      | **合計ではなく最大**を使う項ではない。使う在庫の点数そのもの（少材料レシピの下駄を消す） |

**`expiryUrgency` は合計せず最大を採る。** 合計にすると、期限の近い品を 3 つ使うレシピが
他を圧倒して献立が偏る。同点は「期限が近い在庫をいくつ使うか」で割る。

**重みは仮置き。** 実データで並びを見て調整する前提で、
`MENU_WEIGHTS` として 1 か所に出しておく（純関数なので jest で固定できる）。

**退化ケース**: 在庫ゼロ → 全部 coverage 0 で `recency` と `pinned` だけが効く（＝作っていない順）。
材料 0 件のレシピは候補から外す。レシピが X 件未満なら**埋めずに少なく出す**。

### 10.4 M1（AI なし）で成立させる

上の 10.2・10.3 は**すべて決定的**で、オフラインでも枠切れでも動く。
理由の一言も、AI を呼ばずに採点の内訳から作れる:

| 決め手だったもの  | 出す文                        |
| ----------------- | ----------------------------- |
| `expiryUrgency`   | 「なすの期限が近いから」      |
| `coverage` が高い | 「いまある 6 品で作れるから」 |
| `pinned`          | 「作りたいリストにあるから」  |
| それ以外          | 「買い足しが 2 品で済むから」 |

**M1 だけで機能として立つ。** これを先に出して、実際に使われるかを見てから AI を足す。

### 10.5 M2 — AI が足すもの

AI が足せるのは**数えられない判断**だけ:

- 主菜の重複（「昨日も鶏だった」）— 主菜/副菜の区別はデータに無い。タイトルから推し量るのは AI の仕事
- 和洋中の散らし — 同上
- 平日は短時間・週末は手のかかるもの、といった配分
- 自然な言い回しの理由

**契約**: こちらは候補 30 件の要約（`id` / `title` / `cookTimeMin` / カバー率 / 不足材料名）と
**在庫の品名だけ**（数量は渡さない＝引き算を始めさせない）、直近に作ったレシピの `title`、日数 X を送る。
返させるのは `{ days: [{ day, recipeId, why }], note }` だけ。

**検証**: 渡していない `recipeId` は捨てる／重複した日は後を落とす／X に満たなくても埋めない／
`why` は表示のみで判断に使わない。**空・失敗・枠切れは M1 の並びにそのまま落とす。**

### 10.6 保存と鮮度

`app_meta` に 1 本だけ持つ（テーブルを増やさない・v1 は同期しない）。

```json
{
  "version": 1,
  "generatedAt": "2026-08-25T10:00:00.000Z",
  "days": [{ "day": 1, "recipeId": "...", "reason": "なすの期限が近いから" }],
  "pantrySignature": "42:2026-08-25T09:58:00.000Z"
}
```

`pantrySignature` は**在庫の件数と最終更新時刻**。開くたびに突き合わせ、
変わっていたら「在庫が変わりました ［作り直す］」を**静かに出すだけ**で、勝手に組み直さない。
**家族が在庫を減らしたときもこれで気づける**（S2 で `updated_at` が動くため）。
削除・アーカイブされたレシピの日は「このレシピは無くなりました」に差し替える。

同期は後付けできる（エンティティ型を足すだけ）。**「家族で同じ献立を見たい」が実際に出てから**やる。

### 10.7 画面

在庫画面の「この在庫で作れるレシピ」の隣に **「X 日分の献立」**（日数は 2 / 3 / 5 / 7）。

- 結果は Day1…DayX の縦並び。各日に **［レシピを開く］［差し替え］**
- **差し替えはその日だけ**。M1 では候補の次点に入れ替えるだけ（AI を呼ばない＝待ち時間ゼロ）
- 下に **［足りないものを買い物リストへ］** → §10.2(2) の印を付けた §5.3-a のシート

**押す前に見せること**: 蔵書庫のレシピ件数が X に満たないなら先に伝える。
在庫が空なら「在庫から」の前提が崩れる（買い物ありきの献立になる）ことを明示する。

### 10.8 コストと段階

- M1 は**推論ゼロ**。サーバーも触らない
- M2 は候補 30 件の要約なので相談機能と同程度。`INFER_GLOBAL_DAILY_LIMIT` を共有し、
  無料枠も AI 写真レシピと**同じ枠**を消費する（枠を機能ごとに分けると利用者が数え分けられない）

| 段階 | 中身                                                       | 目安    |
| ---- | ---------------------------------------------------------- | ------- |
| M1   | 採点・食い合いの割り切り・複数日の買い物リスト・画面・保存 | 4〜6 日 |
| M2   | AI に並べさせる・理由・差し替え                            | 2〜3 日 |
| M3   | 家族で同じ献立を見る（同期）・好き嫌い                     | 未定    |

### 10.9 M1 で諦めること（正直に）

- **主菜が続くのを防げない**（主菜/副菜のデータが無い）。`claimed` で食材は散るが、
  鶏の日が 2 日続くことはある。差し替えで直せる、に留める
- 和洋中の偏りも同じ理由で見られない
- 理由の文が機械的（上の 4 パターン）

**これらが M2 の AI で足りるかを、M1 を使ってから判断する。**
