# 買い物リスト・在庫（パントリー）設計

> 「家の在庫を核にした食材ライフサイクル」の設計。買い物リスト単体ではなく、
> **在庫 ⇄ 買い物リスト ⇄ レシピ** のループとして設計する。実装前に必ず参照。
> 関連: `docs/データ設計.md` / `docs/レシピ作成フロー.md` / `docs/フリーミアム設計.md`

---

## 1. 狙い

- 家にある食材（在庫）を把握し、**足りないものだけ買う／あるもので作る／なくなりそうを知る**を回す。
- 入力の手間を下げる仕掛け（レシピ材料の一括取り込み、レシート読み取り、将来は食事写真）。

## 2. 全体像（3つのループ）

> **4 つ目のループ（設計中）**: 在庫 → **X 日分の献立** → 買い物リスト。§10（#215）。
> 「いま作れる 1 品」（§5.4）と「何日分の買い物」の間に橋を架ける。

```
        ┌──────────────┐   足りない材料を追加      ┌──────────────┐
        │   レシピ      │ ───────────────────────▶ │  買い物リスト  │
        │ (ingredients) │ ◀─ 在庫で作れる？ 判定 ── │  (shopping)   │
        └──────┬───────┘                           └──────┬───────┘
               │ 在庫で充足判定                            │ 「買った」→ 在庫へ
               ▼                                          ▼
        ┌─────────────────────────── 在庫 (pantry) ───────────────────────────┐
        │  家にある食材（数量・単位・残量しきい値）。残量低下で通知。           │
        │  入力: 手動 / 買い物リストから / レシート写真 / (将来)食事写真から推定 │
        └──────────────────────────────────────────────────────────────────────┘
```

## 3. 置き場所（UI / ナビゲーション）

- タブは現状の **4 つ（ホーム/レシピ/＋追加/設定）を維持**。
- **ホーム右上にカート🛒アイコン**（既存のカレンダー/ギャラリー アイコン横）→ 買い物リスト画面。
- 在庫画面へは、買い物リスト画面のヘッダ、または設定/ホームから。
- レシピ詳細に **「買い物リストに追加」**（足りない材料を一括追加）。

新規 2 テーブル。既存 `recipes/ingredients` は変更しない（突合は名前正規化で行う）。

| ---------------------- | ------- | ---------------------------------- |

`(family_id, store_name)` に一意インデックス。照合は**生の店名で完全一致**する。
「マックスバリュ松山店」と「マックスバリュ空港店」は別エントリになるが、どちらも
同じグループに向ければ目的には足りる。チェーン名への機械的な正規化は、ルール保守が必要な割に
「スーパー」のような粗いまとめにはならないので採らない。

### 4.1 グループ（v13）— 置き場所と買う場所

在庫の `group_name` と買い物の `store_group` は**名前が似ているが別物**。

| 何を束ねるか | 例                             | 効くところ                                         |
| ------------ | ------------------------------ | -------------------------------------------------- |
| 置き場所     | 冷蔵庫 / 〇〇の米 / 災害用備蓄 | 在庫の合算キー・作れるレシピ・相談に送る在庫       |
| 買う場所     | スーパー / ドラッグストア      | 買い物リストの絞り込み（**消し込みには使わない**） |

決めごと:

- **どちらも任意。** グループを 1 つも作っていない人にはチップを出さない（画面が変わらない）
- **「未設定」はそれ自体がひとつのバケツ**で、絞り込みからも常に覗ける。
  未設定を隠すと、振り分け忘れた品が埋もれて買い忘れ・二重買いになる
- **置き場所は在庫の合算キーに入る。** 同じ米が「パントリー」と「〇〇の米」に別々にあるのは
  正常なので、鍵から外すと勝手に 1 行へまとめられてしまう。JAN 一致でも同じ理由でグループを見る
- **置き場所を変えたら、移した先に同じ品があればそこへ寄せる**（`updatePantryItem`）。
  寄せないと、移した瞬間に同じ品が 2 行に並ぶ
- **賞味期限は行に 1 つだけ。** 合算時は**近い方（早い日付）を残す**。買った回ごとの
  ロット分割は、合算をやめる代償が大きすぎるので採らない。**通知では追い立てない**
- **使うグループは「そのとき選ぶ」**（グループ自身の属性にしない）。「普段は冷蔵庫だけ、
  旅行前は全部」のように、やりたいこと次第で変わるため

> マイグレーション: `migrate.ts` の `CREATE_TABLES_SQL` に 2 テーブルを追記し、
> `CURRENT_SCHEMA_VERSION` を 2→3 に上げる（`CREATE TABLE IF NOT EXISTS` なので既存 DB にも安全に追加される）。
> Drizzle 定義（`schema.ts`）は既存どおり object-style の index 設定で追加する。

### バックアップ対象（2026-07-30 に是正）

`pantry_items` / `shopping_items` / `jan_catalog` / `name_aliases` の 4 テーブルは
`backup.service.ts` の `BACKUP_TABLES` から漏れており、復元・機種変更で在庫と買い物リストと
名寄せ辞書が失われる状態だった。現在は 4 テーブルとも対象に含まれる。

新テーブルは `optional: true` を付けて登録する。旧バージョンが書き出したファイルには
そのキーが存在しないため、**欠けていれば 0 件として復元**し、`BACKUP_SCHEMA_VERSION` は上げない
（新旧どちらのアプリでも読める。写真同梱 `recipePhotos` と同じ互換方針）。
在庫系テーブルを増やすときは `BACKUP_TABLES`・`createEmptyBackupTables()` の両方に追記すること。

## 5. 機能別設計

### 5.1 買い物リスト（P1）

- 手動で品目追加（name ＋ 任意 amount）。チェック（永続）。並べ替え・削除・**チェック済み一括削除**。
- レシピ詳細「**材料を買い物リストに追加**」: そのレシピの材料を `source='recipe'`, `recipe_id` 付きで追加。
  **P1 は全材料を追加**（「足りない材料だけ」は pantry が要る **P2**）。
- 重複: 同名（正規化）が未チェックで既にあれば**重複追加しない**（amount は結合しない＝単位が多様なため）。
- 旧 per-recipe `shop.tsx`（このレシピ用・セッション限りのチェック、永続化なし）は**廃止済み**（Issue #66）。
  レシピ詳細のカートアイコン・「足りない材料を買い物リストに追加」テキストボタンはいずれも
  `addMissingRecipeIngredientsToList` に統一され、在庫判定つき・永続リストへの追加に一本化された。

### 5.2 在庫（pantry, P2）

- 一覧・追加・編集（数量・単位・しきい値）・削除。**数量は厳密管理（同一商品は合算）**。
- 買い物リストは**タップ＝買った＝即座に在庫へ**（Issue #66③、`moveShoppingItemToPantry`）。
  従来の「チェック→『在庫に入れる』ボタン押下」の2ステップを1タップに統合し、品目は
  pantry へ upsert（数量加算）された上でリストから消える。トースト通知で結果を表示。
  誤タップは pantry 側での削除／数量調整で復旧可能（不可逆ではない）。
  旧来の「チェック状態を保持して一括処理」機構（`setShoppingItemChecked`・
  `clearCheckedShoppingItems`）は用済みのため削除。`moveCheckedShoppingItemsToPantry`
  （旧チェック済みの一括移動）は移行互換のため残置。
- **バーコード(JAN)入力**: expo-camera で JAN をスキャン → 既知 JAN なら名前/単位を自動補完、未知なら**初回だけ名前入力 → `jan_code→名前/単位` をローカル記憶**（外部DB不要、使うほど賢くなる）。包装商品の厳密識別＋安全な合算に使う。

### 5.3 レシピの「足りない材料」→ 買い物リスト（P2）

- レシピ材料（正規化）のうち **pantry に無い／数量がしきい値以下**のものを抽出し、買い物リストへ一括追加。
- 数量の厳密比較はしない（単位が揃わないため、MVP は「在庫に存在するか」で判定）。

#### 5.3-a 「卵が 1 個あると、3 個要るのに追加されない」（2026-08-24 の指摘）

**症状**: 在庫に卵が 1 個でもあると、レシピが 3 個必要でも黙って除外される。
除外されたものを**あとから足す導線が無い**（`addRecipeIngredientsToList` は実装済みだが未配線）。

**類似アプリの調べ（2026-08-24）**:

| アプリ                      | レシピ → 買い物リストの作り                                                   | 数量の引き算         |
| --------------------------- | ----------------------------------------------------------------------------- | -------------------- |
| **Paprika 3**（有料の定番） | **確認画面＋チェックボックス。** 在庫のものは**チェックが外れるだけで見える** | **しない**           |
| **AnyList**（買い物の定番） | 材料を個別タップ or「すべて追加」。リストにある物は印。在庫の概念なし         | しない（合算はする） |
| **クラシル**（国内）        | 人数を調整して進み、**家にあるものは利用者がチェックを外す**                  | しない               |
| **Grocy**（在庫特化 OSS）   | **必要量 − 在庫**で不足だけをリストへ                                         | **する**             |
| 在庫特化の小規模アプリ群    | 「足りない物だけ」を謳う（＝だいどこと同じ作り）                              | 曖昧                 |

**読み取れたこと**:

1. **主流はどこも数量を引き算しない。** 引き算する Grocy は**製品マスタと単位換算**
   （「1dl 小麦粉 = 60g」を品目ごとに登録）が前提で、それでも複数レシピの引き当てが
   合算されない不具合が残っている。レシピの分量が自由文（「大さじ2」「少々」「1/2本」）の
   うちは、引き算は**自信を持って間違える**方に倒れる
2. **主流と決定的に違うのは「引き算の有無」ではなく「見せるか隠すか」。**
   Paprika もクラシルも、在庫にある材料を**画面には出して、チェックだけ外す**。
   だいどこは**一覧から消していた**ので、なぜ入らなかったのかが利用者に分からない
3. Paprika には**複数レシピ間で同じ材料の数量を合算**する機能がある（卵 2 個＋卵 3 個 → 5 個）。
   だいどこには無い

**決定**: 数量の自動計算はしない。**除外されたものを見せて選べるようにする**（下の #214）。
在庫にある物には「在庫 1個」を添える — 引き算はアプリではなく利用者がやる。

### 5.4 在庫で作れるレシピ（P4）

- 各レシピの材料に対する **pantry 充足率**（= 在庫にある材料数 / 全材料数）でランキング。
- 「ほぼ作れる（充足率高 ＋ 不足は調味料程度）」を上位表示。

### 5.5 残量通知（P3）

- pantry の `quantity <= low_stock_threshold` の品目を検出 → **ローカル通知**（先日実装の `notification.service` を流用）。
- トリガ: アプリ起動時／在庫更新時にチェックし、必要なら通知をスケジュール（1日1回まとめる等、頻度は要調整）。
- **通知タップ → 一括買い物リスト追加（Issue #66②）**: 確認画面を経由せず、タップ時点の低在庫アイテム全件を
  `source='low_stock'` で買い物リストへ即時追加し、買い物リスト画面へ遷移する。通知の `data.type` で識別
  （`addLowStockTapListener`＝生存中のタップ、`consumeLowStockLaunchTap`＝タップでのコールドスタート起動）。

### 5.6 レシート登録（P5）

**読み取りは2経路。端末内 OCR は文字起こしに専念し、品目化は必ず AI が行う**
（2026-08-15 / Issue #178。経緯と判断は `docs/在庫・レシート設計レビュー.md` §3.4）:

```
レシート写真
  ├ 端末内OCRが使える → 文字起こし → **テキストだけ**を AI へ → 構造化（品目・数量・単位）
  └ 使えない/読めない → **画像**を AI へ（Vision）
```

- **端末内 OCR（`withDaidokoOcr` / unbundled ML Kit・Android のみ）**：文字起こしまで。以前あった
  ヒューリスティック解析（`utils/receiptParser`）は廃止した — 品目名しか取れず、非食品の除外・重複統合・
  数量抽出をクラウド側と二重に持つことになるため。**画像トークンが要らず、レシート写真が端末から出ない**のが
  この経路の価値。
- **可用性は Play Services に問い合わせる**。unbundled ML Kit は「モジュールはあるがモデルが未取得」という
  状態があり、**インストール直後はたいていそれ**。`DaidokoOcrModule.isAvailable()` が
  `ModuleInstallClient.areModulesAvailable()` で実際に取得済みかを確認し、未取得なら `false` を返して
  deferred install を予約する。
- **失敗はすべて画像経路へ落とす**（モデル未取得・認識失敗・1文字も読めない・テキストからレシートと
  判定できない・品目が0件）。**生の ML Kit エラーを画面に出さない**。
- **クラウド AI（`POST /api/v1/infer/receipt`）**：Gemini の構造化出力から品目を直接抽出（半角カナ正規化・
  非食品/値引き行の除外・重複統合込み）。テキスト入力（`ocrText`）と画像入力でスキーマと後処理は共用し、
  プロンプトだけ差し替える。BYOK キー設定時は端末から直接 Gemini を呼ぶ。無料（クライアント側の回数ゲート
  なし）— コストはサーバーのグローバル日次上限＋利用量メール通知で管理。iOS は端末内 OCR を持たないので
  常に画像経路（Apple Vision は #58）。
- 画面（`app/(tabs)/receipt.tsx`）は**何が端末から出るのかを経路に合わせて明示する**。端末内 OCR が使える
  ときは「文字だけを送る・読めなければ写真を送る」、無いときは「写真を送る」。
- **数量・単位も読む（2026-08-15 / Issue #178-1）**: 構造化出力の品目を `{ name, quantity?, unit? }` に拡張し、
  読み取った数量・単位を確認画面（`app/(tabs)/receipt.tsx`）で編集してから在庫へ渡す。
  - **読めなければ `null` のまま通す**。1 で埋めない — 在庫は同一品目を合算するので、推測した数量は
    「家に無いものが在庫にある」状態として消えずに積もる。`addPantryItem` の「数量未管理（quantity=null）」に素直に乗せる。
  - 単位はレシート表記がばらつく（「2」「2個」「500g」「1P」）。`utils/receiptQuantity.ts` の
    `normalizeReceiptQuantity` で §6 の方針に沿って寄せる（NFKC → 別名表 →「個/本/袋/パック/g/ml」等、
    kg・L はグラム・ミリリットルへ換算、「点」「円」など単位でない付帯表記は捨てて数量だけ残す）。
    数量の妥当性も併せて見る（個数系は 99 まで・g/ml は 100,000 まで。単価や値引き額の紛れ込みを弾く）。
  - 同一レシート内の重複は **在庫と同じ規則（正規化名 × 単位）** でまとめる。片方でも数量が読めなければ合算せず `null`。
  - 単価・購入日・`store` は対象外（`store` は抽出しているが未使用のまま）。

**レシートで買い物リストを消し込む（v13）**

レシートは「何を買ったか」を持っているのに、買い物リストは手つかずのままだった。
在庫へ追加すると同時に、買った品を買い物リストから消し込む。

- **消さずにチェックを付ける。** 誤照合で行が消えると気づけないが、チェックなら取り消せる。
  買い物リスト側はチェック済みの行を打ち消し線で出し、タップで**取り消し**にする
  （そのまま「買った→在庫へ」に流すと在庫へ二重に積む）
- **照合は品目名（正規化＋名寄せ辞書）だけ。** 店では絞らない — 同じ品を別の店で買うのは普通で、
  店で絞ると取りこぼす
- **数量は不問。** 「牛乳2本」必要で1本だけ買った場合もチェックは付く（外すのは利用者の判断）
- **追加する前に「◯件を消し込みます」と見せる。** 黙って消すと誤照合に気づけない
- 在庫へ入れる置き場所は `defaultGroupFor`（その品が**1 か所だけ**にあるならそこ）。
  置き場所を使っている人の買い足しが「未設定」に別行で積まれるのを防ぐ
- 店名は初めてのときだけ買う場所と結び付けて覚える（`store_group_aliases`）。毎回選ばせない

### 5.7 毎食写真 → 消費推定（P6・実験的・プレミアム特典）

- 食事写真 → 料理推定 → 典型材料を推定 → pantry を概算で減らす。**Vision＝プレミアム特典**。
- **精度は未知**。あくまで補助（自動で減らしすぎない・確認を挟む）。opt-in。研究フェーズとして最後。

## 6. 食材名の正規化・突合（肝）

レシピ材料・在庫・レシート・手動入力を**名前で突合**するため、正規化が要。

- 正規化ヘルパ `normalizeItemName` を新設：`String.normalize('NFKC')`（全/半角統一）＋ 既存 `normalizeKana`（カナ→かな・小文字・trim）＋ 連続空白除去。
  ※ `normalizeKana` 単体は全/半角を統一しないため NFKC を併用する。
- 分量や修飾を除去（例: 「玉ねぎ 1個」→「玉ねぎ」、「みじん切り玉ねぎ」→ 要検討）。
- MVP は**完全一致（正規化後）**。表記ゆれ辞書（玉ねぎ＝玉葱＝たまねぎ）は段階的に。
- **包装商品は JAN コードで厳密識別**（名前突合より優先）。レシピ材料・バラ売りは JAN を持たないため名前正規化で突合（**JAN と名前正規化を併用**）。
- **数量は厳密管理＝同一商品は合算**（JAN 一致 or 同名(正規化)×同単位）。異なる単位は合算しない。
  **名寄せの対象と時機（2026-08 改訂）**

当初は「**在庫名** → canonical」の辞書として作り、埋めるのも「在庫で作れるレシピ」画面だけだった。
これだと突合が成立しない:

- 突合は **在庫 × レシピ材料**。片側（在庫名）しか canonical に写さないので、
  在庫「にんじん」・レシピ「人参」は、**AI が選んだ canonical とレシピの表記が偶然揃ったときだけ**当たる
- 辞書を埋める呼び出し元が cookable 画面ひとつだったので、**その画面を開かなければ辞書は空のまま**

改めた点は 2 つ:

1. **辞書は「任意の食材表記 → canonical」。** レシピ材料名も解決の対象にする
   （`collectUnmatchedNames` が在庫側・材料側の両方から集める）
2. **解決するのは「ルールで当たらなかった残り」だけ。** 完全一致・部分一致で当たる名前
   （「玉ねぎ」など）は AI に投げない。呼び出し回数は語彙数へ自然に収束し、無料枠を無駄に使わない

**突合が起きる場所では必ず育てる。** 現在の呼び出し元は「在庫で作れるレシピ」（表示時）と
「足りない材料を買い物リストへ」（追加前）。枠切れ・オフライン・AI 無効のときは黙って素通しし、
ルール 1〜2 だけで従来どおり動く。

- **`name_aliases`（AI名寄せキャッシュ）のメンテUI（Issue #66④）**: 設定画面「データ」→「名寄せ辞書」
  から一覧・編集・削除ができる（`getAliasEntries` / `updateAliasCanonical` / `deleteAlias`）。
  誤って解決された対応（例: 別の食材が同一視された）を手動修正でき、削除した項目は次回同じ表記が
  出た際に再度AIで解決される。

## 10. 在庫から X 日分の献立を組む（#215・設計確定 2026-08-25）

> 多エージェントの深掘り（6 観点）と敵対的検証を経た確定版。
> 途中で落とした案は各節の「落とした案」に理由ごと残す — 同じ案をもう一度検討して
> 同じ穴に落ちないため。

### 10.0 一枚で言うと

**在庫から X 日分の献立を決定的に組み（M1・推論ゼロ）、AI はボタン 1 本の
「並べ替え」だけに使う（M2）。数量は一切計算しない。** 在庫の食い合いは
「どの在庫を何日が取り合っているか」を**見せる**ことで扱い、決めるのは常に利用者。

| 原則                         | 根拠                                                               |
| ---------------------------- | ------------------------------------------------------------------ |
| 数量を計算しない             | §10.2。分数（½）も人数スケーリングも解析できず、出す数字は嘘になる |
| AI 無しで成立する            | §10.5。枠切れ・オフラインで画面が空になる作りは行き止まり          |
| AI は「組む」1 操作 1 回     | §10.5。無料枠は生涯 1 回。差し替えごとに呼ぶと課金の罠になる       |
| 名寄せ辞書を献立から育てない | §10.3。1 回開くだけで名寄せの日次枠 30 を食い切る                  |
| 行は素の名前・突合だけ辞書   | §10.4。辞書でまとめると別の粉が 1 行に潰れて消える                 |

### 10.1 狙いと範囲

**「何を作るか」で毎日詰まるのを、いま家にあるものから解く。**
§5.4「作れるレシピ」は**いま作れる 1 品**しか出さず、買い物は「何日分」で考える。
その間に橋が無い。同時に、蔵書庫に溜まったまま使われないレシピを在庫から掘り起こす。

やらないこと（v1）:

- 栄養・カロリー計算（裏付けるデータが無い）
- 好き嫌い・アレルギー（プロフィールに情報が無い。M3 の拡張点）
- 献立の自動確定・自動更新（決めるのは常に利用者）
  → **2026-08-28 決定変更: オプトインの自動モードを §10.11 に新設**（既定オフ・
  差し替え/取り消し/オフがいつでも効く。入る/出るを決めるのが利用者）
- 献立の家族同期（「家族で同じ献立を見たい」が実際に出てから。§10.7）

### 10.2 数量を計算しない（この設計の背骨）

X 日分の献立は在庫を食い合う——1 日目が卵を使えば 3 日目の卵は「ある」ではない。
これを**数量の引き算で解くことを 2 度検討し、2 度落とした**:

**落とした案 1: 常に引き算する。** レシピの分量は自由文（「大さじ2」「少々」「½本」）で、
在庫は数値＋任意単位。揃わないまま引くと**自信を持って間違えた買い物リスト**ができ、
間違いが利用者に見えない（§5.3-a と同じ判断）。

**落とした案 2: 単位が完全に揃うときだけ引き算する（折衷）。** 2 つの実データで落ちた。

1. アプリ自身のシードが `1/2` ではなく **`½`（U+00BD）を 9 箇所**で使っており、
   NFKC 正規化は `1⁄2`（U+2044 FRACTION SLASH）を生むため、素朴な `/` の解析には
   **一度も当たらない**。主力の経路が自社データで発火せず、粗い側の判定だけが動く
2. **人数を見ていない。** `recipe_revisions.servings` は nullable で、詳細画面には
   分量スケーリング（NumberStepper）が既にある。「2 人分のレシピを 4 人分で作る」が
   日常である以上、材料欄の合計は**根拠のある数字の顔をした嘘**になる

さらに「にんにく 2かけ」対 在庫「にんにく 1個（=1玉=約10かけ）」のような
**単位の橋が原理的に無い**組が薬味類に集中しており、これは毎週の献立で毎回出る。

**採る形**: 数量には触れず、**引き当てグラフ**（在庫の行 → それを要求する日の集合）
だけを持つ。順序は付けない——「1 日目が卵を取った」と言える根拠は無い
（並びはこちらが決めただけ）。勝者を決めずに「この卵を 3 日が使います」と見せる。

#### 取り分ける調味料は食い合いに数えない

醤油・砂糖・油は毎日出るが、1 回の使用で在庫が消えない。数えると
**全レシピで全調味料が警告になり、警告そのものが読まれなくなる**。

レシピ側の分量表記が「取り分け」を示す語を含む claim は数から外す:

```
大さじ / 小さじ / 大匙 / 小匙 / カップ / 少々 / 少量 / 適量 / 適宜 /
ひとつまみ / ふたつまみ / お好み / tbsp / tsp
```

判定は**レシピの自由文への語彙一致だけ**（NFKC 後）。数量も単位換算も要らず、
AI もサーバーも要らない。**「取り分けを除いた claim が 2 件以上」**のときだけ
食い合いとして扱う。

落とした案: 在庫側に「調味料」フラグを持つ → 入力が続かない（#200 で
賞味期限に対して同じ判断をしている）。置き場所（`groupName`）で推定 → 軸が違う。

### 10.3 候補の採点と並び（M1・純関数）

#### 突合

`itemNamesMatch` のルール（完全一致＋3 文字以上の部分一致）＋**既にある名寄せ辞書**だけ。
**献立画面から `resolveNames`（AI 名寄せ）を呼ばない**:

- 日次枠は 30 件（`NAME_RESOLVE_FREE_DAILY`）。7 日献立は 7 レシピ × 8 材料 ≒ 40 の
  異表記で、**1 回開くだけで枠を食い切る**
- 未解決の材料は「在庫に無い」側に倒れ、**在庫にあるのに買わせる**
- 翌日開くと残りが解決されて**答えが変わる**。端末間でも辞書の同期状態で食い違う

辞書を育てるのは従来どおり単一レシピの「足りない材料」と cookable の側。

#### 採点

```
score(r) =  1.0 * coverage(r)        // 0..1  在庫にある材料数 / 材料数
          + 0.3 * useCount(r)        // 0..1  min(使う在庫の点数, 5) / 5
          + 0.6 * expiryUrgency(r)   // 0..1  下表。NULL は 0
          + 0.2 * pinned(r)          // 0 / 1 作りたいリスト
          - 0.3 * missingCount(r)    // 0..1  min(買い足す材料数, 5) / 5
          - 0.8 * recency(r)         // 0..1  ≤7日:1.0 / ≤14日:0.5 / ≤30日:0.2
```

- `useCount` と `missingCount` は `coverage` の**少材料バイアス**
  （材料 3 個・全部常備品のレシピが、12 個中 10 個揃うレシピに勝つ）を打ち消す絶対数の項
- `expiryUrgency` は使う在庫の期限の**最も近い 1 件**で決める（≤1日:1.0 / ≤3日:0.8 /
  ≤7日:0.5 / 他:0）。**合計しない** — 合計すると期限間近の品を複数使う 1 レシピが
  他を圧倒し、献立が偏る
- **期限はほとんど入っていない前提**で組む。#200 は入力を強制しない方針なので
  `expires_on` は大半が NULL。全件 NULL でも並びが成立することをシードで確かめる。
  期限は「入っている人にだけ効く上乗せ」
- 重みは `MENU_WEIGHTS` として 1 か所に置く仮置き。純関数なので jest で固定できる

#### 並べる

```
claimed = ∅                       // 採点にだけ使う内部状態（保存しない・表示しない）
for day in 1..X:
    pick = argmax score(r, pantry \ claimed)   // 未選択のレシピから
    claimed ∪= ingredients(pick) ∩ pantry
```

`claimed` は**採点上の割り切り**（1 つの在庫の恩恵は 1 品まで）であって残量ではない。
副作用として献立が別の食材へ散り、変化が付く。

退化: 在庫ゼロ → coverage 全 0 で recency と pinned だけが効く（＝しばらく作っていない順）。
材料 0 件のレシピは除外。候補が X 件未満なら**埋めずに少なく出す**。

#### 理由の一言（AI 不要）

採点の決め手から機械的に作る: `expiryUrgency` →「なすの期限が近いから」／
`coverage` →「いまある 6 品で作れるから」／`pinned` →「作りたいリストにあるから」／
他 →「買い足しが 2 品で済むから」。

### 10.4 買い物リストへの橋

選ばれた X 日ぶんの材料を**先に 1 行へまとめてから** §5.3-a の選択シートに流す。
`addShoppingItem` は同名の未購入行があると **null を返して黙って捨てる**ため、
1 件ずつ足すと 2 日目以降が消える（#214 の「見えない除外」の再発）。

#### 鍵を 2 つに分ける

| 用途                       | 鍵                                      |
| -------------------------- | --------------------------------------- |
| 買い物リストの行をまとめる | `normalizeItemName(材料名)`（素の名前） |
| 在庫との突合・食い合い     | 名寄せ辞書を通した canonical 名         |

名寄せは製品名→一般名（`春よ恋強力小麦粉 → 小麦粉`）を作るので、**辞書でまとめると
「強力粉」と「薄力粉」が 1 行に潰れて片方が消える**。別の行のまま同じ在庫を指し、
どちらにも食い合いの印が付くのが正しい。

#### シートの行

| 状態                       | 既定       | 見せ方                                                        |
| -------------------------- | ---------- | ------------------------------------------------------------- |
| 在庫に無い                 | ☑ チェック | 「玉ねぎ 1個 / ½個」（日ごとの分量を `/` で併記・合算しない） |
| 在庫にある・1 日だけが使う | ☐ 外す     | 「在庫 1個（たまご）」                                        |
| 在庫にある・2 日以上が使う | ☐ 外す     | 「在庫 1個（たまご）・**3日で使います**」＋**最上段に固定**   |

**落とした案: 2 日以上なら既定を ON にする。**
牛乳 1 本を 3 日が 200ml ずつ使うだけで ON になり、毎週 2 本買うことになる。
単位を見ない以上この誤りは系統的で、しかも§5.3-a の原則
（アプリが決めずに理由を見せる）に反する。既定は倒さず**最上段に固定**して
見落としを防ぐ。実地で足りなければ、倒すのは 1 行の変更。

**在庫の実名を必ず併記する**（「在庫 1個（たまご）」）。部分一致による
偽の食い合い（レシピ「小麦粉」× 在庫「春よ恋強力小麦粉」）に利用者が 1 秒で気づける。

追加後は §7-1 の条件どおりトースト（画面に留まる純粋な成功）。

### 10.5 AI の役割（M2）と契約

AI が足せるのは**数えられない判断**だけ: 主菜の重複・和洋中の散らし・
**調理時間の長い料理を連続させない**配分と、自然な言い回しの理由。
（当初「平日は短時間」としていたが、契約が渡すのは日数 X だけで開始曜日が無く、
AI には Day3 が平日か分かりようがない。書けば曜日への言及＝捏造を誘発する。
曜日を渡す契約拡張は M3 送り — §10.10.0）主菜/副菜のデータは無いので、タイトルから推し量るのは
AI にしかできない仕事。

**呼ぶのは「組む」1 操作につき 1 回。差し替えでは絶対に呼ばない。**
（**2026-08-28 決定変更 D**: プレミアム/BYOK 限定の自動モード A2 は
「1 日 1 回・朝の初回起動時・自動」も許す — §10.11.5。失敗は無言で M1 続行）
無料枠は**インストールごとに生涯 1 回**（**2026-08-27 に方針変更: 月 N 回・
サーバー側で端末単位に管理する形へ移行予定。N と枠の帰属は §10.10.7-1**）、
以降はリワード広告 1 本＝1 回
（`docs/フリーミアム設計.md` §2）。差し替えごとに呼ぶと「広告を見ないと献立を
1 日直せない」になり、7 日一巡で広告 7 本。差し替えは**渡した候補 30 件の残り**から
次点を入れる（¥0・即時・オフライン可）。

**契約**:

- 渡す: 候補 ≤30 件の `{id, title, cookTimeMin, カバー率, 不足材料名}`・在庫の**品名だけ**
  （数量は渡さない＝引き算を始めさせない）・直近に作った `title`（日付は渡さない）・日数 X。
  個人情報は渡さない（同期 §0-2 と同じ線）
- 返す: `{ days: [{ day, recipeId, why }], note }` のみ
- 検証: 渡していない `recipeId` は捨てる／重複日は後を落とす／
  **同一 `recipeId` の 2 日目以降を落とす**（M1 の「1 レシピ 1 日」不変条件を AI 出力にも通す）／
  X 未満でも埋めない／
  `why` は表示のみ。**空・失敗・枠切れは M1 の並びへそのまま落とす**
- 出力言語は `ai-output-locale` に従う（unitSystem は渡さない — 分量を出力しない推論に
  単位系の指示は「分量を書け」という圧力になるだけ）

### 10.6 保存と鮮度

`app_meta` に 1 本（テーブルを増やさない）:

```json
{
  "version": 1,
  "generatedAt": "2026-08-25T10:00:00.000Z",
  "source": "coverage",
  "days": [{ "day": 1, "recipeId": "...", "reason": "なすの期限が近いから", "doneAt": null }],
  "pantrySignature": "42:2026-08-25T09:58:00.000Z"
}
```

- `source` は `"coverage"`（M1 の決定的な並び）か `"ai"`。**どちらの経路で出たかを残す** —
  枠切れ・オフラインで落ちたことが後から分かり、実機検証でも「AI が効いたか」を確かめられる
- `pantrySignature` = 在庫の件数 + 最終更新時刻。開くたびに突き合わせ、変わっていたら
  「在庫が変わりました ［作り直す］」を**静かに出すだけ**。勝手に組み直さない。
  家族が在庫を消費したときも S2 の `updated_at` が動くのでこれで気づける
- **`doneAt`: 作り終わった日は引き当てグラフから外す。** 「作った！」は在庫を
  **一切減らさない**（`cooking-log.service.ts` に pantry 参照 0 件）ので、外さないと
  claim が残り続け、利用者が手で在庫を減らすと**二重に数えて**誤って「足りない」と言う。
  `generatedAt` 以降にその `recipeId` の調理記録が付いたら埋める——献立に「作った」を
  持たせるのではなく、**既存の調理記録を読んで印を付けるだけ**
- 削除・アーカイブされたレシピの日は「このレシピは無くなりました」に差し替える
- 引き当てグラフと食い合いの印は**保存しない**。開くたびに再計算する
  （保存すると古い警告が残り、古いことが利用者に見えない）

#### 10.10.0 契約の確認と、§10.5 への修正 2 点

契約（渡す/返す/検証/言語/フォールバック）は §10.5 のとおりで変えない。

#### 10.10.2 プロンプト v1 と responseSchema

書き方は `recipe-consult.ts` の SYSTEM_PROMPT（`join('\n')` 配列・`## 見出し`・
「してはならないこと」節）。日本語で持ち、出力言語は `withOutputLanguage()` で足す。

```
あなたは、家庭の献立の並びを整える料理人です。
候補のレシピ一覧から指定の日数ぶんを選び直し、飽きの来ない並びにします。

## 前提
- 候補は「おすすめ順」に並んでいる。在庫との相性・最近作ったか・作りたい
  リスト入りなどを機械的に採点した順であり、カバー率の順ではない。
- 各候補の coveragePct は「いま家にある材料でどれだけ作れるか」（0〜100%）、
  missing は足りない材料の名前、cookTimeMin は調理時間（分）。
- あなたの仕事は候補の中からの選び直しと並べ替えだけ。新しいレシピを発明しない。
- 決めるのは利用者。あなたの並びは提案であって、そのまま採用されるとは限らない。

## 直すのは次の 3 点だけ
1. 主菜の食材が続かないようにする。鶏の日が 2 日続く・魚の日が無い、のような
   偏りを散らす。食材の系統はタイトルから推し量ってよい。
2. 和・洋・中の系統が続かないようにする。これもタイトルから推し量ってよい。
3. 調理時間の長い料理を連続させない。cookTimeMin の大きい日は散らす。
このために coveragePct が多少低い候補を選んでよい。ただし coveragePct がほぼ 0 の
候補を高い候補より優先しない（買い物が増えるだけの並びは改悪）。

## 選び方
- 各日 1 レシピ。候補一覧にある id だけを使う。
- 同じレシピを 2 つの日に入れない。
- 「直近に作った料理」と同じ・よく似た料理は前半の日に置かない。
- 日数ぶんの候補が無いときは、あるぶんだけ返す。埋めるために無理をしない。
- 散らしようが無いとき（候補が日数ちょうど・全部同系統）は、無いなりの並びで
  よい。やってもいない工夫を理由に書かない。

## why（各日の理由の一言）
- その日にその料理を選んだ理由を 1 文・全角 40 字以内で書く。
- 言及してよいのは渡された情報から言えることだけ: 料理名・調理時間・
  「いまある材料で作れる」（coveragePct）・足りない材料の名前・在庫の品名・
  直近に作った料理・並びの工夫（例:「前の日が肉なので魚に」）。
- 同じ言い回しを全部の日に繰り返さない。
- note は、献立全体に本当に伝えるべき補足があるときだけ 1 文
  （例: 後半は買い足しが前提になる）。無ければ書かない。

## してはならないこと
- 分量・個数・グラム数を書く（渡されていない。書けば嘘になる）。
- 賞味期限・鮮度・旬・季節・気温に触れる（渡されていない）。
- 栄養・カロリー・健康効果・効能を書く（このアプリの扱う範囲ではない）。
- 曜日・平日・週末に触れる（何曜日に作るかは渡されていない）。
- 家族構成・好み・アレルギーを推測する。値段・節約に触れる。
- 候補に無い id・レシピ名を作る。在庫に無い品名を「ある」と書く。
```

入力は 1 つの user メッセージに束ねる。候補は id 転記ミスを防ぐため JSON のまま
（`name-resolve.ts` が JSON.stringify を user パートに使う先例）。在庫は
`.slice(0, 200)` で頭打ち（`recipe-consult.ts` の buildContextText と同じキャップ）:

```ts
function buildMenuContext(input: MenuArrangeInput): string {
  return [
    '## 日数',
    String(input.days),
    '## 候補（おすすめ順）',
    JSON.stringify(input.candidates),
    '## 在庫にある品名',
    input.pantry.slice(0, 200).join('、') || '（在庫は空）',
    '## 直近に作った料理',
    (input.recentTitles ?? []).join('、') || '（記録なし）',
  ].join('\n');
}
```

responseSchema（`recipe-consult.ts` の GEMINI_RESPONSE_SCHEMA の書き方）:

#### 10.10.3 検証（純関数）— 置き場所・ルール・テスト

**正典は `apps/server/src/lib/menu-arrange.ts` の `sanitizeMenuDays()`。**
評価ハーネス（`apps/server/scripts/`）は同一パッケージなので直接 import できる。
**モバイルは写しを持つ**（BYOK 経路はサーバーを通らないので必須。managed 応答にも
防御的に通す——[client-must-survive-server-skew] の方針）。写しには
`recipe-consult.provider.ts` と同じ「**片方だけ直さないこと**」コメントを付ける。
shared に置かない理由は §10.10.1 冒頭のとおり（サーバー tsconfig の strict rootDir・
既存ルートも全てローカル写し）。

```ts
export function sanitizeMenuDays(
  raw: MenuArrangeRaw['days'],
  candidateIds: ReadonlySet<string>,
  dayCount: number,
): MenuDayPick[] {
  // 1. recipeId が candidateIds に無い行 → 捨てる（ハルシネーション遮断）
  // 2. day が 1..dayCount の整数でない行 → 捨てる
  // 3. 同じ day の 2 件目以降 → 捨てる（「後を落とす」）
  // 4. 同じ recipeId の 2 日目以降 → 捨てる（§10.10.0 の追加規則）
  // 5. why は文字列整形（上限 100 字で切る）。無ければ undefined —— M1 の機械的
  //    理由への差し替えはクライアントの仕事。サーバーは埋めない
  // 6. day 昇順に整列。dayCount 未満でも埋めない
```

#### 10.10.5 評価: 採点軸・評価セット・合格ライン

**評価は M2 本体と別の作業単位にする**（R0 #118 と同じ扱い。§10.10.8 の見積りが理由）。
様式は `docs/レシピ推論の評価設計.md`（軸→合格ライン→評価セット→ハーネス、

「UI への波及」と「端末内 OCR」が並存——を先に解消すること）。

写真評価との最大の違い: **入力が合成できる**ので、評価ケース側に正解ラベル

why の質だけ。ベースラインは常に「候補の先頭 X 件」（候補は M1 スコア順で渡す契約
なので、M1 実装に依存せずハーネスが完結する）。

- 評価セットは **`apps/server/scripts/menu-eval-cases.json` としてコミットする**。
  vision の評価セットは個人の外食写真だから gitignore だが、こちらはシード由来の
  合成 JSON で個人情報ゼロ。回帰を回す価値が守秘に勝る。結果 md は
  `docs/eval/menu-rank/` へ（vision と同じ置き方）
- ケースの材料: `seed.ts` の実レシピ 7 件＋ `STRESS_TITLES` 20 種（和/中/洋が揃う）。
  各タイトルに評価用ラベル `{ mainCategory, genre }` を一度だけ人手で振り、
  **ハーネスは契約のフィールドだけに剥がしてから送る**（ラベルを見せたら試験にならない）
- **初回は 8 ケース**: baseline-7 / chicken-top（上位 5 件が全部鶏・E 誘発）/
  chinese-top（F 誘発）/ few-candidates（候補 4 件に X=7・埋めない）/

  recent-repeat（直近 title=候補 1 位）/ near-dup-titles（カレー 3 種・系統推定）/
  en-locale（baseline-7 の en 版）。各 2 実行 ≒ 16 呼び出し ≒ **¥6 以下**。
  long-cook-top・zero-coverage-tail・mega-30 は報告のみ項目なので 2 周目以降に足す

| 項目                             | 定義                                                                                                                            | 合格ライン                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |

#### 10.10.6 落とした案（理由ごと）

- **a. menu 専用のレートプール新設** → プールを分けた既存理由は毎回「安い呼び出しが
  高い呼び出しに締め出される」だが、menu は ¥0.35/回で写真レシピ・相談と同じ帯・
  頻度も週 1 程度。refine/consult が「別枠にすると上限管理が二重になる」として
  RECIPE_POOL に同居した判断をそのまま踏襲
- **b. 月次カウンタを sync-store（PostgreSQL）に載せる** → `DATABASE_URL` が無いと
  同期ごと無効になる構成で、献立は同期未使用の端末でも動くべき。in-memory も不可
  （月次窓は Railway 再デプロイをまたぐ）。share-store 方式の SQLite に載せる
- **c. スキーマ・検証純関数を packages/shared に置く** → サーバー tsconfig の
  strict rootDir がクロスパッケージ import を排しており、既存 6 ルートも全て
  ローカル写し（photo-infer.agent.ts 冒頭コメント）。1 機能のために構成を変えない
- **d. checkRateLimit を月次枠チェックより先に置く** → checkRateLimit は許可時に
  即カウンタを増やすため、月次枠切れの端末の連打が Gemini を呼ばずに共有プールを
  食い潰し、10% 刻みメールの分母も汚す。無料のローカル読みである月次枠が先
- **e. MenuArrangeError に kind（'quota'|'offline'|…）を持たせる** → 既存の
  ConsultError / ReceiptVisionError は retryable のみで、文言の出し分けは throw 時に
  `t()` で message に焼き込む方式。kind の消費者が存在しないまま形だけ増える
- **f. プロンプトに「候補はカバー率の高い順」と書く** → 実際に渡すのは §10.3 の
  M1 スコア順（期限・pinned・recency 込み）で、coveragePct が候補 JSON に入っている
  以上モデルは矛盾を直接観測できる。why の捏造を縛る設計で、プロンプト自身が入力に
  ついて嘘を言うのは自殺行為。「おすすめ順（機械的に採点した順）」と書く
- **g. X 未満の結果を M1 で埋め直す** → 埋めた日が AI の顔をする。空カードで残す
- **h. AI 実行中の全面スピナー・専用画面** → M1 が生きているのに隠すのは §10.7 違反
- **i. why の語彙照合（在庫品名との突き合わせ・機械）** → 形態素解析なしの部分一致は
  偽陽性が多く、合否に使えない参考表示に工数を割かない。捏造検知は正規表現ゲート＋
  G 軸人手で足りる（入力が合成なので照合対象を md に併記でき、1 文 10 秒で判定できる）
- **j. 「平日は短時間」をプロンプトに書く** → 開始曜日を渡さない契約では Day3 が
  平日か分からず、書けば曜日への言及（捏造）を誘発する。「長い料理を連続させない」へ
- **k. 検証で本番 env（INFER_GLOBAL_DAILY_LIMIT=0）を一時変更して 429 を再現** →
  その間、実利用者の AI が全部止まる。ローカルサーバーへ向けた検証ビルドで再現する

#### 10.10.7 実装時に確認すること

1. **月次無料枠の N と帰属**（献立専用か、写真レシピ込みの全体枠の月次化か。
   §10.8「枠を機能ごとに分けると数え分けられない」との整合込み）——ユーザー決定
   → **決定 2026-08-28: 全体枠**（§10.8 の「数え分けさせない」を採る）。
   `device_monthly_usage.category` は **将来 'infer' 一本**へ（§10.10.1 の 'menu' は
   全体枠移行までの過渡）。**N = 5**（2026-08-28 利用者決定。イメージ生成は別勘定のまま — フリーミアム §11）
2. **広告トークンとサーバー月次枠の接続**（サーバーは広告視聴を検証できない。
   案: 超過後はクライアントがトークンを消費し `x-quota-source: token` を添える）——
   **M2 に含める（2026-08-28 決定変更・当初の「切り離す」を撤回）。**

   **撤回の理由**: 切り離すと「広告を 30 秒見たのにサーバーが枠超過で弾く」が起きる。
   **現状（クライアント側カウント）は広告を見れば必ず続行できる**ので、これは
   **機能の後退**であり、リワード広告の対価を踏み倒す形になる（AdMob ポリシー上も悪い）。

   **採る形**: クライアントが `x-quota-source: token` ヘッダを添え、サーバーは
   **月次枠のチェックを飛ばす**（日次の共有プールとコストガードは通常どおり通す）。
   - **信頼水準は現状と同じ。** 今の無料枠カウンタ（`app_meta`）も完全にクライアント側の
     自己申告で、サーバーは検証していない。ヘッダ方式は**後退ではない**
   - **本当のコストガードは `INFER_GLOBAL_DAILY_LIMIT`**（全体の日次上限）。
     ヘッダを詐称されても、ここが天井として効く
   - トークン残高の管理は従来どおり端末ローカル（`ai_photo_recipe_token_balance`）。

### 10.11 毎日の自動献立モード（設計確定 2026-08-28・§10.1 からの決定変更）

> **利用者の直接指示（2026-08-28）による決定変更。** §10.1 の「やらないこと（自動確定・自動更新）」を、
> **オプトイン**の自動モードとして解禁する — 入る/出るを決めるのが利用者になる点で
> 「決めるのは常に利用者」の精神は保たれる。あわせて §10.5 の「1 操作 1 回」に
> A2（プレミアム/BYOK 限定・1 日 1 回・自動）の例外を設ける。
> 導線全体は `docs/画面設計.md` 末尾「献立導入後の全体導線」、検証済みの背景は

#### 10.11.1 実行モデル — 起動時の鮮度判定＋ローリング

- **背景実行（expo-background-task）は却下**: 公式が「システムが決めた将来のどこかで走る」「電池とネットワークの条件付き」と明記。発火保証ゼロの機構に「毎日できている」を約束させない。サーバー cron も却下（献立非同期 §10.1・push 内容ゼロ §0-2 に二重衝突）
- 起動（isReady）/ フォアグラウンド復帰時に `runDailyMenuMaintenance()`:
  1. auto 設定オフ → 何もしない
  2. 保存プランの `anchorDate`（Day1 の暦日・auto のみ持つ）< 今日 → 経過日ぶん**ローリング**（先頭を落とし、末尾に M1 argmax で補充。生き残った日は触らない — 「昨日見た明日」が今日も同じ）
  3. doneAt 突合・引き当て再計算（§10.6 どおり）
  4. 自動買い物追加（子トグル ON 時・§10.11.2）
  5. 翌朝の one-shot 通知を 1 本だけ予約し直す
- **検証反映（同期完了フックの新設）**: 現行 `_layout.tsx` の `runSync` は fire-and-forget で「pull 完了」の接続点が無い。`runSync` の Promise を await してから 4. を実行する配線を新設する。**オフラインで pull が完了しない朝は自動追加をスキップ**し、次のオンライン起動で実施する（古い在庫観で家族のリストに書き込まない）。1〜3 と 5 はオフラインでも実行する

#### 10.11.2 買い物リストへの自動追加の作法

- 二段オプトイン: 親「毎日の献立」（既定オフ・日数 X と通知時刻）→ 子「足りない材料を自動で追加」（**既定オフ**・「家族と共有中の買い物リストにも入ります」を明記）
- 追加するのは**新しく末尾に入った日の不足分だけ**（毎日高々数品）。§10.4 どおり 1 行へまとめてから `addShoppingItem`（normalized-name 突合で同名未購入行には足さない）
- `source: 'menu_auto'` 新設（sync payload は z.string() なので旧端末でも壊れない）。行に「献立から」バッジ＋タップで由来レシピ
- 取り消し: `autoAddedItemIds` をプラン JSON に省略可フィールドで持ち、「自動で追加した◯件を取り消す」。checked 済みは消さない。**自動で消すことは一切しない**
- **検証反映（名寄せの残存リスクを明記）**: 突合は完全一致＋3 文字部分一致＋既存辞書のみで、§10.3 は「未解決は在庫に無い側に倒れる」設計。手動シートでは在庫の実名併記が安全弁だが、自動はその安全弁を外す — **在庫にある品が買い物リストに入るケースは構造的に残る**（例: 在庫「春よ恋強力小麦粉」×レシピ「薄力粉」）。初版はバッジ＋1 タップ取り消しで回復可能にして出し、誤追加の苦情が出たら「名寄せ未解決品は自動で足さず献立画面に確認待ちで見せる」へ強化する。子トグルの説明文でもこの限界に触れる（「在庫にある物が入ることがあります。タップで取り消せます」）

#### 10.11.3 家族との整合（**検証反映・重い問題の修正**）

初稿の「M1 は決定的だから両端末が同じプランを出す」は**誤り**として撤回する。ピン（作りたいリスト）は同期されず（クラウド同期設計 286 行）、ローリング後のプランは anchorDate・差し替え・オン時期という端末ローカル状態に依存するため、**端末ごとに献立は別**、が正直な前提。

修正後の防御（順に）:

1. **第一防御=文言**: 子トグルの説明に「**家族で 1 人がオンにすれば足ります。2 人がオンにすると、それぞれの献立の不足分が同じリストに入ります**」。強制はしない（どの端末が正かをアプリが決めるのは献立同期の持ち込みで §10.1 に反する）
2. 第二防御=突合: 自動追加は同期 pull 完了後に走り、同名品は normalized-name 突合が黙って弾く（プランが違っても品名が重なる分は防げる）
3. 回復: バッジ＋取り消しで片付けは 1 タップ。同時オフライン起動の同名 2 行は手動でも起きる既存の性質

#### 10.11.4 通知

- **one-shot を毎起動で 1 本だけ予約し直す**（TIME_INTERVAL・翌 HH:MM までの秒数・両 OS 同一コード）。DAILY 繰り返しは使わない — 開かなくなった利用者に届くのは最大 1 本で自然に止まる（決定変更 E の根拠）
- 文言は静的「今日の献立ができています」。料理名は載せない（予約後の在庫変化・差し替えで嘘になる。外れた約束は汎用文より悪い）
- 許可はオプトインの瞬間に要求（notification.service の既定方針）。拒否されてもモードは動く（開けばできている）
- Android チャンネル `menu`（importance DEFAULT）。`SCHEDULE_EXACT_ALARM` は足さない（朝の案内は数分ずれてよい・権限追加は審査面の負債）
- タップ → menu（`consumeMenuLaunchTap` を low-stock 三点セットと同型で新設）。**通知 → menu → 歯車 → OFF の 3 タップで止められる**ことを設計要件にする

#### 10.11.5 プレミアムとの関係・M1/M2 との組み合わせ

- **A1（初版）= M1 ローリング＋通知＋自動追加。AI を 1 回も呼ばない。全員無料**（原価 ¥0。§10.5 の契約を一切触らない）
- **A2 = 毎日 AI 並べ替え（朝の初回起動時 1 回・失敗は無言で M1）。プレミアム（iOS）/ BYOK 限定**。原価 ≒¥10.5/月（¥0.35×30・一次確認済み単価）
- **検証反映（A2 のサーバー前提を正直に）**: 現行サーバーのチェック順は月次枠が常に先に走り、premium バイパス（`x-quota-source: premium`）は §10.10.7-2 が「M2 から切り離す」とした**未設計項目**。このままでは N 超過日から毎朝 FREE_QUOTA_EXCEEDED → 特典が空手形になる。よって **A2 の前提作業としてサーバー側 premium 受け入れ（自己申告ヘッダ・既存の信頼水準と同等）を +0.5〜1 日計上し、A2 合計を +2〜2.5 日とする**。またモバイル側も「ゲート UI（ペイウォール遷移・広告確認）を通さない自動経路」「トークンを消費しない成功処理」という**新分岐が必然**であることを認める（「§10.10.4 をそのまま使う」のは検証・保存・失敗時 M1 続行の部分だけ）
- 自動モードは月次無料枠 N を**消費しない**（対話用の枠を見えないところで焼かない）。共有プール `INFER_GLOBAL_DAILY_LIMIT` は消費する（コストガードとして正しい・枠切れの朝は静かに M1）
- Android は プレミアム非提供（方針 A）のため **A2 の入口ごと非表示**（押せるのに買えないトグルを見せない）。BYOK 設定済みなら Android でも A2 が開く（**2026-08-28 本人確認済み**）
