## 2. Claude フック（`.claude/settings.json` で配線）

### PreToolUse — `scripts/agent/hook-pretool-guard.mjs`（Bash / PowerShell 対象）

実際に事故った・時間を失った操作だけをルール化する方針。

| 判定 | 対象                                                                                                           | 理由                                                                              |
| ---- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| deny | `git reset --hard`                                                                                             | 作業消失                                                                          |
| deny | `git checkout [ref] -- ` / `git checkout .` / `git restore`（`--staged` のみは除く）                           | 作業ツリーの変更破棄（restore に `--worktree` 併用は deny）                       |
| deny | `adb uninstall` / `pm clear`                                                                                   | 端末のローカルデータ（SQLite・写真）消去                                          |
| deny | 生 `gradlew assembleRelease/bundleRelease`                                                                     | `EXPO_NO_METRO_WORKSPACE_ROOT` 未設定で必ず失敗 → `build-android.mjs` へ誘導      |
| deny | `git push` で main を対象（`--force` 併用でも deny — force の ask より先に評価）                               | main 直 push 禁止（PR 経由のみ — CLAUDE.md）                                      |
| deny | `eas submit`（Android向け）で現在の versionCode に対応する git タグが無い場合                                  | リリース物と git 履歴の対応が追跡不能になるのを防ぐ（タグ運用は本セクション末尾） |
| deny | `eas submit`（Android向け）で**実機検証の記録が無い / エミュレーターの記録 / 記録後に `apps/` が変わっている** | 未検証のビルドを世に出さない（§4-2）                                              |
| ask  | `railway variables`（`--json` なし）                                                                           | テーブル表示がシークレット値を会話ログに晒す                                      |
| ask  | `railway up` / `eas submit`（タグ済み・iOS向け）                                                               | 本番デプロイ・ストア提出（ユーザー明示承認の確認）                                |
| ask  | Bash ツールでの `adb` + `/sdcard`                                                                              | Git Bash のパス変換で壊れる → PowerShell へ誘導                                   |
| ask  | `adb install`（`-r` なし） / `git push --force`（with-lease 除く・引数順不問）                                 | データ保持・履歴保護                                                              |
| ask  | `cd apps/mobile && pnpm install/add`                                                                           | hoisted ワークスペースのハイジャック防止（install はルートから）                  |
| ask  | `eas build --profile production`                                                                               | EAS はローカルディレクトリをアップロード — main checkout の規約確認               |
| deny | `gh pr merge` で**現在のブランチに未 push のコミットがある**（upstream 無しも含む）                            | PR は push 済みのコミットしか含まない → 手元の変更が黙って落ちる（下記）          |
| ask  | `gh pr merge` / `git merge`                                                                                    | マージ前実機確認の規約（CLAUDE.md §5）                                            |

**git ルールはグローバルオプション耐性あり**: `git -C <path> …` / `git -c k=v …` / `git --no-pager …` の
挟み込みでも同じ判定になる（`gitRule()` ヘルパーが吸収。素朴な `/git\s+reset/` はバイパスされた実績）。

**注意**: ペイロードは snake_case（`tool_name` / `tool_input`）。settings.json の変更はセッション中でも即反映される。
ルール単体テストはトリガー文字列をコマンドラインに含めない（自分自身が deny される）— JSON ファイル経由で stdin に流す。
**同じ理由でコミットメッセージにも書けない。** ガードはコマンド文字列全体を見るので、
`git commit -m "... PR のマージ手順 ..."` のように本文へトリガー語を入れると
**その commit 自体が deny される**（2026-08-24 に被弾）。`git commit -F <file>` で回避する。

**未 push コミットのガード**: コミットしただけで push せずに PR をマージすると、
その変更は **main に入らない**。PR は push 済みのコミットしか含まないからで、CI は通り、
マージも成功し、次に実機で触るまで気づけない（2026-08-18 に 6 ファイル落ちた）。
`unpushedCommits()` が現在のブランチと upstream の差分を見て deny する。
main / detached HEAD は対象外、git 呼び出し失敗時はフェイルオープン。

**upstream が main を指していると誤検知する**（2026-08-23 に被弾）。
`git checkout -B <feat> origin/main` でブランチを作ると **upstream が `origin/main` になる**ため、
push 済みでもガードは「未 push が N 件」と言って `gh pr merge` を止める。
`git status -sb` の 1 行目が `<feat>...origin/main` になっていたらこれ。
直し方は `git branch --set-upstream-to=origin/<feat> <feat>`。
**リモートとの実差分は `git rev-list --left-right --count origin/<feat>...HEAD` で確かめる**
（0 0 なら本当に push 済み）。ガード自体は正しく働いているので、無効化ではなく upstream を直す。

**squash マージした PR の続きブランチは rebase しない。** squash は元の個々のコミットを
別物として main に載せるので、`git rebase origin/main` すると**全コミットが衝突する**
（2026-08-23。#210 を squash マージした後、その上に積んだブランチで発生）。
`git checkout -B <feat> origin/main` してから**まだ main に入っていないコミットだけ
`git cherry-pick`** する。取り違え防止に、捨てる前のブランチを
`git branch backup-<feat>` で退避しておく。

**リリースタグ運用（`eas submit` ガード）**: `apps/mobile/app.json` の `expo.version` /
`expo.android.versionCode` を読み、`git tag -l` にその versionCode を含むタグが1件も無ければ
Android 向け `eas submit` を deny する（`releaseTagStatus()` が判定・app.json/git 呼び出し失敗時は
フェイルオープン）。タグ命名規則は `v<version>-play-<versionCode>`（例: `v1.4.1-play-10012`）。
提出前に `git tag -a v<version>-play-<versionCode> -m "..."` → `git push origin <tag>` で作成する。
iOS 向け submit（`-p ios` / `--platform ios`）はこのガード対象外。

### Stop — `scripts/agent/hook-stop-docs-guard.mjs`

ターン終了時に **2 つ**を確かめ、必要なら停止を一度だけブロックする。どちらも
`stop_hook_active` で再ブロックしない（無限ループ防止）。

**(1) ドキュメント自律更新の2段目（強制力）**。連動ファイルが変更されているのに対応ドキュメント / Skill が一切未更新なら停止をブロックし、更新（または「更新不要」の理由明示）を実行させる。

- 検査範囲: 作業ツリー＋（feature ブランチなら）`develop...HEAD` の差分
- docs / `.claude/skills|agents` / CLAUDE.md のいずれかが同時に変更済みなら督促しない

**(2) 分かったことの記録（`CLAUDE.md` §5）**。実機・エミュレーターの操作や調査コマンド
（`adb` / `logcat` / `dumpsys` / `uiautomator` / `build-android.mjs` 等）を実行したターンで、
記録（`docs/` ・ Skill ・ `CLAUDE.md`）が 1 行も増えていなければ停止をブロックし、
記録先の索引を添えて書かせる。

- 「調べたか」は**トランスクリプトの直近 400KB**を `knowledge-map.mjs` の
  `INVESTIGATION_SIGNALS` で見る。読めなければ**督促しない**（フェイルオープン）
- 「記録したか」は**作業ツリー＋直近 18 時間のコミット**（最大 30 件）で見る。
  ブランチ全体で見ると、一度でも docs を触った長寿命ブランチで二度と鳴らなくなる。
  逆に**直近 1 コミットだけ**で見ると、記録をコミットした直後に無関係な小さい修正を
  1 つ積むだけで誤検知する（2026-08-22 に導入直後に踏んだ）
- **ゲートではなく立ち止まり**。記録すべき発見が無ければ、その旨を報告に明記すれば通せる
- 書き方は `.claude/skills/record-finding`（症状 → 原因 → 対処）

## 3. Git フック（`.githooks/`）

**pre-commit**（順に実行・いずれか失敗でコミット中止）:

1. `scan-staged-secrets.mjs` — 追加行の PEM 秘密鍵 / Google API キー / サービスアカウント JSON を遮断
2. `format-staged.mjs` — ステージ済みファイルを Prettier で**自動整形して再ステージ**（整形差分での失敗ループを根絶）
3. `validate-changed-slice.mjs --staged` — 変更パッケージの prettier check / lint / typecheck
4. `test-customizations.mjs`

初回セットアップ: `node scripts/agent/install-git-hooks.mjs`（`core.hooksPath` を設定）。

### 罠: 新しい worktree では docs だけのコミットも止まっていた（2026-09-01 修正済み）

**症状**: `git worktree add` した作業ツリーで、docs と `scripts/` しか触っていないのに
pre-commit が `[NG] Agent environment preflight` で落ちてコミットできない。

**原因**: preflight の `gradle-wrapper` が `apps/mobile/android/gradlew.bat` を要求するが、
`apps/mobile/android/` は **`expo prebuild` の生成物で `.gitignore` 済み**（`.gitignore:13`）。
つまり**新しい worktree には必ず存在しない**。Android を一切触らない変更でも止まる。

**対処**: ディレクトリごと無い＝まだ prebuild していないだけ、として通す
（`play-signing-env` の "not configured (acceptable…)" と同じ扱い）。
**ディレクトリはあるのに wrapper だけ無い場合は prebuild の壊れなので従来どおり落とす。**
フックを `--no-verify` で迂回して回避しないこと — 迂回すると secrets スキャンも消える。

### CI 側の追加ゲート — `check-script-tdz.mjs`

`pnpm agent:check:tdz`（CI の Q-6・`agent:verify` にも同梱）。
**`scripts/**`と`e2e/**` の module スコープ TDZ** を検出する。

なぜ専用の検査が要るか。2026-09-01 に撮影スクリプトが `let sessionGuardUsable` の TDZ で
**マージ以降ずっと 1 枚も撮れずに落ちていた**（`docs/品質基準.md` §2.3）が、
**既存の道具はどれも捕まえなかった**:

| 道具                          | 結果                                   |
| ----------------------------- | -------------------------------------- |
| `node --check`                | 通る（構文としては正しい）             |
| eslint `no-use-before-define` | **素通り** — 実測済み。下記の理由      |
| typecheck / テスト            | `scripts/**` には無い                  |
| レビュー                      | 通った（ロジックレビュー・監査の両方） |

eslint が効かない理由: 危険なのは**参照の位置ではなく呼び出しの順序**。
トップレベルで `run()` を呼び、`run` の中で読む `let` がファイル後半で宣言されていると、
宣言行は関数定義より前にあるので eslint からは正しく見える。実行時だけ落ちる。

検査は「宣言より前のトップレベル実行から、呼び出しを辿ってその変数へ到達できるか」を見る
（間接呼び出しも辿る）。単純に「実行文より後ろの `let`」で報告すると誤検知だらけになり
（初版がそれで 6 件中 5 件が無害だった）、**誤検知の多い検査は必ず無視される**ので、
到達可能性まで見ている。

**これは実行の代わりにはならない。** 動的 import や eval 経由は見えない。
`scripts/**` は**マージ前に想定した使い方で最低 1 回実行する**（`docs/品質基準.md` §2.3）
のが第一で、これはその手前の安い網。

## 4. 実機検証の規約（要点）

詳細は `.claude/agents/android-verifier.md` の「実機操作の実務規約」。

- adb は **PowerShell ツール**で（Git Bash は `/sdcard` を壊す）
- エミュレーターに入れる APK は `node scripts/agent/build-android.mjs --arch x86_64`。
  既定の `arm64-v8a` のまま入れると**インストールは成功するのに起動時に落ちる**
  （`libreactnative.so` が見つからない）。`--arch` 未指定なら端末の主 ABI を見て警告が出る
- **Expo の版が SDK とずれているとビルドが止まる**（build-android.mjs）。ずれたまま組むと
  ビルドもインストールも成功するのに**起動直後に落ちる**うえ、JS のテストは native を
  読まないので全部緑のまま通る。詳細と実例は `docs/リリース手順.md` §ローカルビルド
- **端末の言語を変えて確認するとき**（英語表示の確認など）は
  `adb root` → `setprop persist.sys.locale en-US` → `stop; start`。
  ただし **`stop; start` は system_server ごと落ちることがある**（2026-08-09 に4回発生し、
  bluetooth/phone が連鎖クラッシュしてアプリも巻き添えで消えた）。
  アプリのログに例外が無いのにプロセスが消えていたら、まずエミュレーターの健全性を疑う
- **レイアウトの確認を日本語だけで済ませない。** 日本語にはディセンダ（`p` `y` `g` の
  下にはみ出す部分）が無いので、**文字が下端で切れていても見た目では気づけない**。
  2026-08-27、App Store 用に英語でスクショを撮って初めてタブバーのラベルが切れていると
  分かった（`(tabs)/_layout.tsx` の `tabBarStyle` に `height` を直書きしていて、
  React Navigation が足すはずの下 safe-area が消えていた）。**公開中の Play の日本語スクショにも
  同じ不具合が写っていた** — ジェスチャーバーの白い横棒が「追加」を横切っているのに、
  日本語だけを見ていたので 1.12.1 まで誰も気づかなかった。
  **下端に文字が来る画面は、英語ロケールでも必ず見る。**
- **Play からインストールした端末には、ローカルビルドを入れられない。**
  症状: `adb install -r` が `INSTALL_FAILED_UPDATE_INCOMPATIBLE: signatures do not match`
  で落ちる（2026-08-31・Pixel 9a で実測）。原因: Play 版は **Play アプリ署名の鍵**で
  再署名されて配布されるため（`installerPackageName=com.android.vending`）、
  ローカル gradle ビルドの署名（debug 鍵 or アップロード鍵）とは**永久に一致しない**。
  アップロード鍵で署名しても解決しない — Play が別の鍵で署名し直すため。
  切り分け: `adb shell dumpsys package com.daidoko.app | grep -E 'Signatures|installerPackageName'`
  と、ローカル APK 側の
  `<build-tools>/apksigner.bat verify --print-certs <apk>` の SHA-256 を突き合わせる
  （`keytool -printcert -jarfile` は v2/v3 署名の APK を読めず「JAR ファイルではありません」で落ちる）。
  対処は 3 つ: (1) **その端末から一度アンインストール**する（**データが消える**ので、
  先に機種変更バックアップを書き出すこと）、(2) **Play 版が入っていない端末で検証する**、
  (3) Play の内部テスト配信 / Internal App Sharing で**Play 署名済みの成果物**を配る。
  **リリース検証の端末は Play 版を入れないでおく**のがいちばん安い。
- スクショは `pwsh scripts/agent/device-shot.ps1`（縮小込み・ロック検知つき）
- `svc power stayon true` は作業後に必ず `false`
- セキュアロックは adb で解除不可 → ユーザーに依頼
- 座標タップは直前スクショで確認（UI 変更でずれる）
- かな入力はローマ字合成で自動化可・漢字はユーザー依頼。
  **Gboard の12キーかな配列だと `input text` が飲み込まれる** → 先に「あa1」で英数配列へ切り替える
- フォーム編集中に `keyevent 4`（戻る）を押すとフォームが破棄される。
  キーボードを閉じたいだけなら、キーボード自身の「∨」をタップする
- **キーボードに隠れた入力欄を叩くと、キーボードのキーが押される**（2026-08-22 Pixel 9a）。
  `uiautomator dump` の bounds は**キーボードの裏の欄も返す**ので、座標だけ見て叩くと
  打鍵が別の欄に入り、原因が分からないまま文字化けした値が保存される。
  叩く前に `dumpsys input_method | Select-String mInputShown` で閉じているか確かめ、
  叩いた後は dump の `focused=true` がどの欄かを見る
- **日本語 IME だと `input text` にかなが混ざる**（`PIXELSYNC` → `PIXELSYNCま`）。
  Gboard 12 キーだけの問題ではなく、Pixel の既定 IME でも起きる。
  入力後は必ず dump で実際の値を確認する
- **漢字は adb からは入れられないが、「既にある文字を削る」なら IME 抜きでできる**（2026-08-26）。
  `keyevent 123`(MOVE_END) / `122`(MOVE_HOME) / `67`(DEL) / `112`(FORWARD_DEL) の組み合わせで
  前後から任意の文字数を削れる。例:
  `牛肉（ローストビーフ用薄切り、または牛モモ肉ブロック）` → 末尾から 1、先頭から 18 削って
  `牛モモ肉ブロック`。**掲載スクショ用にデータを整える程度なら、これで足りることが多い**
  （文字数は全角・半角を問わず 1 キーイベント = 1 文字）
- **日本語 IME は英数字を全角で確定することがある**（AQUOS SH-RM19s の Gboard 12 キー・2026-08-23）。
  招待コードが `９ＴＸ９２ＤＣＺ` のまま送られ、正しいコードなのにサーバーが 404 を返した。
  **入力を受ける側で NFKC 正規化する**（`normalizeInviteCode` / 入力欄の `onChangeText`）。
  エミュレータの英語キーボードでは再現しないので、コード入力のある画面は実機で通すこと
- **実機検証の記録は versionCode しか照合しない。同じ versionCode のビルドが複数あると、
  どれを検証したのか記録から分からない**（2026-08-26）。実際に 10029 が EAS に 2 本あり
  （タグから組んだものと、未マージのブランチから組んだもの）、`1.12.0-10029.json` も
  2 つのブランチに別々に存在した。**`record-device-verification.mjs` は headCommit を
  記録する**ので、`git diff <headCommit> <tag> -- apps/` が空かどうかで対応は確かめられる。
  提出は `--id <BUILD_ID>` で固定する（`docs/リリース手順.md` §2-6）
- **エミュレータ（API 36）で `adb push` が無言で失敗することがある**（2026-08-27）。
  「1 file pushed」と出るのに**ファイルがどこにも存在しない** — `/sdcard` も `/data/local/tmp` も。
  `adb root` を挟んでも同じ。**シェル経由の書き込み（`cp`・リダイレクト）は通る**ので、
  ファイルを送りたいときは base64 で流す:

  ```bash
  base64 -w0 local.jpg > /c/tmp/x.b64
  adb -s <emu> shell "cat > /data/local/tmp/x.b64" < /c/tmp/x.b64
  adb -s <emu> shell 'base64 -d /data/local/tmp/x.b64 > /sdcard/Pictures/x.jpg'
  ```

  さらに **`am broadcast MEDIA_SCANNER_SCAN_FILE` は効かない**（Android 13+ で無効化）。
  ギャラリーに出すには `content call --uri content://media/external --method scan_volume
--arg external_primary` を叩く。`cmd media scan` は「Can not find service: media」で失敗する

- **エミュレータは ICMP を通さないので `ping` は必ず失敗する。** 疎通を確かめるなら
  `dumpsys connectivity` の `VALIDATED` を見る（`curl` はエミュレータに入っていない）
- **エミュレータの疑似カメラは「漫画の家」の風景**なので、料理写真の代わりにならない。
  AI にかけると当然おかしなレシピが出る。写真が要る検証は上の base64 で入れる
- **`adb devices` のシリアルが IMEI のことがある**（AQUOS SH-RM19s・2026-08-27）。
  Sharp / 国内キャリア系の端末は USB シリアルとして **IMEI をそのまま返す**。
  `docs/verification/*.json` 11 件すべてに Luhn 検証を通る有効な IMEI が入っていた
  （TAC=35997191・機種名 SH-RM19s と並置）。**IMEI は端末固有で変更できず、漏れたら取り消せない。**
  `record-device-verification.mjs` は `serialHash`（sha256 の先頭 12 桁）を書くようにした。
  **作業ツリーは伏せたが git 履歴には残っている**（blob を含むコミットは 356 件）。
  リポジトリを public にするなら履歴の書き換えが要る。
  端末のシリアルをログ・記録・スクショに出すときは、まず IMEI でないか疑うこと
- **リポジトリのルートで `npx eas …` を叩くと、空の `app.json` が作られる**（2026-08-26）。
  eas CLI は cwd に Expo プロジェクトが無いと `{"expo": {}}` を置いていく。
  そのままコミットすると、本物の `apps/mobile/app.json` と紛らわしいゴミが残る。
  **eas は `apps/mobile` で叩く**（`pnpm --filter mobile exec eas …`）
- **無線 adb で `svc wifi disable` を打つと adb ごと切れる**（当たり前だが実際にやって 10 分溶かした）。
  オフライン → 復帰の検証は**エミュレータか USB 接続の実機**で行う
- **レシピの保存は材料 1 行と手順 1 行が埋まっていないと通らない**（zod の `min(1)`）。
  エラーは画面下の「手順」節に出るので、上部の保存ボタンだけ見ていると
  「押しても何も起きない」に見える（2026-08-22 に 20 分溶かした）
- **ローカルサーバーへ向ける検証ビルドは平文 HTTP が遮断される**（targetSdk 28+ の既定。
  `localhost` も例外ではない）。`android/app/src/main/AndroidManifest.xml` の
  `<application>` に `android:usesCleartextTraffic="true"` を手で足してから組み、
  **検証後に必ず戻す**（`android/` は gitignore 対象だが、戻さないとローカル生成の
  release APK に残る）。端末 → ホストは `adb reverse tcp:<port> tcp:<port>` を端末ごとに
- **実機が使えないときは別の実機で代替する**。AQUOS SH-RM19s は暗証番号ロックが掛かると
  `screencap` が真っ黒になり操作できない（リモート解除は不可）。2026-08-22 の同期 S1 検証は
  Pixel 9a（`5B131JEBF16695`）で実施した。Pixel を使うときは Play 版と署名が違うので
  **上書きインストールできない** — 入っているアプリの `installerPackageName` を先に見る

### 4-2. リリース前の実機検証（記録が無いと提出できない）

**エミュレーターだけでは足りない。** 1.4.5 の準備では、エミュレーターで1件も出なかった不具合が
実機で **4 件**出た。いずれも実データの規模・構造・明るさでしか現れないものだった。

| 実機のみで出た不具合                           | エミュレーターで出なかった理由          |
| ---------------------------------------------- | --------------------------------------- |
| 大きなレシピで AI 調整の結果が空になる         | テストが材料3件で、出力枠に余裕があった |
| 注記だけの変更で差分プレビューが埋まる         | 同上                                    |
| 同名材料（卵が2つ・塩が2つ）の取り違え         | テストレシピに同名材料が無かった        |
| 明るい表紙写真でヘッダーのボタンが見えなくなる | テストレシピの表紙写真が暗かった        |

そこで、**実機検証の記録が無いと `eas submit`（Android）が deny される**ようにした。

```bash
node scripts/agent/record-device-verification.mjs \
  --checked "R2 の一気通貫" --checked "起動即カメラ"
```

このスクリプトは端末に実際に接続して確かめる:

- 端末がつながっていること（**エミュレーターは既定で不可**）
- **端末に入っているアプリの versionCode が app.json と一致すること**
  （古いビルドを触って「確認した」と記録する取り違えを防ぐ）
- スクリーンショットを証跡として保存する

記録は `docs/verification/<version>-<versionCode>.json`。フックは次の3つを見て deny する。

1. 記録が無い
2. 記録がエミュレーターのもの
3. **記録した後に `apps/` が変更されている**（その変更は検証されていない）

3 があるので、「検証 → コードを直す → そのまま提出」ができない。直したら入れ直して記録し直す。

## 5. ガードレールの多層構造

1. **Claude フック（PreToolUse）** — リポジトリ固有の既知事故の遮断・確認
2. **Claude Code 権限モード / auto-mode classifier** — 本番シークレット書き込み・本番デプロイ等の横断ガード（フックと重複してよい。フックは「理由の言語化」、classifier は「最後の砦」）
3. **git pre-commit** — シークレット・品質のコミット前ゲート
4. **CI（GitHub Actions）** — Quality Gates / Security Audit（LF 環境での最終判定。ローカル CRLF ノイズはここで白黒つく）
5. **リポジトリ規約（CLAUDE.md）** — マージ前実機確認・main 直 push 禁止

### 罠: `release/*` ブランチには CI が一度も走っていなかった（2026-09-02 発見・修正）

**症状**: `release/1.13.0` 宛ての PR（#268・#269）で `gh pr checks` が
「no checks reported」を返し続けた。`mergeable` は判定されるのに、Quality Gates /
Security Audit のどちらも一度も起動しない。

**原因**: `ci.yml` の `on.push.branches` / `on.pull_request.branches` が
`[main, develop]` だけで、`release/**` を含んでいなかった。**`ci.yml` が新規作成された
2026-05-08 の最初のコミットからこの状態**で、`release/1.4.1` 以降のすべてのリリース
ブランチ（1.4.1・1.4.2・1.4.5・1.5.0・1.7.0・1.8.0・1.12.1・1.12.2・1.13.0）宛ての PR は
**CI に一度も守られずマージされてきた**。ローカルでの手動ゲート（`pnpm typecheck` /
`lint` / `test` / `format:check`）に頼るしかなく、LF 環境での最終判定（§4 の層 4）が
まるごと欠けていた。#268 は実際にこの状態でマージされている。

**対処**: `branches` に `'release/**'` を追加（push・pull_request の両方）。
push 側も入れたのは、リリースブランチへの直接コミット（マージコミット含む）も
CI の対象にするため。今後の `release/x.y.z` は自動的に拾われる（ワイルドカードなので
新しい版番号を追記する必要はない）。

### 7-2. タスク管理: GitHub Issues が正、セッション Task ツールが作業中スプリント

**永続タスクボード = GitHub Issues（keisato848/daidoko）**。無料・認証済み（gh CLI）・Windows/Mac の
どのセッションからも同じボードが見え、公式 GitHub MCP サーバーでも操作できる。

- **担当** = `agent:*` ラベル（上表のエージェント名 / `agent:user` = ユーザー本人の作業 / `agent:main-loop` = 司令塔）
- **待ち要因** = `blocked:external`（Google/Apple 審査）・`blocked:decision`（ユーザーの方針判断）
- **トラック** = `track:monetization` / `track:ios` / `track:feature` / `track:harness` / `track:maintenance`
- **マイルストーン** = M1: 広告有効化リリース / M2: iOS 初回リリース / M3: バックログ
- 依存関係は Issue 本文の「前提: #NN」で表現。着手時に `gh issue edit` でセルフアサインし、完了時にクローズ

セッション内の **Task ツール**（TaskCreate/Update/List）は「いま進行中のスプリント」の追跡に使い、
着手時に該当 Issue 番号をタスク説明へ記す（セッション終了で消えるため、恒久情報は Issue へ）。

- **委譲の原則**: 外部待ちで動けないタスクにエージェントを起動しない（トークンの無駄）。着手可能になってから委譲する。
- **共有ワークツリーで `git stash pop` を安易に打たない。** 症状: 意図しないファイル
  （`ci.yml`）が staged に混入。原因: 「念のため `git stash` → 作業 → `git stash pop`」の
  定型を打ったが、自分の stash は作られておらず（ツリーがクリーンだった）、
  **別セッションが残していた古い stash を pop して消費**してしまった（2026-08-29）。
  pop は成功すると drop するので、他人の退避が消える二重の事故になる。対処:
  pop の前に `git stash list` で**自分がいま積んだものか**を確認する。誤って適用したら
  破棄せず `git stash push <file>` で退避し直し、持ち主に返す。
- **git を触るエージェントを同一ワークツリーで並行させない。** 症状: サブエージェントの
  コミットが**別のブランチに載った**（2026-08-29 実例 — 親セッションが Stop フック対応で
  ブランチを切り替えた瞬間に、並行中のサブエージェントがコミットした）。原因: ブランチは
  ワークツリー単位の共有状態で、チェックアウトは他プロセスのコミット先も変える。対処:
  git 操作（ブランチ切替・コミット）を伴うエージェントは**同時に 1 本**にし、親もその間
  ブランチを触らない。分離が要るなら Agent の worktree 隔離を使う。事故ったら
  fast-forward で正しいブランチへ移し、元ブランチを origin に合わせて戻す（今回の復旧手順）。
- **承認ゲート**: エージェントは外向きアクションの**直前で必ず止め**、メインループがユーザー承認を取ってから実行する。

### 7-3. パイプライン（Skill の連結）と保存ワークフロー

代表的な一連のワークフロー:

- **Android リリース**: `release-readiness`（保存ワークフローで事前監査）→ `release-verify`（成果物検証）→ `release-play`（提出）
- **広告有効化**: `monetize-golive` = console-browser-ops（申告）＋ emulator-verify（E2E）＋ release-play（提出）の連結
- **iOS リリース**: `ios-release`（macOS。ios-release-mac エージェントが実務、提出は司令塔）
- **ストア掲載更新**: store-ops（整備・dry-run）→ 司令塔（承認・公開反映 = update-store-listing）
- **障害時**: `incident-rollback`
- **実装 → PR**（2026-09-05 から）: 実装 → `test-writer`（別の目でテスト）→ `diff-critic`（差分の批判）→ 指摘対応 →
  `drift-audit`（`scope: 'changed'`）→ PR。`diff-critic` は「この変更」を、`drift-audit` は「出荷物と説明の食い違い」を見るので両方回す
- **セッションの締め**: `close-session` の §2 で `finding-recorder` に分かったことを渡す（Stop フックの督促を待たない）
- **サーバーのデプロイ**: `server-verifier`（ローカル→変数キー確認）→ 司令塔（承認・`railway up` = `deploy-server`）→ `server-verifier`（疎通・ログ）
- **リリースノート**: `release-notes-drafter`（ja/en 下書き）→ 司令塔（提出完了後に `update-play-release-notes.mjs`）
- **ボードの棚卸し**: `issue-groomer`（提案）→ 司令塔（ユーザー確認のうえラベル適用・クローズ）。`release-readiness` の前に回すと readiness が正確になる

### 7-5. 束ねる役（PM / QM / PjM / アプリリーダー）

**目的**: 専門役を「誰を・どの順で・何のために」呼ぶかの組み立てを、メインループから 4 つの役へ移す
（2026-09-05 導入）。各役は 1 つの問いを持ち、配下の専門役を直接呼んで**結論まで**出す。

| 役                | 問い                         | 直接呼べる専門役（`Agent(...)` 許可リスト）                                                                                               |
| ----------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `product-manager` | 作る価値があるか・何を削るか | Explore / persona-\*×5 / audit-listing-claims / audit-copy-drift / issue-groomer                                                          |
| `quality-manager` | 出してよいか                 | diff-critic / audit-\*×6 / test-writer / server-verifier / eval-inference                                                                 |
| `project-manager` | 次に何をすべきか             | issue-groomer / release-notes-drafter / Explore（GitHub は MCP か `gh`）                                                                  |
| `app-leader`      | どう入れるか                 | Explore / diff-critic / audit-design-drift / audit-route-match / audit-nav-duplication / test-writer / server-verifier / finding-recorder |

**設計上の割り切り（変えるときはここを直す）**:

- **最終承認はユーザー。** 束ねる役は「判断・判断根拠・反対材料」を簡潔に、事実を正確に返す。
  QM の no-go も推奨であって命令ではない（ただし覆すなら理由をユーザーが書く）
- **束ねる役は編集しない。** コード・設計書・Issue を変えるのはメインループか、束ねる役が呼んだ
  書く役（`test-writer` / `finding-recorder` / `release-notes-drafter`）。外向きアクションは全て司令塔
- **専門役の報告をそのまま貼らない。** 要約し「誰が何を根拠に言ったか」を添える。
  食い違いは両論併記で丸投げせず、どちらを採るかと理由を書く
- **ネストは 2 段まで**（メインループ → 束ねる役 → 専門役）。束ねる役どうしは呼ばない。
  PM → アプリリーダーのような受け渡しはメインループを経由する
- **コスト**: セッション開始の現状報告は毎回かかる（15 行以内・5 分以内に縛った）。
  急ぎの指示があるときは飛ばしてよい。重いのは QM のリリース前全体監査で、PR 前は差分に関係する検査役だけを呼ぶ
- **`release-readiness` ワークフローとの関係**: あちらは `gh` CLI 前提でリモートでは動かない。
  `project-manager` が同じ 3 観点を GitHub MCP で代替する。どちらかに寄せる判断は数回回してから

## 8. ペルソナレビュー（リリースごとの定性評価）

**目的**: 「使い勝手が伝わるか」「課金導線のどこで価値が伝わっていないか」を、
スクショ確定後・提出前に機械的に点検する（2026-08-28 導入）。

- 実行: `Workflow persona-review`、`args = { version, jaDir, enDir }`（スクショのディレクトリ）
- 評価者: `.claude/agents/persona-*.md` の 5 人（軽量モデル指定）。
  ひな=初心者 / たけし=共働き親 / みさ=コレクター・課金慎重 / Emma=**英語話者** / のりこ=63歳・可読性
- 入力は**確定済みスクショ列（Play 掲載順）**。決定的なので再現でき、前リリースとの差分が取れる
- レポートは `docs/reviews/persona/<version>.md` に保存。採用する指摘は Issue 化する

**設計上の割り切り（変えるときはここを直す）**:

- **課金意向は予測させない。** LLM の「払う/払わない」は実際の支払い行動と相関が保証されない。
  ペルソナが答えるのは「価値が伝わったか・不快だったか」まで。実際の信号は
  リワード視聴率・BYOK 設定率・Play 指標で見る
- 英語話者ペルソナを必ず入れる。タブバーのディセンダ切れ（1.12.1 まで公開されていた）は
  **日本語だけで見ていて気づけなかった**不具合で、この編成はその再発防止でもある（§4）
- スクショに写らないもの（もたつき・入力の面倒さ・通知）は評価できない。
  そこまで見たくなったら実機操作型（v2）を検討する — コスト・脆さ・AI 枠消費が跳ねるので
  数リリース回して価値を見てから

## 9. drift 監査（説明・導線・ルート・テスト・設計の食い違い）

**目的**: 型・lint・テストが全部通るのに壊れている、という種類の欠陥を機械的に拾う
（2026-09-01 導入）。

- 実行: `Workflow drift-audit`、`args = { scope: 'changed' | 'full', focus?, context? }`
- 検査役: `.claude/agents/audit-*.md` の 6 体
  - `audit-copy-drift` — 文言と実装の食い違い（コーチマークが指す先とのずれ・
    出荷済み機能の「今後追加予定」表示・i18n の死にキー）
  - `audit-nav-duplication` — 同じ遷移先の導線の重複・ホームの情報密度・金塗りの重複
  - `audit-route-match` — `includes('/cook')` が `/cookable` に当たる類の誤爆
  - `audit-test-teeth` — 差し替えた mock を assert しない・実物とずれた手動モック
  - `audit-design-drift` — 設計書と実装の乖離・文書化された閾値が未強制
  - `audit-listing-claims` — **ストア掲載文の主張が実装で裏取りできるか**
    （アプリ内の文言は `audit-copy-drift`。掲載文は公開される約束で審査対象なので分けてある）
- **いつ回すか**: PR 前は `scope: 'changed'`（変更に関係しない指摘をしない）、
  リリース前は `scope: 'full'`。
  **掲載文（`docs/store/`）を触ったら、docs だけの変更でも必ず回す**
  （`focus: ['audit-listing-claims']` で 1 体だけ回してもよい）

**なぜ作ったか（2026-08-31 の監査で見つかった 5 件が種）**:

| 型             | 実際に起きたこと                                                                                                                                                                                                                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文言の嘘       | 初回ガイドが**設定の歯車をハイライトして「このカートから」**と買い物を説明していた（1.12.2 まで出荷）。`#219` で ref を付け替えたとき i18n が取り残された                                                                                                                                                            |
| 文言の嘘       | 設定が**出荷済みのクラウド同期を「今後追加予定」**と表示して無効化していた                                                                                                                                                                                                                                           |
| 導線の重複     | 同じ遷移先の入口が 5 組。いずれも「前の対処を置き換えず上へ積んだ」結果                                                                                                                                                                                                                                              |
| パス誤爆       | `pathname.includes('/cook')` が `/cookable` に当たり、**調理直前でいちばん復帰導線が要る画面**で Now Cooking バーが消えていた                                                                                                                                                                                        |

**設計上の割り切り**:

- **判断は人に残す。** とくに `audit-design-drift` は「設計書と実装のどちらが正か」を決めない。
  両方の事実を並べるところまでが仕事

- **見つからなければ空で返す。** 分量で価値を示そうとすると、次から誰も読まなくなる
